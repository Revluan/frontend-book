## 微前端与架构

### 1. 为什么选择 Garfish，而不是 qiankun 或 Module Federation？
选择 Garfish，主要是因为它更适合我们这种“多仓库、多团队、技术栈逐步升级”的控制台场景。
相比 qiankun，Garfish 在性能、资源隔离和构建工具兼容性上更灵活一些。
* qiankun 更偏向传统单页应用微前端，底层基于 single-spa，接入成本不算低，对应用生命周期、路由模式有一定约束。
* Garfish 对 React、Vue、Vite、Webpack 等不同技术栈兼容更好，尤其适合老项目逐步迁移，不需要所有子应用统一技术栈。
* Garfish 提供更完善的沙箱能力，包括样式隔离、JS 隔离、资源预加载等，子应用之间相互污染更少。
* 在子应用数量比较多时，Garfish 的预加载、缓存机制和资源复用能力更适合控制台这种复杂后台场景。
相比 Module Federation，核心原因是它更偏“构建时共享”，而不是“运行时集成”。
* Module Federation 更适合多个应用之间共享组件、共享依赖，比如设计系统、公共模块。
* 但我们场景里更强调“独立部署、独立运行、独立升级”，子应用甚至可能用不同构建工具，比如主应用是 Next.js，子应用是 Vite。
* Module Federation 对构建工具和版本兼容要求更高，尤其早期更依赖 Webpack 体系，跨 Vite、Webpack 混用时复杂度比较高。
* 它对路由、生命周期、沙箱隔离、样式隔离这些微前端核心能力支持不如 Garfish 完整，很多能力需要自己补。
所以最后的判断是：
* 如果只是做公共组件共享，我会优先考虑 Module Federation。
* 如果是中后台、多团队、多子应用、长期演进的微前端平台，我会更倾向于 Garfish。
* 如果团队里已经全是 Webpack 技术栈，而且微前端规模不大，qiankun 也是可以的。
本质上，Garfish 更符合“运行时集成 + 技术栈解耦 + 渐进式迁移”这个目标。

### 2. 主应用和子应用之间是如何通信的？你们如何避免状态耦合？
主应用和子应用之间，我们尽量避免直接共享复杂状态，而是采用“主应用下发、子应用消费”的方式。

主应用会通过微前端框架提供的 props，把一些公共能力传给子应用，比如：

* 用户信息
* 登录态
* 权限信息
* 当前地域、租户、渠道
* 全局方法，比如埋点、跳转、通知、退出登录
* 部分全局配置，比如主题、语言
子应用拿到这些 props 后，只负责消费，不会反向直接修改主应用状态。这样可以减少双向依赖，也避免多个子应用同时改一份数据导致状态混乱。
对于需要跨页面、跨模块共享的数据，我们使用 Zustand 做全局状态管理，但也会控制边界。
我们的原则是：
* 真正全局的状态，比如用户信息、主题、权限、租户，放在主应用的 Zustand Store。
* 子应用自己的业务状态，比如表单、列表筛选、分页、当前会话，不放全局，只放子应用内部。
* 子应用如果需要使用主应用状态，就通过 props 注入 Store 实例或者注入需要的方法，而不是直接 import 主应用代码。
这样做有几个好处：
* 子应用仍然可以独立开发、独立运行，不会因为依赖主应用 Store 而无法本地启动。
* 避免出现“一个全局 store 什么都放”的问题，否则后期会非常难维护。
* 子应用拆出来单独部署时，不需要跟主应用强绑定。
如果遇到需要子应用通知主应用的场景，比如更新导航角标、刷新用户信息、切换租户，我们一般不会直接操作主应用 Store，而是通过回调函数或者事件机制通知主应用，再由主应用统一修改状态。
核心思路就是：**公共状态集中在主应用，业务状态留在子应用；共享能力通过 props 注入，而不是直接互相依赖代码。**

### 3. 微前端下公共依赖（如 React、Ant Design）是如何处理的？如何避免重复打包？
微前端下，像 React、React DOM、Ant Design 这种体积大、版本稳定、所有子应用都会依赖的公共库，我们会尽量做外部化和共享，避免每个子应用都重复打包一份。
我们的做法主要有几层。
首先，React、React DOM 这类核心依赖，由主应用统一提供。
主应用提前加载 React 和 React DOM，挂到全局或者通过微前端框架共享，子应用构建时把它们配置成 external，不再打包进自己的 bundle。这样多个子应用同时加载时，不会出现每个应用都带一份 React 的问题。
对于 Ant Design，我们没有完全 external 到 CDN，而是统一版本后通过 Monorepo 控制依赖一致性。
因为 Ant Design 除了 JS 还有样式、图标、主题 Token，如果不同子应用版本不一致，很容易出现样式冲突、组件行为不一致。所以我们会：
* 在 Monorepo 里统一 React、Ant Design、dayjs 等基础依赖版本
* 子应用尽量只允许使用锁定版本
* 公共组件和 design token 统一从共享包里引入
* 避免多个子应用带出不同版本的 Ant Design CSS
另外，构建时也会做一些优化：
* 开启依赖预构建和缓存
* 使用 Tree Shaking 去掉未使用代码
* Ant Design 使用按需加载
* 图标库按需引入，避免整个 icon 包都打进去
* 对公共 chunk 做拆包，让多个页面复用浏览器缓存
最终效果是：
* 首屏不会因为多个子应用重复加载 React、Ant Design 而明显变慢
* bundle 体积更小
* 多个子应用切换时，公共依赖可以直接复用缓存
* 依赖版本统一后，也降低了线上因为 React 多实例、Context 失效、样式冲突导致的问题
微前端里最怕的就是“每个子应用都自带一套 React 和 UI 库”，短期开发方便，但后面体积、兼容性、性能都会出问题，所以一定要统一管理。

### 5. 为什么主应用使用 Next.js，子应用使用 Vite？
主应用使用 Next.js，子应用使用 Vite，本质上是因为两者承担的职责不同。

主应用更偏“平台层”。

它负责官网、文档、控制台入口、全局路由、登录态、权限、导航、SEO 等能力，所以更适合用 Next.js。

* Next.js 自带 SSR、SSG、路由、Head 管理，对官网和文档场景非常友好。
* 官网、产品页、文档页都有 SEO 诉求，SSR 和静态生成能提升首屏速度和搜索引擎收录。
* 主应用还需要统一处理登录态、全局布局、主题、权限、埋点等平台能力，Next.js 的应用组织能力更强。
* 后续如果需要做边缘渲染、流式渲染、Server Actions，这些能力 Next.js 也更成熟。

子应用更偏“业务层”。

大多数子应用是控制台业务页面，比如模型管理、算力租赁、支付、配置中心，这类页面不需要 SEO，更关注开发效率和构建速度，所以选择 Vite。

* Vite 冷启动和热更新非常快，业务开发体验比传统 Webpack 更好。
* 子应用通常由不同团队维护，独立开发、独立部署，Vite 配置轻、学习成本低，更容易快速接入。
* 子应用不需要承担 SSR 压力，绝大部分都是登录后的后台页面，CSR 足够。
* 使用 Vite 后，打包速度、构建耗时、开发时 HMR 体验都会明显改善，特别适合子应用数量多的场景。

另外，Next.js 做主应用、Vite 做子应用，还有一个很重要的点是“降低升级成本”。

主应用相对稳定，不会频繁升级；子应用变化快，可以单独升级 React、构建工具甚至 UI 框架，而不会影响整个平台。这样既能保证平台层稳定，也能让业务层快速演进。

### 13. 为什么选择 pnpm-workspace，而不是 Lerna、Nx 或 TurboRepo？

**回答思路：**  
强调 pnpm 在**磁盘效率、依赖管理严格性**上的优势，并结合你们项目规模不大、任务编排需求简单的特点。

**参考回答：**  
- **硬链接与节省空间**：pnpm 通过硬链接将所有包存放在全局 store，不同项目同一版本的包只存一份，对 Monorepo 尤其友好。我们的工具包在本地开发时会同时存在多个版本（不同分支），pnpm 不会重复下载。  
- **幽灵依赖治理**：pnpm 使用符号链接构建严格的 `node_modules` 结构，只能访问 `package.json` 中声明的依赖。避免了 Lerna + npm/yarn 常见的“未声明但能引用”问题，提升包独立性。  、
- **Lerna 的定位**：Lerna 早期流行但核心能力（版本发布、执行脚本）已被 pnpm 内置的 `pnpm publish`、`pnpm -r exec` 覆盖，而且 Lerna 默认不解决依赖提升问题，仍需配合 yarn workspaces。  
- **Nx / TurboRepo 对比**：它们强在**构建缓存和分布式任务编排**，适合大型复杂项目（如几十个包、需要远程缓存）。我们只有三个公共包，任务简单，引入 Nx 或 TurboRepo 会增加配置成本，而 pnpm-workspace 足够轻量。  

**结论**：满足当前需求，且为未来扩展（如用 Turborepo 优化构建）保留了迁移路径。

### 14. Monorepo 中多个包之间如何管理依赖关系？

**回答思路：**  
说明 `workspace:` 协议的使用、pnpm 的本地链接机制，以及版本发布的转换。

**参考回答：**  
- 在 `pnpm-workspace.yaml` 中定义包目录（如 `packages/*`）。  
- 包之间通过 `workspace:` 协议声明依赖，例如 `ai-service` 依赖 `ai-design-tokens`：  
  ```json
  "dependencies": {
    "ai-design-tokens": "workspace:*"
  }
  ```
- 本地开发时，`pnpm install` 会自动将 `workspace:*` 链接到本地的 `packages/ai-design-tokens`，无需发布。  
- 发布到私有 npm 时，使用 `pnpm publish` 或 `changesets` 将 `workspace:` 协议自动转换为对应包的**实际版本号**（如 `^1.0.0`）。  
- 跨包的命令执行：`pnpm -r run build` 会按拓扑顺序执行（根据依赖关系自动排序）。

### 15. 你们的私有 npm 包是如何发布和版本管理的？

**回答思路：**  
结合公司私有源和语义化版本工具（如 changesets）。

**参考回答：**  
- **私有源**：使用公司自建的 Verdaccio 或 Nexus，通过 `.npmrc` 配置 `registry`。  
- **版本管理工具**：采用 `@changesets/cli`。流程如下：  
  1. 开发者修改包后运行 `pnpm changeset`，选择影响的包、版本变更类型（major/minor/patch），并填写变更日志。  
  2. 合并 MR 后，CI 执行 `pnpm changeset version` —— 自动更新所有受影响包的 `package.json` 版本，并生成/更新 `CHANGELOG.md`。  
  3. 运行 `pnpm publish -r` 将每个包发布到私有源（按拓扑顺序）。  
- **版本策略**：  
  - 工具包（如 `acd-cli`）使用 `major.minor.patch` 遵循 semver。  
  - 设计令牌包 `ai-design-tokens` 颜色变更属于 `patch`（向后兼容），结构变更（如 token 命名）为 `major`。

### 16. ai-design-tokens 是怎么设计的？如何同时兼容 Ant Design 和 Tailwind？

**回答思路：**  
设计令牌 -> 适配层生成不同框架的配置。

**参考回答：**  
- **核心设计**：用 JSON / JS 对象定义原始设计令牌（design tokens），例如：  
  ```js
  // tokens/colors.json
  { "colorPrimary": "#1890ff", "colorBgBase": "#ffffff", "spacing": { "md": "16px" } }
  ```
- **兼容 Ant Design**：  
  Ant Design 5 支持通过 `ConfigProvider` 的 `theme` 对象定制（算法 + token）。我们写一个转换函数，将设计令牌映射为 Ant Design 的 `theme` 结构：  
  ```js
  import { theme } from 'antd';
  export const antdTheme = { token: { colorPrimary: tokens.colorPrimary, ... } };
  ```
  对于 Ant Design 4 的 Less 变量，生成 `variable.less` 文件。  
- **兼容 Tailwind**：  
  生成 Tailwind 配置扩展，例如：  
  ```js
  // tailwind-preset.js
  module.exports = { theme: { extend: { colors: { primary: tokens.colorPrimary }, spacing: { md: tokens.spacing.md } } } };
  ```
  业务项目直接 `presets: [require('ai-design-tokens/tailwind')]`。  
- **可选方案**：导出 CSS 自定义属性（CSS Variables），Ant Design 和 Tailwind 都可通过 `:root` 变量消费，实现运行时动态主题。

### 17. 如果设计稿更新颜色体系，你们如何让所有项目快速同步？

**回答思路：**  
只需更新令牌包 -> 发版 -> 下游项目升级依赖。

**参考回答：**  
- **步骤**：  
  1. 在 `ai-design-tokens` 中修改颜色令牌定义，提交并触发 CI。  
  2. 使用 `changeset` 标记为 `patch` 版本（若兼容）或 `minor`（新增令牌）。  
  3. 发布新版本到私有 npm（如 `1.0.1 → 1.0.2`）。  
- **下游同步策略**：  
  - **主动升级**：通过 Renovate / Dependabot 自动向所有主子应用提交依赖更新 MR，合并后重新构建。  
  - **被动升级**：业务项目将依赖版本写为 `^1.0.0`，执行 `pnpm update ai-design-tokens` 即可。  
- **保障**：在令牌包中增加单元测试，对比新旧主题快照；CI 中构建一个示例页面验证视觉回归。

### 18. acd-cli 是如何实现模板初始化和自动配置的？

**回答思路：**  
CLI 交互 -> 克隆模板 -> 变量替换 -> 后置脚本。

**参考回答：**  
- **技术栈**：Node.js + `commander`（命令解析）+ `inquirer`（交互式问答）+ `degit` / `simple-git`（克隆模板）。  
- **流程**：  
  1. 用户执行 `acd init <project-name>`，CLI 询问微应用信息：端口号、路由 base、业务类型等。  
  2. 从公司 Git 仓库的模板仓库（如 `gitlab.com/templates/micro-app-template`）克隆到目标目录，使用 `degit` 避免 .git 历史。  
  3. **自动配置**：  
     - 读取模板中的占位符（如 `__PROJECT_NAME__`、`__PORT__`）文件（package.json、webpack 配置、nginx 配置等）。  
     - 用用户输入的值替换所有占位符（通过 `replace-in-file` 或 ejs 模板引擎）。  
     - 如果主子应用需要注册（如 qiankun 需要 `registerMicroApps`），CLI 可调用公司内部的平台 API 自动注册，或生成配置片段提示用户添加。  
  4. 执行 `pnpm install` 安装依赖，输出启动命令。

### 20. ai-service 统一服务层为什么有必要？解决了什么问题？

**回答思路：**  
微前端下重复封装、配置分散、升级困难的问题。

**参考回答：**  
- **背景**：主子应用各自调用地域可用区服务、渠道服务时，每个子应用都要写请求封装、错误处理、baseURL 配置，甚至不同子应用使用的接口版本不一致。  
- **解决的问题**：  
  1. **消除重复代码**：将服务初始化、请求拦截器、鉴权（如携带 token）统一放在 `ai-service` 中。  
  2. **配置一致**：子应用只需调用 `createService({ env: 'prod' })`，不需要关心服务端点。  
  3. **易于升级**：若需要给所有服务调用增加日志埋点或性能监控，只需修改 `ai-service` 并升级版本，无需改动几十个子应用。  
  4. **类型安全**：用 TypeScript 定义服务接口，子应用获得完备的 IDE 提示。  
- **实现举例**：  
  ```js
  // ai-service 导出
  export function initRegionService(config) { return { getRegionList: () => request('/region') }; }
  ```
  子应用：`import { initRegionService } from 'ai-service'; const regionSvc = initRegionService();`

### 21. Monorepo 下如何避免循环依赖？

**回答思路：**  
工具检测 + 架构设计原则。

**参考回答：**  
- **工具检测**：  
  - pnpm 在安装时会自动检测循环依赖并报错（`ERR_PNPM_CYCLIC_DEPENDENCIES`）。  
  - 使用 `dependency-cruiser` 在 CI 中生成依赖图并设置规则，禁止出现循环。  
- **架构原则**：  
  - 分层：`ai-design-tokens` 为基础层，不依赖任何其他业务包；`ai-service` 可以依赖 `ai-design-tokens`，但不能反向依赖；`acd-cli` 是开发工具，不应被其他包依赖。  
  - 若出现 A ↔ B 相互需要，则提取公共部分到新包 C，让 A 和 B 都依赖 C。  
  - 使用依赖倒置：通过接口（interface）或事件总线解耦，避免直接引用。  
- **实践**：在代码审查时重点检查 `package.json` 中的依赖声明，确保依赖方向是单向的。

### 22. 如果某个公共包升级后导致多个项目异常，你们如何快速回滚？

**回答思路：**  
立即降级版本 + 发布 revert 版本 + 长期测试策略。

**参考回答：**

## AI 对话应用

以下是针对你 AI 模型应用业务项目的面试题回答，结合了你提到的 EventSource、流式分流、虚拟滚动、扁平化 Map 等具体实现。

---

### 23. 为什么选择 EventSource 做流式输出，而不是 WebSocket？

**参考回答：**  
- **场景匹配**：大模型对话是**单向、实时流式返回**（用户发送一次请求，服务端持续推送文本增量），不需要全双工通信。EventSource（SSE）天然为服务端到客户端的单向流设计，协议更轻量（纯 HTTP，无握手升级负担）。  
- **自动重连**：EventSource 内置断线重连机制（会发送 Last-Event-ID），WebSocket 需要手动实现。  
- **实现简单**：前端 `new EventSource(url)` 即可，无需额外库；后端只需设置 `Content-Type: text/event-stream`。  
- **WebSocket 的劣势**：需要建立长连接、处理心跳、管理连接池，对简单的文本流输出过于沉重。且 WebSocket 默认不携带认证 Cookie 容易遇到跨域问题。  
- **结论**：SSE 足够满足需求，开发维护成本低。

---

### 24. EventSource 的断线重连机制你们是怎么处理的？

**参考回答：**  
- **原生重连**：EventSource 断开后会自动尝试重连（间隔 3 秒，可通过 `retry` 字段调整）。但原生重连会重新发送整个请求，导致丢失之前的流式数据。  
- **恢复断点**：  
  1. 后端在每条消息中附带 `id`（如增量序号或 token 偏移量）。  
  2. 前端将最后收到的 `id` 保存在 `localStorage` 或会话变量中。  
  3. 重连时，在新 EventSource 的 URL 上附加 `?lastEventId=xxx`。  
  4. 后端从该 id 之后继续推送，前端从断点处继续渲染。  
- **业务层重试**：如果重连失败超过 3 次，提示用户“网络不稳定，请刷新页面重试”，并提供一个手动重试按钮。  
- **心跳保活**：为避免代理服务器超时关闭连接，后端每 15 秒发送一个 `:` 注释行（无数据的心跳）。

---

### 25. 流式响应时，如何实现“思考过程”和“最终答案”的分流展示？

**参考回答：**  
- **数据结构约定**：后端在 SSE 事件中区分 `type` 字段，例如：
  ```
  event: reasoning
  data: {"content": "首先，用户问的是..."}
  
  event: answer
  data: {"content": "根据现有知识，答案是..."}
  ```
- **前端处理**：  
  - 维护两个独立的渲染区域：一个用于“思考过程”（折叠/可展开），一个用于“最终答案”。  
  - 监听不同的 `event` 类型，将增量内容追加到对应区域的状态变量中。  
  - 例如：  
    ```js
    if (event.type === 'reasoning') {
      setReasoning(prev => prev + event.data.content);
    } else if (event.type === 'answer') {
      setAnswer(prev => prev + event.data.content);
    }
    ```
- **时序问题**：思考过程可能先结束，答案后结束；也可能交替（思考过程中夹杂部分答案预览）。我们使用 `useRef` 存储累积内容，避免闭包陈旧值问题。

---

### 26. 打字机效果是怎么实现的？为什么要按句子增量更新而不是字符级？

**参考回答：**  
- **实现方式**：  
  - 前端每收到一个文本增量块（例如几个词或一句话），立即将其追加到对应消息的 `content` 字段，React 触发重渲染，视觉上产生逐字/逐句出现的效果。  
  - 为了平滑，可以使用 `requestAnimationFrame` 或 `setTimeout` 做微延迟，但通常直接更新即可（现代浏览器重绘很快）。  
- **为什么按句子增量而不是字符级**：  
  - **网络与解析效率**：后端按语义边界（句子或短语）切分，减少 SSE 消息数量，降低前端解析频率。  
  - **性能**：字符级更新会导致每来一个字符就触发一次 React 渲染（500+ 消息时极卡）。  
  - **用户体验**：句子级增量更符合阅读习惯，不会出现“半个字突然补全”的闪烁。  
  - **实际做法**：后端使用流式 token 生成，但累积到标点符号（句号、问号等）或固定长度（如 20 个 token）再发送一次事件。

---

### 27. 为什么使用 Map 存储消息，而不是数组？

**参考回答：**  
- **O(1) 更新单条消息**：流式输出中，每收到一个文本增量，需要找到对应消息并追加内容。数组查找是 O(n)（需 `findIndex`），而 Map 通过 `messageId` 直接访问。  
- **避免深拷贝**：使用数组时，更新某条消息通常要 `map` 生成新数组，产生大量临时对象；Map 可以只修改目标条目的引用，配合不可变更新库（如 Immer）或直接 `set` 新 Map。  
- **扁平化存储**：原始数据可能包含嵌套回复树，Map 可以将所有消息扁平化存放（id → 消息对象），通过 `parentId` 关联。方便虚拟滚动按顺序渲染。  
- **内存友好**：Map 在频繁增删改查时，相比数组减少内存碎片。

---

### 28. 扁平化 Map 结构如何支持消息排序？

**参考回答：**  
- **维护一个顺序数组**：除了 Map 存储消息内容，额外维护一个 `messageOrder` 数组，存放所有消息 id，按时间顺序排列。  
  ```js
  // state
  const messagesMap = useRef(new Map());
  const orderRef = useRef([]);
  ```
- **新增消息**：`messagesMap.set(id, msg); orderRef.current.push(id);`  
- **渲染虚拟列表**：根据 `orderRef.current` 按索引从 Map 中取消息对象。  
- **插入消息（如用户编辑后重新发送）**：在数组指定位置 `splice`，同时 Map 更新。  
- **优点**：消息内容更新（如流式追加）只改 Map，不改数组，性能高；排序逻辑与内容存储解耦。

---

### 29. 500+ 条消息时，主要性能瓶颈在哪里？

**参考回答：**  
- **DOM 节点数量**：如果不做虚拟滚动，直接渲染 500 个复杂的消息组件（包含 Markdown、代码高亮、图片），浏览器重排/重绘成本极高，滚动掉帧。  
- **React 渲染开销**：每次收到新消息增量，若状态变化导致整个消息列表重新 diff，即使 React 有 Fiber，也会消耗大量 CPU。  
- **内存占用**：每条消息存储完整内容（可能很长）、思考过程、元数据，500 条后可达几十 MB，长时间对话会持续增长。  
- **流式更新频率**：每秒可能收到 10+ 次增量事件，每次触发组件更新，没有 memo 优化会导致大量无意义渲染。  
- **解决**：虚拟滚动 + memo + 扁平化 Map + 增量更新。

---

### 30. 为什么选择 react-window，而不是 react-virtualized？

**参考回答：**  
- **体积**：`react-window` 更轻量（gzip 后 ~3KB），`react-virtualized` 约 25KB+。我们只需要基础的变高列表能力，不需要 Table、Grid、Masonry 等复杂组件。  
- **API 简洁**：`VariableSizeList` 的用法直观，`itemSize` 可以传函数动态计算高度。  
- **维护活跃度**：`react-window` 由同一个作者（bvaughn）维护，且持续更新；`react-virtualized` 已进入维护模式。  
- **性能**：`react-window` 在大量滚动场景下更轻快，因为它不做额外功能（如自动滚动到底部等，这些我们可以自己实现）。

---

### 31. VariableSizeList 的高度缓存是怎么做的？

**参考回答：**  
- `react-window` 内部维护一个 `itemSizeMap`，记录每个索引对应的实际高度。  
- 我们需要在消息渲染后，通过 `ref` 获取真实 DOM 高度，调用 `list.resetAfterIndex(index)` 通知列表重新计算。  
- 具体步骤：  
  1. 给每个消息组件包装一个 `div`，用 `ResizeObserver` 监听尺寸变化。  
  2. 当高度改变时（流式输出内容增长，或图片加载完成），调用 `listRef.current.resetAfterIndex(messageIndex)`。  
  3. `react-window` 会重新测量该索引及之后的所有项目，并调整滚动偏移量。  
- **缓存策略**：对于已经稳定（流式结束）的消息，高度不再变化，无需重复测量；我们用一个 `Map` 缓存最终高度，减少 `resetAfterIndex` 调用。

---

### 32. 如果消息内容高度是动态变化的，比如流式输出过程中不断增长，虚拟列表如何刷新高度？

**参考回答：**  
- **监听内容变化**：每条消息组件内部，当 `content` 变化时，通过 `useEffect` 触发父组件调用 `resetAfterIndex`。  
- **批量更新**：频繁 reset 会导致列表抖动。优化方案：  
  - 使用 `requestAnimationFrame` 防抖：在流式输出期间，收集变化的消息索引，在下一帧统一调用一次 `resetAfterIndex(最小索引)`。  
  - 或者设置一个“正在流式”标志，仅在流式结束时（收到 `[DONE]`）做一次全量高度重置。  
- **保持滚动位置**：如果用户正在查看最新消息（滚动条在底部），刷新高度后需要自动滚动到底部。我们监听 `onScroll`，当 `scrollOffset + clientHeight >= totalHeight - 10` 时，在重置高度后手动调用 `scrollToItem(末尾)`。  
- **避免无限循环**：重置高度可能引发二次测量，确保重置条件中排除“高度未实际变化”的情况。

---

### 33. React.memo 和 useMemo 分别用在了哪些地方？

**参考回答：**  
- **React.memo**：  
  - 包裹每条消息组件 `MessageItem`。因为消息列表重新渲染时，只有内容变化的消息需要重绘。  
  - 包裹工具组件如 `ThinkingChain`、`SearchResultPanel`，它们通常依赖 props 是否变化。  
  - 自定义比较函数：对 `MessageItem` 比较 `message.id`、`content`、`isStreaming` 等核心字段，忽略回调函数的引用变化（通过 `useCallback` 配合）。  
- **useMemo**：  
  - 计算虚拟列表传入的 `itemData`（消息数组的派生数据），避免每次渲染重新构建。  
  - 对 Markdown 渲染的 HTML 结果进行缓存（输入相同内容 + 相同主题配置）。  
  - 对消息分组（按日期分组）的结果缓存，仅在 `orderRef` 或消息 Map 变化时重新计算。  
- **注意**：不要过度优化；我们只在已验证的热路径上使用。

### 34. 长对话下，内存占用为什么会越来越高？你们做了哪些优化？

**参考回答：**  
- **原因**：  
  - 消息内容不断累积（尤其是每条消息可能包含几千字的 Markdown + 代码块）。  
  - DOM 节点虽然虚拟滚动只渲染可视区，但 React 内部仍然持有全部消息的虚拟 DOM 节点（Fiber 节点）和状态。  
  - 流式输出过程中产生了大量临时字符串和事件回调。  
- **优化措施**：  
  1. **消息分页/存档**：超过 200 条消息时，将早期消息存储到 IndexedDB，并从前端状态中卸载（仅保留摘要）。用户滚动到顶部时再异步加载。  
  2. **内容裁剪**：对于极长的单条消息（如超过 10 万字符），提供“折叠”功能，只显示前 5000 字符。  
  3. **清理流式缓冲区**：每条消息流式结束后，释放临时拼接用的 `ref` 引用。  
  4. **使用 `react-window` 的 `overscanCount` 控制**：减少不可见区域的渲染。  
  5. **弱引用缓存**：Markdown 解析结果用 `WeakMap` 缓存，避免长期持有大字符串。

---

### 35. 如果用户快速切换会话，如何避免旧请求返回后污染当前会话数据？

**参考回答：**  
- **核心方法**：给每个会话请求关联一个唯一标识（如 `sessionId` 或 `requestId`），在收到 SSE 数据时检查是否与当前激活的会话匹配。  
- **具体实现**：  
  1. 用户发送消息时，生成一个 `reqId`，存储在 `useRef` 中，同时存入当前会话状态。  
  2. EventSource 的回调中，携带该 `reqId`（后端原样返回）。  
  3. 前端收到事件后：  
     ```js
     if (currentReqIdRef.current !== event.reqId) {
       return; // 丢弃
     }
     ```
  4. 当用户切换会话时，立即关闭旧的 EventSource 连接（`source.close()`），并清空当前会话的流式状态。  
  5. 同时设置一个“取消令牌”标志，在异步操作（如解析 Markdown）前检查。  
- **异常处理**：如果旧请求的响应在切换后到达，但连接已关闭，浏览器会触发 `onerror`，我们直接忽略。

### 36. 联网搜索场景下，如何处理多个搜索结果并发返回？

**参考回答：**  
- **场景**：用户提问后，模型可能触发联网搜索，同时返回多个信息来源（如 3 个网页摘要），这些结果可能在同一流式过程中陆续返回。  
- **设计**：  
  - 后端在 SSE 中增加 `type: 'search_result'` 事件，包含 `resultId`、`title`、`snippet`、`url`、`index` 等字段。  
  - 前端维护一个 `searchResultsMap`（key 为 `resultId`），以及一个 `searchOrder` 数组。  
  - 每个搜索结果独立渲染（卡片形式），支持点击跳转。  
- **并发处理**：  
  - 使用 `useReducer` 统一管理搜索结果的增量和顺序。  
  - 结果可能乱序返回，按 `index` 字段排序后再显示。  
  - 提供“收起/展开”所有搜索结果的控件，避免占据过多屏幕空间。  
- **性能**：搜索结果卡片也应用 `React.memo`，并配合虚拟滚动（如果结果数量很多，通常联网搜索结果不超过 10 个，暂不需虚拟滚动）。  
- **与消息流的关系**：搜索结果作为一个特殊块，显示在最终答案之前；如果流式答案已经开始输出后才返回新的搜索结果，可以动态插入到答案上方，不影响已有内容。

## OpenClaw AI 助手

以下是针对你 **OpenClaw AI 助手** 项目的面试题回答，结合了 WebSocket、多会话管理、工具调用、消息队列、智能滚动等关键实现。

---

### 37. 为什么这里选择 WebSocket，而不是 EventSource？

**参考回答：**  
- **双向通信需求**：OpenClaw 需要支持**工具调用**——前端发送工具执行指令（如“发送企微消息”），后端需要主动推送调用结果。EventSource 是单向的（服务端→客户端），无法发送消息。  
- **低延迟交互**：WebSocket 建立长连接后，消息收发在同一连接上完成，延迟更低，适合实时对话和工具调用反馈。  
- **灵活的消息格式**：WebSocket 支持二进制和自定义 JSON 结构，便于封装工具调用 ID、会话标识等。  
- **EventSource 的限制**：只能传文本，且遇到 HTTP 代理可能缓冲流式数据，影响实时性。  
- **结论**：因为需要客户端主动发起工具调用并接收异步结果，WebSocket 是必然选择。

---

### 38. WebSocket 心跳机制是如何设计的？

**参考回答：**  
- **目的**：检测连接是否健康，防止中间代理（如 Nginx）因空闲超时而断开连接。  
- **设计**：  
  - 前端每隔 `30s` 发送一个 `{ type: 'ping' }` 消息。  
  - 后端收到后立即回复 `{ type: 'pong' }`。  
  - 前端维护一个 `heartbeatTimeout`：发送 ping 后设置定时器，若 10s 内未收到 pong，则认为连接失效，触发重连。  
  - 后端也可主动发送 ping，前端回复 pong。  
- **实现细节**：  
  - 使用 `setInterval` 发送 ping，但需注意在页面不可见时（`visibilitychange`）降低频率或暂停，节省资源。  
  - 重连成功后重置心跳定时器。

---

### 39. 如何实现断线重连？重连失败怎么办？

**参考回答：**  
- **重连策略**：  
  - 监听 WebSocket 的 `onclose` 和 `onerror` 事件，启动重连逻辑。  
  - 采用**指数退避**算法：重连间隔从 1s 开始，每次翻倍，最大 30s（例如 1s, 2s, 4s, 8s, 16s, 30s…）。  
  - 重连时，携带上一次会话的 `sessionId` 和最后收到的消息序号，以便后端恢复上下文。  
- **重连失败处理**：  
  - 尝试最多 5 次后仍失败，停止重连，显示“连接失败，请检查网络或刷新页面”的提示。  
  - 提供手动重连按钮，并保存用户未发送成功的消息到本地队列（IndexedDB），待连接恢复后重发。  
- **注意**：重连期间，用户发送的消息应进入离线队列，而不是直接丢弃。

---

### 40. 多会话管理的数据结构是怎么设计的？

**参考回答：**  
- **前端存储**：  
  - 使用 `Map<sessionId, Session>` 存储所有会话。  
  - `Session` 对象包含：  
    - `sessionId`：唯一标识  
    - `title`：会话标题（可由第一条消息生成）  
    - `messages`：消息数组（或扁平化 Map + 顺序数组，参考之前设计）  
    - `unreadCount`：未读消息数（用于通知）  
    - `lastActiveTime`：最后活跃时间  
    - `status`：'active' | 'archived' | 'deleted'  
    - `config`：该会话特有的连接器配置（如绑定的企微群 ID）  
  - 维护 `currentSessionId` 指向当前激活会话。  
- **持久化**：  
  - 使用 `localStorage` 或 IndexedDB 保存会话列表和最近 N 条消息，刷新页面后恢复。  
  - 会话数量过多时（>50），将 30 天未活跃的会话归档或提示用户清理。  
- **后端配合**：后端存储所有会话历史，前端按需分页加载（一次加载 20 条消息，滚动顶部时加载更早的消息）。

### 41. 工具调用的消息格式是如何定义的？

**参考回答：**  
- **统一格式**：使用 JSON 结构，包含 `type`、`toolCallId`、`name`、`arguments`、`result` 等字段。  
- **客户端 → 后端**（发起工具调用）：  
  ```json
  {
    "type": "tool_call",
    "toolCallId": "uuid",
    "sessionId": "xxx",
    "name": "send_wecom_message",
    "arguments": { "to": "user123", "content": "hello" }
  }
  ```
- **后端 → 客户端**（工具调用结果）：  
  ```json
  {
    "type": "tool_result",
    "toolCallId": "uuid",
    "status": "success" | "error",
    "result": { "messageId": "xxx" },
    "error": "optional error message"
  }
  ```
- **流式对话中混用**：对话文本增量用 `type: "delta"`，工具调用用 `type: "tool_call"`。前端根据 `toolCallId` 关联调用和结果，并在 UI 中显示“正在执行工具...”的 loading 状态，收到结果后更新。  
- **扩展性**：支持 `timeout` 字段（如工具执行超过 30s 自动超时）。

### 42. 如果工具调用特别慢，前端如何处理用户体验？

**参考回答：**  
- **视觉反馈**：  
  - 在消息气泡中展示“正在调用工具：发送企微消息...”的骨架屏或 loading 动画。  
  - 显示一个进度条或“取消”按钮（如果工具支持取消）。  
- **超时机制**：  
  - 前端设置每个工具调用的超时定时器（例如 30s）。超时后，取消本地等待状态，显示“工具调用超时，请重试”，并允许用户手动重试。  
  - 同时向后端发送取消指令（如果后端支持）。  
- **队列管理**：  
  - 慢工具调用期间，用户后续的新消息或工具调用进入队列，等待当前完成后再发送（避免并发混乱）。  
  - 提供一个全局的“正在执行工具”指示器，禁止用户在工具完成前发送依赖该工具结果的下一条消息。  
- **长时间运行提示**：  
  - 如果超过 10 秒，提示“工具执行时间较长，您可以继续发送新消息（结果返回后会插入）”。设计为异步结果返回后自动插入到对话流中，不阻塞对话。  
- **可观测性**：记录慢工具调用的日志，便于后端优化。

### 43. 为什么要做消息队列？解决了什么并发问题？

**参考回答：**  
- **问题场景**：  
  - 用户在 WebSocket 连接不稳定时快速发送多条消息，导致部分消息丢失。  
  - 工具调用结果返回时，用户又发送了新消息，消息顺序错乱。  
  - 多个工具并发调用，结果返回顺序不可控，导致 UI 显示混乱。  
- **解决方案**：  
  - 设计一个**客户端消息队列**，所有待发送的消息（用户输入、工具调用请求）先入队，按顺序发送。  
  - 只有收到后端的确认（`{ type: 'ack', msgId: 'xxx' }`）后，才从队列中移除，否则保留并重试。  
  - 对于工具调用结果，后端应携带对应的 `toolCallId`，前端根据 ID 更新对应消息，不依赖返回顺序。  
- **解决的具体问题**：  
  - **消息不丢失**：断线重连后，队列中的消息会重新发送。  
  - **顺序保证**：同一会话的消息严格按用户发送顺序处理。  
  - **并发堆积**：限制队列最大长度（如 100 条），超出时提示用户“消息发送过快，请稍后”。  
  - **流式与工具调用交错**：消息队列确保增量文本和工具调用结果按正确时序渲染。

### 44. 智能滚动具体是怎么实现的？

**参考回答：**  
- **核心逻辑**：  
  - 监听滚动容器的 `scroll` 事件，判断用户是否**主动向上滚动**查看历史。  
  - 如果用户滚动后，滚动条距离底部超过 `50px`，则进入“暂停跟随”模式，新消息到来时不自动滚动到底部。  
  - 当用户主动滚动到底部（距离 < 10px），或点击“回到底部”按钮时，恢复自动跟随。  
- **实现细节**：  
  - 使用 `useRef` 记录 `isUserScrollingUp` 状态，并设置一个 `scrollTimeout`：用户停止滚动 3 秒后自动重置跟随（可选，不强制）。  
  - 新消息到来时，检查 `shouldAutoScroll` 标志，若为 true 则调用 `scrollToBottom`（平滑滚动）。  
  - 用户点击“新消息提示条”（例如“有 3 条新消息”）时，立即滚动到底部并恢复跟随。  
- **辅助功能**：  
  - 在暂停跟随期间，显示一个悬浮按钮“↓ 回到底部”，点击后滚动到底部并重新启用自动跟随。  
  - 当新消息到来且处于暂停模式时，显示未读消息计数。

### 45. 当用户在查看历史消息时，如何判断不应该自动滚动到底部？

**参考回答：**  
- **判断条件**：  
  - 监听滚动事件，计算 `distanceToBottom = scrollHeight - scrollTop - clientHeight`。  
  - 如果 `distanceToBottom > 50`（可配置阈值），则认为用户不在底部。  
  - 同时记录用户的滚动方向：如果是向上滚动（`scrollTop` 变小），更确信用户在查看历史。  
- **状态管理**：  
  - 设置 `autoScrollEnabled` 状态，初始为 `true`。  
  - 用户滚动时，如果 `distanceToBottom > 50`，将 `autoScrollEnabled` 设为 `false`。  
  - 如果用户滚动到底部（`distanceToBottom < 10`），将 `autoScrollEnabled` 设回 `true`。  
- **边界情况**：  
  - 用户使用鼠标中键或键盘（PageUp/PageDown）滚动，同样监听。  
  - 当窗口大小改变（如键盘弹起）导致滚动高度变化时，重新计算距离，但不自动改变 `autoScrollEnabled`。  
- **实现方式**：使用 `useCallback` 包装滚动处理函数，并用 `throttle`（100ms 节流）提升性能。

### 46. 超长输出截断后，如何保证用户还能查看完整内容？

**参考回答：**  
- **场景**：工具调用返回的结果或模型生成的文本超过前端显示限制（例如超过 5000 字符），我们会在 UI 上截断显示，避免 DOM 过大。  
- **截断策略**：  
  - 默认只显示前 2000 个字符 + 一个“...展开”按钮。  
  - 截断发生在文本渲染层，原始完整数据仍然保存在状态中（`fullContent`）。  
- **查看完整内容的方式**：  
  1. **展开按钮**：点击后切换显示完整内容（重新渲染整个消息）。如果完整内容仍然很长，内部再嵌套虚拟滚动。  
  2. **模态框预览**：提供一个“在新窗口查看”或“复制全文”的按钮，将完整内容展示在模态框中（支持滚动）。  
  3. **下载为文件**：对于超长日志或代码，提供下载为 `.txt` 或 `.json` 文件的功能。  
  4. **后端分页**：如果内容极大（例如几十万字符），前端仅请求前 N 个字符，用户点击“加载更多”时通过 WebSocket 请求后续片段。  
- **性能考虑**：  
  - 展开完整内容时，使用 `React.lazy` 动态加载富文本渲染组件，避免首屏包体积。  
  - 对完整内容也应用虚拟滚动（如果内部是列表形式）。  
- **用户体验**：截断提示应明确告知用户“内容过长，已截断”，并提供一键展开/复制，不隐藏信息。

### 78. 你做过最复杂的一次性能优化是什么？优化前后效果如何？

### 79. 你做过最难排查的一次线上问题是什么？最后怎么解决的？

**参考回答：**  
**问题**：微前端工具包升级后，某个子应用出现样式错乱，且只在特定路由下复现，无法在本地复现。  
- **排查过程**：  
  1. 怀疑是 CSS 命名冲突 → 检查 `ai-design-tokens` 改动，发现只改了颜色值，不应影响布局。  
  2. 通过浏览器 Performance 录制，发现错乱前有一个 `ResizeObserver` 报错，导致某个容器高度计算错误。  
  3. 定位到子应用里一个第三方图表库，它监听 `window.resize` 并直接修改 DOM 样式，与我们的虚拟滚动高度缓存机制冲突。  
  4. 最终原因是 `react-window` 重置高度时触发 resize，图表库重新计算位置时拿到了过时的容器尺寸。  
- **解决**：  
  - 在子应用中将图表库的 resize 监听改为 `ResizeObserver` 并增加防抖。  
  - 在公共包中增加 `resetAfterIndex` 的批量更新，避免频繁触发。  
- **预防**：增加了集成测试，模拟子应用真实场景。

### 81. 如果让你重新做一遍微前端架构，你会有哪些地方改进？

**参考回答：**  
1. **更早引入类型安全**：设计令牌、服务层都应该用 TypeScript 严格定义，避免运行时属性错误。

### 82. 你如何平衡“快速交付”和“技术债治理”？

### 84. 如果新同事接手你的项目，你会重点提醒哪些坑？

**参考回答：**  
1. **Monorepo 的 workspace 协议**：本地开发用 `workspace:*`，发布时会自动转换，不要手动改版本号。  
2. **EventSource 的断线重连**：没有做 Last-Event-ID 恢复的话，重连后会丢失流式数据，务必让后端支持。  
3. **虚拟滚动的高度缓存**：流式输出中频繁 `resetAfterIndex` 会导致滚动跳动，必须用防抖或仅在结束时重置。  
4. **WebSocket 消息队列**：不要直接发送用户消息，一定要经过队列，否则断线重连会丢消息。  
5. **设计令牌的兼容性**：修改 token 名称是 breaking change，必须发 major 版本，否则会破坏 Ant Design 主题。  
6. **工具调用超时**：后端可能不响应，前端必须有 fallback UI 和重试机制。  
7. **会话切换时的请求取消**：旧会话的异步结果回来后不要污染当前会话，务必检查 sessionId。

### 86. 你如何评估一个前端项目是否需要重构？

**参考回答：**  
从四个维度评估：  
1. **代码健康度**：圈复杂度、重复率、测试覆盖率、TS 任何覆盖率。  
2. **业务需求匹配度**：新增一个类似功能，需要改多少处代码（比如改主题色要改 10 个文件 vs 1 个令牌）。  
3. **团队效率**：构建时间、本地启动时间、新人上手时间（超过 3 天才能跑起来算差）。  
4. **故障率**：线上 bug 中，有多少是因为架构缺陷导致的（如样式冲突、状态错乱）。  
**决策**：如果任何一项评分低于 6/10，且下季度该模块有迭代计划，则启动重构。重构采用“绞杀者模式”——新功能用新架构，逐步替换老代码。

### 87. 你觉得一个成熟的前端架构应该具备哪些能力？

**参考回答：**  
1. **标准化**：代码规范、Git 流程、构建配置统一。  
2. **可扩展**：新增页面/功能不需要改核心代码，通过插件或配置完成。  
3. **可维护**：组件/模块高内聚低耦合，有清晰的依赖关系图。  
4. **性能**：内置懒加载、虚拟滚动、缓存策略，能支持复杂场景。  
5. **可观测**：自动上报错误、性能指标、用户行为埋点。  
6. **安全**：XSS 防护、CSRF token、敏感信息不暴露在前端。  
7. **开发体验**：热更新、类型提示、Mock 数据、可视化调试工具。  
8. **部署与回滚**：灰度发布、版本管理、一键回滚。

### 88. 你如何做前端监控和异常告警？

**参考回答：**  
- **错误监控**：接入 Sentry 或自研上报，捕获 JS 错误、Promise rejection、资源加载失败。  
- **性能监控**：使用 Web Vitals（LCP、FID、CLS），结合 Performance API 上报首屏时间、TTFB。  
- **API 监控**：拦截 fetch/XHR，上报接口耗时、状态码、错误率。  
- **自定义事件**：关键流程埋点（如“开始对话”、“工具调用成功”）。  
- **告警策略**：  
  - 错误率超过 1% 且持续 5 分钟 → 钉钉/企微群告警  
  - 首屏时间 P95 > 3s → 发送周报，不立即告警  
  - 某个接口 500 错误连续 10 次 → 立即电话告警  
- **用户侧日志**：支持用户一键导出本地日志（IndexedDB 存储的操作记录），便于排查个体问题。

### 89. 你做过哪些埋点和数据分析方案？

**参考回答：**  
- **埋点方式**：自定义指令 `v-track` + 全局点击监听，自动采集页面、元素 id、额外参数。  
- **核心埋点**：  
  - 页面 PV/UV  
  - 对话相关：用户提问字数、模型响应时长、工具调用次数、联网搜索点击率  
  - 性能：流式首 token 时间、虚拟滚动卡顿次数  
  - 异常：EventSource 重连次数、消息队列堆积长度  
- **数据上报**：批量压缩上报，避免影响主线程；离线缓存 + retry。  
- **分析工具**：自建看板（Grafana + ClickHouse）或接入第三方（如 GrowingIO）。  
- **驱动决策**：发现 30% 的用户会手动停止流式输出，于是增加了“停止生成”按钮；发现工具调用超时率 15%，优化了后端并发。

### 90. 你如何保证大型前端项目的代码质量？

**参考回答：**  
- **编码规范**：ESLint + Prettier + husky + lint-staged，提交前自动格式化。  
- **类型安全**：TypeScript 严格模式，禁止 `any`（除非显式标注 `// eslint-disable-next-line @typescript-eslint/no-explicit-any` 并说明原因）。  
- **单元测试**：Jest + React Testing Library，核心工具函数覆盖率 > 90%，组件测试重点测试交互逻辑。  
- **集成测试**：Cypress 或 Playwright 覆盖关键用户流程（如登录、发送消息、工具调用）。  
- **代码评审**：至少一人 approve，且 reviewer 需要本地运行验证；复杂改动需附带设计文档。  
- **CI 检查**：构建、测试、类型检查、sonar 质量门禁（重复率<3%，复杂度<10）。  
- **定期质量周会**：每周复盘线上 bug，分析根因，补充测试用例。

### 91. 你们有没有做 CI/CD？前端发布流程是怎样的？

**参考回答：**  
- **CI**：  
  - GitLab CI / GitHub Actions  
  - 分支合并时触发：lint → test → build → 上传产物到 CDN（OSS）  
  - 使用 `pnpm changeset` 自动生成 CHANGELOG 和版本号  
- **CD**：  
  - 合并到 `main` 后自动构建并部署到**预发环境**  
  - 预发验证通过后，在发布平台点击“生产发布”  
  - 部署方式：静态资源上传到 CDN，HTML 上传到服务器；或使用 Docker + Nginx 容器化部署  
- **流程**：  
  - 开发分支 → MR → CI 通过 → 合并到 main → 自动部署预发 → QA 验证 → 手动触发生产部署（支持灰度）  
- **工具**：Jenkins / Argo CD / 公司自研发布平台。

### 92. 你如何做灰度发布和快速回滚？

**参考回答：**  
- **灰度策略**：  
  - 基于用户 ID hash：10% → 30% → 100%  
  - 基于地域或白名单（内部员工先试）  
  - 前端实现方式：通过 Nginx 层根据 cookie 分发不同版本；或者使用配置中心动态加载不同 CDN 路径  
- **监控**：灰度期间重点对比错误率、性能指标、业务转化率  
- **自动熔断**：如果灰度组错误率超过基线 2 倍，自动停止灰度并回滚  
- **快速回滚**：  
  - 静态资源：保留最近 5 个版本，一键切换 CDN 路径  
  - 后端接口：配合 API 版本号，前端降级到上一版本  
  - 前端代码中内置“紧急回滚开关”：通过配置中心强制使用旧版本入口  
- **案例**：某次 AI 对话升级后导致消息发送失败，5 分钟内通过切换 CDN 版本回滚，影响面 < 1% 用户。

### 93. 如何处理线上版本缓存导致用户代码不一致的问题？

**参考回答：**  
- **问题**：用户浏览器缓存了旧的 HTML/JS/CSS，导致新功能不生效或报错。  
- **解决方案**：  
  1. **文件名 hash**：Webpack/Vite 生成 `main.[contenthash].js`，缓存天然隔离。  
  2. **HTML 不缓存**：设置 `Cache-Control: no-cache`，每次请求最新入口文件。  
  3. **版本检测机制**：前端定期请求 `/version.json`，与当前加载的版本对比，不一致则弹窗提示“检测到新版本，请刷新页面”。  
  4. **主动刷新**：对于非破坏性更新，静默刷新资源（先加载新 JS，再替换全局变量）；对于破坏性更新，强制刷新页面。  
  5. **Service Worker 管理**：在 SW 中控制缓存清除时机。  
- **经验**：最稳妥的是 HTML 不缓存 + JS/CSS 强缓存（1 年），并配合版本检测。

### 94. 如果用户反馈页面卡顿，你会如何定位问题？

**参考回答：**  
1. **收集基础信息**：浏览器版本、设备型号、网络、操作步骤、卡顿发生时的截图/录屏。  
2. **远程调试**：引导用户打开 DevTools → Performance 录制，导出 profile。  
3. **分析方向**：  
   - 如果长任务（Long Task）频繁 → 主线程被阻塞，可能是大量 DOM 操作或复杂计算。  
   - 如果内存持续增长 → 内存泄漏，检查是否未取消事件监听、闭包引用、全局变量。  
   - 如果网络请求慢 → 查看接口耗时、是否并发过多。  
4. **复现尝试**：模拟用户环境（降级 CPU、限制网络）。  
5. **常见原因**：  
   - 未使用虚拟滚动导致 500+ DOM 节点  
   - React 组件未 memo，父组件频繁重绘  
   - 流式输出中每字符都更新 state  
   - WebSocket 消息堆积未处理  
6. **修复后验证**：提供内测版本给用户确认。

### 95. React 19 相比 React 16/17，你认为最大的变化是什么？

**参考回答：**  
（假设 React 19 已发布，按 2025 年知识）  
- **编译器优化**：React Forget（自动 memoization），大幅减少手动 useMemo/useCallback。  
- **Actions**：内置 `useActionState`、`useFormStatus`，简化表单提交和加载状态。  
- **Server Components 稳定**：零打包体积的组件，直接读取数据库。  
- **Asset 加载**：`<script>`、`<style>` 支持优先级和预加载。  
- **文档元数据**：`<title>`、`<meta>` 等可直接在任何组件中定义，自动提升到 head。  
- 相比 16/17（Hooks、Concurrent Mode 引入），19 更注重开发者体验和性能自动化。

### 96. 你如何理解 Server Components、Streaming SSR 这些新特性？

**参考回答：**  
- **Server Components**：组件在服务端运行，不发送 JavaScript 到客户端，直接输出 HTML。适合数据获取、访问后端资源，可降低客户端 bundle 大小。  
- **Streaming SSR**：服务端分块传输 HTML，浏览器可以逐步渲染，不必等待整个页面完成。配合 `<Suspense>` 可以实现快速的 TTFB 和渐进式加载。  
- **对 AI 产品的价值**：  
  - 对话历史列表可以用 Server Component 预取，减少客户端请求。  
  - 长对话的首屏加载可以用 Streaming SSR 先显示骨架屏，再逐步填充。  
  - 工具调用结果也可以在服务端流式处理，减轻客户端负担。  
- **挑战**：状态管理复杂，需要区分 Client/Server 边界；学习成本高。

### 97. 为什么很多 AI 产品前端会更强调性能和交互体验？

**参考回答：**  
- **流式输出的特殊性**：每几十毫秒就更新一次 UI，性能不好会直接导致掉帧、输入延迟，用户能直观感受到“卡”。  
- **长对话场景**：用户可能连续对话数百条，前端必须保证滚动流畅、内存可控。  
- **工具调用实时反馈**：用户期待看到“模型正在思考”、“正在发送企微消息”等即时状态，如果 UI 响应慢，会误以为系统挂了。  
- **多会话管理**：快速切换会话时，需要立即显示历史消息，加载慢会中断心流。  
- **品牌信任**：AI 产品本身带有“智能”标签，前端卡顿会严重损害用户对产品的信任。  
- **移动端占比高**：很多 AI 助手在手机上使用，性能限制更强。

### 98. 你如何理解“前端工程化”和“前端架构”之间的区别？

**参考回答：**  
- **前端工程化**：侧重**流程、工具、规范**，解决“如何高效、稳定地开发和交付”。  
  - 例如：ESLint、CI/CD、Mock 服务、自动化测试、构建优化、环境配置。  
- **前端架构**：侧重**设计、结构、决策**，解决“如何组织代码以适应业务变化”。  
  - 例如：Monorepo vs Multi-repo、状态管理选型、微前端拆分、组件库设计、数据流设计。  
- **关系**：架构是骨架，工程化是肌肉和血管。好的架构需要工程化来落地，工程化反过来又会影响架构的演进。  
- **案例**：我们的 Monorepo 工具包（架构决策）依靠 pnpm、changesets、CI 脚本（工程化）才得以实现。

### 100. 如果你加入新公司，前三个月你会怎么快速熟悉业务和技术体系？

- 独立负责一个中型 feature，并尝试提出一个小的优化点（比如增加缓存、重构重复代码）。
