1. 你们为什么选择 Garfish 而不是 qiankun 或 Module Federation？各自的优缺点是什么？

这道题可以从**选型背景 → 对比分析 → 最终决策**三个层次来回答，以下是一个比较自然的面试口答版本：

***

## 参考回答

我们当时选型主要考虑三个因素：**技术栈兼容性、接入成本、社区背景**。

**qiankun** 是国内用得最广的方案，文档完善、社区成熟，但它基于 single-spa 封装，底层 JS 沙箱是用 with + Proxy 实现的，在 React 18+ 的并发模式下有一些兼容性问题，我们主应用用的是 React 19，担心踩坑风险比较高。另外 qiankun 对 Vite 子应用的支持不是很友好，需要额外的插件处理，而我们子应用全部用 Vite，这是一个比较大的阻碍。

**Module Federation** 是 Webpack 5 原生支持的方案，优势是不需要额外框架、共享依赖做得很好。但它本质上是模块共享而不是应用级别的隔离，样式隔离、JS 沙箱都需要自己处理，而且我们子应用用 Vite，虽然有 `@originjs/vite-plugin-federation` 可以支持，但跨构建工具的兼容性在当时还不够稳定，踩坑成本比较高。

**Garfish** 是字节跳动开源的微前端框架，有几点比较适合我们：第一，对 Vite 子应用的支持更好，官方有明确的接入文档；第二，它的沙箱机制和 React 19 的兼容性更稳；第三，字节内部大规模使用过，稳定性有一定保障。当然它的社区相比 qiankun 小一些，遇到问题可参考的资料相对少，这是它的缺点，我们踩过几个坑基本都是靠看源码解决的。

综合下来，在我们 **React 19 + Vite 子应用**的技术背景下，Garfish 是最合适的选择。

***

1. Garfish 是如何实现子应用隔离的？JS 沙箱和 CSS 隔离的原理分别是什么？

这道题考察你对微前端底层原理的理解，属于追问技术深度的高频题。

***

## 参考回答

Garfish 的隔离主要分两块：**JS 沙箱**和 **CSS 隔离**。

***

### JS 沙箱

Garfish 的 JS 沙箱是基于 **Proxy** 实现的，核心思路是给每个子应用创建一个独立的 `fakeWindow`，用 Proxy 代理对全局变量的读写操作，让子应用以为自己在操作真实的 `window`，但实际上所有的副作用都被拦截到了自己的沙箱环境里。

大致原理是这样的：

```javascript
const fakeWindow = Object.create(null);

const proxy = new Proxy(fakeWindow, {
  get(target, key) {
    // 优先从 fakeWindow 取，取不到再去真实 window 取
    if (key in target) return target[key];
    return window[key];
  },
  set(target, key, value) {
    // 写操作只写到 fakeWindow，不污染真实 window
    target[key] = value;
    return true;
  }
});
```

子应用的代码在执行时，会被包裹在一个函数作用域里，把 `window` 替换成这个 proxy 对象，所以子应用对全局变量的所有读写都被隔离在自己的 `fakeWindow` 中。子应用卸载时，直接丢弃这个 `fakeWindow` 就完成了清理，不会对主应用或其他子应用造成污染。

**但有一个局限**：对于一些直接操作 DOM 的全局副作用，比如 `document.body.appendChild`、`addEventListener` 挂在真实 DOM 上的事件，Proxy 沙箱是拦截不到的，需要 Garfish 额外做快照或记录来处理卸载时的清理。

***

### CSS 隔离

Garfish 的 CSS 隔离有两种方式，可以按需选择：

**第一种：动态样式表挂载/卸载**
子应用激活时，把它的 `<style>` 和 `<link>` 标签插入 DOM；子应用卸载时，把这些样式标签从 DOM 里移除。这样同一时间只有当前激活的子应用样式生效，实现基础隔离。但这种方式的问题是切换子应用时会有样式闪烁，而且如果多个子应用同时存在，就失效了。

**第二种：ShadowDOM 隔离**
把子应用的根节点挂载在一个 `Shadow DOM` 容器里，Shadow DOM 天然具备样式隔离能力，内部样式不会泄露到外部，外部样式也不会渗透进来。这是隔离最彻底的方案，但也有明显缺点：部分第三方组件库（比如 Ant Design 的 Modal、Tooltip）会把弹层直接挂到 `document.body`，跑到 Shadow DOM 外面，导致样式完全丢失，需要额外处理。

**我们实际的做法**：用的是动态样式表方案，同时在 CSS 命名上约定了子应用前缀（比如 `.app-name-xxx`），配合 CSS Modules 或 Tailwind 的 prefix 配置，双重保险避免样式冲突，没有用 ShadowDOM，主要是因为 Ant Design 弹层的兼容问题太难处理。

***

## 一句话总结（方便记忆）

| <br />        | 原理                           | 局限                |
| ------------- | ---------------------------- | ----------------- |
| JS 沙箱         | Proxy 代理 fakeWindow，隔离全局变量读写 | DOM 副作用、原生事件需额外处理 |
| CSS 动态挂载      | 激活插入、卸载移除样式标签                | 多应用并存时失效          |
| CSS ShadowDOM | 浏览器原生隔离                      | 组件库弹层样式丢失         |

***

**面试加分点**：主动说出你们实际用的方案和遇到的坑，比只背原理更有说服力。如果面试官追问"ShadowDOM 弹层问题怎么解决"，可以说通过 `ConfigProvider` 的 `getPopupContainer` 把弹层挂到 ShadowDOM 内部容器上，这是 Ant Design 官方推荐的处理方式。

1. 主应用和子应用之间如何通信？你们用的是什么方案？

根据你提供的实际方案来组织回答：

***

## 参考回答

我们的通信需求主要有两类：**主应用状态共享给子应用**，以及**子应用向主应用注册能力**。

***

### 主应用状态 → 子应用（Zustand Store 下发）

主应用用 Zustand 管理全局状态，比如用户信息、当前地域、权限数据等。子应用加载时，Garfish 会通过 `props` 把主应用的 store 实例直接传递给子应用：

```javascript
// 主应用挂载子应用时
garfish.run({
  apps: [{
    name: 'sub-app',
    props: {
      store: useMainStore  // 把 Zustand store 传给子应用
    }
  }]
});

// 子应用内部接收并订阅
const { store } = props;
const userInfo = store.getState().userInfo;

// 订阅状态变化
store.subscribe((state) => {
  // 响应主应用状态更新
});
```

这样子应用拿到的是主应用 store 的引用，状态变化是响应式的，不需要子应用自己维护一份重复的全局状态。

***

### 子应用 → 主应用（注册路由、菜单、国际化）

子应用需要向主应用注册自己的路由、菜单配置和国际化消息，我们也是通过 `props` 暴露注册方法给子应用调用：

```javascript
// 主应用提供注册方法
garfish.run({
  apps: [{
    name: 'sub-app',
    props: {
      store: useMainStore,
      registerRoutes: (routes) => mainStore.addRoutes(routes),
      registerMenus: (menus) => mainStore.addMenus(menus),
      registerI18n: (messages) => i18nInstance.mergeMessages(messages),
    }
  }]
});

// 子应用在初始化时调用注册
export function mount(props) {
  props.registerRoutes(subAppRoutes);
  props.registerMenus(subAppMenus);
  props.registerI18n(subAppI18nMessages);
}
```

子应用卸载时，对应的路由和菜单也会从主应用里清除，保证状态干净。

***

### 为什么不用其他方案

- **CustomEvent 自定义事件**：发布订阅模式，解耦好，但状态不是响应式的，需要手动维护，不适合我们频繁读取全局状态的场景。
- **localStorage / sessionStorage**：只能传字符串，无法传递方法引用，且没有响应式，不适合。
- **Garfish 内置 EventEmitter**：适合简单的事件通知，但做不到状态订阅，我们用它处理一些一次性通知事件作为补充。

***

## 一句话总结                  

| 通信方向  | 方案                       | 用途              |
| ----- | ------------------------ | --------------- |
| 主 → 子 | props 传 Zustand store 引用 | 用户信息、地域、权限等全局状态 |
| 子 → 主 | props 传注册方法              | 路由、菜单、国际化消息注册   |
| 事件通知  | Garfish EventEmitter     | 一次性通知类事件（补充）    |

***

**面试加分点**：这套方案的核心优势是**类型安全**，因为 props 是直接传引用，可以完整保留       TypeScript 类型，比 CustomEvent 序列化传字符串要可靠得多。如果面试官追问"子应用卸载后会        ·           不会内存泄漏"，可以说在子应用的 `unmount` 生命周期里取消了 store 的 subscribe 订阅，避免了引用残留。                     

1. 子应用独立部署时，如何处理路由冲突的问题？

这道题考察你对微前端路由设计的理解，结合你们的实际方          案来回答会更有说服力。

***

## 参考回答

路由冲突在微前端里是一个很常见的问题，我们主要从**路由命名约定**和**激活规则配置**两个层面来解决。

***

### 第一层：路由前缀约定

每个子应用在注册时都有唯一的 `activeWhen` 激活规则，约定以子应用名称作为路由前缀，从根本上避免路径重叠：

```javascript
garfish.run({
  apps: [
    {
      name: 'app-model',
      activeWhen: '/ai/model',    // AI模型子应用
    },
    {
      name: 'app-image',
      activeWhen: '/ai/image',    // 镜像管理子应用
    },
    {
      name: 'app-compute',
      activeWhen: '/ai/compute',  // 算力子应用
    }
  ]
});
```

子应用内部的路由只需要维护自己前缀下的相对路径，不需要感知其他子应用的路由结构，天然隔离。

***

### 第二层：子应用内部路由配置

子应用用 React Router 时，需要设置 `basename` 与主应用约定的前缀保持一致，否则子应用内部跳转会出现路径错误：

```javascript
// 子应用从 props 接收 basename
export function mount(props) {
  const { basename } = props;

  ReactDOM.render(
    <BrowserRouter basename={basename}>
      <App />
    </BrowserRouter>,
    el
  );
}
```

主应用下发 `basename`，子应用不硬编码路径，这样同一个子应用在不同环境下部署时路由也不会出问题。

***

### 实际踩过的坑

有一个比较典型的问题：子应用独立运行时不需要 `basename`，但集成进主应用后必须加，如果处理不好，本地开发和生产环境行为不一致。我们的解法是在子应用入口判断当前运行环境：

```javascript
// 判断是否在 Garfish 环境中运行
const isGarfish = !!window.__GARFISH__;
const basename = isGarfish ? props.basename : '/';

ReactDOM.render(
  <BrowserRouter basename={basename}>
    <App />
  </BrowserRouter>,
  el
);
```

这样子应用既能独立开发调试，集成后路由也完全正常。

***

### 另一个边界情况：404 处理

子应用卸载后，如果用户直接访问一个已卸载子应用的路径，主应用需要有兜底的 404 处理，而不是白屏。我们在主应用路由配置里加了一个通配符兜底：

```javascript
// 主应用路由兜底
{ path: '*', element: <NotFound /> }
```

同时 Garfish 的 `activeWhen` 匹配不到时也不会挂载任何子应用，页面会降级展示主应用的 404 页。

***

## 一句话总结

| 问题           | 解决方案                                      |
| ------------ | ----------------------------------------- |
| 子应用路由冲突      | activeWhen 前缀约定，各子应用路由命名空间隔离              |
| 子应用内部路径错误    | 主应用下发 basename，子应用配置 BrowserRouter        |
| 独立开发与集成行为不一致 | 通过 `window.__GARFISH__` 判断环境动态设置 basename |
| 路由未匹配时白屏     | 主应用配置通配符 404 兜底                           |

***

**面试加分点**：主动提到`window.__GARFISH__`环境判断这个细节，说明你真的在项目里处理过本地开发和生产集成的差异，不是只背了理论。如果被追问"为什么用 BrowserRouter 不用 HashRouter"，可以说 HashRouter 虽然能规避部分路由冲突，但 `#` 后的路径对 Garfish 的 `activeWhen` 匹配不友好，SEO 也差，所以统一用 BrowserRouter 加 basename 的方式。

1. Next.js 主应用和 Vite 子应用混用时，有没有遇到什么兼容性问题，怎么解决的？

这道题要结合实际踩坑经历来回答，没踩过坑反而显得不真实。根据你们的技术栈整理了几个最典型的问题：

***

## 参考回答

Next.js 和 Vite 混用确实踩了不少坑，主要集中在**模块格式差异**、**环境变量**、**CSS 冲突**这几个方面。

***

### 第一个坑：模块格式不兼容

Next.js 默认使用 CommonJS，而 Vite 子应用输出的是 ESM 格式。Garfish 加载子应用时，子应用需要输出一个 UMD 或 IIFE 格式的入口文件，否则主应用无法正确识别子应用的生命周期函数（mount/unmount）。

解决方式是在子应用的 Vite 配置里明确指定构建格式：

```javascript
// 子应用 vite.config.ts
export default defineConfig({
  build: {
    lib: false,
    rollupOptions: {
      output: {
        format: 'umd',         // 指定 UMD 格式
        entryFileNames: 'index.js',
      }
    }
  }
});
```

同时子应用入口需要显式导出 Garfish 约定的生命周期：

```javascript
// 子应用 main.tsx
export const provider = () => ({
  render({ dom }) {
    ReactDOM.render(<App />, dom);
  },
  destroy({ dom }) {
    ReactDOM.unmountComponentAtNode(dom);
  }
});
```

***

### 第二个坑：环境变量前缀不一致

Next.js 的环境变量需要加 `NEXT_PUBLIC_` 前缀才能在客户端访问，而 Vite 子应用用的是 `VITE_` 前缀。两套体系混用时，子应用如果不小心读了 `NEXT_PUBLIC_` 的变量，在本地能跑，部署后就取不到值了。

我们的解决方式是在子应用里统一用 `import.meta.env` 读取，同时在 Garfish 挂载时通过 props 把主应用的公共配置下发给子应用，子应用不直接依赖环境变量：

```javascript
// 主应用通过 props 下发配置
props: {
  config: {
    apiBase: process.env.NEXT_PUBLIC_API_BASE,
    region: process.env.NEXT_PUBLIC_REGION,
  }
}

// 子应用从 props 读取，不直接用 import.meta.env
const { config } = props;
```

***

### 第三个坑：CSS Reset 样式冲突

Next.js 主应用会注入全局 CSS Reset，而 Tailwind CSS 的 preflight 也会做一遍全局样式重置，两者叠加后子应用的部分基础样式表现异常，比如 `ul` 的 `list-style`、`button` 的默认样式被双重重置，和预期不一致。

解决方式是在子应用的 Tailwind 配置里关掉 preflight，避免重复重置：

```javascript
// 子应用 tailwind.config.js
module.exports = {
  corePlugins: {
    preflight: false,  // 关闭 preflight，避免和主应用冲突
  }
}
```

***

### 第四个坑：HMR 热更新在集成环境下失效

子应用在独立开发时 HMR 完全正常，但集成进 Next.js 主应用后，Vite 的 HMR WebSocket 连接会因为端口不一致而断开，导致开发时改了子应用代码需要手动刷新页面。

解决方式是在 Vite 的 server 配置里显式指定 HMR 的 host 和 port：

```javascript
// 子应用 vite.config.ts
server: {
  port: 3001,
  hmr: {
    host: 'localhost',
    port: 3001,       // 明确指定，避免 WebSocket 连接到错误端口
  }
}
```

***

## 一句话总结

| 问题       | 原因                           | 解决方案                           |
| -------- | ---------------------------- | ------------------------------ |
| 生命周期识别失败 | Vite 默认 ESM，主应用需要 UMD        | rollupOptions 指定 format: 'umd' |
| 环境变量取不到值 | NEXT\_PUBLIC\_ 和 VITE\_ 前缀不同 | 主应用通过 props 下发公共配置             |
| 基础样式异常   | CSS Reset 双重叠加               | 子应用关闭 Tailwind preflight       |
| HMR 失效   | WebSocket 端口不一致              | vite.config 显式配置 hmr host/port |

***

**面试加分点**：这道题最好的回答策略是**每个问题都说清楚"为什么会发生"而不只是"怎么解决"**，这样面试官能感受到你是真正理解了问题的根因，而不是搜了个答案就糊弄过去。如果被追问"为什么选 UMD 不选 SystemJS"，可以说 Garfish 对 UMD 的支持是开箱即用的，SystemJS 需要额外引入 polyfill，接入成本更高。

1. 微前端场景下，公共依赖（如 React）是如何处理的？有没有做共享避免重复加载？

这道题考察你对微前端性能优化和依赖管理的理解，结合实际方案回答：

***

## 参考回答

公共依赖重复加载是微前端里一个很实际的性能问题，我们主要通过**externals 外部化 + 主应用统一挂载**的方式来处理。

***

### 核心方案：externals 外部化

子应用构建时，把 React、ReactDOM 这类公共依赖标记为 external，不打进子应用的 bundle，运行时直接复用主应用已经加载好的实例：

```javascript
// 子应用 vite.config.ts
export default defineConfig({
  build: {
    rollupOptions: {
      external: ['react', 'react-dom'],  // 不打包进子应用
      output: {
        globals: {
          'react': 'React',              // 运行时从全局变量取
          'react-dom': 'ReactDOM',
        }
      }
    }
  }
});
```

主应用（Next.js）在启动时已经加载了 React，并把实例挂到 `window.React` 和 `window.ReactDOM` 上，子应用运行时直接从全局变量引用，不会重复加载。

***

### 为什么不用 Module Federation 的共享方案

Module Federation 有原生的 `shared` 配置，可以做版本协商和按需加载，理论上更优雅：

```javascript
// webpack module federation shared 配置
shared: {
  react: { singleton: true, requiredVersion: '^19.0.0' },
  'react-dom': { singleton: true }
}
```

但我们没用这个方案，原因有两点：第一，我们子应用用的是 Vite，和 Webpack 的 Module Federation 跨工具集成比较麻烦；第二，我们所有子应用的 React 版本是统一的（都是 19），没有版本协商的需求，externals 方案已经足够解决问题，没必要引入额外复杂度。

***

### 哪些依赖做了共享，哪些没有

不是所有依赖都适合共享，我们有一个基本原则：**全局单例的共享，业务强相关的不共享**。

```javascript
// 适合共享的（全局单例，版本统一）
external: [
  'react',
  'react-dom',
  'react-router-dom',  // 路由需要单例，否则 context 会断
  'antd',              // 组件库体积大，值得共享
  'dayjs',             // 工具库，全局一份即可
]

// 不共享的（业务相关，子应用各自维护）
// zustand store、业务 hooks、子应用私有工具函数等
```

`react-router-dom` 必须共享是因为它内部用了 React Context，如果主子应用各自加载了不同的实例，Context 会断开，子应用里用 `useNavigate` 之类的 hook 会直接报错，这个坑我们实际踩过。

***

### 验证是否真的没有重复加载

上线前我们用 Chrome DevTools 的 Network 面板过滤了 JS 资源，确认子应用的 bundle 里没有包含 React 相关代码，同时在控制台验证 `window.React === 子应用内部用的 React` 是同一个引用：

```javascript
// 在子应用内部验证
import React from 'react';
console.log(React === window.React); // true，确认是同一个实例
```

***

## 一句话总结

| 方案                       | 我们的选择 | 原因                            |
| ------------------------ | ----- | ----------------------------- |
| externals + window 全局挂载  | ✅ 采用  | Vite 友好，版本统一，简单可靠             |
| Module Federation shared | ❌ 未采用 | 跨构建工具兼容差，版本统一无需协商             |
| 每个子应用各自打包                | ❌ 未采用 | bundle 体积膨胀，React 多实例有 bug 风险 |

### 第三步：替换模板变量

```javascript
// 模板文件中的占位符
// package.json:  "name": "{{APP_NAME}}"
// vite.config.ts: port: {{APP_PORT}}
// garfish 配置:  activeWhen: '/{{APP_ROUTE_PREFIX}}'

const replaceMap = {
  '{{APP_NAME}}': answers.appName,
  '{{APP_PORT}}': answers.port,
  '{{APP_ROUTE_PREFIX}}': answers.appName.replace('app-', ''),
  '{{APP_DESCRIPTION}}': answers.description,
};

// 遍历目录，替换所有文件中的占位符
async function replaceInFiles(dir) {
  const files = await fs.readdir(dir);
  for (const file of files) {
    const filePath = path.join(dir, file);
    const stat = await fs.stat(filePath);
    if (stat.isDirectory()) {
      await replaceInFiles(filePath);  // 递归处理子目录
    } else {
      let content = await fs.readFile(filePath, 'utf-8');
      for (const [placeholder, value] of Object.entries(replaceMap)) {
        content = content.replaceAll(placeholder, value);
      }
      await fs.writeFile(filePath, content);
    }
  }
}
```

### 包的版本管理

我们遵循**语义化版本**规范，三个数字对应不同的变更级别：

```
major.minor.patch
  1  .  2  .  3

patch：bug 修复，向下兼容        1.2.3 → 1.2.4
minor：新增功能，向下兼容        1.2.3 → 1.3.0  
major：破坏性变更，不向下兼容    1.2.3 → 2.0.0
```

实际执行时用 `pnpm version` 命令管理，不手动改 `package.json`：

```bash
pnpm version patch   # 修复 bug
pnpm version minor   # 新增功能
pnpm version major   # 破坏性更新
```

Monorepo 下多个包同时发版时，用 `changeset` 管理版本号和 changelog，避免手动维护出错：

```bash
# 开发完成后，记录本次变更
pnpm changeset

# 统一更新所有受影响包的版本号
pnpm changeset version

# 发布
pnpm changeset publish
```

### 依赖关系管理

Monorepo 下包之间的依赖关系主要靠 **pnpm workspace 协议 + TypeScript 项目引用** 两层来保证。

**第一层：pnpm workspace 协议**

包之间互相依赖时，统一用 `workspace:*` 协议声明，而不是写死版本号：

```json
// ai-service 的 package.json
{
  "name": "ai-service",
  "dependencies": {
    "ai-design-tokens": "workspace:*"  // 引用本地包
  }
}
```

`workspace:*` 的好处是开发阶段直接链接本地源码，发布时 pnpm 会自动把它替换成实际版本号，不需要手动维护版本对应关系。如果写死版本号，本地改了包但忘了发版，依赖方拿到的还是旧版本，很容易出问题。

**第二层：TypeScript 项目引用**

光靠 pnpm 还不够，TS 类型在包之间传递时也需要正确解析。我们在根目录的 `tsconfig.json` 里配置了 `references`，让 TS 知道包之间的引用关系：

```json
// 根目录 tsconfig.json
{
  "references": [
    { "path": "./packages/ai-design-tokens" },
    { "path": "./packages/ai-service" },
    { "path": "./packages/acd-cli" }
  ]
}
```

每个包自己的 `tsconfig.json` 也声明对其他包的引用：

```json
// ai-service/tsconfig.json
{
  "references": [
    { "path": "../ai-design-tokens" }  // 依赖 tokens 包
  ],
  "compilerOptions": {
    "composite": true,     // 必须开启，project references 要求
    "declaration": true,   // 生成 .d.ts 文件供其他包使用
  }
}
```

这样 TS 编译时会按依赖顺序构建，类型变更能正确传递，不会出现类型文件过期的问题。

**第三层：构建顺序保证**

Monorepo 里如果并行构建，可能出现依赖包还没编译完，消费方就开始构建的情况。我们用 `pnpm --filter` 配合拓扑排序来保证构建顺序：

```bash
# --filter ... 表示按依赖拓扑顺序构建所有包
pnpm --filter "..." build
```

pnpm 会自动分析 workspace 依赖图，先构建被依赖的包，再构建依赖方，不需要手动指定顺序。

### 虚拟滚动的核心原理

虚拟滚动的本质是**只渲染用户可见区域内的 DOM 节点**，可见区域之外的内容用空白占位撑开滚动条，让用户感觉所有内容都在，但实际 DOM 里只有一小部分。

用一个简单模型来描述：

```
完整列表：1000 条消息
可见区域：能显示 10 条
实际 DOM：只渲染第 15 ~ 25 条（可见10条 + 上下各缓冲几条）

滚动时：
  - 计算当前 scrollTop 对应哪些条目进入可见区
  - 销毁滚出区域的 DOM 节点
  - 创建滚入区域的 DOM 节点
  - 用 paddingTop / paddingBottom 撑开上下空白，维持滚动条位置
```

react-window 帮我们做的就是这个计算和渲染调度，不需要手动维护。

基本用法：

```jsx
import { VariableSizeList } from 'react-window';

<VariableSizeList
  height={600}          // 可见区域高度
  itemCount={messages.length}
  itemSize={getItemSize} // 每条消息的高度
  width="100%"
>
  {({ index, style }) => (
    <div style={style}>
      <MessageItem message={messages[index]} />
    </div>
  )}
</VariableSizeList>
```

***

### 动态高度的难点

固定高度用 `FixedSizeList` 直接搞定，但聊天消息的高度是动态的：短消息一行，长消息多行，带代码块的消息更高，还有 SSE 流式接收时消息高度会实时增长。这就必须用 `VariableSizeList`，但它需要提前知道每条消息的高度，这就是矛盾所在。

***

### 我们的处理方案

**第一步：先估算，后测量**

消息渲染前无法精确知道高度，所以先给一个估算值，渲染后再测量真实高度回写：

```javascript
// 高度缓存，存每条消息的实际高度
const heightCache = useRef({});

// 估算高度，渲染前用
const getItemSize = (index) => {
  return heightCache.current[index] ?? 80; // 默认估算 80px
};
```

**第二步：渲染后测量真实高度**

每条消息渲染完成后，用 `ResizeObserver` 监听它的实际高度，更新缓存并通知 react-window 重新计算：

```javascript
const listRef = useRef();

const MessageItem = ({ index, style }) => {
  const rowRef = useRef();

  useEffect(() => {
    if (!rowRef.current) return;

    const observer = new ResizeObserver(([entry]) => {
      const height = entry.contentRect.height;

      // 高度变化时更新缓存
      if (heightCache.current[index] !== height) {
        heightCache.current[index] = height;
        // 通知 react-window 从这条消息开始重新计算
        listRef.current?.resetAfterIndex(index, false);
      }
    });

    observer.observe(rowRef.current);
    return () => observer.disconnect();
  }, [index]);

  return (
    <div style={style}>
      <div ref={rowRef}>
        <MessageItem message={messages[index]} />
      </div>
    </div>
  );
};
```

`resetAfterIndex` 是 react-window 提供的 API，告诉它从第 index 条开始后面的高度缓存都失效了，需要重新计算偏移量。

***

### SSE 流式消息的特殊处理

流式接收时消息内容实时增长，高度也在实时变化，如果每次内容变化都触发 `resetAfterIndex`，会导致频繁重计算，页面抖动明显。

我们加了一个节流处理，限制重计算频率：

```javascript
const resetAfterIndexThrottled = useCallback(
  throttle((index) => {
    listRef.current?.resetAfterIndex(index, false);
  }, 100), // 100ms 内最多触发一次
[]
);
```

同时 SSE 消息始终追加在列表末尾，所以 `resetAfterIndex` 只需要从最后一条开始重算，不影响历史消息，性能开销可控。

***

### 滚动到底部的处理

聊天场景有个特殊需求：新消息来了要自动滚到底部，但用户主动往上翻历史时不能强制跳回底部。我们加了一个"是否在底部"的判断：

```javascript
const isAtBottom = useRef(true);

const handleScroll = ({ scrollOffset, scrollUpdateWasRequested }) => {
  if (!scrollUpdateWasRequested) {
    // 用户主动滚动
    const distanceFromBottom = totalHeight - scrollOffset - visibleHeight;
    isAtBottom.current = distanceFromBottom < 50; // 距离底部50px内认为在底部
  }
};

// 新消息到来时
useEffect(() => {
  if (isAtBottom.current) {
    listRef.current?.scrollToItem(messages.length - 1, 'end');
  }
}, [messages.length]);
```

## 参考回答

我觉得最有挑战的是 **AI 文本模型聊天界面的性能优化**，它难在不是单一问题，而是多个问题叠加在一起，每解决一个又会暴露新的问题。

***

### 问题是怎么发现的

上线初期用户反馈长对话下页面越来越卡，但我们本地测试时消息量不够，复现不了。后来用 Chrome DevTools 的 Performance 面板录制了一段真实用户场景的操作，才发现问题有多严重：消息量超过 200 条时，每次 SSE 推送新内容，都会触发整个消息列表的重渲染，帧率直接掉到 15fps 以下，页面肉眼可见的卡顿。

***

### 第一个难点：SSE 推送频率太高

SSE 流式消息推送速度很快，每隔几十毫秒就来一条 token，每次收到新内容都 `setState` 更新，导致组件高频重渲染。

最初的写法是直接在 onmessage 里更新状态：

```javascript
// 有问题的写法
eventSource.onmessage = (e) => {
  setMessages(prev => ({
    ...prev,
    [id]: prev[id] + e.data  // 每条 token 都触发 setState
  }));
};
```

这样每秒可能触发几十次 setState，React 即使有批处理也扛不住。

解决方式是把 SSE 数据先攒到 ref 里，用 requestAnimationFrame 控制刷新频率，每帧最多更新一次 UI：

```javascript
const pendingTokens = useRef({});
const rafId = useRef(null);

eventSource.onmessage = (e) => {
  // 先攒到 ref，不触发渲染
  pendingTokens.current[id] = (pendingTokens.current[id] ?? '') + e.data;

  if (!rafId.current) {
    rafId.current = requestAnimationFrame(() => {
      // 每帧统一 flush 一次
      setMessages(prev => ({ ...prev, ...pendingTokens.current }));
      pendingTokens.current = {};
      rafId.current = null;
    });
  }
};
```

这一步做完帧率从 15fps 回到了 45fps 左右，但还不够流畅。

***

### 第二个难点：消息列表整体重渲染

继续用 Profiler 分析，发现每次新消息来，历史消息也在重渲染，根本原因是消息数据结构用的是数组，每次更新都生成新数组引用，所有子组件的 props 都变了，React.memo 完全失效。

把数据结构从数组改成以 id 为 key 的 Map：

```javascript
// 之前：数组，每次更新整体替换
const [messages, setMessages] = useState([]);

// 之后：扁平 Map，只更新变化的那条
const [messages, setMessages] = useState({});
// { 'msg-1': {...}, 'msg-2': {...} }

// 更新时只改目标消息，其他消息引用不变
setMessages(prev => ({
  ...prev,
  [id]: { ...prev[id], content: newContent }
}));
```

这样历史消息的引用没有变化，React.memo 能正确命中缓存，不再重渲染。这一步把不必要重渲染降低了 70%。

***

### 第三个难点：动态高度虚拟滚动

引入 react-window 做虚拟列表后，遇到了新问题：聊天消息高度不固定，而且 SSE 流式接收时消息高度实时在涨，react-window 需要提前知道每条消息的高度才能正确计算偏移量。

这个问题花了最多时间，最终用 ResizeObserver 测量真实高度回写缓存，再节流调用 resetAfterIndex 通知 react-window 重算，同时对 SSE 消息的高度重算做了额外的节流，避免流式过程中频繁抖动。具体实现之前有详细聊过，这里就不展开了。

***

### 最终效果和复盘

三个问题逐个解决后，整体效果是：200 条消息下帧率稳定在 60fps，内存占用降低了 40%，消息响应速度提升了 50%。

复盘下来有两个感受：

第一，**性能优化一定要先测量再动手**。最开始我们猜测是渲染问题，差点直接上虚拟滚动，但用 Profiler 分析后发现 SSE 频率才是根因，如果顺序搞反了，虚拟滚动做完问题还是在。

第二，**每个优化都会暴露新瓶颈**。SSE 节流解决了重渲染频率，才暴露出数据结构的问题；数据结构解决了，才能真正发挥虚拟滚动的效果。这种层层递进的优化过程，比一次性全上收益更可控，也更容易定位是哪一步起了作用。

### 关键设计要点

1. **Next.js 路由只做占位**：`[...slug]/page.tsx` 渲染空组件，真正的内容由 Garfish 接管
2. **双层路由**：Next.js 负责 SSR 和不返回 404，Garfish 负责客户端子应用激活
3. **`sandbox: false`**：主子应用共享 window，子应用的 JS 可以直接访问主应用挂载的全局变量
4. **运行时数据共享**：Store、Service、主题配置通过 Garfish props 传递，而非通过共享依赖包
5. **开发/生产入口不同**：开发时直接访问子应用 Vite dev server（`127.0.0.1:8083`），生产时通过 nginx 代理（`/public/modelverse`）
