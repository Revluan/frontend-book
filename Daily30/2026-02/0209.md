1. JavaScript中的AbortController是什么？如何使用它取消fetch请求？

## AbortController 是什么？

`AbortController` 是浏览器原生提供的 Web API，用于**中止（取消）一个或多个 Web 请求**。它由两部分组成：

- **`AbortController`**：控制器本身，提供 `abort()` 方法
- **`AbortController.signal`**：一个 `AbortSignal` 对象，传递给需要被取消的异步操作

---

## 基本用法

```javascript
const controller = new AbortController();
const signal = controller.signal;

fetch('https://api.example.com/data', { signal })
  .then(res => res.json())
  .then(data => console.log(data))
  .catch(err => {
    if (err.name === 'AbortError') {
      console.log('请求已被取消');
    } else {
      console.error('请求出错', err);
    }
  });

// 3秒后取消请求
setTimeout(() => controller.abort(), 3000);
```

---

## 典型应用场景

**场景一：超时取消**

```javascript
function fetchWithTimeout(url, timeout = 5000) {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), timeout);

  return fetch(url, { signal: controller.signal })
    .finally(() => clearTimeout(timer));
}
```

**场景二：React 中组件卸载时取消请求**（防止内存泄漏）

```javascript
useEffect(() => {
  const controller = new AbortController();

  fetch('/api/user', { signal: controller.signal })
    .then(res => res.json())
    .then(data => setUser(data))
    .catch(err => {
      if (err.name !== 'AbortError') throw err;
    });

  return () => controller.abort(); // 组件卸载时取消
}, []);
```

**场景三：取消上一次搜索请求（搜索框防抖配合使用）**

```javascript
let controller = null;

async function search(query) {
  if (controller) controller.abort(); // 取消上次
  controller = new AbortController();

  try {
    const res = await fetch(`/api/search?q=${query}`, {
      signal: controller.signal
    });
    return await res.json();
  } catch (err) {
    if (err.name === 'AbortError') return; // 被取消，忽略
    throw err;
  }
}
```

---

## 关键细节

| 要点 | 说明 |
|------|------|
| 取消后抛出的错误 | `err.name === 'AbortError'`，需单独处理 |
| 一个 signal 可复用 | 同一个 signal 可传给多个 fetch，一次 `abort()` 全部取消 |
| abort 后不可重置 | 每次需要重新 `new AbortController()` |
| 兼容性 | 现代浏览器均支持，Node.js 15+ 支持 |

> `abort()` 只是取消了 JS 层面对响应的处理，实际网络请求可能已经发出，服务器可能已经收到请求。

2. 什么是尾递归？JavaScript引擎如何优化递归调用？如何将普通递归改写为尾递归？
好的，用最直白的方式说：
### 什么是尾递归？
递归函数的**最后一步**只是调用自身，没有其他运算（比如加法、乘法）。

✅ 尾递归例子：
```js
function fn(n, acc) {
  if (n <= 0) return acc;
  return fn(n - 1, acc + n);   // 最后一步只有调用自己
}
```

❌ 非尾递归：
```js
function fn(n) {
  if (n <= 0) return 0;
  return n + fn(n - 1);        // 最后一步是加法，不是单纯的函数调用
}
```

---

### JavaScript 引擎怎么优化？
- **理论上**：尾递归可以复用当前栈帧，不会爆栈，空间 O(1)。
- **实际上**：ES6 规定要有这个优化，但 **Chrome / Node.js 都不支持**，只有 Safari 支持。
- **结论**：别指望 JS 引擎帮你优化，自己改写成循环更靠谱。

---

### 怎么把普通递归改成尾递归？
**核心技巧**：多加一个“累加器”参数，把要做的计算提前到参数里。

例子：阶乘
```js
// 普通递归
function fact(n) {
  if (n === 1) return 1;
  return n * fact(n - 1);
}

// 尾递归版本
function factTail(n, total = 1) {
  if (n === 1) return total;
  return factTail(n - 1, n * total);
}
```
### 一句话总结
尾递归 = 递归在最后一步 + 不依赖当前帧；JS 优化基本没用，直接用循环代替更安全。

4. 什么是IIFE（立即执行函数表达式）？它的应用场景有哪些？为什么能避免变量污染？

## IIFE 是什么？

**IIFE**（Immediately Invoked Function Expression）即**立即执行函数表达式**，是一种定义后立即执行的函数写法。

```javascript
(function() {
  console.log('我立即执行了');
})();

// 箭头函数写法
(() => {
  console.log('同样立即执行');
})();
```

语法关键点：外层 `()` 将函数变为**表达式**，末尾 `()` 立即调用它。

---

## 为什么能避免变量污染？

核心原因：**函数作用域隔离**。

JavaScript 中函数会创建独立作用域，函数内部声明的变量对外部不可见：

```javascript
var globalVar = 'global';

(function() {
  var localVar = 'local'; // 外部访问不到
  var globalVar = 'inner'; // 不会覆盖外部同名变量
  console.log(globalVar); // 'inner'
})();

console.log(globalVar); // 'global' ✅ 不受影响
console.log(localVar);  // ReferenceError ✅ 不泄漏
```

在 `var` 没有块级作用域的时代，IIFE 是隔离变量的**唯一可靠手段**。

## 应用场景

**场景一：模块化封装（ES Module 出现前）**

```javascript
var MyModule = (function() {
  var privateData = '私有数据'; // 外部无法访问

  function privateMethod() { /* ... */ }

  return {
    publicMethod() {
      return privateData; // 只暴露公共接口
    }
  };
})();

MyModule.publicMethod(); // ✅
MyModule.privateData;    // undefined ✅
```

这正是经典的**模块模式**，jQuery 等早期库大量使用。

**场景二：解决 `var` 循环变量问题**

```javascript
// ❌ 经典 Bug：全部输出 3
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100);
}

// ✅ IIFE 捕获每次循环的 i 值
for (var i = 0; i < 3; i++) {
  (function(j) {
    setTimeout(() => console.log(j), 100); // 0, 1, 2
  })(i);
}
```

**场景三：初始化逻辑，避免暴露临时变量**

```javascript
// 复杂初始化时产生的中间变量不污染全局
(function() {
  var config = loadConfig();
  var processed = processConfig(config); // 临时变量
  App.init(processed);
})();
```

**场景四：与第三方库的 `$` 符号冲突时安全隔离**

```javascript
(function($) {
  // 此处 $ 就是 jQuery，不受其他库影响
  $('.btn').on('click', handler);
})(jQuery);
```

| 场景 | 过去用 IIFE | 现在推荐 |
|------|------------|---------|
| 变量隔离 | IIFE | `let` / `const` 块级作用域 `{}` |
| 模块封装 | IIFE 模块模式 | ES Module (`import/export`) |

6. JavaScript的观察者模式和发布订阅模式有什么区别？请分别实现。

| 维度 | 观察者模式 | 发布订阅模式 |
|------|-----------|------------|
| 耦合度 | 观察者与被观察者**直接依赖** | 通过**事件中心解耦**，双方互不感知 |
| 通信方式 | Subject 直接调用 Observer 的方法 | Publisher 发消息给中心，中心转发给 Subscriber |
| 适用场景 | 同一模块内状态同步 | 跨模块、跨组件通信 |

观察者模式：  Subject ←→ Observer（直接关联）
发布订阅：    Publisher → [EventBus] → Subscriber（通过中间人）

观察者模式实现
```javascript
// 被观察者
class Subject {
  constructor() {
    this.observers = [];
  }

  subscribe(observer) {
    this.observers.push(observer);
  }

  unsubscribe(observer) {
    this.observers = this.observers.filter(ob => ob !== observer);
  }

  notify(data) {
    this.observers.forEach(observer => observer.update(data));
  }
}

// 观察者
class Observer {
  constructor(name) {
    this.name = name;
  }

  update(data) {
    console.log(`${this.name} 收到通知:`, data);
  }
}

// 使用
const subject = new Subject();
const obs1 = new Observer('观察者A');
const obs2 = new Observer('观察者B');

subject.subscribe(obs1);
subject.subscribe(obs2);
subject.notify('状态变了'); // 观察者A 收到通知: 状态变了 / 观察者B 收到通知: ...
subject.unsubscribe(obs1);
subject.notify('再次通知'); // 只有观察者B 收到
```

发布订阅模式实现
```javascript
class EventBus {
  constructor() {
    this.events = {}; // { eventName: [callback, ...] }
  }

  // 订阅
  on(event, callback) {
    if (!this.events[event]) this.events[event] = [];
    this.events[event].push(callback);
    return this; // 支持链式调用
  }

  // 发布
  emit(event, ...args) {
    (this.events[event] || []).forEach(cb => cb(...args));
    return this;
  }

  // 取消订阅
  off(event, callback) {
    if (!this.events[event]) return this;
    this.events[event] = this.events[event].filter(cb => cb !== callback);
    return this;
  }

  // 只订阅一次
  once(event, callback) {
    const wrapper = (...args) => {
      callback(...args);
      this.off(event, wrapper);
    };
    return this.on(event, wrapper);
  }
}

// 使用
const bus = new EventBus();

const handler = (data) => console.log('收到:', data);

bus.on('login', handler);
bus.once('init', () => console.log('只执行一次'));

bus.emit('login', { user: 'Alice' }); // 收到: { user: 'Alice' }
bus.emit('init');  // 只执行一次
bus.emit('init');  // 不再触发

bus.off('login', handler);
bus.emit('login', { user: 'Bob' }); // 无输出
```

7. 什么是稀疏数组？Array的map、forEach、filter对稀疏数组的处理有什么不同？

稀疏数组是存在"空槽"（empty slot）的数组，空槽不等于 undefined，是真正的"空位"：
```javascript
const sparse = [1, , , 4];       // 字面量创建，索引1、2是空槽
const sparse2 = new Array(3);    // [empty × 3]

console.log(0 in sparse);  // true（有值）
console.log(1 in sparse);  // false（空槽，不是真实属性）
console.log(sparse[1]);    // undefined（访问时返回 undefined，但并非存在）
```

map / forEach / filter 对空槽的处理
结论：三者都会跳过空槽，但返回结果有差异。

8. JavaScript中如何实现函数的记忆化（Memoization）？请实现一个通用的memoize函数。

基础实现
```javascript
function memoize(fn) {
  const cache = new Map();

  return function(...args) {
    // 用参数序列化作为 key
    const key = JSON.stringify(args);

    if (cache.has(key)) {
      console.log('命中缓存');
      return cache.get(key);
    }

    const result = fn.apply(this, args);
    cache.set(key, result);
    return result;
  };
}

// 使用
const expensiveAdd = memoize((a, b) => {
  console.log('计算中...');
  return a + b;
});

expensiveAdd(1, 2); // 计算中... → 3
expensiveAdd(1, 2); // 命中缓存 → 3
expensiveAdd(2, 3); // 计算中... → 5
```

进阶版：支持自定义 key 策略 + 缓存上限
```javascript
function memoize(fn, {
  resolver,    // 自定义 key 生成函数
  maxSize = Infinity  // 最大缓存数量（LRU 简化版）
} = {}) {
  const cache = new Map();

  const memoized = function(...args) {
    const key = resolver ? resolver(...args) : JSON.stringify(args);

    if (cache.has(key)) {
      // 命中时移到最后（LRU：最近使用）
      const value = cache.get(key);
      cache.delete(key);
      cache.set(key, value);
      return value;
    }

    const result = fn.apply(this, args);

    // 超出上限，删除最久未使用的（Map 有序，第一个是最老的）
    if (cache.size >= maxSize) {
      cache.delete(cache.keys().next().value);
    }

    cache.set(key, result);
    return result;
  };

  // 提供清除缓存的能力
  memoized.clear = () => cache.clear();
  memoized.cache = cache;

  return memoized;
}

// 使用示例
const memoFetch = memoize(
  (id) => fetchUser(id),
  {
    resolver: (id) => `user_${id}`, // 自定义 key
    maxSize: 100                    // 最多缓存100条
  }
);
```

9. React中的useId是什么？它解决了什么问题？在什么场景下使用？

## useId 是什么？

`useId` 是 React 18 引入的内置 Hook，用于**生成在服务端和客户端之间稳定且唯一的 ID**。

```javascript
import { useId } from 'react';

function MyComponent() {
  const id = useId();
  console.log(id); // 类似 ":r0:" ":r1:" 这样的字符串
}
```

## 它解决了什么问题？

### 核心问题：SSR 场景下的 ID 不一致（Hydration 错误）

在服务端渲染（SSR）中，如果手动生成 ID，服务端和客户端生成的值往往不匹配，导致 **Hydration Mismatch**：

```javascriptw
// ❌ 错误做法一：Math.random() 每次不同
const id = Math.random(); // 服务端: 0.123, 客户端: 0.456 → 报错

// ❌ 错误做法二：全局自增计数器
let count = 0;
const id = ++count; // 服务端/客户端执行顺序不同 → 不稳定

// ✅ useId：React 根据组件树结构生成，两端完全一致
const id = useId();
```

### 附带解决的问题：手动维护 ID 的麻烦

组件复用时手动传 ID 容易重复或遗忘，`useId` 自动保证每个组件实例的 ID 唯一。

---

## 典型使用场景

**场景一：表单 label 与 input 关联（最常见）**

```javascript
function FormField({ label }) {
  const id = useId();

  return (
    <div>
      <label htmlFor={id}>{label}</label>
      <input id={id} type="text" />
    </div>
  );
}

// 复用多次，ID 自动不同，互不干扰
<FormField label="用户名" />
<FormField label="邮箱" />
```

**场景二：ARIA 无障碍属性关联**

```javascript
function Dialog({ title, content }) {
  const titleId = useId();
  const descId = useId();

  return (
    <div
      role="dialog"
      aria-labelledby={titleId}
      aria-describedby={descId}
    >
      <h2 id={titleId}>{title}</h2>
      <p id={descId}>{content}</p>
    </div>
  );
}
```

**场景三：一个组件需要多个关联 ID（加后缀）**

```javascript
function PasswordField() {
  const id = useId();

  return (
    <div>
      <label htmlFor={`${id}-input`}>密码</label>
      <input id={`${id}-input`} type="password" />
      <span id={`${id}-hint`}>至少8位字符</span>
      <input
        type="text"
        aria-describedby={`${id}-hint`}
      />
    </div>
  );
}
```

> 推荐用同一个 `useId()` 加不同后缀，而不是多次调用 `useId()`，可以减少开销。

---

## 注意事项

| 注意点 | 说明 |
|--------|------|
| 不能用于列表 key | `key` 需要来自数据本身，语义不同 |
| 不要用于 CSS 选择器 | 生成的 ID 含 `:` 字符，CSS 中需转义 |
| 仅限组件内部调用 | 遵循 Hook 的基本规则 |
| React 17 及以下不可用 | 需要 React 18+ |

---

## 一句话总结

> `useId` 专为**需要 DOM ID 做关联**的场景设计（表单、ARIA），其核心价值是在 SSR + Hydration 场景下保证服务端与客户端 ID 完全一致，避免报错。纯客户端项目中它同样能省去手动管理 ID 的麻烦。

10. 什么是React的并发特性？startTransition的使用场景是什么？它和setTimeout有什么区别？

## React 并发特性是什么？

React 18 引入的**并发模式（Concurrent Mode）** 让 React 能够同时准备多个 UI 版本，并根据优先级**中断、暂停、恢复**渲染工作，而不是像以前一样一旦开始渲染就必须同步完成。

核心思想：**将渲染任务分级，紧急任务优先，非紧急任务可被打断。**

```
旧模型（同步）：  任务A ████████████████ 完成后才处理交互
新模型（并发）：  任务A ████ → 被打断 → 处理紧急交互 → 继续任务A
```

并发特性的主要 API 包括 `startTransition`、`useDeferredValue`、`Suspense` 等。

---

## startTransition 解决什么问题？

### 问题场景

输入框搜索时，每次击键都触发大量列表重渲染，导致**输入卡顿**：

```javascript
// ❌ 用户输入 → 触发大量渲染 → 输入框响应延迟
function Search() {
  const [query, setQuery] = useState('');
  const [list, setList] = useState(allData);

  function handleChange(e) {
    setQuery(e.target.value);           // 需要立即响应
    setList(filterData(e.target.value)); // 耗时操作，拖慢了上面那行
  }
}
```

### startTransition 的解法

```javascript
import { useState, startTransition } from 'react';

function Search() {
  const [query, setQuery] = useState('');
  const [list, setList] = useState(allData);

  function handleChange(e) {
    const value = e.target.value;

    // 紧急更新：直接调用，立即响应
    setQuery(value);

    // 非紧急更新：标记为 transition，可被打断
    startTransition(() => {
      setList(filterData(value));
    });
  }

  return (
    <>
      <input value={query} onChange={handleChange} />
      <List data={list} />
    </>
  );
}
```

React 会优先处理 `setQuery`（保证输入流畅），在浏览器空闲时再处理 `setList`，如果期间有新的输入，旧的列表渲染会被**直接丢弃**，重新开始。

### 配合 isPending 显示加载态

```javascript
import { useTransition } from 'react';

function Search() {
  const [isPending, startTransition] = useTransition();
  const [list, setList] = useState(allData);

  function handleChange(e) {
    startTransition(() => {
      setList(filterData(e.target.value));
    });
  }

  return (
    <>
      <input onChange={handleChange} />
      {isPending && <span>更新中...</span>}
      <List data={list} />
    </>
  );
}
```

## startTransition vs setTimeout

这是面试高频对比题，两者看起来都能"延迟执行"，但本质完全不同：

### 行为对比

```javascript
// setTimeout 方案
function handleChange(e) {
  setQuery(e.target.value);
  setTimeout(() => {
    setList(filterData(e.target.value)); // 延迟执行，但执行时无法被打断
  }, 0);
}

// startTransition 方案
function handleChange(e) {
  setQuery(e.target.value);
  startTransition(() => {
    setList(filterData(e.target.value)); // 低优先级，执行中可被打断
  });
}
```

| 维度 | `setTimeout` | `startTransition` |
|------|-------------|-------------------|
| 执行时机 | 宏任务队列，至少延迟一个事件循环 | React 调度器控制，尽快但低优先级 |
| 能否被打断 | ❌ 一旦开始执行，同步跑完 | ✅ 可被更高优先级任务中断 |
| 过期更新处理 | 每次都执行，旧的结果也会渲染 | 自动丢弃过期的中间状态 |
| isPending 支持 | ❌ 无法感知状态 | ✅ 可通过 `useTransition` 获取 |
| 延迟时间 | 固定（至少 4ms，嵌套后更长） | 动态，React 根据帧时间智能调度 |
| 语义 | "等会儿再做" | "这件事不紧急，用户交互优先" |

### 关键差异举例

快速连续输入 "a" "ab" "abc" 时：

```
setTimeout：
  渲染("a的结果") → 渲染("ab的结果") → 渲染("abc的结果")
  // 三次都渲染，中间状态用户可能看到闪烁

startTransition：
  "a"触发transition → 还没渲染完，"ab"来了 → 丢弃"a"的渲染
  "ab"触发transition → 还没渲染完，"abc"来了 → 丢弃"ab"的渲染
  渲染("abc的结果") // 只渲染最终结果，更高效
```

---

## 使用场景总结

适合用 `startTransition` 的场景都满足一个特征：**更新结果依赖当前最新状态，中间过程无需展示**。

**适合使用：**搜索过滤大列表、Tab 切换加载新内容、路由跳转页面渲染、图表数据实时更新。

**不适合使用：**受控输入框本身的更新、动画、需要立即反馈的操作（如按钮点击后的状态变化）。

> 一句话记忆：`setTimeout` 是"推迟执行"，`startTransition` 是"告诉 React 这不紧急，用户操作永远优先"。

12. 什么是React的批量更新？如何手动触发批量更新？flushSync的作用是什么？

## 什么是批量更新？

批量更新（Batching）是指 React 将**多次 setState 合并成一次重渲染**，而不是每次调用都触发一次渲染，以此减少不必要的渲染次数。

```javascript
function handleClick() {
  setCount(c => c + 1);
  setName('Alice');
  setVisible(true);
  // React 不会渲染 3 次，而是合并成 1 次渲染
}
```

---

## React 18 前后的批量更新对比

这是面试高频考点，两个版本行为差异显著。

### React 17：只有事件处理函数内自动批量更新

```javascript
// ✅ 合并：React 合成事件内，自动批量
function handleClick() {
  setCount(c => c + 1); // 不渲染
  setName('Alice');     // 不渲染
  // 合并为 1 次渲染 ✓
}

// ❌ 不合并：异步回调中，每次 setState 都触发渲染
setTimeout(() => {
  setCount(c => c + 1); // 渲染一次
  setName('Alice');     // 又渲染一次
  // 共 2 次渲染 ✗
}, 0);

// ❌ 不合并：原生事件、Promise 中同样不批量
fetch('/api').then(() => {
  setCount(c => c + 1); // 渲染一次
  setName('Alice');     // 又渲染一次
});
```

### React 18：所有场景自动批量更新

React 18 引入**自动批量更新（Automatic Batching）**，覆盖所有场景：

```javascript
// 以下场景在 React 18 中全部自动合并

setTimeout(() => {
  setCount(c => c + 1);
  setName('Alice');
  // ✅ 合并为 1 次渲染
}, 0);

fetch('/api').then(() => {
  setCount(c => c + 1);
  setName('Alice');
  // ✅ 合并为 1 次渲染
});

element.addEventListener('click', () => {
  setCount(c => c + 1);
  setName('Alice');
  // ✅ 合并为 1 次渲染
});
```

---

## 手动触发批量更新（React 17 场景）

React 17 中如果需要在异步代码里手动批量，使用 `unstable_batchedUpdates`：

```javascript
import { unstable_batchedUpdates } from 'react-dom';

setTimeout(() => {
  unstable_batchedUpdates(() => {
    setCount(c => c + 1);
    setName('Alice');
    // ✅ 强制合并为 1 次渲染
  });
}, 0);
```

React 18 升级后此 API 仍保留兼容，但通常不再需要手动调用。

---

## flushSync：强制同步、退出批量更新

`flushSync` 的作用与批量更新**相反**，它强制 React **立即、同步地**完成渲染，不等待批量合并。

```javascript
import { flushSync } from 'react-dom';

function handleClick() {
  // 第一次 flushSync：立即渲染，count 变化马上反映到 DOM
  flushSync(() => {
    setCount(c => c + 1);
  });
  // 执行到这里时，DOM 已经更新完毕

  // 第二次 flushSync：再次立即渲染
  flushSync(() => {
    setName('Alice');
  });
  // 执行到这里时，DOM 再次更新完毕
}
// 总计触发 2 次渲染，而非合并为 1 次
```

### flushSync 的典型使用场景

**场景一：渲染后立即读取 DOM 尺寸**

```javascript
function handleAddItem() {
  flushSync(() => {
    setList(prev => [...prev, newItem]);
  });
  // 此时 DOM 已更新，可以准确读取新列表的高度
  listRef.current.scrollTop = listRef.current.scrollHeight;
}
```

不用 `flushSync` 的问题：`setState` 是异步的，下一行读取 DOM 时列表还没渲染，拿到的是旧高度，滚动位置计算错误。

**场景二：第三方库需要同步 DOM 更新**

```javascript
function syncWithLegacyLibrary(data) {
  flushSync(() => {
    setChartData(data);
  });
  // 确保 React 渲染完毕后，再调用第三方库操作 DOM
  legacyChart.redraw(chartRef.current);
}
```

**场景三：调试时观察中间状态**

```javascript
// 开发调试用，生产环境应避免
flushSync(() => setStep(1));
console.log('step 1 DOM:', document.querySelector('.step').textContent);
flushSync(() => setStep(2));
console.log('step 2 DOM:', document.querySelector('.step').textContent);
```

---

## 三者关系总结

```
自动批量更新
    │
    │  多次 setState → 合并 → 1 次渲染（默认行为）
    │
    ▼
unstable_batchedUpdates        flushSync
    │                              │
    │  React 17 异步场景            │  强制退出批量，立即同步渲染
    │  手动开启批量更新              │  用于需要立即读取/操作 DOM 的场景
    │  React 18 已不需要            │  性能有损耗，谨慎使用
```

| API | 方向 | 版本 | 使用频率 |
|-----|------|------|---------|
| 自动批量 | 合并渲染 | React 18 默认 | 无需手动 |
| `unstable_batchedUpdates` | 合并渲染 | React 17 手动 | 逐渐淘汰 |
| `flushSync` | 强制立即渲染 | React 18 仍需要 | 谨慎使用 |

---

## 一句话总结

> 批量更新是 React 的性能优化机制，React 18 已将其扩展到所有场景自动生效；`flushSync` 是逃生舱口，在**必须拿到最新 DOM 再执行后续逻辑**时使用，代价是打破批量合并、触发额外渲染，应尽量少用。

15. React中的Context性能问题如何优化？如何避免Provider导致的全局重渲染？

## Context 性能问题的根源

先明确问题本质：**Context 的 value 发生变化时，所有调用了 `useContext` 的组件都会重渲染**，无论它们是否真正用到了变化的那部分数据。

```javascript
// ❌ 典型的性能陷阱
const AppContext = createContext();

function App() {
  const [user, setUser] = useState({ name: 'Alice' });
  const [theme, setTheme] = useState('dark');

  return (
    // user 或 theme 任意一个变化，所有消费者全部重渲染
    <AppContext.Provider value={{ user, theme, setUser, setTheme }}>
      <Header />   {/* 只用 theme，但 user 变了也会渲染 */}
      <Profile />  {/* 只用 user，但 theme 变了也会渲染 */}
      <Footer />
    </AppContext.Provider>
  );
}
```

---

## 优化方案

### 方案一：拆分 Context（最有效，优先使用）

按数据的**变化频率和使用范围**拆分成多个 Context，让组件只订阅自己关心的数据：

```javascript
const UserContext = createContext();
const ThemeContext = createContext();

function App() {
  const [user, setUser] = useState({ name: 'Alice' });
  const [theme, setTheme] = useState('dark');

  return (
    <UserContext.Provider value={{ user, setUser }}>
      <ThemeContext.Provider value={{ theme, setTheme }}>
        <Header />   {/* 只订阅 ThemeContext，user 变了不触发 */}
        <Profile />  {/* 只订阅 UserContext，theme 变了不触发 */}
      </ThemeContext.Provider>
    </UserContext.Provider>
  );
}

// 组件只消费自己需要的
function Header() {
  const { theme } = useContext(ThemeContext); // user 变化不影响我
  return <header className={theme}>...</header>;
}
```

### 方案二：稳定 value 引用（用 useMemo）

Provider 的 value 如果是对象字面量，每次父组件渲染都会生成新引用，导致所有消费者重渲染：

```javascript
// ❌ 每次 App 渲染，value 都是新对象引用
<Context.Provider value={{ user, setUser }}>

// ✅ 用 useMemo 稳定引用，只有 user 变化时才产生新对象
function App() {
  const [user, setUser] = useState({ name: 'Alice' });

  const value = useMemo(() => ({ user, setUser }), [user]);

  return (
    <Context.Provider value={value}>
      <Children />
    </Context.Provider>
  );
}
```

### 方案三：分离静态数据与动态数据

将**不变的数据（如 dispatch、setter）** 和**频繁变化的数据**放入不同 Context，因为 setter 函数本身引用稳定：

```javascript
const StoreContext = createContext();    // 存放状态（会变）
const DispatchContext = createContext(); // 存放 dispatch（稳定）

function App() {
  const [state, dispatch] = useReducer(reducer, initialState);

  return (
    // dispatch 引用永远稳定，DispatchContext 的消费者永远不会因状态变化重渲染
    <DispatchContext.Provider value={dispatch}>
      <StoreContext.Provider value={state}>
        <DeepChild />
      </StoreContext.Provider>
    </DispatchContext.Provider>
  );
}

// 只需要触发操作的组件，不订阅状态变化
function ActionButton() {
  const dispatch = useContext(DispatchContext); // 永远不重渲染！
  return <button onClick={() => dispatch({ type: 'increment' })}>+</button>;
}
```

### 方案四：用 memo 隔离子树

对不依赖 Context 但处于 Provider 内的子组件使用 `memo`，避免因父组件重渲染而连带渲染：

```javascript
// ❌ Footer 不用 Context，但每次 Provider value 变化都跟着渲染
function App() {
  return (
    <Context.Provider value={value}>
      <Header />
      <Footer /> {/* 无辜受害 */}
    </Context.Provider>
  );
}

// ✅ memo 包裹后，Footer 的 props 不变就不渲染
const Footer = memo(function Footer() {
  return <footer>...</footer>;
});
```

### 方案五：选择性订阅（自定义 Hook 封装）

通过自定义 Hook 封装 Context 消费逻辑，集中管理并便于后续替换方案：

```javascript
// 封装 Context 消费
function useUser() {
  const context = useContext(UserContext);
  if (!context) throw new Error('useUser 必须在 UserProvider 内使用');
  return context;
}

// 只暴露组件需要的字段，语义更清晰
function useUserName() {
  const { user } = useUser();
  return user.name; // 只取 name，但注意：user 对象变化仍会触发渲染
}

// 使用
function Profile() {
  const name = useUserName();
  return <div>{name}</div>;
}
```

> 注意：自定义 Hook 本身**不能阻止重渲染**，它只是封装访问方式。真正要实现"只有用到的字段变化才渲染"，需要配合状态管理库（见下方）。

---

## 各方案对比

| 方案 | 效果 | 成本 | 适用场景 |
|------|------|------|---------|
| 拆分 Context | ⭐⭐⭐⭐⭐ | 低 | 数据有明显分组 |
| useMemo 稳定引用 | ⭐⭐⭐ | 低 | 简单场景兜底 |
| 分离静态/动态数据 | ⭐⭐⭐⭐ | 低 | 有 dispatch 模式 |
| memo 隔离子树 | ⭐⭐⭐ | 低 | 子组件不依赖 Context |
| 状态管理库 | ⭐⭐⭐⭐⭐ | 中 | 复杂全局状态 |

---

## 根本性解法：何时该放弃 Context？

Context 本质是为**低频变化的全局数据**设计的（主题、语言、用户信息），当出现以下情况时应考虑换用状态管理库：

```
✅ Context 适合：theme、locale、当前用户、权限
❌ Context 不适合：频繁更新的表单状态、实时数据、复杂的跨组件联动
```

Zustand 的订阅粒度控制是解决这类问题的典型方案：

```javascript
// Zustand：组件只在自己订阅的字段变化时重渲染
const useStore = create((set) => ({
  user: { name: 'Alice' },
  theme: 'dark',
  setTheme: (theme) => set({ theme }),
}));

function Header() {
  // 只订阅 theme，user 变化完全不影响此组件
  const theme = useStore((state) => state.theme);
  return <header className={theme}>...</header>;
}
```

---

## 一句话总结

> Context 性能优化的核心是**减少不必要的订阅范围**：优先按变化频率拆分 Context，用 `useMemo` 稳定 value 引用，将静态的 dispatch 与动态的 state 分开存放。当 Context 数据频繁变化且消费者众多时，应直接换用支持细粒度订阅的状态管理库。

16. 什么是React的时间切片（Time Slicing）？它如何提升用户体验？

## 什么是时间切片？

时间切片（Time Slicing）是 React 并发模式的底层机制，核心思想是：**将长时间的渲染任务拆分成多个小片段，在浏览器每一帧的空闲时间内分批执行，而不是一次性阻塞主线程。**

### 先理解问题根源：为什么会卡顿？

浏览器渲染和 JS 执行共用同一个主线程，正常情况下浏览器需要**每 16.6ms 渲染一帧**（60fps）才能让用户感觉流畅：

```
正常帧节奏（流畅）：
│ JS(4ms) │ 渲染(8ms) │ 空闲 │ JS(4ms) │ 渲染(8ms) │ 空闲 │
  16.6ms                        16.6ms

长任务阻塞（卡顿）：
│ JS ████████████████████████(200ms) │ 渲染 │ 渲染 │ ...
  用户操作在这 200ms 内完全得不到响应 ↑
```

React 18 之前，组件树一旦开始渲染就是**同步且不可中断**的，复杂页面很容易产生这种长任务。

---

## 时间切片如何工作？

React 借助 `MessageChannel`（而非 `requestIdleCallback`，因为后者延迟不够稳定）实现自己的调度器，将渲染工作切成 **5ms 左右的小片**：

```
时间切片后：
│ React(5ms) │ 渲染帧 │ React(5ms) │ 渲染帧 │ React(5ms) │ 渲染帧 │
              ↑ 用户交互可以在这里插入，不会被阻塞
```

每执行完一个小片，React 会**主动让出主线程**，询问：

```
"现在有更紧急的任务吗？（用户点击/输入）"
  ├─ 有 → 先处理紧急任务，之后回来继续
  └─ 没有 → 继续执行下一个渲染片段
```

### Fiber 架构是时间切片的基础

时间切片能够实现，依赖 React 16 引入的 **Fiber 架构**。Fiber 将组件树变成链表结构，每个节点（Fiber 节点）都记录了"从哪里暂停、下次从哪里继续"，使得渲染过程可以随时中断和恢复：

```
旧架构（递归，无法中断）：
renderApp()
  └─ renderHeader()
       └─ renderNav() ...  // 调用栈深，无法暂停

Fiber 架构（链表，可中断）：
App → Header → Nav → ...  // 每个节点处理完可暂停
 ↑                         // 保存当前进度，随时恢复
```

---

## 时间切片如何提升用户体验？

### 对比示例：渲染 10000 个列表项

```javascript
// 模拟耗时渲染
function HeavyList({ items }) {
  return (
    <ul>
      {items.map(item => (
        <HeavyItem key={item.id} data={item} /> // 每个组件都很重
      ))}
    </ul>
  );
}
```

**没有时间切片（React 17 同步模式）：**

```
用户输入 → React 开始渲染(300ms) → 输入框更新 → 用户感受到明显卡顿
              ↑ 这 300ms 内任何交互都无响应
```

**有时间切片（React 18 并发模式）：**

```
用户输入 → 输入框立即更新（紧急）
         → 列表分片渲染：5ms → 让出 → 5ms → 让出 → ...（非紧急）
              ↑ 每次让出时用户交互都能被响应
```

### 三个层面的体验提升

**输入响应不卡顿**，即便后台在渲染大量内容，用户输入也能即时反馈，因为输入事件优先级高于 transition 渲染任务。

**页面不会白屏/冻结**，长任务被切碎后浏览器能持续渲染帧，用户至少能看到部分内容和动画，而不是页面完全静止。

**自动丢弃过期渲染**，快速触发多次更新时（如连续输入），中间过程的渲染片段会被直接放弃，只渲染最终结果，避免无效计算。

---

## 时间切片 vs 虚拟列表

两者都能解决大量 DOM 的性能问题，但思路不同：

| 维度 | 时间切片 | 虚拟列表 |
|------|---------|---------|
| 核心思路 | 分批渲染，不阻塞主线程 | 只渲染可视区域内的 DOM |
| DOM 数量 | 最终全部创建 | 始终只有少量 DOM |
| 适用场景 | 组件渲染耗时长 | 列表项数量极大（万级以上） |
| 内存占用 | 较高（全量 DOM） | 低（少量 DOM 复用） |
| 实现复杂度 | React 自动处理 | 需要额外库或手动实现 |

> 数据量极大时（10万条），虚拟列表仍是首选；时间切片更适合解决**组件本身渲染复杂**导致的卡顿。两者可以结合使用。

---

## 一句话总结

> 时间切片的本质是**把 React 的渲染从"独占主线程的长跑"变成"见缝插针的短跑"**，让浏览器始终有机会响应用户交互，从根本上解决复杂 UI 的渲染卡顿问题。

## 什么是 Turborepo？

Turborepo 是由 Vercel 开发的**高性能 Monorepo 构建系统**，核心目标是解决大型 Monorepo 项目中构建速度慢的问题。它本身不是包管理器，而是架在 npm/yarn/pnpm workspace 之上的**任务编排和缓存层**。

```
你的 Monorepo
├── apps/
│   ├── web/          # Next.js 应用
│   └── admin/        # React 应用
├── packages/
│   ├── ui/           # 共享组件库
│   ├── utils/        # 工具函数
│   └── config/       # 共享配置
└── turbo.json        # Turborepo 配置
```

## 一、Turborepo 如何加速构建？

### 核心机制一：任务依赖图（Pipeline）

Turborepo 根据 `turbo.json` 中声明的依赖关系，构建任务的有向无环图（DAG），精确控制执行顺序：

```json
// turbo.json
{
  "pipeline": {
    "build": {
      "dependsOn": ["^build"],  // ^ 表示先执行依赖包的 build
      "outputs": [".next/**", "dist/**"]
    },
    "test": {
      "dependsOn": ["build"],   // 先 build 再 test
      "inputs": ["src/**/*.ts", "test/**/*.ts"]
    },
    "lint": {
      "dependsOn": []           // 无依赖，可立即并行执行
    },
    "dev": {
      "cache": false,           // 开发服务器不缓存
      "persistent": true
    }
  }
}
```

### 核心机制二：最大化并行执行

Turborepo 分析依赖图后，将**没有依赖关系的任务并行执行**：

```
没有 Turborepo（串行）：
ui:build → utils:build → web:build → admin:build
────────────────────────────────────────── 总耗时 40s

有 Turborepo（并行 + 拓扑排序）：
ui:build ──┐
           ├──→ web:build ──┐
utils:build┘               ├──→ 完成
           ├──→ admin:build─┘
────────────────────────────── 总耗时 15s
```

### 核心机制三：本地缓存（最关键）

Turborepo 对每个任务计算一个**哈希指纹**，命中缓存时直接复原输出，跳过执行：

```
哈希输入 = hash(
  源文件内容,          // src/**
  依赖包版本,          // package.json
  环境变量,            // turbo.json 中声明的 env
  任务配置本身,        // pipeline 配置
  依赖任务的哈希       // 上游任务的输出哈希
)
```

```bash
# 第一次构建（无缓存）
turbo run build
# ui:build    3.2s
# web:build   8.1s
# 总计: 11.3s

# 第二次构建（代码未变，命中缓存）
turbo run build
# ui:build    cache hit  0.1s  ← 直接复原输出
# web:build   cache hit  0.1s
# 总计: 0.2s  🚀
```

缓存命中时，Turborepo 做的事情：从缓存恢复 `outputs` 中声明的文件，并重放终端日志（让 CI 日志看起来和真实执行一样）。

## 二、远程缓存原理

本地缓存只对单台机器有效，**换一台机器（CI 服务器、同事电脑）缓存就失效了**。远程缓存解决的正是这个问题。

### 工作流程

```
开发者 A（本地）               远程缓存服务器          开发者 B / CI
      │                              │                       │
      │  1. 计算任务哈希              │                       │
      │  hash("abc123")              │                       │
      │                              │                       │
      │  2. 本地无缓存，执行构建       │                       │
      │  build → dist/               │                       │
      │                              │                       │
      │  3. 上传缓存                  │                       │
      │  PUT /cache/abc123 ─────────→│ 存储 tar.gz           │
      │                              │                       │
      │                              │  4. 同样代码，相同哈希   │
      │                              │←─ GET /cache/abc123 ──│
      │                              │                       │
      │                              │  5. 命中！返回缓存      │
      │                              │──────────────────────→│
      │                              │                       │ 直接复原，无需构建
```

### 缓存存储内容

```
/cache/{hash}/
  ├── outputs.tar.gz    # 构建产物（dist/、.next/ 等）
  └── metadata.json     # 任务元信息、执行时间、日志
```

### 接入 Vercel 远程缓存

```bash
# 登录 Vercel
npx turbo login

# 关联团队远程缓存
npx turbo link

# 之后正常执行，自动使用远程缓存
turbo run build
```

不想依赖 Vercel 可以自建，Turborepo 提供了标准 API 协议：


```javascript
class ErrorCollector {
  install() {
    this._captureJsError();
    this._capturePromiseError();
    this._captureResourceError();
    this._captureHttpError();
    this._captureConsoleError();
    this._captureFrameworkError(); // React/Vue 专属
  }

  // 1. JS 运行时错误
  _captureJsError() {
    window.addEventListener('error', (event) => {
      // 区分 JS 错误和资源加载错误
      if (event.error) {
        this._report({
          type: 'js_error',
          message: event.message,
          stack: event.error.stack,
          filename: event.filename,
          lineno: event.lineno,
          colno: event.colno,
        });
      }
    }, true); // 捕获阶段，能拦截资源错误
  }

  // 2. Promise 未捕获异常
  _capturePromiseError() {
    window.addEventListener('unhandledrejection', (event) => {
      const error = event.reason;
      this._report({
        type: 'promise_error',
        message: error?.message ?? String(error),
        stack: error?.stack,
      });
    });
  }

  // 3. 资源加载错误（图片、脚本、CSS）
  _captureResourceError() {
    window.addEventListener('error', (event) => {
      const target = event.target;
      if (target && target !== window) {
        this._report({
          type: 'resource_error',
          tagName: target.tagName,
          src: target.src || target.href,
          outerHTML: target.outerHTML?.slice(0, 200),
        });
      }
    }, true);
  }

  // 4. HTTP 请求错误（拦截 fetch 和 XHR）
  _captureHttpError() {
    // 拦截 fetch
    const originalFetch = window.fetch;
    window.fetch = async (...args) => {
      const startTime = Date.now();
      try {
        const response = await originalFetch(...args);
        if (!response.ok) {
          this._report({
            type: 'http_error',
            url: args[0],
            status: response.status,
            duration: Date.now() - startTime,
          });
        }
        return response;
      } catch (error) {
        this._report({
          type: 'http_error',
          url: args[0],
          message: error.message,
          duration: Date.now() - startTime,
        });
        throw error;
      }
    };
  }

  // 5. React 错误边界集成
  createErrorBoundary(React) {
    const reporter = this;
    return class ErrorBoundary extends React.Component {
      componentDidCatch(error, info) {
        reporter._report({
          type: 'react_error',
          message: error.message,
          stack: error.stack,
          componentStack: info.componentStack,
        });
      }
      render() {
        return this.props.children;
      }
    };
  }
}
```

```javascript
class BreadcrumbCollector {
  constructor() {
    this.crumbs = [];
    this.maxSize = 50;
    this._install();
  }

  _install() {
    // 记录用户点击
    document.addEventListener('click', (e) => {
      this.push({
        type: 'click',
        target: e.target.tagName,
        text: e.target.textContent?.slice(0, 50),
        id: e.target.id,
      });
    });

    // 记录路由变化
    window.addEventListener('popstate', () => {
      this.push({ type: 'navigation', to: location.href });
    });

    // 记录 console.error
    const originalError = console.error;
    console.error = (...args) => {
      this.push({ type: 'console', level: 'error', message: args.join(' ') });
      originalError.apply(console, args);
    };

    // 记录 HTTP 请求
    this.push({ type: 'http', method, url, status, duration });
  }

  push(crumb) {
    this.crumbs.push({ ...crumb, timestamp: Date.now() });
    if (this.crumbs.length > this.maxSize) {
      this.crumbs.shift(); // 超出上限移除最老的
    }
  }

  getRecent(n) {
    return this.crumbs.slice(-n);
  }
}
```

## 三、上报层设计

### 多策略上报

```javascript
class ErrorReporter {
  constructor(config) {
    this.endpoint = config.endpoint;
    this.queue = [];
    this.maxQueueSize = 20;
    this.flushInterval = 5000;

    // 定时批量上报
    setInterval(() => this.flush(), this.flushInterval);

    // 页面关闭前确保上报（最关键）
    window.addEventListener('pagehide', () => this.flushSync());
    window.addEventListener('visibilitychange', () => {
      if (document.visibilityState === 'hidden') this.flushSync();
    });
  }

  report(error) {
    this.queue.push(error);

    // 严重错误立即上报，不等批量
    if (error.level === 'fatal' || this.queue.length >= this.maxQueueSize) {
      this.flush();
    }
  }

  // 普通上报：批量 + 异步
  async flush() {
    if (!this.queue.length) return;
    const errors = this.queue.splice(0);

    try {
      await fetch(this.endpoint, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ errors }),
      });
    } catch {
      // 上报失败，存入 localStorage 下次重试
      this._persistToLocal(errors);
    }
  }

  // 页面关闭时的可靠上报（fetch 可能被取消）
  flushSync() {
    if (!this.queue.length) return;
    const errors = this.queue.splice(0);

    // sendBeacon 在页面关闭时仍能可靠发送
    navigator.sendBeacon(
      this.endpoint,
      new Blob([JSON.stringify({ errors })], { type: 'application/json' })
    );
  }

  // 采样控制（高流量下避免上报量过大）
  _shouldSample(error) {
    const rate = error.level === 'fatal' ? 1.0 : this.sampleRate;
    return Math.random() < rate;
  }

  // 失败后从 localStorage 恢复重试
  _persistToLocal(errors) {
    const stored = JSON.parse(localStorage.getItem('__error_queue') ?? '[]');
    localStorage.setItem('__error_queue', JSON.stringify([...stored, ...errors].slice(-50)));
  }

  _retryStored() {
    const stored = JSON.parse(localStorage.getItem('__error_queue') ?? '[]');
    if (stored.length) {
      localStorage.removeItem('__error_queue');
      stored.forEach(e => this.report(e));
    }
  }
}
```

## 四、错误聚合——指纹计算

聚合的核心是**将同一问题的不同实例识别为同一条错误**，而不是每次都产生一条新记录。

```javascript
// 服务端：计算错误指纹
function generateFingerprint(error) {
  // 对 stack trace 做规范化处理，去除动态变量
  const normalizedStack = normalizeStack(error.stack);

  const components = [
    error.type,
    error.message
      .replace(/\d+/g, 'N')         // 数字替换（行号、ID）
      .replace(/'[^']*'/g, "'STR'") // 字符串替换
      .slice(0, 200),
    normalizedStack,
  ].filter(Boolean);

  return md5(components.join('|'));
}

function normalizeStack(stack = '') {
  return stack
    .split('\n')
    .slice(0, 5)                           // 只取前5帧，忽略尾部框架噪音
    .map(line =>
      line
        .replace(/:\d+:\d+/g, '')          // 移除行列号（编译后会变）
        .replace(/\?[^)]+/g, '')           // 移除 query string
        .trim()
    )
    .join('\n');
}

// 聚合写入（服务端 upsert 逻辑）
async function upsertError(error) {
  const fingerprint = generateFingerprint(error);

  await db.errorGroups.upsert({
    where: { fingerprint },
    update: {
      count: { increment: 1 },
      lastSeen: new Date(),
      affectedUsers: { addToSet: error.userId },
    },
    create: {
      fingerprint,
      type: error.type,
      message: error.message,
      stack: error.stack,          // 存第一次出现的 stack
      firstSeen: new Date(),
      lastSeen: new Date(),
      count: 1,
    },
  });
}
```

### Source Map 还原

```javascript
import { SourceMapConsumer } from 'source-map';

async function restoreStack(stack, appVersion) {
  // 从对象存储获取对应版本的 source map
  const sourceMap = await fetchSourceMap(appVersion);
  const consumer = await new SourceMapConsumer(sourceMap);

  const restored = stack.replace(
    /at .+ \((.+):(\d+):(\d+)\)/g,
    (match, file, line, col) => {
      const pos = consumer.originalPositionFor({
        line: parseInt(line),
        column: parseInt(col),
      });
      return pos.source
        ? `at ${pos.name ?? 'anonymous'} (${pos.source}:${pos.line}:${pos.column})`
        : match;
    }
  );

  consumer.destroy();
  return restored;
}
```

### 多维度告警策略

```javascript
class AlertEngine {
  rules = [
    // 规则一：错误率突增（相比过去1小时环比）
    {
      name: '错误率突增',
      check: async () => {
        const current = await getErrorRate('5m');
        const baseline = await getErrorRate('1h', { offset: '1h' });
        return current > baseline * 2 && current > 10; // 翻倍且超过阈值
      },
      level: 'warning',
    },

    // 规则二：新错误出现（从未见过的 fingerprint）
    {
      name: '新错误出现',
      check: async (error) => {
        return error.count === 1; // 第一次出现
      },
      level: 'info',
    },

    // 规则三：影响用户数超阈值
    {
      name: '大规模影响',
      check: async (errorGroup) => {
        return errorGroup.affectedUsers > 100;
      },
      level: 'critical',
    },

    // 规则四：核心页面错误（首页、结算页）
    {
      name: '核心链路错误',
      check: async (error) => {
        const criticalRoutes = ['/checkout', '/payment', '/login'];
        return criticalRoutes.some(r => error.page.route.includes(r));
      },
      level: 'critical',
    },
  ];

  // 告警降噪：同一规则 N 分钟内只告警一次
  async trigger(rule, context) {
    const key = `alert_lock:${rule.name}`;
    const locked = await redis.get(key);
    if (locked) return; // 冷却中，静默

    await redis.set(key, 1, 'EX', 300); // 5 分钟冷却
    await this._notify(rule, context);
  }

  async _notify(rule, context) {
    const message = this._buildMessage(rule, context);

    await Promise.all([
      rule.level === 'critical' && sendPagerDuty(message),
      sendSlack(message),
      sendEmail(message),
    ]);
  }
}
```

| 压缩混淆栈无法读 | 构建时上传 Source Map，上报后还原 |
| 网络失败丢数据 | LocalStorage 持久化 + 重试 |
| 告警风暴 | 分级告警 + 冷却期 + 环比而非绝对值 |

> 核心设计原则：**采集要全、上报要稳、聚合要准、告警要静**。采集覆盖所有错误类型，上报在页面关闭时也可靠，聚合用指纹合并同类项，告警加冷却避免轰炸。

## 二、WebSocket 长连接设计

### 核心连接管理类

```javascript
class WebSocketClient {
  constructor(config) {
    this.url = config.url;
    this.reconnectDelay = config.reconnectDelay ?? 1000;
    this.maxReconnectDelay = config.maxReconnectDelay ?? 30000;
    this.maxReconnectAttempts = config.maxReconnectAttempts ?? 10;

    this.ws = null;
    this.reconnectAttempts = 0;
    this.reconnectTimer = null;
    this.heartbeatTimer = null;
    this.messageQueue = [];       // 离线消息队列
    this.pendingMessages = new Map(); // 等待 ACK 的消息
    this.listeners = new Map();
    this.status = 'disconnected'; // disconnected | connecting | connected
  }

  connect() {
    if (this.status === 'connecting' || this.status === 'connected') return;
    this.status = 'connecting';
    this.ws = new WebSocket(this.url);

    this.ws.onopen    = () => this._onOpen();
    this.ws.onmessage = (e) => this._onMessage(e);
    this.ws.onclose   = (e) => this._onClose(e);
    this.ws.onerror   = (e) => this._onError(e);
  }

  _onOpen() {
    this.status = 'connected';
    this.reconnectAttempts = 0;
    this.reconnectDelay = 1000;    // 重置退避延迟
    this._startHeartbeat();
    this._flushQueue();            // 发送离线期间积压的消息
    this.emit('connected');
  }

  _onClose(event) {
    this.status = 'disconnected';
    this._stopHeartbeat();
    // 非主动关闭才重连
    if (!event.wasClean) this._scheduleReconnect();
    this.emit('disconnected', event);
  }
}
```

```javascript
    return;
  }

  // 处理业务消息...

}
```

## 三、断线重连——指数退避策略

```javascript
_scheduleReconnect() {
  if (this.reconnectAttempts >= this.maxReconnectAttempts) {
    this.emit('reconnect_failed');
    return;
  }

  // 指数退避 + 随机抖动，避免大量客户端同时重连冲垮服务器
  const jitter = Math.random() * 1000;
  const delay = Math.min(this.reconnectDelay * 2 ** this.reconnectAttempts, this.maxReconnectDelay) + jitter;

  this.reconnectAttempts++;
  this.emit('reconnecting', { attempt: this.reconnectAttempts, delay });

  this.reconnectTimer = setTimeout(() => this.connect(), delay);
}

// 重连序列示例：
// 第1次: 1s + 抖动
// 第2次: 2s + 抖动
// 第3次: 4s + 抖动
// 第4次: 8s + 抖动
// ...最长 30s + 抖动
```

## 四、消息可靠性保证

### 消息状态机

```
发送 → sending → sent（服务端收到）→ delivered（用户收到）→ read
                 ↓ 超时
               failed → 可重试
```

### 实现消息 ACK 机制

```javascript
// 发送时携带唯一 msgId，等待服务端 ACK
sendMessage(content) {
  const message = {
    msgId: generateUUID(),    // 客户端生成唯一 ID（幂等键）
    sessionId: this.sessionId,
    content,
    timestamp: Date.now(),
    status: 'sending',
  };

  // 加入待确认队列
  this.pendingMessages.set(message.msgId, {
    message,
    timer: setTimeout(() => this._onMessageTimeout(message.msgId), 10000),
  });

  this._sendOrQueue(message);
  return message;
}

// 收到服务端 ACK
_handleAck(ack) {
  const pending = this.pendingMessages.get(ack.msgId);
  if (!pending) return;

  clearTimeout(pending.timer);
  this.pendingMessages.delete(ack.msgId);
  // 更新消息状态为 sent
  MessageStore.updateStatus(ack.msgId, 'sent');
}

// 消息超时处理
_onMessageTimeout(msgId) {
  this.pendingMessages.delete(msgId);
  MessageStore.updateStatus(msgId, 'failed');
}
```

### 离线消息队列（断网期间不丢消息）

```javascript
_sendOrQueue(message) {
  if (this.status === 'connected') {
    this.ws.send(JSON.stringify(message));
  } else {
    // 断网时入队，重连后自动发送
    this.messageQueue.push(message);
  }
}

_flushQueue() {
  while (this.messageQueue.length > 0) {
    const message = this.messageQueue.shift();
    this.ws.send(JSON.stringify(message));
  }
}
```

```javascript
// 重试时携带同一个 msgId，服务端根据 msgId 去重
async retryMessage(msgId) {
  const message = MessageStore.getMessage(msgId);
  if (!message) return;

  // msgId 不变，服务端收到重复 msgId 直接返回之前的 ACK
  MessageStore.updateStatus(msgId, 'sending');

}
```

```javascript
// 转接状态机
const TransferStatus = {
  IDLE: 'idle',
  WAITING: 'waiting',    // 排队中
  CONNECTED: 'connected', // 已接通
  ENDED: 'ended',
};

function useAgentTransfer(sessionId) {
  const [status, setStatus] = useState(TransferStatus.IDLE);
  const [queuePosition, setQueuePosition] = useState(0);

  const requestTransfer = useCallback(async () => {
    setStatus(TransferStatus.WAITING);
    wsClient.send({ type: 'transfer_request', sessionId });
  }, [sessionId]);

  useEffect(() => {
    const unsubscribes = [
      // 排队位置更新
      wsClient.on('queue_update', ({ position }) => {
        setQueuePosition(position);
      }),
      // 人工接入
      wsClient.on('agent_connected', ({ agentInfo }) => {
        setStatus(TransferStatus.CONNECTED);
        // 将 AI 对话历史同步给人工客服
        wsClient.send({ type: 'sync_history', sessionId });
      }),
    ];
    return () => unsubscribes.forEach(fn => fn());
  }, [sessionId]);

  return { status, queuePosition, requestTransfer };
}
```
