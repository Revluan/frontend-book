## 前端构建部署发布 (28题)

1. 什么是构建产物的增量更新？如何实现只更新变化的文件？
**增量更新**是指在应用发布新版本时，只替换（或让客户端下载）那些**内容发生变化的文件**，而不是重新部署或下载整个应用。这能大幅减少更新流量，提升发布效率和用户体验。

### 实现原理
1. **文件名哈希**  
   构建工具（如 Webpack）根据文件内容生成唯一的哈希值（如 `app.8f3d2c.js`）。内容不变，哈希不变；内容变化，哈希改变。

2. **版本清单**  
   构建时生成一个 `asset-manifest.json`（或类似文件），记录原始文件名与带哈希文件名的映射关系。服务器部署时保留历史版本文件，新版本只上传哈希变化的文件。

3. **客户端更新**  
   - 首次访问：加载 HTML，其中引用带哈希的 JS/CSS，所有文件缓存到浏览器。
   - 再次访问：HTML 可能被缓存（或协商缓存），但若新版本发布，HTML 会更新，其中引用的资源哈希发生变化，浏览器自动下载新文件，旧文件继续缓存但不被引用。

### 如何实现只更新变化的文件？
- **构建配置**：Webpack 中设置 `output.filename: '[name].[contenthash].js'`，并使用 `HtmlWebpackPlugin` 自动注入新哈希。
- **部署策略**：将带哈希的静态文件上传到 CDN，覆盖式上传（同名文件覆盖），但由于哈希变了，实际上是新文件。CDN 上会同时存在新旧文件。
- **旧文件清理**：定期清理 CDN 上不再被引用的旧文件，或使用版本化目录（如 `/v1.2.3/`）并在发布时更新软链接。

**优势**：结合 HTTP 强缓存，未变化的文件可直接从缓存加载，仅需下载变化部分，实现高效增量更新。

2. 前端如何实现蓝绿部署？切换策略如何设计？回滚方案是什么？

## 前端蓝绿部署

### 核心思路

同时维护两套完全独立的生产环境，切换时只改流量路由，旧环境保留作为回滚后备。

```
平时：  用户 → Nginx/负载均衡 → 蓝环境（当前线上 v1.1.0）
                                 绿环境（空闲）

发布：  将新版本部署到绿环境并验证
        ↓
切换：  用户 → Nginx → 绿环境（新版本 v1.2.0）
                       蓝环境（保留，随时回滚）
```

---

## 一、Nginx 切换配置

```nginx
# /etc/nginx/conf.d/frontend.conf

upstream blue {
    server blue-frontend:80;
}

upstream green {
    server green-frontend:80;
}

# 当前激活的环境（只需改这一行完成切换）
upstream active {
    server blue-frontend:80;   # ← 改为 green-frontend:80 即切换
}

server {
    listen 80;
    server_name example.com;

    location / {
        proxy_pass http://active;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # 直接访问蓝/绿环境（用于验证，不对外暴露）
    location /internal/blue/ {
        allow 10.0.0.0/8;   # 只允许内网访问
        deny all;
        proxy_pass http://blue/;
    }

    location /internal/green/ {
        allow 10.0.0.0/8;
        deny all;
        proxy_pass http://green/;
    }
}
```

切换只需两步：

```bash
# 修改 active upstream 指向，然后热重载（不中断连接）
sed -i 's/blue-frontend:80/green-frontend:80/' /etc/nginx/conf.d/frontend.conf
nginx -s reload   # 平滑重载，不会断开已有连接
```

## 二、Docker Compose 完整方案

```yaml
# docker-compose.yml
services:
  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/frontend.conf
    depends_on:
      - blue
      - green

  blue:
    image: my-frontend:${BLUE_VERSION:-v1.1.0}
    container_name: blue-frontend

  green:
    image: my-frontend:${GREEN_VERSION:-v1.2.0}
    container_name: green-frontend
```

```bash
# scripts/blue-green-deploy.sh

NEW_VERSION=$1
CURRENT=$(grep -o 'blue\|green' /etc/nginx/conf.d/frontend.conf | head -1)
TARGET=$([ "$CURRENT" = "blue" ] && echo "green" || echo "blue")

echo "当前环境: $CURRENT → 目标环境: $TARGET"

# 1. 更新目标环境镜像
docker compose pull ${TARGET}-frontend
${TARGET^^}_VERSION=$NEW_VERSION docker compose up -d ${TARGET}

# 2. 等待目标环境启动
sleep 5

# 3. 健康检查
HEALTH=$(curl -s -o /dev/null -w "%{http_code}" http://localhost/internal/${TARGET}/)
if [ "$HEALTH" != "200" ]; then
  echo "❌ 健康检查失败（$HEALTH），部署终止"
  exit 1
fi

# 4. 冒烟测试（可扩展）
echo "🔍 运行冒烟测试..."
npm run test:smoke -- --base-url=http://localhost/internal/${TARGET}/

# 5. 切换流量
sed -i "s/${CURRENT}-frontend/${TARGET}-frontend/" /etc/nginx/conf.d/frontend.conf
nginx -s reload

echo "✅ 切换完成！当前线上: $TARGET ($NEW_VERSION)"
echo "⚠️ 旧环境 $CURRENT 保留 30 分钟后释放"
```

## 三、切换策略

### 全量切换（适合大多数场景）

```
验证通过 → nginx reload → 100% 流量切换
耗时：秒级
风险：新版本有问题影响所有用户
```

### 渐进切换（高风险发布）

```nginx
# 先切 10% 流量观察
upstream active {
    server green-frontend:80 weight=1;   # 10%
    server blue-frontend:80  weight=9;   # 90%
}

# 观察 15 分钟无异常，切 50%
upstream active {
    server green-frontend:80 weight=1;
    server blue-frontend:80  weight=1;
}

# 全量切换
upstream active {
    server green-frontend:80;
}
```

### 按用户特征切换

```nginx
# 内部员工先体验新版本（通过 Header 或 Cookie 标识）
map $http_x_employee $upstream {
    "true"  green;
    default blue;
}

server {
    location / {
        proxy_pass http://$upstream;
    }
}
```

## 四、回滚方案

蓝绿部署的回滚极其简单，旧环境从未停止：

```bash
# scripts/rollback.sh
CURRENT=$(grep -o 'blue\|green' /etc/nginx/conf.d/frontend.conf | head -1)
FALLBACK=$([ "$CURRENT" = "blue" ] && echo "green" || echo "blue")

echo "🔄 回滚：$CURRENT → $FALLBACK"

sed -i "s/${CURRENT}-frontend/${FALLBACK}-frontend/" /etc/nginx/conf.d/frontend.conf
nginx -s reload

echo "✅ 回滚完成，耗时 < 10 秒"
```

| 回滚触发方式 | 耗时 |
|---|---|
| 手动执行脚本 | < 10 秒 |
| CI/CD 一键回滚 | < 1 分钟 |
| 监控自动触发 | < 2 分钟 |

---

## 总结

```
蓝绿部署的本质：空间换时间
  旧环境不销毁 → 回滚成本趋近于零
  切换只改路由 → 用户无感知
  新环境先验证 → 风险在切换前消除
```

蓝绿 vs 灰度的选择：流量切换要"快准狠"用蓝绿，要"渐进稳健"用灰度，两者也可以组合——先蓝绿切 10%，观察无误再全量。

3. 什么是金丝雀发布（Canary Release）？如何控制流量比例？监控指标有哪些？

## 金丝雀发布

### 什么是金丝雀发布？

名字来源于矿工用金丝雀探测矿井毒气——金丝雀对毒气敏感，先死则矿工撤退。发布同理：**让一小部分用户先"探路"，无问题再全量推送**。

```
蓝绿部署：全量切换（要么0%，要么100%）
金丝雀：  渐进切换（5% → 20% → 50% → 100%）
```

---

## 一、流量比例控制

### Nginx 权重分流

```nginx
upstream canary_pool {
    server stable-frontend:80 weight=95;  # 旧版本 95%
    server canary-frontend:80 weight=5;   # 新版本 5%
}

server {
    location / {
        proxy_pass http://canary_pool;
    }
}
```

### 基于 Cookie 的精准分流（推荐）

权重分流每次请求随机，同一用户可能切换版本。Cookie 方案保证**同一用户体验一致**：

```nginx
map $cookie_canary $upstream {
    "true"  canary-frontend:80;
    default stable-frontend:80;
}

server {
    location / {
        proxy_pass http://$upstream;

        # 对 5% 用户种下 Cookie，此后固定走金丝雀
        # 由业务服务或 lua 脚本来下发 Cookie
    }
}
```

```ts
// 前端或 BFF 控制金丝雀分配
function assignCanary(userId: string, ratio = 0.05): boolean {
  // 用 userId hash 保证同一用户结果稳定
  const hash = userId.split('').reduce((acc, c) => acc + c.charCodeAt(0), 0)
  const inCanary = (hash % 100) < (ratio * 100)

  if (inCanary) {
    document.cookie = 'canary=true; path=/; max-age=86400'
  }

  return inCanary
}
```

### 按用户特征分流

```nginx
# 内部员工 → 金丝雀（最先体验）
map $http_x_user_group $upstream {
    "internal"  canary-frontend:80;   # 内部员工
    "beta"      canary-frontend:80;   # 公测用户
    default     stable-frontend:80;   # 普通用户
}
```

## 二、发布节奏

```
Day 1：  内部员工（~100人）→ 观察 2 小时
Day 2：  5%  外部用户      → 观察 24 小时
Day 3：  20% 用户          → 观察 12 小时
Day 4：  50% 用户          → 观察 6 小时
Day 5：  100% 全量         → 完成
```

每个阶段未达到回滚阈值才进入下一阶段，自动化系统可替代人工判断。

---

## 三、监控指标

金丝雀发布必须对比新旧版本的关键指标，而不是只看绝对值：

```
核心指标（必须监控）：
  ├── JS 错误率         新版本 JS 报错数 / 请求数
  ├── 接口错误率        4xx / 5xx 比例
  ├── 页面加载时间      FCP、LCP、TTI
  └── 核心业务转化率    下单率、支付成功率等

对比方式：
  金丝雀用户指标  vs  稳定版用户指标
  超过阈值差异   →   自动触发回滚
```

```ts
// 前端上报时携带版本标识，监控平台按版本聚合对比
reporter.send({
  event: 'page_load',
  duration: performance.now(),
  version: __APP_VERSION__,
  isCanary: document.cookie.includes('canary=true'),
})
```

### 自动回滚阈值示例

| 指标 | 金丝雀阈值 | 触发动作 |
|---|---|---|
| JS 错误率 | 比稳定版高 > 2% | 自动回滚 |
| 接口 5xx | 比稳定版高 > 1% | 自动回滚 |
| LCP | 比稳定版慢 > 20% | 告警 + 人工确认 |
| 转化率下降 | > 5% | 自动回滚 |

---

## 总结

```
金丝雀发布 = 小流量探路 + 指标对比 + 自动回滚 + 逐步放量

关键点：
  分流要稳定（同一用户始终在同一版本）
  监控要对比（不是看绝对值，是看与稳定版的差异）
  回滚要自动（人工响应太慢，超阈值立即触发）
```

4. 前端如何实现多环境构建？dev、test、staging、prod环境如何区分配置？

## 前端多环境构建

### 核心方案：环境变量 + 模式文件

主流构建工具（Vite / Webpack / CRA）都基于 **`.env` 文件 + 构建模式** 来区分环境。

---

## 一、Vite 方案（主流）

### 1. 环境文件结构

```bash
.env                  # 所有环境共享的基础变量
.env.development      # dev 环境（vite dev 默认加载）
.env.test             # 测试环境
.env.staging          # 预发环境
.env.production       # 生产环境（vite build 默认加载）
```

### 2. 文件内容示例

```bash
# .env（公共）
VITE_APP_NAME=MyApp
VITE_APP_VERSION=1.0.0

# .env.development
VITE_API_BASE_URL=http://localhost:3000
VITE_ENABLE_MOCK=true
VITE_LOG_LEVEL=debug

# .env.test
VITE_API_BASE_URL=https://test-api.example.com
VITE_ENABLE_MOCK=false
VITE_LOG_LEVEL=info

# .env.staging
VITE_API_BASE_URL=https://staging-api.example.com
VITE_ENABLE_MOCK=false
VITE_LOG_LEVEL=warn

# .env.production
VITE_API_BASE_URL=https://api.example.com
VITE_ENABLE_MOCK=false
VITE_LOG_LEVEL=error
```

> ⚠️ Vite 中只有 `VITE_` 前缀的变量才会暴露给客户端代码，防止敏感信息泄露。

### 3. package.json 脚本配置

```json
{
  "scripts": {
    "dev":           "vite --mode development",
    "build:test":    "vite build --mode test",
    "build:staging": "vite build --mode staging",
    "build:prod":    "vite build --mode production",
    "preview":       "vite preview"
  }
}
```

### 4. 代码中使用环境变量

```ts
// 访问环境变量
const apiBase = import.meta.env.VITE_API_BASE_URL
const isDev = import.meta.env.DEV        // Vite 内置，boolean

  apiBase: import.meta.env.VITE_API_BASE_URL,
  enableMock: import.meta.env.VITE_ENABLE_MOCK === 'true',
  logLevel: import.meta.env.VITE_LOG_LEVEL,
}
```

5. 什么是Docker容器化部署？如何编写前端项目的Dockerfile？多阶段构建如何优化镜像大小？

## Docker 容器化部署

### 什么是容器化部署？

容器化部署是将应用程序及其**运行所需的一切**（代码、依赖、配置、运行时环境）打包成一个标准化的**镜像（Image）**，通过容器引擎运行，实现"一次构建，到处运行"。

```
传统部署：代码 + 服务器环境（手动配置，容易环境不一致）
容器化部署：代码 + 环境 = 镜像（标准化，环境完全一致）
```

**核心优势**：环境一致性、快速扩缩容、隔离性强、便于 CI/CD 集成。

---

## 一、基础 Dockerfile（不推荐用于生产）

先看一个朴素写法，理解问题所在：

```dockerfile
FROM node:18

WORKDIR /app

COPY . .

RUN npm install
RUN npm run build

EXPOSE 80

CMD ["npm", "run", "preview"]
```

**问题**：
- 镜像包含完整 Node.js + 所有 node_modules（体积可达 1GB+）
- 源码、开发依赖全部打进镜像，存在安全隐患
- 构建缓存利用率极低，每次改代码都重装依赖

---

## 二、多阶段构建（Multi-stage Build）✅ 推荐

核心思路：**构建环境和运行环境分离**，最终镜像只保留运行所需的产物。

```dockerfile
# ==================== 阶段一：依赖安装 ====================
FROM node:18-alpine AS deps

WORKDIR /app

# 单独复制 package.json，利用 Docker 层缓存
# 只要依赖没变，这一层就不会重新执行
COPY package.json package-lock.json ./

RUN npm ci --frozen-lockfile


# ==================== 阶段二：构建 ====================
FROM node:18-alpine AS builder

WORKDIR /app

# 从 deps 阶段复制已安装的依赖
COPY --from=deps /app/node_modules ./node_modules
COPY . .

# 注入构建时环境变量
ARG VITE_API_BASE_URL
ENV VITE_API_BASE_URL=$VITE_API_BASE_URL

RUN npm run build


# ==================== 阶段三：运行 ====================
# 只用轻量级 nginx 镜像，不含 Node.js
FROM nginx:1.25-alpine AS runner

# 自定义 nginx 配置（处理 SPA 路由、gzip、缓存等）
COPY nginx.conf /etc/nginx/conf.d/default.conf

# 只复制构建产物，源码和 node_modules 完全不进入最终镜像
COPY --from=builder /app/dist /usr/share/nginx/html

EXPOSE 80

CMD ["nginx", "-g", "daemon off;"]
```

### nginx.conf 配置

```nginx
server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;

    # gzip 压缩
    gzip on;
    gzip_types text/plain text/css application/javascript application/json image/svg+xml;
    gzip_min_length 1024;

    # SPA 路由支持（history 模式必须）
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 静态资源强缓存（文件名带 hash，内容不变则永久缓存）
    location ~* \.(js|css|png|jpg|svg|woff2)$ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # index.html 不缓存
    location = /index.html {
        add_header Cache-Control "no-cache, no-store, must-revalidate";
    }
}
```

## 四、进一步优化技巧

### 1. 利用 .dockerignore 减少构建上下文

Docker 每一层都会缓存，层内容未变则直接复用。关键原则是**变化频率低的层放前面**：

```dockerfile
# ✅ 正确顺序：依赖变化少，源码变化多

RUN npm ci                               # 层2：依赖不变时直接缓存命中
COPY . .                                 # 层3：每次改代码都变，但不影响层2
RUN npm run build                        # 层4：重新构建

# ❌ 错误顺序：每次改代码都导致 npm install 重新执行
COPY . .
RUN npm install
RUN npm run build
```

### 3. 使用 pnpm 加速依赖安装

```dockerfile
FROM node:18-alpine AS deps

RUN npm install -g pnpm

WORKDIR /app
COPY pnpm-lock.yaml package.json ./
RUN pnpm install --frozen-lockfile
```

6. 前端如何实现静态资源的版本管理？文件指纹、版本号、时间戳的选择策略是什么？

## 前端静态资源版本管理

### 为什么需要版本管理？

浏览器和 CDN 会积极缓存静态资源，版本管理要解决的核心矛盾是：

```
缓存时间越长 → 性能越好，但更新越难感知
缓存时间越短 → 更新及时，但性能越差
```

版本管理的目标是：**让不变的资源永久缓存，让变化的资源立刻更新**。

---

## 一、三种方案对比

### 1. 时间戳（Timestamp）

在资源 URL 后拼接当前构建时间：

```html
<script src="/app.js?t=1709712000000"></script>
<link rel="stylesheet" href="/app.css?t=1709712000000">
```

```js
// webpack 简单实现
const timestamp = Date.now()
output: {
  filename: `[name].js?v=${timestamp}`
}
```

**缺点非常明显**：每次构建时间戳都变，即使文件内容完全没变，缓存也会全部失效，等于没有缓存。只适合临时调试，**不推荐生产使用**。

---

### 2. 版本号（Version）

在资源 URL 中加入语义化版本号，通常与 `package.json` 中的 version 字段联动：

```html
<script src="/v1.2.3/app.js"></script>
<!-- 或 query 形式 -->
<script src="/app.js?v=1.2.3"></script>
```

```js
// vite.config.js
import { version } from './package.json'

export default {
  base: `/${version}/`,
  build: {
    outDir: `dist/${version}`
  }
}
```

**适用场景**：整包发布、需要回滚到历史版本、Native App 内嵌 H5（版本号与 App 版本对应）。

**缺点**：粒度太粗，版本号升级会导致所有资源缓存失效，即使大部分文件没有变化。

---

### 3. 文件指纹 / contenthash（推荐）

根据文件**内容**计算 hash，内容不变则 hash 不变，内容变了 hash 才变：

```html
<!-- 构建后文件名包含 hash -->
<script src="/assets/app.8f3d2c1a.js"></script>
<link rel="stylesheet" href="/assets/app.3e7b9f2d.css">
```

```js
// vite.config.js
export default {
  build: {
    rollupOptions: {
      output: {
        // JS 入口文件
        entryFileNames: 'js/[name].[hash].js',
        // 异步分割的 chunk
        chunkFileNames: 'js/[chunk].[hash].js',
        // CSS、图片等静态资源
        assetFileNames: 'assets/[name].[hash][extname]',
      }
    }
  }
}
```

```js
// webpack.config.js
output: {
  filename: '[name].[contenthash:8].js',      // 入口
  chunkFilename: '[name].[contenthash:8].js', // 异步 chunk
}
```

> contenthash 和 chunkhash 的区别：`contenthash` 只跟单个文件内容相关，`chunkhash` 跟整个 chunk 相关。CSS 应使用 `contenthash`，避免 JS 变化带着 CSS 缓存一起失效。

---

## 二、三种方案对比总结

| | 时间戳 | 版本号 | 文件指纹 |
|---|---|---|---|
| 缓存粒度 | 全量失效 | 全量失效 | 按文件精确控制 |
| 未修改文件 | 缓存失效 ❌ | 缓存失效 ❌ | 缓存命中 ✅ |
| 回滚能力 | 无 | 支持 | 支持（hash 唯一） |
| CDN 友好 | 否 | 一般 | 最佳 |
| 实现复杂度 | 最低 | 低 | 中（构建工具支持） |
| 推荐场景 | 临时调试 | 整包/App 内嵌 | **Web 生产首选** |

---

## 三、最佳缓存策略配置

文件指纹配合 HTTP 缓存头，才能发挥最大效果：

```nginx
# nginx.conf

# index.html — 不缓存，每次都请求最新版
location = /index.html {
    add_header Cache-Control "no-cache, no-store, must-revalidate";
}

# 带 hash 的 JS/CSS — 永久缓存，内容不变则永不过期
location ~* \.(js|css)$ {
    add_header Cache-Control "max-age=31536000, immutable";
}

# 带 hash 的图片/字体
location ~* \.(png|jpg|webp|svg|woff2)$ {
    add_header Cache-Control "max-age=31536000, immutable";
}
```

**为什么 index.html 不能缓存？** 它是资源入口，引用了带 hash 的 JS/CSS 路径，必须每次获取最新版，才能让用户拿到最新的资源引用。

## 四、hash 粒度优化 — 避免缓存被动失效

一个常见的坑：改了业务代码，却导致第三方库的 hash 也变了。

```js
// vite.config.js — 按粒度拆分 chunk
build: {
  rollupOptions: {
    output: {
      manualChunks: {
        // 第三方库单独打包，几乎不变，可长期缓存
        vendor: ['vue', 'vue-router', 'pinia'],
        utils:  ['lodash-es', 'dayjs', 'axios'],
      }
    }
  }
}
```

```
不拆分：                        拆分后：
app.abc123.js (500KB)          vendor.111aaa.js (300KB) ← 不变，永久缓存
  ├── vue                       utils.222bbb.js  (80KB)  ← 不变，永久缓存
  ├── axios                     app.333ccc.js    (120KB) ← 只有业务代码变
  └── 业务代码                  
  
改了一行业务代码 →              改了一行业务代码 →
整个 500KB 缓存失效 ❌          只有 120KB 缓存失效 ✅
```

## 五、完整的版本管理方案

综合来看，生产环境推荐的完整策略是：

```
构建阶段：文件指纹（contenthash）
    ↓
缓存策略：index.html no-cache，其余 max-age=1年 + immutable
    ↓
Chunk 拆分：vendor / utils / 业务代码 分层管理
    ↓
发布流程：先上传新资源 → 再更新 index.html（灰度/CDN）
    ↓
应急手段：CDN 刷新指定路径，或 index.html 追加版本号参数
```

对于需要多版本共存的场景（如 App 内嵌 H5），可以**文件指纹 + 版本号目录结合**使用：

```
/h5/v2.3.0/assets/app.8f3d2c1a.js   ← 精确到文件级别的缓存控制
/h5/v2.3.0/assets/app.3e7b9f2d.css  ← 版本目录支持回滚
```

8. 前端如何实现CDN部署？CDN刷新和预热的区别是什么？
### 核心思路

前端 CDN 部署的核心是将**静态资源**（JS、CSS、图片、字体等）托管到 CDN 节点，利用就近访问加速用户请求。

### 实施步骤

**1. 资源构建 — Hash 指纹**

构建工具（Webpack/Vite）对静态资源文件名加 contenthash，实现强缓存 + 按需更新：

```js
// vite.config.js
build: {
  rollupOptions: {
    output: {
      entryFileNames: 'js/[name].[hash].js',
      chunkFileNames: 'js/[chunk].[hash].js',
      assetFileNames: 'assets/[name].[hash][extname]'
    }
  }
}
```

**2. 配置 CDN 域名**

将静态资源的 base 路径指向 CDN 域名：

```js
// vite.config.js
base: 'https://cdn.example.com/project/'
```

**3. 上传资源到 CDN**

CI/CD 流水线中将构建产物上传到 OSS/S3 等对象存储，并绑定 CDN 加速域名：

```bash
# 示例：上传到阿里云 OSS
ossutil cp -r ./dist oss://bucket/project/ --update
```

**4. HTML 单独部署**

`index.html` 不上传 CDN，而是部署到服务器并设置 `no-cache`，确保每次都能拿到最新的资源引用（带 hash 的 JS/CSS）。

**5. 设置缓存策略**

| 资源类型 | Cache-Control |
|---|---|
| index.html | `no-cache` |
| JS/CSS（有 hash） | `max-age=31536000, immutable` |
| 图片/字体（有 hash）| `max-age=31536000, immutable` |

---

## CDN 刷新 vs 预热

### CDN 刷新（Purge / 缓存清除）

**定义**：主动删除 CDN 节点上已缓存的旧资源，使节点在下次请求时回源拉取最新内容。

**使用场景**：
- 线上出现 bug，紧急发布了新版本但文件名未变
- 图片/配置文件更新后需要立刻生效
- 发布后发现用户仍访问旧资源

**流程**：
```
CDN 节点存有旧缓存
    ↓ 触发刷新
缓存标记为失效（删除）
    ↓ 用户请求到来
CDN 回源服务器拉取新资源
    ↓
缓存新资源并响应用户
```

---

### CDN 预热（Prefetch / 缓存预加载）

**定义**：在用户请求之前，提前主动将资源从源站推送并缓存到 CDN 各节点。

**使用场景**：
- 大促活动（双11、618）前，提前预热商品图片、活动页资源
- 新版本发布后，避免大量用户同时回源导致源站压力骤增
- 热门资源全球分发，降低首次访问延迟

**流程**：
```
触发预热任务
    ↓
CDN 主动回源拉取资源
    ↓
资源提前缓存到各节点
    ↓ 用户请求到来
直接命中缓存，无需回源
```

---

### 对比总结

| | CDN 刷新 | CDN 预热 |
|---|---|---|
| **方向** | 删除旧缓存 | 提前填充缓存 |
| **时机** | 资源更新后 | 资源上线前 |
| **目的** | 保证内容最新 | 保证首次命中率 |
| **对源站影响** | 刷新后首次请求会回源 | 预热时主动回源（集中一次） |
| **典型场景** | 热修复、紧急更新 | 大促活动、版本预发布 |

> 💡 **最佳实践**：新版本发布流程 = **上传新资源** → **刷新旧缓存** → **预热新资源** → **更新 HTML**，可以做到无缝切换且用户无感知。

9. 什么是Nginx的反向代理？如何配置前端项目的Nginx？gzip压缩如何开启？

## Nginx 反向代理 & 前端配置

### 什么是反向代理？

```
正向代理：客户端 → 代理 → 服务器   （代理的是客户端，如 VPN）
反向代理：客户端 → 代理 → 服务器   （代理的是服务器，如 Nginx）
```

区别在于：反向代理对客户端透明，用户不知道背后有多少台服务器，Nginx 负责转发、负载均衡、SSL 终止等。

---

### 前端项目完整 Nginx 配置

```nginx
server {
    listen 80;
    server_name example.com;
    
    # 重定向到 HTTPS
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name example.com;

    ssl_certificate     /etc/ssl/cert.pem;
    ssl_certificate_key /etc/ssl/key.pem;

    root /usr/share/nginx/html;
    index index.html;

    # ==================== gzip 压缩 ====================
    gzip on;
    gzip_min_length 1024;        # 小于 1KB 不压缩
    gzip_comp_level 6;           # 压缩级别 1-9，6 是性能与压缩率的平衡点
    gzip_vary on;                # 响应头加 Vary: Accept-Encoding
    gzip_types
        text/plain
        text/css
        application/javascript
        application/json
        image/svg+xml
        application/xml;

    # ==================== SPA 路由 ====================
    location / {
        try_files $uri $uri/ /index.html;
    }

    # ==================== 缓存策略 ====================
    # index.html 不缓存
    location = /index.html {
        add_header Cache-Control "no-cache, no-store, must-revalidate";
    }

    # 带 hash 的静态资源永久缓存
    location ~* \.(js|css|png|webp|woff2)$ {
        add_header Cache-Control "max-age=31536000, immutable";
    }

    # ==================== 反向代理 API ====================
    location /api/ {
        proxy_pass http://backend:3000/;   # 转发到后端服务
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        
        # 超时配置
        proxy_connect_timeout 10s;
        proxy_read_timeout 30s;
    }
}
```

---

### gzip 效果

| 资源类型 | 原始大小 | gzip 后 | 压缩率 |
|---|---|---|---|
| JS | 500KB | ~150KB | 70% |
| CSS | 80KB | ~20KB | 75% |
| JSON | 100KB | ~15KB | 85% |
| 图片/二进制 | — | 几乎不变 | 不适合压缩 |

> 💡 比 gzip 更进一步：开启 **Brotli**（`brotli on`），同等质量下体积再小 15~20%，需要 Nginx 安装 `ngx_brotli` 模块。

12. 前端如何实现零停机部署？如何保证用户访问不中断？

## 前端零停机部署

### 核心思路

停机的根本原因是**新旧版本之间存在空窗期**，用户请求到达时服务不可用。零停机的关键是让新旧版本**同时存在**，流量平滑切换。

---

## 一、静态资源：天然零停机

前端使用文件指纹（contenthash）后，静态资源本身就是零停机的：

```
发布前：
  /assets/app.aaa111.js  ← 旧版本，CDN 有缓存

发布中（上传新资源）：
  /assets/app.aaa111.js  ← 旧版本，仍然存在
  /assets/app.bbb222.js  ← 新版本，已上传

更新 index.html：
  引用从 app.aaa111.js → app.bbb222.js

结果：
  正在访问的用户 → 继续用 aaa111（旧资源仍在 CDN）
  新进入的用户   → 拿到 bbb222（新资源）
```

**发布顺序至关重要**：必须先上传新资源，再更新 index.html，绝不能反过来。

```bash
# CI/CD 正确发布顺序
# 第一步：上传所有带 hash 的静态资源（JS/CSS/图片）
ossutil cp -r ./dist/assets oss://bucket/assets/ --update

# 第二步：等待 CDN 同步（可加短暂 sleep）
sleep 5

# 第三步：最后更新 index.html（此刻新版本才对用户可见）
ossutil cp ./dist/index.html oss://bucket/index.html --force

# 第四步：只刷新 index.html 的 CDN 缓存
aliyun cdn RefreshObjectCaches --ObjectPath "https://cdn.example.com/index.html"
```

---

## 二、灰度发布 / 金丝雀发布

不直接全量切换，而是先让一小部分用户访问新版本，观察无误后再逐步放量：

```
发布初期：  5% 用户 → 新版本   95% 用户 → 旧版本
观察 30min：20% 用户 → 新版本  80% 用户 → 旧版本
稳定后：    100% 用户 → 新版本
```

### Nginx 按比例分流

```nginx
upstream frontend_stable {
    server old-frontend:80;
}

upstream frontend_canary {
    server new-frontend:80;
}

# 按权重分流：5% 流量给新版本
split_clients "${remote_addr}${uri}" $variant {
    5%    canary;
    *     stable;
}

server {
    location / {
        if ($variant = "canary") {
            proxy_pass http://frontend_canary;
        }
        proxy_pass http://frontend_stable;
    }
}
```

### 基于 Cookie 的精确灰度

```nginx
# 通过 Cookie 标记灰度用户，保证同一用户体验一致
map $cookie_canary_user $upstream {
    "true"  "http://new-frontend:80";
    default "http://old-frontend:80";
}

server {
    location / {
        proxy_pass $upstream;
    }
}
```

```ts
// 前端：命中灰度的用户打上 Cookie 标记
// 后端下发灰度名单，或前端按比例随机分配
function assignCanary(ratio = 0.05): void {
  if (Math.random() < ratio) {
    document.cookie = 'canary_user=true; path=/; max-age=86400'
    location.reload()
  }
}
```

## 三、蓝绿部署

同时维护两套完全独立的生产环境（蓝/绿），切换时只改路由指向：

```
平时：
  用户流量 → 负载均衡 → 蓝环境（当前线上）
                        绿环境（空闲备用）

发布时：
  1. 将新版本部署到绿环境
  2. 在绿环境做完整验证
  3. 负载均衡切换：流量 → 绿环境（秒级切换）
  4. 蓝环境保留一段时间，出问题立刻切回

切换完成：
  用户流量 → 负载均衡 → 绿环境（新版本）
                        蓝环境（随时可回滚）
```

```ts
// src/utils/versionChecker.ts
class VersionChecker {
  private currentVersion: string = __APP_VERSION__  // 构建时注入
  private timer: ReturnType<typeof setInterval> | null = null

  start(intervalMs = 5 * 60 * 1000) {  // 每 5 分钟检查一次
    this.timer = setInterval(() => this.check(), intervalMs)

      // 请求 index.html，从 etag 或自定义 header 判断版本
      const res = await fetch('/version.json?t=' + Date.now(), {
        cache: 'no-store'

        this.notify()

      // 网络异常静默处理，不影响用户
    }

    showToast({
      message: '✨ 新版本已就绪，刷新后生效',
      action: { text: '立即刷新', onClick: () => location.reload() },
      duration: 0,  // 不自动消失，等用户主动操作
    })
  }
  
  stop() {
    if (this.timer) clearInterval(this.timer)
  }
}

export const versionChecker = new VersionChecker()
```

## 五、旧资源保留策略

零停机的隐患：旧版本用户仍在使用旧 hash 的资源，如果发布时删除了旧资源会导致 404。

```bash
# 错误做法：发布时清空 CDN 目录再上传
ossutil rm -r oss://bucket/assets/ --force  # ❌ 旧用户请求 404

# 正确做法：只上传新文件，保留旧文件
ossutil cp -r ./dist/assets oss://bucket/assets/ --update  # ✅ 增量上传

# 定期清理：保留最近 N 个版本的资源
# 可用脚本对比最近3个版本的 hash 清单，删除不在任何版本中的文件
```

## 一、静态资源回滚

### 多版本并存是回滚的基础

```
CDN 存储结构：
  /frontend/
    ├── v1.1.0/
    │     ├── index.html
    │     └── assets/app.aaa111.js
    ├── v1.2.0/
    │     ├── index.html
    │     └── assets/app.bbb222.js
    └── current → 指向当前版本（软链接/配置）
```

回滚本质上只是**把 current 指向改回旧版本**，旧资源从未删除，所以可以秒级生效。

### 回滚脚本

```bash
#!/bin/bash
# scripts/rollback.sh

TARGET_VERSION=$1
BUCKET="oss://prod-bucket/frontend"
CDN_DOMAIN="https://cdn.example.com"

if [ -z "$TARGET_VERSION" ]; then
  echo "❌ 请指定回滚版本，例如：./rollback.sh v1.1.0"
  exit 1
fi

# 检查目标版本是否存在
VERSION_EXISTS=$(ossutil ls $BUCKET/$TARGET_VERSION/ 2>&1)
if [[ $VERSION_EXISTS == *"No"* ]]; then
  echo "❌ 版本 $TARGET_VERSION 不存在"
  exit 1
fi

echo "🔄 开始回滚到 $TARGET_VERSION..."

# 将目标版本的 index.html 覆盖到根路径
ossutil cp \
  $BUCKET/$TARGET_VERSION/index.html \
  $BUCKET/index.html \
  --force

# 只刷新 index.html 的 CDN 缓存（静态资源有 hash，无需刷新）
aliyun cdn RefreshObjectCaches \
  --ObjectPath "$CDN_DOMAIN/index.html" \
  --ObjectType File

# 记录回滚日志
echo "$(date): rollback to $TARGET_VERSION by $USER" >> ./deploy.log

echo "✅ 回滚完成！当前版本：$TARGET_VERSION"
echo "📊 请监控错误率是否下降..."
```

## 二、回滚策略设计

### 版本保留策略

```
不能无限保留历史版本（存储成本），但保留太少又无法回滚

推荐策略：
  ├── 最近 5 个版本  → 完整保留（随时可回滚）
  ├── 更早的版本     → 只保留 index.html（资源可重新构建）
  └── 90天以前       → 完全清理
```

```bash
# scripts/cleanup-old-versions.sh
# 保留最近 N 个版本，清理更早的

KEEP_VERSIONS=5
BUCKET="oss://prod-bucket/frontend"

# 获取所有版本，按时间排序
ALL_VERSIONS=$(ossutil ls $BUCKET/ --limited-num 100 | grep "v[0-9]" | sort -r)

# 跳过前 N 个，删除其余
echo "$ALL_VERSIONS" | tail -n +$((KEEP_VERSIONS + 1)) | while read version; do
  echo "🗑️ 清理旧版本：$version"
  ossutil rm -r "$version" --force
done
```

### 自动回滚触发条件

```ts
// 监控系统：错误率超阈值自动触发回滚
// monitor/autoRollback.ts

const ROLLBACK_RULES = {
  errorRate: {
    threshold: 0.05,      // 错误率 > 5% 触发
    windowMs: 5 * 60000,  // 5 分钟窗口
  },
  p99Latency: {
    threshold: 3000,      // P99 响应时间 > 3s 触发
    windowMs: 3 * 60000,
  },
  jsErrorCount: {
    threshold: 100,       // 5 分钟内 JS 报错 > 100 次触发
    windowMs: 5 * 60000,
  }
}

async function checkAndRollback(currentVersion: string, prevVersion: string) {
  const metrics = await fetchMetrics(ROLLBACK_RULES.errorRate.windowMs)

  const shouldRollback =
    metrics.errorRate > ROLLBACK_RULES.errorRate.threshold ||
    metrics.p99 > ROLLBACK_RULES.p99Latency.threshold ||
    metrics.jsErrors > ROLLBACK_RULES.jsErrorCount.threshold

  if (shouldRollback) {
    console.error('🚨 指标异常，触发自动回滚', metrics)

    // 调用回滚 API
    await triggerRollback(prevVersion)

    // 告警通知
    await notify(`自动回滚至 ${prevVersion}，原因：错误率 ${metrics.errorRate}`)
  }
}
```

## 三、数据兼容性处理（最复杂的部分）

回滚最大的风险不在代码，而在**数据结构变了之后代码回滚，旧代码读不懂新数据**。

### localStorage 数据迁移

```ts
// src/storage/migrations.ts

type Migration = {
  version: number
  up: (data: any) => any    // 升级
  down: (data: any) => any  // 降级（支持回滚）
}

const migrations: Migration[] = [
  {
    version: 2,
    // v1 → v2：userInfo 从扁平结构改为嵌套结构
    up: (data) => ({
      ...data,
      userInfo: {
        basic: { name: data.userName, email: data.userEmail },
        settings: { theme: data.theme ?? 'light' }
      },
      // 清除旧字段
      userName: undefined,
      userEmail: undefined,
      theme: undefined,
    }),
    // v2 → v1：展开嵌套结构（支持回滚）
    down: (data) => ({
      ...data,
      userName: data.userInfo?.basic?.name,
      userEmail: data.userInfo?.basic?.email,
      theme: data.userInfo?.settings?.theme ?? 'light',
      userInfo: undefined,
    }),
  },
  {
    version: 3,
    // v2 → v3：购物车数据结构变更
    up: (data) => ({
      ...data,
      cart: (data.cart ?? []).map((item: any) => ({
        ...item,
        addedAt: item.addedAt ?? Date.now(),  // 新增字段给默认值
      }))
    }),
    down: (data) => ({
      ...data,
      cart: (data.cart ?? []).map(({ addedAt, ...rest }: any) => rest)
    }),
  }
]

class StorageMigrationManager {
  private STORAGE_KEY = 'app_data'
  private VERSION_KEY = 'app_data_version'
  private CURRENT_VERSION = 3  // 当前版本

  // 应用启动时执行迁移
  migrate() {
    const storedVersion = Number(localStorage.getItem(this.VERSION_KEY) ?? 1)
    const data = JSON.parse(localStorage.getItem(this.STORAGE_KEY) ?? '{}')

    if (storedVersion === this.CURRENT_VERSION) return

    let migratedData = data

    if (storedVersion < this.CURRENT_VERSION) {
      // 升级：依次执行 up
      const pendingMigrations = migrations.filter(
        m => m.version > storedVersion && m.version <= this.CURRENT_VERSION
      )
      migratedData = pendingMigrations.reduce((d, m) => m.up(d), data)

    } else {
      // 降级（回滚场景）：依次逆序执行 down
      const pendingMigrations = migrations
        .filter(m => m.version > this.CURRENT_VERSION && m.version <= storedVersion)
        .reverse()
      migratedData = pendingMigrations.reduce((d, m) => m.down(d), data)
    }

    localStorage.setItem(this.STORAGE_KEY, JSON.stringify(migratedData))
    localStorage.setItem(this.VERSION_KEY, String(this.CURRENT_VERSION))
  }
}

// main.ts — 应用启动时第一步执行
new StorageMigrationManager().migrate()
```

```ts
// src/auth/tokenAdapter.ts
// 新版 Token 格式变更时，兼容旧格式解析

interface TokenV1 { uid: string; exp: number }
interface TokenV2 { userId: string; expiredAt: number; roles: string[] }

function parseToken(token: string): TokenV2 {
  const payload = JSON.parse(atob(token.split('.')[1]))

  // 判断是 v1 还是 v2 格式，统一转换为 v2
  if (payload.uid !== undefined) {
    // 旧格式，适配为新格式
    return {
      userId: payload.uid,
      expiredAt: payload.exp,
      roles: [],  // 旧版无此字段，给默认值
    }
  }

  return payload as TokenV2
}
```

## 静态资源跨域配置

### 什么是跨域？

浏览器的**同源策略**限制：协议、域名、端口三者任一不同，就是跨域，请求会被浏览器拦截。

```
https://app.example.com  →  https://api.example.com   ❌ 域名不同
https://example.com      →  http://example.com         ❌ 协议不同
https://example.com:80   →  https://example.com:443    ❌ 端口不同
https://example.com      →  https://example.com        ✅ 同源
```

> 注意：跨域拦截发生在**浏览器端**，请求实际上已经到达服务器，只是响应被浏览器拦截了。服务器通过响应头告诉浏览器"我允许你访问"。

---

### Nginx CORS 配置

```nginx
server {
    listen 443 ssl http2;
    server_name api.example.com;

    # ==================== CORS 配置 ====================

    # 处理预检请求（OPTIONS）
    # 浏览器在发送非简单请求前，先发 OPTIONS 探路
    location / {
        # 允许的来源（生产环境不要用 * ，明确指定域名）
        add_header Access-Control-Allow-Origin  "https://app.example.com" always;

        # 允许携带 Cookie / Authorization（使用此项时 Allow-Origin 不能为 *）
        add_header Access-Control-Allow-Credentials "true" always;

        # 允许的请求方法
        add_header Access-Control-Allow-Methods "GET, POST, PUT, DELETE, OPTIONS" always;

        # 允许的请求头
        add_header Access-Control-Allow-Headers "Authorization, Content-Type, X-Request-ID" always;

        # 预检结果缓存时间（秒），缓存期内不再发 OPTIONS
        add_header Access-Control-Max-Age "86400" always;

        # 允许前端读取的响应头（默认只能读到基础头）
        add_header Access-Control-Expose-Headers "X-Total-Count, X-Request-ID" always;

        # 拦截 OPTIONS 预检请求，直接返回 204，不走业务逻辑
        if ($request_method = OPTIONS) {
            return 204;
        }

        proxy_pass http://backend:3000;
    }
}
```

### 多域名动态 Allow-Origin

`Access-Control-Allow-Origin` 只能设置一个值，多域名需要动态匹配：

```nginx
# 维护允许的域名白名单
map $http_origin $cors_origin {
    default                          "";
    "https://app.example.com"        $http_origin;
    "https://admin.example.com"      $http_origin;
    "https://m.example.com"          $http_origin;
    # 本地开发环境
    "http://localhost:3000"          $http_origin;
    "http://localhost:5173"          $http_origin;
}

server {
    location /api/ {
        add_header Access-Control-Allow-Origin  $cors_origin always;
        add_header Access-Control-Allow-Credentials "true" always;

        if ($request_method = OPTIONS) {
            add_header Access-Control-Allow-Methods "GET, POST, PUT, DELETE, OPTIONS";
            add_header Access-Control-Allow-Headers "Authorization, Content-Type";
            add_header Access-Control-Max-Age "86400";
            return 204;
        }

        proxy_pass http://backend:3000/;
    }
}
```

### 简单请求 vs 预检请求

```
简单请求（直接发送，无 OPTIONS）：
  方法：GET / POST / HEAD
  请求头：只含 Content-Type: text/plain | form-data | urlencoded

预检请求（先发 OPTIONS）：
  方法：PUT / DELETE / PATCH
  请求头：含 Authorization / Content-Type: application/json / 自定义头
  → 浏览器先问服务器"我能不能发？"，服务器回答后再发真实请求
```

### 常见错误排查

| 错误信息 | 原因 | 解决 |
|---|---|---|
| `No 'Access-Control-Allow-Origin'` | 服务器没有返回 CORS 头 | 检查 Nginx 配置是否生效 |
| `Allow-Origin` 不能为 `*` 同时带 `Credentials` | 规范限制 | 明确指定域名，不用 `*` |
| 预检请求 404 | OPTIONS 没有对应路由 | 添加 OPTIONS 处理，返回 204 |
| 响应头读不到 | 头没有在 `Expose-Headers` 声明 | 补充 `Access-Control-Expose-Headers` |
| `always` 缺失 | 错误响应（4xx/5xx）不带 CORS 头 | 所有 `add_header` 加上 `always` |

## 构建预检查 & Git Hooks

### 什么是预检查？

预检查是在代码**提交或推送之前**自动运行的校验流程，在问题进入代码库之前就拦截，而不是等到 CI/CD 才发现。

```
没有预检查：
  写代码 → commit → push → CI 跑 10 分钟 → 发现 lint 错误 → 返工

有预检查：
  写代码 → commit → 本地 1 秒检查 → 发现错误 → 立即修复
```

## 五、pre-push 钩子

推送前运行更重的检查（单测、构建验证）：

```bash
if [ "$BRANCH" = "main" ] || [ "$BRANCH" = "develop" ]; then
  echo "🧪 运行单元测试..."
  npm run test:unit -- --run  # vitest 单次运行（非 watch 模式）

    echo "❌ 单元测试失败，push 已阻止"
    exit 1
  fi
fi

npx tsc --noEmit

if [ $? -ne 0 ]; then
  echo "❌ 类型检查失败，push 已阻止"
  exit 1
fi

echo "✅ 所有检查通过，允许 push"
```

24. 前端如何实现多地域部署？如何保证全球用户的访问速度？

## 前端多地域部署

### 核心问题

物理距离导致网络延迟，用户离服务器越远，访问越慢：

```
北京用户 → 北京节点：  ~5ms
北京用户 → 美国节点：  ~180ms
北京用户 → 欧洲节点：  ~250ms
```

多地域部署的目标是：**让每个用户都从距离最近的节点获取资源**。

---

## 一、整体架构

```
用户请求
    │
    ▼
DNS 智能解析（GeoDNS）
    │ 根据用户 IP 判断地域
    ├── 亚太用户  → 新加坡/香港节点
    ├── 欧洲用户  → 法兰克福节点
    ├── 北美用户  → 弗吉尼亚节点
    └── 南美用户  → 圣保罗节点
         │
         ▼
    CDN 边缘节点（静态资源）
         │ 未命中则回源
         ▼
    各地域源站（动态接口）
         │
         ▼
    全球数据库同步层
```

---

## 二、静态资源：全球 CDN 分发

前端静态资源（HTML/JS/CSS/图片）通过 CDN 天然实现多地域加速，这是最核心也最简单的一步。

### 主流 CDN 选型

| CDN 服务 | 适合场景 | 节点覆盖 |
|---|---|---|
| Cloudflare | 全球（尤其欧美） | 300+ 城市 |
| AWS CloudFront | 配合 AWS 生态 | 全球 |
| 阿里云 CDN | 中国大陆为主 | 全球 |
| 腾讯云 CDN | 中国大陆为主 | 全球 |
| Fastly | 欧美高性能场景 | 全球 |

### 国内外 CDN 分离策略

对于同时面向国内和海外用户的产品，单一 CDN 往往无法兼顾，常见做法是双 CDN：

```
                    DNS 智能解析
                         │
              ┌──────────┴──────────┐
         中国大陆用户           海外用户
              │                    │
        阿里云/腾讯云 CDN      Cloudflare CDN
        （ICP 备案，合规）      （全球节点优化）
              │                    │
              └──────────┬─────────┘
                     同一个源站
                  （或各地域源站）
```

### CDN 配置要点

```nginx
# 响应头配置 — 让 CDN 节点正确缓存
location ~* \.(js|css|woff2|png|webp)$ {
    # 带 hash 的资源，永久缓存
    add_header Cache-Control "public, max-age=31536000, immutable";
    
    # 允许 CDN 缓存（Cloudflare 等会读取此头）
    add_header Vary "Accept-Encoding";
    
    # 开启 gzip/br 压缩
    gzip on;
    gzip_types text/css application/javascript image/svg+xml;
    brotli on;  # Brotli 压缩比 gzip 更高
}

location = /index.html {
    # HTML 不缓存，保证用户总能拿到最新版
    add_header Cache-Control "no-cache, no-store, must-revalidate";
    
    # 不让 CDN 缓存 HTML
    add_header CDN-Cache-Control "no-store";
}
```

## 三、智能 DNS 调度

CDN 背后的流量调度依赖 DNS 层的地域识别，自建源站时也需要配置 GeoDNS：

```
# Route53 / Cloudflare 地理路由示例（伪配置）

api.example.com
  ├── 记录1: 39.x.x.x  → 生效地区: CN（中国）
  ├── 记录2: 52.x.x.x  → 生效地区: US（北美）
  ├── 记录3: 18.x.x.x  → 生效地区: EU（欧洲）
  └── 记录4: 13.x.x.x  → 默认（其他地区）
```

### DNS 层的健康检查与故障转移

```yaml
# AWS Route53 健康检查配置（示意）
HealthCheck:
  Type: HTTPS
  FullyQualifiedDomainName: ap-api.example.com
  Port: 443
  RequestInterval: 30      # 每 30s 检查一次
  FailureThreshold: 3      # 连续 3 次失败则标记不健康

  Primary:   ap-api.example.com   # 亚太主节点
  Secondary: us-api.example.com   # 故障时自动切换到北美
```

## 四、多地域源站部署

静态资源靠 CDN 解决了，动态 API 接口同样需要就近部署：

### 部署结构

```
Region: ap-southeast-1（新加坡）    ← 亚太主节点
  ├── Nginx / API Gateway
  ├── Node.js / Java 应用服务
  ├── Redis 缓存
  └── RDS（主库）
         │ 数据同步
         ▼
Region: eu-central-1（法兰克福）    ← 欧洲节点
  ├── Nginx / API Gateway
  ├── Node.js / Java 应用服务
  ├── Redis 缓存
  └── RDS（从库 / 只读）
         │
         ▼
Region: us-east-1（弗吉尼亚）      ← 北美节点
  ├── ...
  └── RDS（从库 / 只读）
```

### 前端接口请求就近路由

```ts
// src/utils/apiRouter.ts
// 前端根据用户时区或 IP 归属，选择最近的 API 节点

const REGION_ENDPOINTS = {
  'Asia/Shanghai':    'https://ap-api.example.com',
  'Asia/Tokyo':       'https://ap-api.example.com',
  'Asia/Singapore':   'https://ap-api.example.com',
  'America/New_York': 'https://us-api.example.com',
  'America/Chicago':  'https://us-api.example.com',
  'Europe/Berlin':    'https://eu-api.example.com',
  'Europe/London':    'https://eu-api.example.com',
} as const

function getNearestEndpoint(): string {
  const timezone = Intl.DateTimeFormat().resolvedOptions().timeZone

  for (const [tz, endpoint] of Object.entries(REGION_ENDPOINTS)) {
    if (timezone.startsWith(tz.split('/')[0])) {
      return endpoint
    }
  }

  // 兜底：默认节点
  return 'https://api.example.com'
}

export const API_BASE = getNearestEndpoint()
```

> 更可靠的方案是在 DNS/网关层做调度，前端时区判断只作为辅助兜底。

## 五、性能优化补充手段

多地域部署解决的是物理距离问题，以下手段进一步压榨性能：

### HTTP/2 + QUIC（HTTP/3）

```nginx
server {
    listen 443 ssl http2;   # HTTP/2 多路复用，减少连接开销
    listen 443 quic;        # HTTP/3 基于 UDP，弱网环境提升明显

    ssl_certificate     /etc/ssl/cert.pem;
    ssl_certificate_key /etc/ssl/key.pem;

    # 开启 0-RTT，复用会话加速握手
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 1d;
}
```

### 资源预加载 + 预连接

```html
<!-- 提前与 CDN/API 域名建立连接，消除 DNS + TCP 握手耗时 -->
<link rel="preconnect" href="https://cdn.example.com" crossorigin>
<link rel="preconnect" href="https://ap-api.example.com">
<link rel="dns-prefetch" href="https://cdn.example.com">

<!-- 预加载关键资源 -->
<link rel="preload" href="/assets/app.abc123.js" as="script">
<link rel="preload" href="/assets/app.3e7css.css" as="style">
```

### 图片自适应 — 按地区/网速分发不同规格

```ts
// 根据网络状况动态选择图片质量
function getImageUrl(path: string): string {
  const connection = (navigator as any).connection
  const effectiveType = connection?.effectiveType ?? '4g'

  const qualityMap: Record<string, string> = {
    'slow-2g': '?q=30&w=400',
    '2g':      '?q=50&w=600',
    '3g':      '?q=70&w=800',
    '4g':      '?q=85&w=1200',
  }

  const params = qualityMap[effectiveType] ?? '?q=85&w=1200'
  return `https://cdn.example.com${path}${params}`
}
```

### Service Worker 离线缓存

```ts
// sw.ts — 缓存关键资源到本地，弱网/断网也能访问
import { precacheAndRoute, cleanupOutdatedCaches } from 'workbox-precaching'
import { registerRoute } from 'workbox-routing'
import { NetworkFirst, CacheFirst, StaleWhileRevalidate } from 'workbox-strategies'

// 预缓存构建产物
precacheAndRoute(self.__WB_MANIFEST)
cleanupOutdatedCaches()

// HTML — 网络优先，离线降级到缓存
registerRoute(
  ({ request }) => request.mode === 'navigate',
  new NetworkFirst({ cacheName: 'html-cache' })
)

// JS/CSS — 缓存优先（有 hash，内容不变）
registerRoute(
  ({ request }) => ['script', 'style'].includes(request.destination),
  new CacheFirst({ cacheName: 'static-cache' })
)

// API — 先用缓存响应，后台更新（适合非实时数据）
registerRoute(
  ({ url }) => url.pathname.startsWith('/api/config'),
  new StaleWhileRevalidate({ cacheName: 'api-cache' })
)
```

## 六、监控：全球节点拨测

部署完成后需要持续监控各地域的实际访问质量：

```ts
// 前端性能上报 — 收集真实用户数据（RUM）
window.addEventListener('load', () => {
  const nav = performance.getEntriesByType('navigation')[0] as PerformanceNavigationTiming

  const metrics = {
    // DNS 解析耗时
    dns: nav.domainLookupEnd - nav.domainLookupStart,
    // TCP + TLS 握手
    tcp: nav.connectEnd - nav.connectStart,
    // 首字节时间（衡量服务器响应速度）
    ttfb: nav.responseStart - nav.requestStart,
    // 页面完全加载
    load: nav.loadEventEnd - nav.fetchStart,
    // 用户地域
    timezone: Intl.DateTimeFormat().resolvedOptions().timeZone,
    region: navigator.language,
  }

  // 上报到监控平台
  navigator.sendBeacon('/api/metrics', JSON.stringify(metrics))
})
```

## 总结

```
全球访问加速 = 静态资源 CDN 分发
             + DNS 智能地域调度
             + 多地域源站就近部署
             + HTTP/2 & QUIC 协议优化
             + Service Worker 本地缓存
             + 持续拨测监控
```

| 手段 | 解决的问题 | 收益 |
|---|---|---|
| 全球 CDN | 静态资源物理距离 | 最大，必做 |
| GeoDNS | API 接口就近路由 | 大，中大型产品必做 |
| HTTP/3 | 弱网/高延迟场景 | 中，优先级次之 |
| Service Worker | 重复访问、弱网 | 中，体验提升明显 |

## 前端热修复发布

### 什么是热修复（Hotfix）？

热修复是指在**不走完整发布流程**的前提下，针对线上紧急 bug 快速修复并上线的机制。核心矛盾是：

```
常规发布：开发 → 测试 → staging → 审批 → 上线（可能需要数天）
热修复：  定位 → 修复 → 最小化验证 → 上线（目标 30 分钟内）
```

---

## 一、热修复的完整流程

### Git 分支策略

```
main/master（线上代码）
    │
    ├── hotfix/fix-payment-crash    ← 从 main 直接切出
    │       │
    │       ├── 修复代码
    │       ├── merge → main        ← 合并回主干，触发上线
    │       └── merge → develop     ← 同步回开发分支，避免下次发布覆盖修复
    │
    └── develop（日常开发）
```

```bash
# 标准 hotfix 操作流程

# 1. 从线上分支切出 hotfix 分支
git checkout main
git pull origin main
git checkout -b hotfix/fix-payment-crash

# 2. 修复 bug，提交
git add .
git commit -m "fix: 修复支付页面金额计算异常 #issue-123"

# 3. 合并回 main，打 tag
git checkout main
git merge hotfix/fix-payment-crash
git tag -a v1.2.1 -m "hotfix: fix payment crash"
git push origin main --tags

# 4. 同步回 develop，避免修复丢失
git checkout develop
git merge hotfix/fix-payment-crash
git push origin develop

# 5. 删除 hotfix 分支
git branch -d hotfix/fix-payment-crash
```

## 二、CI/CD 热修复流水线

热修复流水线和常规发布流水线的核心区别是**跳过耗时环节，保留关键卡点**：

```yaml
# .github/workflows/hotfix.yml
name: Hotfix Release

on:
  push:
    tags:
      - 'v*.*.*-hotfix*'   # 打特定格式 tag 触发
  workflow_dispatch:        # 支持手动触发
    inputs:
      skip_e2e:
        description: '跳过 E2E 测试（紧急情况）'
        type: boolean
        default: false

jobs:
  hotfix-build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3

      - name: 安装依赖（利用缓存）
        uses: actions/setup-node@v3
        with:
          node-version: 18
          cache: 'npm'

      - run: npm ci

      # 只跑关键单元测试，跳过完整 E2E
      - name: 单元测试（核心模块）
        run: npm run test:unit -- --testPathPattern="payment|auth|core"

      - name: 构建
        run: npm run build:prod
        env:
          VITE_API_BASE_URL: ${{ secrets.PROD_API_URL }}

      # 直接发布到生产，不经过 staging
      - name: 上传 CDN
        run: |
          ossutil cp -r ./dist oss://prod-bucket/frontend/ \
            --update --jobs 10

      - name: 刷新 CDN 缓存
        run: |
          aliyun cdn RefreshObjectCaches \
            --ObjectPath "https://cdn.example.com/index.html" \
            --ObjectType File

      - name: 通知钉钉/飞书
        run: |
          curl -X POST ${{ secrets.DINGTALK_WEBHOOK }} \
            -H "Content-Type: application/json" \
            -d '{"text": {"content": "🚨 热修复已上线：${{ github.ref_name }}"}}'
```

## 三、前端层面的紧急止血手段

在代码修复、构建、发布都需要时间的情况下，前端有几种**无需发版**的快速止血方案：

### 方案一：远程配置开关（功能降级）

提前在代码中埋好开关，紧急时直接后台关闭问题功能：

```ts
// src/config/remoteConfig.ts
// 应用启动时拉取远程配置，支持实时生效
class RemoteConfig {
  private config: Record<string, boolean> = {}

  async fetch() {
    const res = await fetch('/api/feature-flags')
    this.config = await res.json()
  }

  isEnabled(flag: string): boolean {
    return this.config[flag] ?? true // 默认开启
  }
}

export const remoteConfig = new RemoteConfig()

// 组件中使用
if (!remoteConfig.isEnabled('payment_new_flow')) {
  // 降级到旧流程
  return <OldPaymentFlow />
}
return <NewPaymentFlow />
```

```json
// 后台直接修改配置，0 秒生效，无需发版
{
  "payment_new_flow": false,  // ← 紧急关闭出问题的新功能
  "user_profile_v2": true
}
```

### 方案二：版本快速回滚

CDN 多版本共存，出问题时秒级切回上个版本：

```bash
# nginx 或 CDN 路由配置
# 只需修改 index.html 指向的资源版本路径

# 当前线上：v1.2.0
/frontend/v1.2.0/assets/app.abc123.js

# 出问题后，直接将 index.html 回滚到 v1.1.9 的内容
# 新资源（v1.2.0）仍然存在，不需要删除

# 脚本化回滚
./scripts/rollback.sh v1.1.9
```

```bash
#!/bin/bash
# scripts/rollback.sh
TARGET_VERSION=$1

echo "🔄 回滚到版本 $TARGET_VERSION"

# 从版本备份恢复 index.html
ossutil cp \
  oss://prod-bucket/backup/$TARGET_VERSION/index.html \
  oss://prod-bucket/frontend/index.html \
  --force

# 刷新 CDN 上的 index.html
aliyun cdn RefreshObjectCaches \
  --ObjectPath "https://cdn.example.com/index.html"

echo "✅ 回滚完成，当前版本：$TARGET_VERSION"
```

### 方案三：动态加载补丁脚本

适合修复量极小（几行代码）且无法立刻走构建流程的场景：

```html
<!-- index.html 预留补丁入口 -->
<script>
  // 从远端动态加载补丁，支持随时更新
  fetch('/api/patch-config')
    .then(r => r.json())
    .then(({ patchUrl, enabled }) => {
      if (enabled && patchUrl) {
        const script = document.createElement('script')
        script.src = patchUrl
        document.head.appendChild(script)
      }
    })
</script>
```

```js
// patch-v1.2.1.js — 上传到 CDN 的补丁文件
// 直接覆盖有问题的方法
import { paymentUtils } from '/assets/utils.abc123.js'

paymentUtils.calculateTotal = function(price, quantity) {
  // 修复：原来少乘了 quantity
  return price * quantity
}
```

> ⚠️ 补丁脚本是最后手段，维护成本高，上线后必须尽快用正式发版替代。

## 五、热修复流程总结

```
发现问题
    │
    ├── 能否立刻止血（不发版）？
    │       ├── 是 → 远程配置关闭功能 / 回滚版本  ← 优先
    │       └── 否 → 进入修复流程
    │
    ↓
从 main 切出 hotfix 分支
    │
    ↓
最小化修复（只改必要代码，不顺手重构）
    │
    ↓
核心模块单测通过
    │
    ↓
触发热修复流水线（跳过完整 E2E，直接构建上线）
    │
    ↓
上线后监控 5~15 分钟（观察错误率）
    │
    ├── 正常 → hotfix 分支合并回 develop，关闭 issue
    └── 异常 → 立刻回滚，重新分析
```

| 手段 | 生效速度 | 适用场景 | 风险 |
|---|---|---|---|
| 远程配置开关 | 秒级 | 新功能引发的 bug | 低 |
| 版本回滚 | 分钟级 | 整体功能异常 | 低 |
| 补丁脚本 | 分钟级 | 极小范围逻辑修复 | 中 |
| 热修复发版 | 15~30 分钟 | 需要代码修改的 bug | 中 |
| 常规发版 | 数小时起 | 非紧急问题 | 低 |

核心原则只有一条：**止血优先于完美，上线后持续观察，事后补充完整测试覆盖。**

## 一、整体架构：微前端 + Monorepo

## 二、构建优化

### 2.1 构建工具链
- **使用 Webpack 5** 开启持久化缓存，大幅提升二次构建速度。
- **关键优化**：
  - 使用 `swc-loader` 或 `esbuild-loader` 替代 babel 进行编译和压缩。
  - 开启 `thread-loader` 多进程并行构建。
  - 精细拆分代码：`splitChunks` 提取公共模块，异步路由使用 `import()` 懒加载。
  - 使用 `webpack-bundle-analyzer` 定期分析包体积。

### 2.2 构建流水线（CI）
- **触发方式**：PR 触发 lint/type-check，合并到 main 分支后自动构建。
- **构建缓存**：缓存 `node_modules` 和 Webpack 缓存目录，加速 CI。
- **产物管理**：每个构建生成唯一版本号（如 `build-{timestamp}-{commit-hash}`），产物上传至对象存储（如 S3），并记录版本清单。

### 2.3 增量构建
- 利用 Webpack 的持久化缓存，只重新编译变化的模块，减少构建时间。
- 对于微前端，子应用独立构建，主应用无需重新构建所有子应用。

## 三、发布策略：灰度 + 蓝绿 + AB测试

### 3.1 版本与部署单元
- 每个子应用独立版本，独立部署，通过主应用动态加载。
- 部署单元：静态资源（JS/CSS/图片）和 HTML（可选，若采用客户端渲染则 HTML 由主应用或网关生成）。

### 3.2 灰度发布
- **分流策略**：
  - 按用户 ID 哈希（如 `uid % 1000 < 100` 表示 10% 流量）。
  - 按地域（IP 归属）、设备类型（User-Agent）、自定义标签（如 VIP 用户）。
- **实现方式**：
  - **网关层**：通过 Nginx/OpenResty 或 API 网关根据规则将流量导向不同版本的静态资源入口（如不同的 HTML 或静态资源目录）。
  - **前端配置中心**：主应用启动时拉取灰度配置，动态加载不同版本的子应用资源（如 `subapp@v2` 或 `subapp@v1`）。更适合 AB 测试和子应用级灰度。
- **渐进式放量**：支持手动调整灰度比例，观察监控指标后再逐步扩大。

### 3.3 蓝绿部署
- 同时保留两套完整的静态资源版本（蓝色为当前稳定版，绿色为新版）。
- 通过切换 CDN 回源路径或修改入口 HTML 引用的资源前缀来实现快速切换。
- 回滚只需切换回蓝色版本，秒级完成。

### 3.4 AB 测试
- 与灰度类似，但需同时运行多个实验版本，且用户可能长期处于某个实验组。
- 前端通过配置中心获取实验分组，动态加载不同的组件或样式，或修改行为逻辑。后端也需配合处理实验数据。

---

## 四、版本一致性与 CDN 缓存

### 4.1 资源版本控制
- **静态资源**：使用 `[name].[contenthash].js` 命名，内容变化时 URL 改变，确保缓存精确。
- **HTML 入口**：不缓存或设置极短缓存（如 `max-age=0, must-revalidate`），保证每次请求都获取最新 HTML。HTML 中引用的资源 URL 已包含哈希，因此即使 HTML 缓存，资源仍可正确加载。

### 4.2 CDN 缓存策略
- **带 hash 的资源**：设置 `Cache-Control: public, max-age=31536000, immutable`，浏览器长期缓存。
- **HTML**：设置 `Cache-Control: no-cache`，每次请求都回源验证，配合 `ETag` 或 `Last-Modified`。
- **版本切换**：灰度时，新版本资源路径需全新（哈希不同），CDN 无需特殊操作；若使用相同 URL 但内容变化，需手动刷新 CDN 缓存，但哈希策略避免了此问题。

### 4.3 多版本共存
- 静态资源按版本存放在不同目录（如 `/v1.2.3/`），或直接使用带哈希的文件名，多个版本文件共存于 CDN。
- 发布新版本时，旧版本仍可被已缓存用户访问，确保平滑过渡。

## 五、快速回滚与自动回滚

### 5.1 手动回滚
- 通过 CI/CD 系统触发回滚任务，将 CDN 回源路径指向旧版本目录，或修改网关路由。
- 回滚过程需保留旧版本资源（蓝绿部署天然支持）。

### 5.2 自动回滚机制
- **监控指标**：发布后实时监控：
  - 错误率（JS 异常、API 失败率）
  - 性能指标（FCP、LCP）
  - 业务指标（转化率、下单成功率）
- **阈值告警**：若错误率超过预设阈值（如 5%）或业务指标下降超过 10%，自动触发回滚。
- **回滚流程**：CI/CD 系统收到告警后，执行回滚脚本，切换流量到上一个稳定版本，并通知开发团队。

### 6.1 前端监控

## 一、部署架构：全球多区域 + CDN + 边缘计算

### 1.1 静态资源全球分发
- **核心**：使用全球CDN（如Cloudflare、Akamai、AWS CloudFront）分发静态资源（HTML、JS、CSS、图片）。CDN边缘节点就近缓存，大幅降低延迟。
- **源站策略**：在**北美、欧洲、亚洲**分别部署源站（如AWS S3桶或自建Nginx集群），CDN回源时通过**地理DNS**或CDN的**多源站**功能，自动选择最近的源站。欧洲源站必须位于欧盟境内，以满足GDPR数据本地化要求。

### 1.2 动态内容与BFF
- **API/BFF层**：在每个区域独立部署BFF服务（如Node.js集群），负责聚合后端数据、处理区域化业务逻辑。BFF与后端核心服务通过内部专线通信，或使用多活数据库。
- **数据合规**：欧洲区域BFF仅调用欧洲内部服务，确保用户数据不离境；亚洲同理。后端数据库按区域拆分（如欧洲数据库、亚洲数据库），全球数据同步由后端负责，前端无感知。

### 1.3 边缘计算
- 利用CDN的**边缘计算能力**（如Cloudflare Workers、Lambda@Edge）执行轻量级逻辑：
  - 根据用户IP判断所属区域，动态返回对应区域的配置或实验分组。
  - 在边缘进行A/B测试、重定向、鉴权，减少到源站的请求。

---

## 二、多地区构建与部署

### 2.1 构建流程
- **CI/CD**：使用GitHub Actions/GitLab CI触发构建。每次合并到主分支生成唯一版本号（如 `build-{timestamp}-{commit}`）。
- **产物**：构建后得到静态资源（带内容哈希）和版本清单（`asset-manifest.json`）。所有资源上传至**中心存储**（如AWS S3全局桶），供各区域源站同步。

### 2.2 同步到各区域源站
- 通过**跨区域复制**（如S3跨区域复制）将中心桶的产物自动同步到北美、欧洲、亚洲的源站桶。或使用CDN的多源站直接回源中心桶，但为降低延迟和合规，建议区域源站。
- **版本一致性**：所有区域源站保存同一版本的文件（哈希文件名保证唯一性），HTML入口文件通过部署时更新引用路径，确保各区域加载的静态资源完全一致。

### 2.3 部署与发布
- **蓝绿部署**：每个区域源站保留当前版本和候选版本目录，通过切换符号链接或更新CDN回源路径实现零停机发布。
- **灰度发布**：结合边缘计算，按用户ID、地域等标签，将部分流量导向新版资源（如返回不同HTML入口）。逐步放量，观察监控指标。

---

## 三、地区配置差异管理

### 3.1 动态配置中心
- 使用**配置中心**（如Apollo、Nacos）或**边缘KV存储**（如Cloudflare Workers KV）存储每个区域的配置（语言包、货币、主题、功能开关）。
- 前端启动时，通过API获取区域配置（可携带用户IP或语言头），或在构建时将配置嵌入HTML但需多版本构建，推荐动态获取，避免重复构建。

### 3.2 个性化配置
- 通过边缘计算注入配置：边缘节点根据用户地理位置，将配置直接写入HTML内联脚本（`window.__REGION_CONFIG__`），首屏即可使用，无需额外请求。

---

## 四、跨地区监控与日志

### 4.1 真实用户监控（RUM）
- 部署RUM探针（如自研sdk或Datadog RUM），采集各区域的**Web Vitals**（FCP、LCP、CLS）、API延迟、错误率。
- 数据按区域打标，上报到中心化分析平台（如自建ClickHouse或云服务）。需在欧洲区域保留一份日志副本以满足合规。

### 4.2 错误追踪
- 使用Sentry或自建错误监控，配置多区域DNS，让用户上报到最近的中转服务器，再聚合到中心。

### 4.3 告警
- 设置多级告警：当某区域错误率突增、延迟超过阈值时，通过钉钉/邮件通知，并触发自动回滚。

---

## 五、灾备与故障转移

### 5.1 多区域故障转移
- **DNS层面**：使用全局负载均衡（如AWS Route 53），配置健康检查。当某区域源站或BFF故障时，自动将流量切换到另一健康区域。
- **CDN层面**：CDN本身具备冗余，若一个源站不可用，可自动回源到其他源站（需配置多源站）。

### 5.2 静态资源灾备
- 各区域源站之间互为备份。若欧洲源站故障，CDN可回源到北美源站（需考虑合规，可临时允许，但需评估）。

### 5.3 自动回滚
- 发布后监控指标，若错误率或核心业务指标下降超阈值，CI/CD自动触发回滚：切换CDN回源路径或更新DNS指向旧版本。

---

## 六、全球用户首屏加载优化

1. **CDN边缘缓存**：静态资源设置长时间缓存（`Cache-Control: public, max-age=31536000, immutable`），用户从最近边缘节点获取。
2. **边缘渲染**：对首屏HTML使用边缘计算动态生成（如Next.js的Edge SSR），结合区域配置，返回直接可渲染的HTML，消除白屏。
3. **资源预加载**：使用`<link rel="preconnect>`、`<link rel="dns-prefetch>`加速跨域连接，`<link rel="preload>`加载关键资源。
4. **图片优化**：使用WebP/AVIF格式、响应式图片、懒加载。
5. **代码分割**：按路由拆分JS，首屏只加载必要代码。
6. **区域化CDN加速**：确保每个区域的CDN节点覆盖全面，对于亚太地区，考虑使用当地CDN服务商（如阿里云CDN）作为补充。

---

## 七、总结

该方案通过全球CDN分发、区域化源站、边缘计算、动态配置、全链路监控及自动化故障转移，实现了**低延迟、高可用、合规**的全球化前端部署。版本一致性通过统一构建和跨区域同步保证，配置差异在边缘动态注入，首屏性能达到最优。此架构可支撑千万级日活的国际化SaaS产品平稳运行。
