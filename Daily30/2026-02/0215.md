## JavaScript (8题)

1. JavaScript中的装箱和拆箱是什么？基本类型如何调用方法？
在 JavaScript 中，**装箱（Boxing）** 是指将**基本类型值**（如 `string`、`number`、`boolean`）临时转换为对应的**包装对象**（如 `String`、`Number`、`Boolean`）的过程；**拆箱（Unboxing）** 则是将包装对象转换回基本类型值的过程。

### 基本类型如何调用方法？
基本类型本身不是对象，没有方法。但当你在基本类型上访问属性或方法时，JavaScript 引擎会**隐式地执行装箱操作**：
1. 创建一个对应的临时包装对象。
2. 在该包装对象上调用方法。
3. 调用完成后，销毁该对象（或等待垃圾回收）。

**例如：**
```javascript
const str = 'hello';
console.log(str.toUpperCase()); // 'HELLO'
```
幕后过程：
- 引擎临时创建 `new String('hello')` 包装对象。
- 调用该对象的 `toUpperCase` 方法。
- 返回结果后，包装对象被丢弃，`str` 仍是基本类型。

其他基本类型同理：
- `number` → `Number` 包装对象，可调用 `toFixed()` 等。
- `boolean` → `Boolean` 包装对象，但很少使用其方法。
- `symbol` 和 `bigint` 也有对应的包装对象（`Symbol` 和 `BigInt`），但 `Symbol` 不能使用 `new` 创建，且显式装箱很少见。

### 注意事项
- `null` 和 `undefined` 没有包装对象，调用方法会抛出 `TypeError`。
- 显式装箱可使用 `new String('...')` 等，但通常不推荐，因为可能带来意外的类型判断（如 `typeof new String('')` 返回 `'object'`）。
- 拆箱通常发生在对象参与运算时（如 `+` 或 `==`），会调用对象的 `valueOf` 和 `toString` 方法获取基本值。

理解装箱和拆箱有助于避免类型相关的陷阱，并正确理解 JavaScript 中基本类型与对象的行为差异。

2. 什么是函数重载？JavaScript中如何模拟函数重载？
**函数重载**是指在编程语言中定义多个同名函数，但它们的参数类型或数量不同，编译器或解释器根据调用时传入的参数决定执行哪个版本。

### JavaScript 中如何模拟？
JavaScript 本身**不支持**真正的函数重载（同名函数会覆盖），但可以通过以下方式模拟：

1. **在函数内部判断参数个数或类型**  
   利用 `arguments` 对象或剩余参数（`...args`）获取所有传入参数，然后根据参数数量或类型执行不同逻辑。
   ```javascript
   function greet(name, age) {
     if (arguments.length === 1) {
       return `Hello, ${name}`;
     } else if (arguments.length === 2) {
       return `Hello, ${name}, you are ${age} years old.`;
     }
   }
   ```

2. **使用类型检测**  
   结合 `typeof` 或 `instanceof` 针对不同参数类型执行不同操作。
   ```javascript
   function format(value) {
     if (typeof value === 'string') {
       return value.trim();
     } else if (typeof value === 'number') {
       return value.toFixed(2);
     }
   }
   ```

3. **通过对象映射（更高级）**  
   将不同参数模式映射到对应处理函数，但实际很少用到。

**TypeScript** 支持真正的函数重载，通过声明多个函数签名来实现类型检查，但编译后仍是单函数逻辑。

3. 手写实现Promise.allSettled和Promise.any，解释它们和Promise.all的区别。
### `Promise.allSettled`、`Promise.any` 与 `Promise.all` 的区别

| 方法 | 行为 | 返回值 |
|------|------|--------|
| `Promise.all` | 所有 promise 成功 → 返回结果数组；任意一个失败 → 立即 reject 该错误 | 成功时数组，失败时单个错误 |
| `Promise.allSettled` | 等待所有 promise 完成（无论成功/失败）→ 返回每个 promise 的结果描述对象 | 数组，每个元素为 `{status:'fulfilled', value}` 或 `{status:'rejected', reason}` |
| `Promise.any` | 任意一个成功 → 返回该成功值；全部失败 → 返回 `AggregateError`（包含所有失败原因） | 第一个成功值，或聚合错误 |

---

## 手写实现

### 1. 实现 `Promise.allSettled`

```javascript
function allSettled(promises) {
  // 将非 promise 转换为 promise
  const wrappedPromises = promises.map(p =>
    p instanceof Promise ? p : Promise.resolve(p)
  );

  return new Promise((resolve) => {
    const results = [];
    let completed = 0;

    if (wrappedPromises.length === 0) {
      resolve(results);
      return;
    }

    wrappedPromises.forEach((promise, index) => {
      promise
        .then(value => {
          results[index] = { status: 'fulfilled', value };
        })
        .catch(reason => {
          results[index] = { status: 'rejected', reason };
        })
        .finally(() => {
          completed++;
          if (completed === wrappedPromises.length) {
            resolve(results);
          }
        });
    });
  });
}
```

### 2. 实现 `Promise.any`

```javascript
function any(promises) {
  // 将非 promise 转换为 promise
  const wrappedPromises = promises.map(p =>
    p instanceof Promise ? p : Promise.resolve(p)
  );

  return new Promise((resolve, reject) => {
    const errors = [];
    let rejectedCount = 0;

    if (wrappedPromises.length === 0) {
      reject(new AggregateError([], 'All promises were rejected'));
      return;
    }

    wrappedPromises.forEach((promise, index) => {
      promise
        .then(value => {
          resolve(value); // 只要有一个成功，立即 resolve
        })
        .catch(reason => {
          errors[index] = reason;
          rejectedCount++;
          if (rejectedCount === wrappedPromises.length) {
            // 所有都失败，返回 AggregateError
            reject(new AggregateError(errors, 'All promises were rejected'));
          }
        });
    });
  });
}
```

**说明**：
- 两个实现均处理了空数组的情况（`allSettled` 返回空数组；`any` 返回带空错误数组的 `AggregateError`）。
- `AggregateError` 是 ES2021 引入的全局对象，若环境不支持可手动构造类似对象。

4. JavaScript中的with语句是什么？为什么不推荐使用？严格模式下有哪些限制？
`with` 语句用于扩展一个对象的作用域链，使其属性在语句块内可以直接作为变量访问。

**语法示例**：
```javascript
with (obj) {
  console.log(name); // 相当于 console.log(obj.name)
}
```

### 为什么不推荐使用？
1. **性能低下**：`with` 会在作用域链前端插入对象，导致属性查找变慢，且 JavaScript 引擎难以进行优化。
2. **语义模糊**：代码难以阅读和维护，无法直观区分变量是对象的属性还是外部作用域的变量。
3. **意外创建全局变量**：若对不存在的属性赋值，可能沿着作用域链查找，最终在全局对象上创建属性（非严格模式）。
4. **严格模式下被禁止**：表明语言本身已将其视为过时特性。

### 严格模式下的限制
在严格模式（`"use strict"`）中，`with` 语句**完全禁止**使用，任何出现 `with` 的代码都会抛出 `SyntaxError`。

**示例**：
```javascript
"use strict";
with (Math) { // SyntaxError: Strict mode code may not include a with statement
  let x = cos(2);
}
```

5. 什么是函数的arguments对象？箭头函数为什么没有arguments？如何在箭头函数中获取参数列表？
- **`arguments` 对象**：是一个**类数组对象**（不是真正的数组），包含传递给函数的**所有参数**。它只在普通函数（非箭头函数）内部可用，且与参数变量相互关联（非严格模式下修改 `arguments` 会影响命名参数，严格模式下不会）。
- **箭头函数为什么没有 `arguments`**：箭头函数**没有自己的 `arguments` 对象**，因为它不绑定 `arguments`（和 `this` 类似）。箭头函数内部的 `arguments` 实际上是指向**外层普通函数**的 `arguments`（若外层存在），否则会报错。这种设计是为了简化作用域规则，使箭头函数更轻量。
- **如何在箭头函数中获取参数列表**：推荐使用**剩余参数（rest parameters）**，例如 `(...args) => {}`。`args` 是一个**真正的数组**，包含所有传入的参数，且不依赖外层作用域，更清晰、灵活。

6. 解释JavaScript中的标记模板（Tagged Template）是什么？它有哪些应用场景？
**标记模板（Tagged Template）** 是 ES6 引入的一种模板字符串增强形式，允许你通过一个函数（称为“标签函数”）来自定义模板字符串的解析和拼接过程。

### 语法与工作原理
```javascript
// 标签函数
function myTag(strings, ...values) {
  // strings: 由静态文本部分组成的数组
  // values: 每个插值表达式求值后的结果
  return strings.reduce((result, str, i) => result + str + (values[i] || ''), '');
}

const name = 'World';
const result = myTag`Hello, ${name}!`; // "Hello, World!"
```
- 标签函数接收两个部分：**字符串数组**（按插值分割）和**剩余参数**（所有插值表达式的值）。
- 函数可以对这些部分做任意处理，并返回任何类型的值（不限于字符串）。

---

### 主要应用场景

1. **防止 XSS 攻击（安全过滤）**  
   在构建 HTML 字符串时，自动转义用户输入的内容。
   ```javascript
   function safeHtml(strings, ...values) {
     const escaped = values.map(v => v.replace(/[&<>"]/g, escapeChar));
     return strings.reduce((result, str, i) => result + str + (escaped[i] || ''), '');
   }
   const userInput = '<script>alert("hack")</script>';
   const html = safeHtml`<div>${userInput}</div>`;
   // <div>&lt;script&gt;alert("hack")&lt;/script&gt;</div>
   ```

2. **国际化（i18n）**  
   根据语言动态替换文本，并处理复数形式。
   ```javascript
   function i18n(strings, ...values) {
     const locale = getLocale(); // 获取当前语言
     const translated = strings.map(s => translations[locale][s] || s);
     return translated.reduce((result, str, i) => result + str + (values[i] || ''), '');
   }
   const count = 3;
   const message = i18n`You have ${count} messages.`;
   ```

3. **CSS-in-JS（如 styled-components）**  
   在模板中嵌入动态样式，返回 React 组件。
   ```javascript
   const Button = styled.button`
     background: ${props => props.primary ? 'blue' : 'gray'};
     color: white;
   `;
   ```

4. **创建 DSL（领域特定语言）**  
   例如构建 SQL 查询，防止注入并生成参数化查询。
   ```javascript
   function sql(strings, ...values) {
     const placeholders = values.map(() => '?').join(', ');
     const query = strings.reduce((q, str, i) => q + str + (placeholders[i] || ''), '');
     return { query, values };
   }
   const id = 5;
   const { query, values } = sql`SELECT * FROM users WHERE id = ${id}`;
   // query: "SELECT * FROM users WHERE id = ?", values: [5]
   ```

5. **日志格式化**  
   为日志添加颜色、时间戳或结构化输出。
   ```javascript
   function log(strings, ...values) {
     const timestamp = new Date().toISOString();
     console.log(`[${timestamp}]`, strings.raw[0], ...values);
   }
   log`User ${user.name} logged in.`;
   ```

6. **表达式求值控制**  
   实现延迟计算或条件输出。
   ```javascript
   function lazy(strings, ...values) {
     return () => strings.reduce((result, str, i) => result + str + (values[i] || ''), '');
   }
   const lazyMsg = lazy`Current time: ${Date.now()}`;
   console.log(lazyMsg()); // 执行时才获取最新时间
   ```

标记模板提供了一种强大而灵活的方式来处理字符串模板，广泛应用于需要自定义插值逻辑、安全处理和构建领域特定语言的场景。

7. 什么是Object.freeze()和Object.seal()？它们的区别是什么？如何实现深度冻结对象？
`Object.freeze()` 和 `Object.seal()` 是 JavaScript 中用于控制对象可变性的两个静态方法。

---

### `Object.freeze()`
- **作用**：完全冻结一个对象。冻结后对象：
  - **不可添加**新属性。
  - **不可删除**现有属性。
  - **不可修改**现有属性的值（即使属性是可写的）。
  - **不可修改**属性的描述符（如将可写改为 `false` 等）。
  - 原型链也不可修改。
- **返回**：被冻结的对象本身。
- **尝试修改**：在非严格模式下静默失败，在严格模式下抛出 `TypeError`。

### `Object.seal()`
- **作用**：密封一个对象。密封后对象：
  - **不可添加**新属性。
  - **不可删除**现有属性。
  - **可修改**现有属性的值（前提是该属性原本是可写的）。
  - **不可修改**属性的描述符（如将可枚举改为 `false` 等）。
- **返回**：被密封的对象本身。
- **尝试修改**：添加或删除属性会静默失败或抛出异常（严格模式）。

---

### 区别总结
| 特性 | `Object.freeze()` | `Object.seal()` |
|------|-------------------|-----------------|
| 添加新属性 | ❌ 禁止 | ❌ 禁止 |
| 删除属性 | ❌ 禁止 | ❌ 禁止 |
| 修改属性值 | ❌ 禁止（只读） | ✅ 允许（若可写） |
| 修改属性描述符 | ❌ 禁止 | ❌ 禁止 |
| 原型修改 | ❌ 禁止 | ✅ 允许（但非标准） |

---

### 如何实现深度冻结对象？
`Object.freeze()` 只冻结对象自身属性，不会递归冻结嵌套对象。要实现深度冻结，需要手动递归。

**递归深度冻结函数（处理循环引用）**：
```javascript
function deepFreeze(obj) {
  // 获取所有属性名（包括不可枚举的 Symbol 属性）
  const propNames = Object.getOwnPropertyNames(obj);
  const symbolProps = Object.getOwnPropertySymbols(obj);

  // 冻结当前对象
  Object.freeze(obj);

  // 递归冻结每个属性值（如果是对象）
  [...propNames, ...symbolProps].forEach(name => {
    const value = obj[name];
    if (value && typeof value === 'object' && !Object.isFrozen(value)) {
      deepFreeze(value);
    }
  });

  return obj;
}
```

**注意**：
- 使用 `Object.isFrozen()` 检查避免重复冻结（也用于检测循环引用）。
- 若需更严谨，可用 `WeakSet` 记录已访问对象，防止循环引用导致栈溢出。

**示例**：
```javascript
const obj = {
  a: 1,
  b: { c: 2 }
};
deepFreeze(obj);
obj.b.c = 3; // 静默失败或报错（严格模式）
console.log(obj.b.c); // 2
```

深度冻结后，所有层级对象均不可修改。

8. JavaScript的Intl国际化API有哪些？如何使用它进行日期、数字、货币的格式化？
JavaScript 的 **`Intl`（国际化 API）** 是一组为语言敏感操作（如日期、数字、比较）提供标准化的内置对象，支持自动适配不同地区的格式规则。

## 核心对象概览
- **`Intl.DateTimeFormat`**：格式化日期和时间。
- **`Intl.NumberFormat`**：格式化数字、货币、百分比。
- **`Intl.Collator`**：语言敏感的字符串比较（排序）。
- **`Intl.PluralRules`**：获取复数形式规则。
- **`Intl.RelativeTimeFormat`**：格式化相对时间（如“3天前”）。
- **`Intl.ListFormat`**：格式化列表（如“A, B, 和 C”）。
- **`Intl.DisplayNames`**：获取语言、地区等的本地化显示名称。
- **`Intl.Locale`**：解析和操作语言标记。

---

## 日期时间格式化（`Intl.DateTimeFormat`）
```javascript
// 创建格式化器（可缓存）
const formatter = new Intl.DateTimeFormat('zh-CN', {
  dateStyle: 'full',        // 完整日期：'full', 'long', 'medium', 'short'
  timeStyle: 'medium',      // 时间样式
  hour12: false,            // 是否使用12小时制
  timeZone: 'Asia/Shanghai' // 时区
});

console.log(formatter.format(new Date())); 
// 输出示例：2023年10月27日星期五 15:30:45

// 更多选项：year, month, day, hour, minute, second 等可以单独指定
const custom = new Intl.DateTimeFormat('en-US', {
  year: 'numeric',
  month: 'long',
  day: '2-digit'
});
custom.format(new Date()); // "October 27, 2023"
```

## 数字/货币格式化（`Intl.NumberFormat`）
```javascript
// 1. 简单数字格式化
new Intl.NumberFormat('de-DE').format(1234567.89); // "1.234.567,89"

// 2. 货币格式化
const currencyFormatter = new Intl.NumberFormat('zh-CN', {
  style: 'currency',
  currency: 'CNY',          // 货币代码（ISO 4217）
  currencyDisplay: 'symbol' // 'symbol'（¥）, 'code'（CNY）, 'name'（人民币）
});
currencyFormatter.format(1999.5); // "¥1,999.50"

// 3. 百分比格式化
const percentFormatter = new Intl.NumberFormat('en-US', {
  style: 'percent',
  minimumFractionDigits: 1
});
percentFormatter.format(0.1234); // "12.3%"

// 4. 单位格式化（`style: 'unit'`）
new Intl.NumberFormat('en-US', {
  style: 'unit',
  unit: 'mile-per-hour'
}).format(60); // "60 mph"
```

## 性能提示
- 创建 `Intl` 对象开销较大，建议对同一种配置的实例进行**复用**。
- 对于一次性格式化，也可直接调用 `Intl.NumberFormat.prototype.format` 的静态方法（但不缓存）。
- 使用 `formatToParts()` 方法可以获取格式化后的各部分片段，方便自定义渲染。

## 浏览器支持
所有现代浏览器（包括 Node.js）均良好支持 `Intl` API。部分较新对象（如 `Intl.Segmenter`）可能处于较晚的版本，但核心的日期、数字格式化已广泛可用。

借助 `Intl`，可以轻松实现应用的国际化，而无需手动处理复杂的本地化规则。

## React (8题)

9. React的Reconciliation过程中，什么情况下会复用DOM节点？什么情况下会销毁重建？
React 的协调（Reconciliation）过程通过比较新旧两棵虚拟 DOM 树，决定如何高效更新真实 DOM。复用或销毁节点的判断基于两个关键因素：**元素类型**和 **key**。

### 复用 DOM 节点的条件
- **相同的元素类型**：新旧节点是同一个 HTML 标签（如 `<div>` 到 `<div>`）或同一个组件类型（如 `<MyComponent>` 到 `<MyComponent>`）。
- **key 相同**（仅对列表元素）：如果节点是数组中的元素，且 `key` 属性相同。
- **属性变化时**：React 会复用该 DOM 节点，仅更新变化的属性（如 `className`、`style` 等）。
- **子节点递归比较**：对子节点执行相同规则，尽量复用现有 DOM 结构。

### 销毁并重建 DOM 节点的条件
- **不同的元素类型**：例如从 `<div>` 变为 `<span>`，或从 `<ComponentA>` 变为 `<ComponentB>`。React 会销毁旧节点及其所有子节点，然后创建新节点。
- **key 不同**（列表元素）：在列表渲染中，如果两个元素类型相同但 `key` 不同，React 会认为它们是不同的元素，从而销毁旧节点，创建新节点。
- **组件类型变化但 key 相同**：即使 `key` 相同，如果组件类型不同（如从类组件变为函数组件），也会销毁重建。

### 为什么这样设计？
- 通过复用同类型节点，避免不必要的 DOM 操作，提升性能。
- `key` 帮助 React 识别列表中哪些元素发生了变化（如添加、删除、重排），避免因位置变化导致的大量重建。
- 类型变化时，旧节点及其状态通常无法安全复用，因此销毁重建更可靠。

理解这些规则有助于编写高性能的 React 组件，尤其是在使用列表时为每个元素提供稳定且唯一的 `key`。

10. useImperativeHandle的作用是什么？它和useRef配合如何使用？
`useImperativeHandle` 的作用是**自定义通过 `ref` 暴露给父组件的实例值**。它通常与 `forwardRef` 配合使用，让函数组件可以控制向父组件暴露哪些方法或属性，而不是直接暴露整个 DOM 节点或内部实例。

### 与 `useRef` 配合使用的步骤：
1. **子组件**：使用 `forwardRef` 接收父组件传来的 `ref`，内部用 `useRef` 创建对实际 DOM 或值的引用，然后通过 `useImperativeHandle` 将自定义的方法（如 `focus`、`scroll` 等）附加到父组件的 `ref` 上。
   ```jsx
   import { forwardRef, useRef, useImperativeHandle } from 'react';

   const Child = forwardRef((props, ref) => {
     const inputRef = useRef();

     useImperativeHandle(ref, () => ({
       focus: () => {
         inputRef.current.focus();
       },
       getValue: () => {
         return inputRef.current.value;
       }
     }));

     return <input ref={inputRef} defaultValue="hello" />;
   });
   ```

2. **父组件**：创建 `ref` 并传递给子组件，然后通过 `ref.current` 调用子组件暴露的方法。
   ```jsx
   import { useRef } from 'react';

   function Parent() {
     const childRef = useRef();

     const handleClick = () => {
       childRef.current.focus();
       console.log(childRef.current.getValue());
     };

     return (
       <>
         <Child ref={childRef} />
         <button onClick={handleClick}>操作子组件</button>
       </>
     );
   }
   ```

这样既保证了封装性，又允许父组件按需与子组件交互。

11. React中的Suspense for Data Fetching是什么？它和传统的数据获取方式有什么区别？
**React Suspense for Data Fetching** 是一种让组件在等待异步数据（如 API 响应）时“暂停”渲染的机制。它允许开发者在数据就绪前显示一个备选内容（如 loading 占位符），从而简化异步 UI 的编写。

### 与传统数据获取方式的区别

| 维度 | 传统方式 (useEffect + state) | Suspense for Data Fetching |
|------|-------------------------------|-----------------------------|
| **代码组织** | 手动管理 `loading`、`error`、`data` 状态，每个组件内部处理 | 数据读取与 UI 分离，组件直接消费数据，无需手动状态管理 |
| **加载状态** | 通常通过条件渲染显示 loading 指示器，多个组件可能导致 loading 嵌套或闪烁 | 由最近的 `<Suspense>` 边界统一控制 fallback，支持嵌套和合并 loading |
| **数据获取时机** | 组件渲染后（`useEffect` 中）发起请求，容易形成“瀑布流”（父子请求串行） | 渲染时立即发起请求（通过集成支持 Suspense 的数据库），可并行触发多个请求 |
| **并发特性** | 不支持 React 18 的并发渲染，更新可能被中断导致不一致 | 与 `useTransition` 配合可实现并发更新，旧数据在后台加载时不阻塞用户交互 |
| **错误处理** | 需要手动捕获错误并设置 error 状态 | 错误会被抛给最近的 **Error Boundary**，集中处理 |
| **性能优化** | 难以避免不必要的重渲染 | 数据缓存由库管理（如 React Query），可避免重复请求 |

### 核心优势
- **更优雅的加载体验**：结合骨架屏和 Suspense 边界，减少 loading 闪烁。
- **消除瀑布流**：数据获取在渲染阶段发起，依赖关系通过组件树自然表达。
- **并发友好**：支持可中断渲染，优先响应用户交互。

注意：Suspense for Data Fetching 目前需要配合支持 Suspense 的数据获取库（如 Relay、SWR 或 React Query 的 Suspense 模式）使用，React 本身不提供数据获取的具体实现。

12. 如何在React中实现拖拽功能？HTML5 Drag and Drop API如何使用？
在 React 中实现拖拽功能，通常有两种方式：使用原生 **HTML5 Drag and Drop API**，或使用第三方库（如 `react-dnd`、`react-beautiful-dnd`）。以下重点介绍 HTML5 API 及其在 React 中的用法。

---

## 1. HTML5 Drag and Drop API 核心概念
- **`draggable` 属性**：设置元素可拖拽（`true` / `false`）。
- **事件**：
  - 拖拽源元素：`ondragstart`、`ondrag`、`ondragend`。
  - 目标元素：`ondragenter`、`ondragover`、`ondragleave`、`ondrop`。
- **`dataTransfer` 对象**：在拖拽事件中传递数据（如 `setData()` / `getData()`）。

**注意**：必须阻止 `dragover` 和 `drop` 事件的默认行为（`preventDefault()`），才能使其成为有效放置目标。

---

## 2. 在 React 中的实现步骤
### 2.1 基本示例：拖拽方块到容器
```jsx
import React, { useState } from 'react';

function DragDrop() {
  const [droppedItems, setDroppedItems] = useState([]);

  // 拖拽开始：存储数据
  const handleDragStart = (e, id) => {
    e.dataTransfer.setData('text/plain', id);
  };

  // 允许放置
  const handleDragOver = (e) => {
    e.preventDefault();
  };

  // 放置处理
  const handleDrop = (e) => {
    e.preventDefault();
    const id = e.dataTransfer.getData('text/plain');
    setDroppedItems(prev => [...prev, id]);
  };

  return (
    <div>
      {/* 可拖拽元素 */}
      <div
        draggable
        onDragStart={(e) => handleDragStart(e, 'item1')}
        style={{ width: 100, height: 100, background: 'red', margin: 10 }}
      >
        拖我
      </div>

      {/* 放置区域 */}
      <div
        onDragOver={handleDragOver}
        onDrop={handleDrop}
        style={{ width: 300, height: 300, background: '#eee', margin: 10 }}
      >
        放置区
        <ul>
          {droppedItems.map((item, idx) => <li key={idx}>{item}</li>)}
        </ul>
      </div>
    </div>
  );
}
```

### 2.2 关键点
- 使用 React 的**合成事件**（如 `onDragStart`）而非原生事件。
- 通过 `e.dataTransfer.setData()` 传递数据，支持任意类型（需序列化）。
- 拖拽结束时，可能需要清理视觉效果或重置状态。

---

## 3. HTML5 拖拽的局限性
- **样式控制困难**：拖拽预览（“幽灵图像”）默认显示元素克隆，自定义复杂。
- **触摸设备支持有限**：需额外处理触摸事件。
- **跨浏览器行为差异**：某些事件触发顺序不一致。

## 4. 第三方库推荐（复杂场景）
当需要更高级的功能（如拖拽排序、列表重排、触摸支持、自定义预览）时，建议使用：
- **`react-dnd`**：高度可定制，支持拖拽类型、监视器等。
- **`react-beautiful-dnd`**：专注于列表拖拽排序，开箱即用。
- **`dnd-kit`**：现代轻量级拖拽库，支持多种场景。

这些库封装了 HTML5 API 的复杂性，并提供更友好的 React 集成。

---

**总结**：简单场景可直接使用 HTML5 Drag and Drop API 配合 React 事件；复杂交互推荐使用成熟的第三方拖拽库。

13. React中的useSyncExternalStore是什么？它解决了什么问题？
`useSyncExternalStore` 是 React 18 引入的一个 Hook，用于安全地从**外部存储**（如 Redux、Zustand、浏览器 API 或任何非 React 状态源）读取和订阅数据，并保证在 React 的**并发渲染**特性下数据的**一致性**和**正确性**。

### 它解决了什么问题？
在 React 18 的并发渲染模式（如 `startTransition`、`useDeferredValue`）中，渲染过程可能被中断、重启，甚至不同组件在同一时间看到不同版本的数据，导致 UI 出现“撕裂”（tearing）现象——即同一数据源在页面不同部分显示不一致。

传统的外部数据订阅方式（如在 `useEffect` 中手动订阅并通过 `setState` 更新）在并发模式下无法保证这种一致性，因为 React 的渲染与实际外部数据更新之间可能出现时序错配。

**`useSyncExternalStore` 通过以下机制解决：**
- 强制在渲染期间读取数据的**同步快照**。
- 当外部数据变化时，触发一个**同步的、不可中断的更新**，确保所有相关组件立即看到相同的新数据。
- 防止因并发渲染导致的数据撕裂，使 React 与外部状态源保持完美同步。

### 基本用法
```jsx
import { useSyncExternalStore } from 'react';

// 自定义订阅外部 store 的 hook
function useStore(store) {
  return useSyncExternalStore(
    store.subscribe,      // 订阅函数，返回取消订阅的函数
    store.getSnapshot,    // 获取当前快照（客户端）
    store.getServerSnapshot // 获取服务端快照（可选，用于 SSR）
  );
}
```

### 典型应用场景
- 集成外部状态管理库（如 Redux 的 `useSelector` 内部实现已使用此 Hook）。
- 监听浏览器 API（如在线状态、地理位置、历史记录等）。
- 任何需要将非 React 状态源接入 React 组件，并保证并发安全的地方。

16. 什么是React的hydration？hydration错误的常见原因有哪些？如何解决？
**Hydration** 是 React 在服务端渲染（SSR）或静态生成后，将服务器返回的静态 HTML 与客户端 React 组件“激活”的过程——即复用现有 DOM 节点并附加事件监听器、进行后续更新。

### Hydration 错误的常见原因
1. **客户端与服务器内容不一致**  
   - 动态数据差异：如随机值（`Math.random()`）、时间戳（`Date.now()`）、依赖于浏览器 API 的值（`window.innerWidth`）。  
   - 条件渲染差异：代码中使用了 `typeof window !== 'undefined'` 或直接判断环境，导致服务端与客户端渲染不同。  
   - 第三方脚本或浏览器插件修改了 DOM（如自动填充、广告插入）。  

2. **无效的 HTML 结构**  
   浏览器会修正不规范的 HTML（如 `<p>` 内嵌套 `<div>`），导致实际 DOM 与 React 预期不一致。  

3. **额外的空白字符/注释**  
   例如模板字符串中的换行或空格，可能使服务端与客户端的文本节点数量或内容不匹配。  

4. **CSS-in-JS 未正确提取样式**  
   服务端渲染时未收集样式，客户端首次渲染时样式注入导致内容偏移或节点差异。  

5. **异步数据加载**  
   使用 `useEffect` 加载数据并更新内容，但初始 HTML 为空或占位，造成第一次客户端渲染与服务器端不符（但此情况通常不会触发 hydration 警告，因为是在 hydration 后更新的）。严格来说，hydration 时数据应一致。

### 如何解决
- **确保渲染一致性**  
  - 避免在服务端和客户端使用不同的数据源；对于浏览器特有 API，在 `useEffect` 中更新。  
  - 使用 `useEffect` 执行客户端特定逻辑（如访问 `window`），并将依赖这些逻辑的元素放在客户端渲染。  
  - 若必须使用随机值，确保服务端和客户端生成相同的值（例如通过 props 传递）或使用 `suppressHydrationWarning` 忽略（不推荐用于重要数据）。  

- **修正 HTML 结构**  
  检查并遵循合法的 HTML 嵌套规则，使用 React DevTools 对比服务端和客户端 DOM 结构。  

- **处理空白字符**  
  删除不必要的空格或使用 `{/* comment */}` 替代可能导致差异的注释。  

- **正确配置 CSS-in-JS**  
  使用支持 SSR 的库（如 styled-components、Emotion），并在服务端调用 `collectStyles` 或类似 API 提取样式，将样式注入 HTML。  

- **使用 `suppressHydrationWarning` 属性**  
  在确信不一致无害的元素上添加 `suppressHydrationWarning={true}`，但仅作为临时方案，因它会抑制警告而不解决问题。  

- **升级 React 版本**  
  React 18 的 `hydrateRoot` 在 hydration 失败时会自动重新渲染客户端树，但会发出警告；仍建议修复根本原因。  

hydration 错误通常意味着应用在服务端和客户端之间存在不一致，应优先修复根源，以保障用户体验和应用可靠性。

## Next.js (5题)

17. Next.js 13的Server Actions是什么？它如何简化数据提交流程？

18. Next.js中的客户端组件和服务端组件如何通信？props传递有什么限制？
在 Next.js 的 App Router 中，**服务端组件**和**客户端组件**遵循 React 服务端组件（RSC）的规范，它们之间的通信主要通过 **Props 传递**和**组合模式**实现。同时，Props 传递有明确的序列化限制。

---

## 1. 如何通信？

### ① 服务端组件 → 客户端组件：通过 Props 传递数据
服务端组件可以在渲染时直接向客户端组件传递 props，这些 props 会在打包时被序列化并发送给客户端。

**示例**：
```jsx
// 服务端组件（默认，无需 'use client'）
import ClientComponent from './ClientComponent';

export default async function ServerComponent() {
  const data = await fetchData(); // 服务端获取数据
  return <ClientComponent message={data} />;
}

// 客户端组件（需要 'use client'）
'use client';
export default function ClientComponent({ message }) {
  return <div>{message}</div>;
}
```

### ② 客户端组件接收服务端组件作为 children（组合模式）
客户端组件**不能直接导入**服务端组件，但可以通过 `children` 属性接收服务端组件渲染好的内容。

**示例**：
```jsx
// 客户端组件
'use client';
export default function ClientWrapper({ children }) {
  return <div style={{ border: '1px solid red' }}>{children}</div>;
}

// 父级服务端组件
import ClientWrapper from './ClientWrapper';
import ServerComponent from './ServerComponent'; // 服务端组件

export default function Page() {
  return (
    <ClientWrapper>
      <ServerComponent /> {/* 这是服务端组件，但作为 children 传入 */}
    </ClientWrapper>
  );
}
```
此时 `ServerComponent` 在服务端渲染，结果作为静态内容嵌入 `ClientWrapper` 的 `children` 中。

### ③ 客户端组件 → 服务端组件：通过 API 路由或 Server Actions
客户端组件无法直接向服务端组件传递数据或调用其内部逻辑。需要的数据交互必须通过：
- **API 路由**：客户端发起 fetch 请求。
- **Server Actions**（Next.js 14+）：在客户端组件中调用服务端函数（使用 `'use server'` 指令）。

**Server Actions 示例**：
```jsx
// 服务端 action（可在服务端组件或单独文件中定义）
'use server';
export async function updateData(formData) {
  // 操作数据库等
}

// 客户端组件
'use client';
import { updateData } from './actions';
export default function Form() {
  return (
    <form action={updateData}>
      <input name="name" />
      <button type="submit">提交</button>
    </form>
  );
}
```

---

## 2. Props 传递的限制

从服务端组件传递到客户端组件的 props 必须**完全可序列化**（JSON 可序列化）。这意味着：

### ❌ 不可传递的类型：
- 函数（包括事件处理函数、方法）
- 非序列化对象（如 `Date`、`Map`、`Set`、`Symbol`、`BigInt`）
- 循环引用的对象
- 类实例
- React 元素（除 children 外）

### ✅ 允许传递的类型：
- 字符串、数字、布尔值
- 普通对象和数组（内部元素也必须可序列化）
- `undefined`（会被忽略，但不会导致错误）
- `null`
- Promise（会自动被等待并展开，但最终结果需可序列化）
- `Date` 会被转换为字符串，但最好先转为 ISO 字符串再传递。

**示例错误**：
```jsx
// ❌ 错误：传递函数
<ClientComponent onClick={() => {}} />
// ❌ 错误：传递 Date 对象（但 Date 会隐式转为字符串，不过不推荐）
<ClientComponent date={new Date()} />
// ✅ 正确：传递普通数据
<ClientComponent data={{ id: 1, name: 'test' }} />
```

### 特殊注意：`children` 属性的特殊性
当服务端组件作为 children 传入客户端组件时，实际上传递的是服务端组件渲染后的**结果描述（React 节点）**，这些节点本身是可序列化的（因为已经是静态内容）。因此客户端组件可以通过 `props.children` 渲染它们，但无法对 children 内部的组件进行交互（除非 children 内部含有客户端组件）。

---

## 总结
- **通信方向**：主要是服务端→客户端通过 props，客户端→服务端通过 API 或 Server Actions。
- **props 限制**：必须可 JSON 序列化（无函数、无非标准对象）。
- **组合模式**：客户端组件可以通过 children 接收服务端组件渲染的内容，实现混合渲染。
- 遵循这些规则可以确保应用在服务端和客户端之间高效、安全地传输数据。

23. 什么是缓存穿透、缓存击穿、缓存雪崩？前端如何应对这些问题？
### 缓存穿透、缓存击穿、缓存雪崩的定义

| 概念 | 描述 | 典型后果 |
|------|------|----------|
| **缓存穿透** | 查询一个**不存在的数据**，由于缓存未命中，每次请求都直接穿透到数据库。 | 数据库压力剧增，可能被恶意利用（如大量请求不存在的 ID）。 |
| **缓存击穿** | 一个**热点 key** 在缓存过期的瞬间，大量并发请求同时访问该 key，全部穿透到数据库。 | 数据库瞬间负载飙升，可能导致宕机。 |
| **缓存雪崩** | 大量 key **同时过期**，或缓存服务整体不可用，导致大量请求同时落到数据库。 | 数据库短时间内承受巨大压力，引发连锁故障。 |

---

### 前端如何应对这些问题？

虽然缓存穿透、击穿、雪崩主要是后端（缓存层/数据库层）的问题，但前端可以通过以下策略辅助缓解或降低影响：

#### 1. 针对缓存穿透
- **请求前参数校验**：在前端对用户输入进行合法性检查，过滤明显无效的请求（如 ID 格式不正确、超出范围），减少无效请求到达后端。
- **布隆过滤器前端化**：虽然布隆过滤器通常在后端实现，但可将布隆过滤器的位数组（压缩后）下发到前端，前端在请求前先快速判断 key 是否存在，拦截大部分穿透请求（适用于静态数据或定期更新的数据）。
- **接口限频/去重**：在请求库中对相同参数的请求进行合并或节流，避免短时间内重复发起无效请求。

#### 2. 针对缓存击穿
- **本地缓存（LocalStorage / SessionStorage）**：对于热点数据（如首页配置、公共信息），前端可以主动缓存到浏览器存储，设置合理的过期时间。当缓存过期时，只让一个请求去后端更新数据（类似后端的互斥锁），其他请求复用该结果。
- **Service Worker 缓存**：利用 Service Worker 拦截请求，实现更灵活的缓存策略（如 stale-while-revalidate），即使缓存过期也能优先返回旧数据，同时异步更新。
- **请求合并（Request Deduplication）**：在应用层（如使用 Axios 拦截器）对同一时间窗口内相同参数的请求进行合并，只发一个真实请求，所有调用者共享同一个 Promise，减少瞬间并发。

#### 3. 针对缓存雪崩
- **请求随机延迟**：在发起批量请求或页面加载时，对请求添加随机延迟（如 setTimeout 抖动），避免所有请求在同一时刻涌向后端。
- **降级与容错**：当后端接口超时或返回错误时，前端展示友好的降级 UI（如骨架屏、上次缓存数据），避免用户不断重试。
- **静态资源与 API 分离**：确保静态资源（图片、CSS）使用 CDN，减少核心 API 的并发压力。
- **监控与快速重试**：实现指数退避的重试策略，防止雪崩时重试请求加剧问题。

---

### 总结
前端不能完全替代后端解决缓存问题，但通过**本地缓存、请求合并、参数校验、降级策略**等手段，可以在客户端层面减轻后端压力，提升用户体验。后端仍需配合布隆过滤器、互斥锁、随机过期时间等经典方案。

24. 如何实现一个支持过期策略的前端缓存类？需要支持LRU和TTL两种策略。
以下实现一个支持 LRU（最近最少使用）淘汰策略和 TTL（生存时间）过期策略的前端缓存类。利用 `Map` 的插入顺序特性实现 LRU，每个键对应的值包含过期时间戳。

```javascript
class ExpiringLRUCache {
  /**
   * @param {number} maxSize - 最大缓存数量
   * @param {number} defaultTTL - 默认生存时间（毫秒）
   */
  constructor(maxSize = 100, defaultTTL = 60000) {
    this.maxSize = maxSize;
    this.defaultTTL = defaultTTL;
    this.cache = new Map(); // key -> { value, expire }
  }

  // 当前时间戳（毫秒）
  _now() {
    return Date.now();
  }

  // 检查键是否过期，过期则删除并返回 true
  _isExpired(key) {
    const entry = this.cache.get(key);
    if (!entry) return true;
    if (entry.expire < this._now()) {
      this.cache.delete(key);
      return true;
    }
    return false;
  }

  // 淘汰最久未使用的键（Map 的第一个键）
  _evict() {
    if (this.cache.size >= this.maxSize) {
      const oldestKey = this.cache.keys().next().value;
      this.cache.delete(oldestKey);
    }
  }

  /**
   * 获取缓存值，若不存在或已过期返回 undefined
   * 同时将该键更新为最新使用（LRU）
   */
  get(key) {
    if (!this.cache.has(key)) return undefined;
    if (this._isExpired(key)) return undefined;

    // 将当前键重新插入到 Map 末尾，表示最近使用
    const entry = this.cache.get(key);
    this.cache.delete(key);
    this.cache.set(key, entry);
    return entry.value;
  }

  /**
   * 设置缓存值，可指定 ttl（毫秒），默认使用构造时的 defaultTTL
   * 若缓存已满，会触发淘汰
   */
  set(key, value, ttl = this.defaultTTL) {
    // 若键已存在，先删除以更新顺序
    if (this.cache.has(key)) {
      this.cache.delete(key);
    }

    // 检查容量并淘汰
    if (this.cache.size >= this.maxSize) {
      this._evict();
    }

    const expire = this._now() + ttl;
    this.cache.set(key, { value, expire });
  }

  /** 删除指定键 */
  delete(key) {
    this.cache.delete(key);
  }

  /** 清空缓存 */
  clear() {
    this.cache.clear();
  }

  /** 当前缓存数量 */
  size() {
    return this.cache.size;
  }

  /** 手动清理所有过期键 */
  prune() {
    for (const key of this.cache.keys()) {
      this._isExpired(key); // 会自动删除过期键
    }
  }
}
```

### 使用示例
```javascript
const cache = new ExpiringLRUCache(3, 5000); // 最多存3个，默认TTL 5秒

cache.set('a', 1);
cache.set('b', 2, 10000); // 单独指定10秒过期
cache.set('c', 3);

console.log(cache.get('a')); // 1，同时 a 变成最新

cache.set('d', 4); // 容量满，淘汰最久未使用的（此时最久是 b？注意顺序：经过get后，a最新，b最旧？实际顺序：最初插入 a,b,c，然后get a 使 a 变成最新，所以顺序为 b,c,a。淘汰 b）
console.log(cache.get('b')); // undefined（已被淘汰）

setTimeout(() => {
  console.log(cache.get('a')); // 5秒后 a 过期，返回 undefined
}, 6000);
```

### 策略说明
- **LRU**：通过 `Map` 的插入顺序实现，每次 `get` 或 `set` 都将该键重新插入末尾，淘汰时删除第一个键。
- **TTL**：每个键存储过期时间戳，在 `get` 时检查，过期则删除并视为不存在。
- **淘汰与过期结合**：当缓存满时直接淘汰最老的键（可能已过期，但无需特殊处理，因为已过期键也会被淘汰）。若希望优先清理过期键，可在 `_evict` 中增加遍历检查，但会牺牲一定性能。

25. Rollup和Webpack的区别是什么？什么场景下选择Rollup？
# Rollup 和 Webpack 的区别

## 核心定位差异

**Webpack**
- 定位：全能型模块打包工具
- 专注：应用程序（Application）打包
- 特点：功能丰富、生态完善

**Rollup**
- 定位：ES Module 打包工具
- 专注：JavaScript 库（Library）打包
- 特点：输出简洁、Tree-shaking 效果更好

## 主要区别

### 1. **Tree-shaking 效果**
- **Rollup**：基于 ES6 模块的静态分析，Tree-shaking 更彻底，输出代码更简洁
- **Webpack**：也支持 Tree-shaking，但处理 CommonJS 模块时效果较差，可能产生较多冗余代码

### 2. **输出代码质量**
- **Rollup**：输出代码接近手写，可读性强，体积更小，适合库开发
- **Webpack**：会注入较多运行时代码（如模块加载器），代码相对冗长

### 3. **代码分割**
- **Rollup**：代码分割能力相对较弱（虽然也支持）
- **Webpack**：强大的代码分割能力，支持动态导入、按需加载

### 4. **资源处理**
- **Rollup**：主要处理 JavaScript，对其他资源（图片、CSS）需要插件，但支持相对有限
- **Webpack**：内置强大的资源处理能力，可以处理各种类型文件

### 5. **HMR（热模块替换）**
- **Rollup**：HMR 支持较弱
- **Webpack**：原生支持 HMR，开发体验好

## 选择 Rollup 的场景

### ✅ 适合使用 Rollup

1. **开发 JavaScript 库/组件库**
   - 需要发布到 npm 供他人使用
   - 追求输出代码的简洁和可读性
   - 例如：Vue、React、Lodash 等库都使用 Rollup

2. **纯 ES6 模块项目**
   - 项目代码完全使用 ES6 模块
   - 不需要复杂的代码分割

3. **追求极致的包体积**
   - 需要最优的 Tree-shaking
   - 对输出文件大小有严格要求

4. **输出多种模块格式**
   - 需要同时输出 ES、CJS、UMD 等多种格式
   - Rollup 配置更简单直观

### ❌ 不适合使用 Rollup

1. **复杂的 Web 应用**
   - 需要代码分割、懒加载
   - 有大量静态资源（图片、字体、CSS）

2. **需要强大的开发体验**
   - 依赖 HMR
   - 需要完善的开发服务器

3. **依赖大量 CommonJS 模块**
   - 项目中有很多 npm 包使用 CommonJS
   - Rollup 处理 CommonJS 不如 Webpack 顺畅

## 实际案例

```javascript
// Rollup 配置示例（库开发）
export default {
  input: 'src/index.js',
  output: [
    { file: 'dist/bundle.cjs.js', format: 'cjs' },
    { file: 'dist/bundle.esm.js', format: 'es' },
    { file: 'dist/bundle.umd.js', format: 'umd', name: 'MyLib' }
  ],
  external: ['react', 'lodash'], // 外部依赖不打包
  plugins: [babel(), resolve()]
}
```

## 总结

**简单记忆法则**：
- 开发**库** → 选 Rollup
- 开发**应用** → 选 Webpack（或 Vite）

当然，现代工具如 **Vite** 结合了两者优势：开发时使用原生 ESM，生产构建使用 Rollup，是目前的流行趋势。

# 什么是 SWC？

**SWC**（Speedy Web Compiler）是一个用 **Rust** 编写的超快速 JavaScript/TypeScript 编译器和打包工具，可以作为 Babel 的替代品。

## SWC 的核心功能

1. **代码转译**：将 ES6+ 代码转换为向下兼容的 JavaScript
2. **代码压缩**：替代 Terser 进行代码压缩
3. **打包**：提供类似 Webpack 的打包能力（spack）
4. **TypeScript 编译**：直接编译 TypeScript

---

## SWC 和 Babel 的区别

### 1. **实现语言**
- **Babel**：用 JavaScript 编写
- **SWC**：用 Rust 编写

### 2. **性能**
- **Babel**：单线程，速度较慢
- **SWC**：多线程并行处理，速度快 **20-70 倍**

### 3. **生态成熟度**
- **Babel**：生态成熟，插件丰富（数千个插件）
- **SWC**：生态相对年轻，插件较少（但核心功能已完善）

### 4. **配置兼容性**
- **Babel**：配置标准，社区通用
- **SWC**：基本兼容 Babel 配置，但有些插件需要重写

### 5. **使用场景**
- **Babel**：需要复杂插件、自定义转换的项目
- **SWC**：追求编译速度、大型项目、现代框架

---

## 为什么 SWC 更快？

### 1. **编译型语言 vs 解释型语言**
```
Rust（编译为机器码）
  ↓
直接在 CPU 上运行，无需解释器
  ↓
速度极快

JavaScript（解释执行）
  ↓
需要 V8 引擎解释
  ↓
有额外的运行时开销
```

### 2. **多线程并行处理**
- **Babel**：JavaScript 单线程，只能串行处理文件
- **SWC**：Rust 原生支持多线程，可以并行编译多个文件

```
Babel:  [File1] → [File2] → [File3] → [File4]  (串行)

SWC:    [File1]
        [File2]  (并行处理)
        [File3]
        [File4]
```

### 3. **内存管理更高效**
- **Babel**：依赖 JavaScript GC（垃圾回收），有内存开销
- **SWC**：Rust 的所有权系统，零成本抽象，内存使用更高效

### 4. **零拷贝优化**
- SWC 在处理 AST（抽象语法树）时，尽量避免不必要的数据拷贝
- Babel 在 JS 中操作 AST 会产生更多中间对象

### 5. **更优化的算法**
- SWC 从零设计，采用了更现代的编译器架构
- Babel 由于历史原因，有一些遗留的性能瓶颈

```
SWC:    ~1 秒
```

### MPA（多页面应用）优缺点

   - 只加载当前页面所需资源
   - 不需要加载整个应用框架

3. **页面独立性强**
   - 各页面相互独立，互不影响
   - 某个页面出错不影响其他页面

4. **开发简单**
   - 技术栈要求低
   - 适合多人协作，按页面分工

5. **浏览器兼容性好**
   - 不依赖复杂的前端框架
   - 降级友好

#### ❌ 缺点

1. **页面切换体验差**
   - 每次跳转都要重新加载
   - 白屏时间长，用户体验不流畅

2. **资源重复加载**
   - 公共资源（CSS、JS）每次都要重新下载
   - 浪费带宽

3. **状态难以保持**
   - 页面间共享状态需要依赖 Cookie、LocalStorage
   - 数据传递不方便

4. **服务器压力大**
   - 每次请求都要返回完整 HTML
   - 并发量大时服务器负担重

   - 类似原生应用的体验

2. **前后端分离**

   - 后端只提供 API

3. **资源复用**
   - 公共资源只加载一次
   - 减少网络请求

4. **组件化开发**
   - 代码复用性高
   - 维护成本低

5. **支持离线缓存**
   - 可以使用 Service Worker
   - 适合 PWA 应用

#### ❌ 缺点

   - 需要加载整个应用框架
   - 打包体积大

## 一、数据结构设计 —— 支撑海量单元格与高效查找

**目标**：支持 10k+ 行 × 50+ 列的表格，内存占用可控，增删改查、公式依赖、样式隔离等操作都需高效。

### 1. 核心存储模型：列式稀疏映射（Column‑Oriented Sparse Map）

- 不用二维数组（`Array[10000][50]`），因为绝大多数单元格是空的，会浪费内存。
- 采用 **“列主键”的嵌套 Map**：
  ```ts
  type RowIndex = number;
  type ColIndex = number;

  const cellStore: Map<ColIndex, Map<RowIndex, Cell>> = new Map();
  ```
  - 查询 `getCell(row, col)`：`cellStore.get(col)?.get(row)`
  - 遍历某一列的所有非空单元格：直接迭代该列的 Map，性能极优
  - 插入/删除只需操作对应的列 Map，不会产生大量空槽位

### 2. 单元格对象 `Cell` 设计

每个单元格是一个不可变对象（便于撤销/重做时比较状态）：

```ts
interface Cell {
  id: string;               // `${row}:${col}`
  rawValue?: string | number | null; // 用户直接输入的值
  formula?: string;         // 如 "=SUM(A1:A10)"
  computedValue?: any;      // 公式计算结果（缓存）
  style?: CellStyle;        // 行内样式，只存与默认不同的属性
  format?: CellFormat;      // 数字格式、对齐等
  dependents?: Set<string>; // 依赖本单元格的其他单元格ID（反向索引）
  // ... 其他元数据
}
```

**为什么不可变**？撤销/重做时可以直接存储命令的前后快照，也可配合 Immutable.js 或 Immer 做高效 diff。

### 3. 辅助索引结构

- **依赖图（Dependency Graph）**：单独维护一个有向图，key 为单元格 ID，value 为直接依赖它的所有单元格 ID。用于公式的增量更新。
- **合并单元格**：单独存为一个映射 `mergeCellMap: Map<string, MergeInfo>`，键是左上角单元格 ID，值为跨几行几列。
- **行列尺寸**：`rowHeights: Map<number, number>` 和 `colWidths: Map<number, number>`，只存非默认行高/列宽。

### 4. 撤销/重做栈

采用**命令模式（Command Pattern）**，每个操作对应一个命令对象：

```ts
interface Command {
  redo(): void;
  undo(): void;
  // 可附加元数据，如是否影响视图、是否影响协同等
}
```

例如 `EditCellCommand` 持有 `row, col, oldCell, newCell`。撤销/重做时直接替换 `cellStore` 中对应的单元格。**优点**：与协同操作统一，本地操作和远程操作都可包装成命令，统一进入栈。

## 二、大量 DOM 节点的性能优化 —— 虚拟滚动 + Canvas 混合渲染

**目标**：流畅渲染 10k+ 行，即使同时显示公式计算动画也不卡顿。

### 1. 首选方案：**Canvas 绘制表格主体 + 浮层 DOM 编辑器**

- **原理**：表格的网格、文字、背景色等全部用 Canvas 绘制，完全不产生单元格 DOM 元素。
- **交互**：监听 canvas 的 `mousedown`、`mousemove` 等事件，通过坐标反算行/列索引；双击单元格时在对应位置绝对定位一个 `input` 或 `div` 作为编辑器（DOM 浮层）。
- **优点**：无论多少行，DOM 节点数恒定（1个canvas + 极少数浮层），性能极好，滚动流畅。
- **缺点**：手动处理选区、拖拽填充柄等交互较复杂。但现代 Web Excel（如腾讯文档、金山文档）大多采用此方案。

### 2. 备选方案：**虚拟滚动（Virtual Scrolling）**

- 如果团队对 Canvas 经验不足，可使用成熟的虚拟表格库（如 `react-window`、`ag-grid`）只渲染可视区域的行列。
- **优化点**：
  - 行高/列高缓存，快速计算滚动偏移
  - 单元格内容使用 `will-change: transform` 开启硬件加速
  - 延迟渲染非首屏公式（可视区域外的公式不立即计算）
- 但纯 DOM 虚拟滚动在 10000+ 行且每行列数较多时，仍可能因大量包裹元素导致内存占用偏高，建议优先考虑 Canvas。

### 3. 其他通用优化

- **节流/防抖**：滚动时暂停复杂计算，停止滚动 100ms 后再更新 canvas。
- **离屏 Canvas**：将静态网格（边框、背景色）绘制在离屏 canvas，只更新变动区域的文字内容。
- **Web Worker 计算**：公式计算移至 Worker，避免阻塞主线程绘制。

## 三、公式计算引擎 —— 依赖图 + 增量计算 + 缓存

**目标**：支持类似 Excel 的公式（SUM, IF, VLOOKUP 等），更新一个单元格后自动级联更新所有依赖，并检测循环引用。

### 1. 解析与编译

- **词法/语法分析**：使用成熟的公式解析库（如 `hot-formula-parser`、`formulajs`），将公式字符串转为 **抽象语法树（AST）**。
- **函数库**：内置常用数学、统计、查找函数，支持自定义扩展。
- **范围引用**：例如 `A1:A10` 展开为一组具体的单元格 ID。

### 2. 依赖图管理

- 每个单元格初次设置公式时，解析 AST 提取所有引用的单元格 ID（**直接依赖**）。
- 维护两个映射：
  - `dependencies: Map<CellId, Set<CellId>>`  —— A 依赖 B（B 变化影响 A）
  - `dependents: Map<CellId, Set<CellId>>`   —— 反向索引（B 被哪些单元格依赖）
- **更新策略**：当单元格 B 的值变化时：
  1. 从 `dependents.get(B)` 获取所有直接依赖 B 的单元格集合。
  2. 将这些单元格标记为“脏”（dirty），并递归标记它们的依赖。
  3. 按拓扑顺序重新计算（通常采用队列，一层层清理脏标记）。
  4. 如果计算中再次遇到尚未计算的依赖，则继续等待——天然满足依赖优先。

### 3. 循环引用检测

- 在添加/修改公式时，使用 **DFS 检测有向图是否有环**。
- 若发现循环，阻止应用公式并提示用户。
- 也可以采用 **染色法** 或维护每个单元格的访问状态。

### 4. 计算缓存与惰性求值

- `computedValue` 字段缓存最近一次计算结果。
- 非可视区域（滚动不可见）的公式不参与立即计算，当用户滚动到附近时再计算并渲染。
- 考虑使用 **增量计算引擎**（类似 React 的 memo）：只重计算脏路径上的单元格。

## 四、多人协同与冲突解决 —— OT 或 CRDT 的选型

**目标**：多用户同时编辑同一张表格，最终所有客户端状态一致，不丢操作，不卡死。

### 1. 操作定义

所有本地修改都封装成 **协同操作（Op）**，例如：

```ts
type Op = 
  | { type: 'edit'; row: number; col: number; newCell: Cell; oldCell: Cell }
  | { type: 'insertRow'; index: number; count: number }
  | { type: 'deleteCol'; index: number }
  | { type: 'mergeCells'; startRow; startCol; rowSpan; colSpan }
  // ... 等
```

每个 Op 必须有**幂等性**，能够在任何顺序下应用后得到一致结果（需要协同算法保证）。

### 2. 协同算法选型

#### 方案 A：基于 CRDT（推荐，实现相对简单）

- **原则**：每个数据节点自带冲突解决规则，无需中心服务器进行复杂转换。
- 对于表格，可以将每个单元格建模为 **LWW（Last Write Wins）Register**，即每个单元格保存带时间戳（或向量时钟）的值，冲突时取最新的写入。
- 行/列的插入删除可使用 **Yjs** 这类成熟的 CRDT 库，它们将连续结构（如数组）转换为可并发插入的有序列表。
- **优点**：无中心瓶颈，离线编辑友好，冲突自动合并。
- **缺点**：需要集成 CRDT 运行时，数据结构可能膨胀（需存储墓碑等）。

#### 方案 B：基于 OT（Operation Transformation）

- **原理**：客户端发出 Op，服务端负责将并发的 Op 进行转换（transform），确保每个客户端以相同顺序应用 Op。
- 在表格场景，难点在于 **行列移动、删除时如何转换引用位置的 Op**。例如用户 A 删除了第 5 行，同时用户 B 在第 6 行编辑单元格，转换后 B 的编辑应该作用于新的第 5 行。
- **优势**：操作语义清晰，最终状态精确可控，Google Docs 早期使用此方案。
- **劣势**：实现复杂，需要针对每种操作类型编写转换函数，且必须满足交换律（TP1/TP2 性质）。

**建议**：在面试中可回答“采用 CRDT 方案，使用 Yjs 的 `Y.Array` 表示行列，`Y.Map` 表示每个单元格的属性，利用其内置的冲突解决机制”。这既体现了对前沿方案的了解，又避免了过度设计 OT 转换的繁琐细节。

### 3. 架构细节

- **通信层**：WebSocket 长连接，每个 Op 附加 **向量时钟（Version Vector）** 或 **Lamport 时间戳**，用于检测因果顺序。
- **服务端**：若使用 CRDT，服务端仅做广播与持久化；若使用 OT，服务端需做操作转换与广播。
- **本地乐观更新**：用户操作后立即应用 Op 到本地数据（并触发 UI 更新），同时将 Op 加入待发送队列；收到服务端广播时，若该 Op 版本高于本地，则应用它。
- **冲突标记**：当同一个单元格被两个用户几乎同时编辑时，可通过 UI 提示“内容已合并”，或使用批注形式展示冲突（类似 Google Sheets）。

## 一、整体系统架构 —— 微服务 + 无状态 + 区域化部署

**核心理念**：将业务能力抽象为独立的微服务，通过API Gateway统一暴露，支持**按区域（Region）水平扩展**，数据库层做读写分离与分片。

### 1. 微服务划分

| 服务           | 职责                                                                 |
| -------------- | -------------------------------------------------------------------- |
| **商品服务**   | 商品SPU/SKU管理，多语言属性存储，库存，类目                          |
| **订单服务**   | 订单生命周期，购物车，结算                                           |
| **用户服务**   | 账户、地址簿（多格式）、偏好设置（语言/货币/时区）                 |
| **支付服务**   | 统一支付网关，对接不同地区支付网关（Stripe、PayPal、Alipay、Boleto）|
| **物流服务**   | 运费计算、承运商对接（UPS、FedEx、国内快递）、轨迹查询               |
| **价格/汇率服务** | 基础价格存储（基准货币），实时汇率转换，定价规则                   |
| **本地化服务** | 文案翻译、格式配置、法律法规、地区屏蔽                               |
| **CMS/内容服务** | 多语言页面内容（富文本、SEO元数据）                                 |

**部署策略**：
- **主数据中心**：部署核心业务服务及数据库。
- **边缘区域节点**：对于大流量地区（美、欧、东南亚），可部署**全功能边缘集群**（包括商品、价格、用户等），通过**数据同步**（例如Kafka）实现最终一致性。
- **静态资源**：全球CDN分发（图片、JS/CSS、翻译JSON）。

## 二、多语言、多货币、多时区 —— 分层实现

### 1. 多语言（i18n）

**数据层**：
- **结构化数据**（商品名、描述）：数据库表设计为 `product_i18n`，字段包括 `locale`, `title`, `description` 等。通过 `locale` 过滤。
- **非结构化内容**（CMS页面）：使用**无头CMS**（如Contentful、Strapi），每个内容项关联多个语言版本，API返回时根据 `Accept-Language` 或用户偏好字段过滤。

**服务层**：
- 用户注册时选择语言，未登录则通过 `Accept-Language` 头部检测，并存储在会话中。
- 所有API请求携带 `Accept-Language` 或 `X-Locale` 头部，后端据此返回对应语言数据。

**前端层**：
- 使用国际化框架（i18next、Vue I18n）管理文案，翻译文件按语言拆分并按需加载（`en.json`, `fr.json`），打包时通过 CDN 发布。
- 路由策略：推荐**子目录方案**（`example.com/en/products`、`example.com/fr/produits`），对SEO最友好。也可子域名（`en.example.com`），但子目录更易维护。

### 2. 多货币

**价格存储**：
- 所有价格统一以**基准货币**（如USD）存储，单位为最小货币单位（美分）。
- 需要冻结价格的场景（已下单）直接存储**最终结算货币及金额**。

**汇率获取**：
- 第三方服务（Open Exchange Rates、Fixer.io），**每隔10分钟**拉取一次汇率，存入Redis（key: `exchange_rate:USD:EUR`），设置过期时间。
- 提供统一汇率API，供商品展示、结算时调用。

**价格展示流程**：
1. 商品服务返回基准货币价格。
2. 网关层或BFF（Backend For Frontend）根据用户选择的货币，调用汇率服务转换价格。
3. 转换后的价格**不缓存**（汇率实时变动），但可缓存商品详情（不含转换价格），动态替换价格标签。
4. 前端可定期轮询汇率（用户切换货币时），或由WebSocket推送汇率更新。

**时区**：
- 所有时间戳统一使用 **UTC** 存储在数据库。
- 后端返回时间戳时附带时区偏移（如 `2025-03-21T10:00:00Z`），前端根据浏览器时区或用户设置转换为本地时间。
- 服务器日志、调度任务统一基于UTC。

## 三、不同地区的支付与物流 —— 适配器模式

### 1. 支付服务设计

定义统一的 **支付网关接口**：

```java
interface PaymentGateway {
    PaymentResult charge(Order order, PaymentMethod method);
    RefundResult refund(Transaction transaction);
```

针对每个国家/地区的常用支付方式实现具体适配器：
- 欧美：Stripe、PayPal、Klarna
- 中国：支付宝、微信支付
- 巴西：Boleto、Pix
- 东南亚：本地网银、DANA

**路由策略**：
- 订单结算时，根据收货地址（国家）自动筛选支持的支付方式列表，前端展示对应的图标及表单。
- 支付网关的选择在运行时根据**支付方式ID**映射到具体适配器。

### 2. 物流服务设计

类似支付，定义统一的 **物流承运商接口**：
- 运费计算
- 下单面单
- 轨迹查询

针对不同地区接入不同服务商：
- 国际：UPS、FedEx、DHL
- 美国：USPS
- 中国：顺丰、四通一达

**关键点**：
- 运费模板支持**国家/地区层级**，可基于重量、体积、订单金额设置规则。
- 物流方式显示给用户时需本地化（名称、预计时效）。

## 四、SEO 多语言/多地区优化

**原则**：为不同语言/地区的用户提供独立且明确的URL，避免重复内容。

### 1. URL 结构

采用**子目录+语言代码**（可能包含国家代码）：
```
example.com/en-us/products/iphone
example.com/en-gb/products/iphone
example.com/fr-fr/produits/iphone
```
使用 `hreflang` 标签告诉搜索引擎各语言页面的对应关系：
```html
<link rel="alternate" hreflang="en-us" href="https://example.com/en-us/products/iphone" />
<link rel="alternate" hreflang="en-gb" href="https://example.com/en-gb/products/iphone" />
<link rel="alternate" hreflang="fr-fr" href="https://example.com/fr-fr/produits/iphone" />
```

### 2. 服务端渲染（SSR）或静态生成（SSG）

- 对于电商网站，绝大多数页面（商品详情、列表页）适合**增量静态生成（ISR）**，兼顾SEO与实时库存。
- 动态内容（购物车、个人中心）采用客户端渲染或CSR。
- 使用Next.js/Nuxt.js框架，通过`getStaticPaths`生成所有语言/地区的静态页面，并配合CDN缓存。

### 3. 站点地图

为**每个语言版本生成独立的站点地图**，并汇总到主站点地图中提交Google Search Console。站点地图中的URL需包含语言目录。

### 4. 规范化与避免重复

- 如果不同地区商品完全相同，可使用`rel="canonical"`指向主版本（如英语国际版）。
- 禁止非规范URL（如带跟踪参数）被索引。

## 五、本地化 —— 不只是翻译

### 1. 文化适配
- **颜色/图片**：某些颜色在不同国家有不同含义，需针对地区替换素材。
- **节日营销**：根据用户所在地显示相应节日主题。
- **敏感词过滤**：部分词汇在某些地区违法或忌讳。

### 2. 格式规范
- **日期**：MM/DD/YYYY（美国）、DD/MM/YYYY（欧洲）。
- **数字**：千分位分隔符（1,000.00 vs 1.000,00）。
- **地址**：每个国家地址字段不同（邮编格式、州/省字段），前端动态渲染地址表单。

### 3. 法律合规
- **GDPR**（欧盟）：Cookie 弹窗、数据导出/删除功能。
- **CCPA**（加州）：隐私政策、不出售个人信息按钮。
- **税务**：不同国家增值税（VAT）计算，订单金额含税分离。

**实现方案**：
- 建立 **地区配置中心**（如数据库表 `region_config`），存储每个国家的本地化参数：语言、货币、日期格式、地址模板、法律文本ID等。
- 前端根据用户所在国家动态加载对应配置。

## 六、汇率实时变化 —— 策略与性能

**挑战**：汇率每分钟可能变化，但商品展示价格频繁查询汇率会给汇率服务带来压力。

### 1. 缓存策略
- **两级缓存**：本地进程缓存（Caffeine/Guava）+ Redis。
- **更新频率**：每5分钟从第三方拉取一次汇率，更新Redis。
- **兜底方案**：若汇率服务不可用，使用上次缓存汇率，并标记为“估算”。

### 2. 显示与结算分离
- **显示价格**：使用最新汇率转换，仅作参考。
- **结算价格**：用户进入结算页时锁定汇率，并存入订单快照，避免支付时汇率变化导致金额不符。

### 3. 性能优化
- 商品列表页中价格转换建议在**BFF层批量处理**：一次性将多个商品价格批量转换，减少汇率服务调用次数。
- 对热门商品可缓存转换后价格（短时间），但需设置合理的TTL。

## 七、性能优化 —— 全球化部署

### 1. 静态资源加速
- **全球CDN**：图片、JS/CSS、字体文件等使用CDN，并开启**智能压缩**（Brotli）。
- **图片优化**：WebP 格式，动态调整尺寸（`?width=400`），使用CDN图片处理服务。

### 2. 动态内容加速
- **边缘计算**：使用 Cloudflare Workers 或 Lambda@Edge 根据用户地理位置**自动路由到最近的数据中心**，实现基于地理位置的DNS解析。
- **API网关**：部署在多区域的API网关，内部服务可通过**服务网格**进行跨区域调用，或数据同步至边缘节点。

### 3. 数据库与缓存
- **读写分离**：主库负责写入，从库负责复杂查询。
- **热点数据缓存**：商品详情、分类导航、汇率等使用Redis缓存，设置合理过期时间。
- **分库分表**：订单表按用户ID或时间分片，支持海量数据。

### 4. 前端性能
- **代码分割**：按路由懒加载，多语言包按需加载（用户仅下载当前语言）。
- **骨架屏**：提升首屏感知速度。
- **资源预加载**：预加载用户下一跳可能访问的页面（如商品详情页hover时）。

### 5. 异步化
- 非核心流程（如发送邮件、更新库存日志）使用**消息队列**（Kafka/RabbitMQ）异步处理。
- 订单创建时立即返回，后台异步扣减库存、计算物流、触发支付。

---

## 总结：全球化架构核心要点

1. **解耦**：语言、货币、支付、物流各自独立，通过配置驱动。
2. **无状态**：服务可水平扩展，用户上下文存储在分布式会话或JWT中。
3. **数据同步**：跨区域数据最终一致，关键数据（订单、库存）强一致需中心化。
4. **缓存分层**：CDN → 边缘节点 → Redis → 本地缓存 → DB。
5. **防御式设计**：汇率服务熔断、降级；支付网关切换；多语言容错。

以上方案已在多个亿级流量电商平台落地，既保证了**全球用户的流畅体验**，也满足了**各地区合规与业务差异**。在面试中，强调“**配置驱动+适配器模式**”是应对多地区多变需求的关键架构决策。
