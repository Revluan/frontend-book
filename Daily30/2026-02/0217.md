## JavaScript (7题)

1. JavaScript中的void运算符是什么？它有什么实际用途？
`void` 是一元运算符，它对给定的表达式求值，然后始终返回 `undefined`。无论表达式是什么，`void` 的结果都是 `undefined`。

### 语法
```javascript
void expression
void (expression)  // 括号可选，用于明确优先级
```

---

### 实际用途

#### 1. 获取 `undefined` 的安全方式
在 ES5 之前，`undefined` 是一个全局变量，且可以被赋值（如 `undefined = 42`），导致判断不可靠。`void 0` 是获得真正 `undefined` 的可靠方法。现在全局 `undefined` 已不可写，但在局部作用域仍可能被覆盖，`void 0` 依然安全。

```javascript
if (someVar === void 0) { // 判断是否为 undefined
  // ...
}
```

#### 2. 阻止 `javascript:` 伪协议的导航
常用于 `<a>` 标签的 `href` 属性，点击链接时不跳转页面，只执行 JavaScript 代码。`javascript:void(0)` 返回 `undefined`，浏览器不会加载新页面。

```html
<a href="javascript:void(0);" onclick="doSomething()">点击</a>
```
现代开发中更推荐使用事件监听并调用 `preventDefault()`，但遗留代码中仍常见。

#### 3. 作为立即执行函数表达式（IIFE）的前缀
防止函数声明被解析为函数定义，确保函数被当作表达式执行。

```javascript
void function() {
  console.log('立即执行');
}();
```
等同于 `(function(){ ... })()`，`void` 明确表示这是一个表达式。

#### 4. 箭头函数中直接返回 `undefined`
当需要箭头函数返回 `undefined` 时，可简写：

```javascript
const noop = () => void 0;       // 返回 undefined
const log = () => void console.log('hi'); // 执行 console.log 并返回 undefined
```

#### 5. 丢弃表达式的结果
如果你调用一个会返回值的函数，但你想忽略它并确保结果是 `undefined`（例如在赋值给变量时），可以用 `void`。

```javascript
const result = void (1 + 1); // result 为 undefined，不会得到 2
```

---

### 注意
`void` 优先级较高，例如 `void 2 + 3` 相当于 `(void 2) + 3` → `undefined + 3` → `NaN`。若要对整个表达式求值，需加括号：`void (2 + 3)`。

2. 什么是JavaScript的ArrayBuffer、SharedArrayBuffer、Atomics？它们如何支持多线程编程？
JavaScript 的 **`ArrayBuffer`**、**`SharedArrayBuffer`** 和 **`Atomics`** 共同提供了在 Web Workers 中进行多线程编程的基础，允许线程间高效共享内存和同步操作。

---

### 1. **`ArrayBuffer`**：二进制数据缓冲区
- 表示一个固定长度的原始二进制数据缓冲区，无法直接读写，必须通过视图（如 `Uint8Array`、`DataView`）来操作。
- 主要用于存储图像、文件、音频等二进制数据，以及作为 `SharedArrayBuffer` 的基础。
- **与多线程的关系**：`ArrayBuffer` 本身不能在多个 Worker 之间直接共享，传递时需要复制（结构化克隆），成本较高。

---

### 2. **`SharedArrayBuffer`**：共享内存
- 是 `ArrayBuffer` 的变体，可以在多个 Web Workers 和主线程之间**共享同一块内存**，无需复制数据。
- 每个 Worker 通过引用同一个 `SharedArrayBuffer` 对象，即可直接读写同一内存区域，极大提升数据传输效率。
- **安全限制**：由于 Spectre 漏洞，使用 `SharedArrayBuffer` 需要站点在 HTTP 响应头中设置 `Cross-Origin-Opener-Policy: same-origin` 和 `Cross-Origin-Embedder-Policy: require-corp`。

---

### 3. **`Atomics`**：原子操作与同步
- 一个静态对象，提供了一系列**原子操作**（如 `add`、`load`、`store`、`compareExchange`）和**同步原语**（`wait`、`notify`）。
- **原子性**：确保对 `SharedArrayBuffer` 的读写操作不会被其他线程中断，避免数据竞争。
- **同步**：`wait` 和 `notify` 允许线程在特定内存位置上等待或唤醒，实现线程间通信（类似于条件变量）。

---

### 如何支持多线程编程？

#### 步骤示例
1. **创建共享内存**：在主线程中创建 `SharedArrayBuffer`，并启动一个或多个 Worker。
   ```javascript
   // 主线程
   const sab = new SharedArrayBuffer(1024); // 1KB 共享内存
   const worker = new Worker('worker.js');
   worker.postMessage(sab); // 传递 SharedArrayBuffer 引用（无需复制）
   ```

2. **在 Worker 中操作共享内存**：通过 `TypedArray` 视图读写，并使用 `Atomics` 保证同步。
   ```javascript
   // worker.js
   self.onmessage = (e) => {
     const sab = e.data;
     const int32 = new Int32Array(sab);
     // 原子地将索引0的值加1
     Atomics.add(int32, 0, 1);
     // 原子地比较并交换
     Atomics.compareExchange(int32, 1, expected, newValue);
     // 等待索引2的值变为 0（阻塞线程）
     Atomics.wait(int32, 2, 0);
   };
   ```

3. **线程间同步**：使用 `Atomics.wait` 和 `Atomics.notify` 实现等待/唤醒机制。
   ```javascript
   // 线程A
   Atomics.store(int32, 0, 1);
   Atomics.notify(int32, 0, 1); // 唤醒等待在索引0上的一个线程

   // 线程B
   Atomics.wait(int32, 0, 0); // 如果索引0的值还是0，则阻塞直到被唤醒
   ```

---

### 总结
- **`SharedArrayBuffer`** 提供了多线程共享内存的能力。
- **`Atomics`** 提供了操作共享内存时的原子性和同步工具。
- 两者结合，使 JavaScript 能够实现高性能的多线程计算（如游戏、图像处理、数据分析），同时保证线程安全。

这种模型类似于其他语言（如 C++ 的 `std::atomic` 和共享内存），但被限制在 Web Workers 环境下，且需遵循安全头要求。

3. 手写实现一个支持过期时间的Map数据结构（带自动清理机制）。
以下是一个支持过期时间的 `Map` 实现，包含自动清理机制。每个键可单独设置 TTL（毫秒），未设置时使用默认值。内部通过 `Map` 存储值及其过期时间戳，结合惰性删除（在 `get`、`has` 等操作时检查）和定期清理（`setInterval`）确保过期键被及时移除。

```javascript
class ExpiringMap {
  /**
   * @param {number|null} defaultTTL 默认过期时间（毫秒），null 表示永不过期
   * @param {number} cleanupInterval 自动清理间隔（毫秒），设为 0 可禁用
   */
  constructor(defaultTTL = null, cleanupInterval = 60000) {
    this.defaultTTL = defaultTTL;
    this.map = new Map(); // 键 -> { value, expire: 时间戳或null }
    if (cleanupInterval > 0) {
      this.intervalId = setInterval(() => this.cleanup(), cleanupInterval);
    }
  }

  /**
   * 设置键值对，可指定 ttl 覆盖默认值
   * @param {any} key
   * @param {any} value
   * @param {number|null} ttl 过期时间（毫秒），null 表示永不过期
   */
  set(key, value, ttl = this.defaultTTL) {
    const expire = ttl !== null ? Date.now() + ttl : null;
    this.map.set(key, { value, expire });
    return this;
  }

  /**
   * 获取键对应的值，如果已过期则删除并返回 undefined
   */
  get(key) {
    const entry = this.map.get(key);
    if (!entry) return undefined;
    if (entry.expire !== null && entry.expire <= Date.now()) {
      this.map.delete(key);
      return undefined;
    }
    return entry.value;
  }

  /**
   * 检查键是否存在且未过期
   */
  has(key) {
    const entry = this.map.get(key);
    if (!entry) return false;
    if (entry.expire !== null && entry.expire <= Date.now()) {
      this.map.delete(key);
      return false;
    }
    return true;
  }

  /**
   * 删除指定键
   */
  delete(key) {
    return this.map.delete(key);
  }

  /**
   * 清空所有键
   */
  clear() {
    this.map.clear();
  }

  /**
   * 返回当前未过期键的数量（会触发一次清理）
   */
  get size() {
    this.cleanup();
    return this.map.size;
  }

  /**
   * 手动清理所有过期键
   */
  cleanup() {
    const now = Date.now();
    for (const [key, entry] of this.map) {
      if (entry.expire !== null && entry.expire <= now) {
        this.map.delete(key);
      }
    }
  }

  /**
   * 停止自动清理
   */
  stopAutoCleanup() {
    if (this.intervalId) {
      clearInterval(this.intervalId);
      this.intervalId = null;
    }
  }

  // 迭代器支持（自动跳过过期键）
  *keys() {
    const now = Date.now();
    for (const [key, entry] of this.map) {
      if (entry.expire !== null && entry.expire <= now) {
        this.map.delete(key);
        continue;
      }
      yield key;
    }
  }

  *values() {
    const now = Date.now();
    for (const [key, entry] of this.map) {
      if (entry.expire !== null && entry.expire <= now) {
        this.map.delete(key);
        continue;
      }
      yield entry.value;
    }
  }

  *entries() {
    const now = Date.now();
    for (const [key, entry] of this.map) {
      if (entry.expire !== null && entry.expire <= now) {
        this.map.delete(key);
        continue;
      }
      yield [key, entry.value];
    }
  }

  [Symbol.iterator]() {
    return this.entries();
  }

  forEach(callback, thisArg) {
    for (const [key, value] of this) {
      callback.call(thisArg, value, key, this);
    }
  }
}

// 使用示例
const cache = new ExpiringMap(5000, 1000); // 默认5秒过期，每秒清理一次
cache.set('a', 1);
cache.set('b', 2, 3000); // 3秒后过期
console.log(cache.get('a')); // 1
setTimeout(() => {
  console.log(cache.get('a')); // undefined（已过期）
  cache.stopAutoCleanup(); // 停止清理
}, 6000);
```

**设计要点**：
- **过期时间存储**：每个条目包含 `value` 和 `expire`（时间戳或 `null` 表示永不过期）。
- **惰性删除**：在 `get`、`has` 等操作时检查当前键是否过期，若过期则立即删除。
- **定期清理**：通过 `setInterval` 遍历所有键，删除过期条目，避免堆积。
- **迭代器安全**：遍历时也会检查并删除过期键，确保返回的键值对均有效。
- **可停止清理**：提供 `stopAutoCleanup()` 方法，用于组件卸载或不再需要时防止内存泄漏。

该实现平衡了实时性和性能，适用于前端缓存、临时数据存储等场景。

4. JavaScript中的new.target是什么？它有什么使用场景？
`new.target` 是一个元属性，在函数或构造函数内部使用，用于检测该函数是否通过 `new` 运算符被调用。如果通过 `new` 调用，`new.target` 指向被调用的构造函数（或类）；否则为 `undefined`。

### 使用场景

#### 1. 强制使用 `new` 调用构造函数
确保构造函数必须用 `new` 实例化，否则抛出错误或自动处理。
```javascript
function Person(name) {
  if (!new.target) {
    throw new Error('Person must be called with new');
  }
  this.name = name;
}
// new Person('Alice')  ✅
// Person('Alice')       ❌ 抛出错误
```

#### 2. 实现抽象基类
在基类中阻止直接实例化，要求必须继承。
```javascript
class Shape {
  constructor() {
    if (new.target === Shape) {
      throw new TypeError('Cannot construct Shape instances directly');
    }
  }
}
class Circle extends Shape {}
new Shape();  // 抛出错误
new Circle(); // 正常
```

#### 3. 判断子类实例化
在基类中根据 `new.target` 执行不同逻辑，或获取实际构造函数的名称。
```javascript
class Parent {
  constructor() {
    console.log(`Instance created by ${new.target.name}`);
  }
}
class Child extends Parent {}
new Parent(); // "Instance created by Parent"
new Child();  // "Instance created by Child"
```

#### 4. 实现工厂函数兼容性
在工厂函数中，如果被误用为构造函数，可以自动返回正确实例。
```javascript
function createInstance(ctor, ...args) {
  if (!new.target) {
    return new createInstance(ctor, ...args);
  }
  this.instance = new ctor(...args);
}
```

`new.target` 在类构造函数和方法中同样有效，为元编程提供了便利。

5. 什么是可选catch绑定？try-catch中的error参数可以省略吗？
**可选 catch 绑定**是 ES2019（ES10）引入的语法特性，允许在 `try-catch` 语句中省略 `catch` 的参数（即错误对象），当不需要使用错误信息时，可以简化代码。

### 用法对比
- **传统写法**（必须提供参数）：
  ```javascript
  try {
    // 可能抛出错误的代码
  } catch (error) {
    // 即使不使用 error，也必须写
  }
  ```
- **可选 catch 绑定**（ES2019+）：
  ```javascript
  try {
    // 可能抛出错误的代码
  } catch {
    // 无需声明参数，直接处理
  }
  ```

### 回答第二个问题
是的，从 ES2019 开始，`try-catch` 中的 `error` 参数**可以省略**。这意味着当你不需要访问错误对象时（例如只需捕获异常但不关心具体错误信息），可以省略括号和参数，使代码更简洁。不过，在旧版 JavaScript 中，必须提供参数（即使未使用），否则会抛出语法错误。

**兼容性**：现代浏览器和 Node.js 12+ 均已支持此特性。

6. JavaScript中的逗号运算符如何工作？它的优先级是怎样的？
逗号运算符（`,`）是 JavaScript 中优先级最低的运算符，它从左到右依次计算每个操作数，并返回最后一个操作数的值。

### 工作原理
语法形式为：`表达式1, 表达式2, ..., 表达式N`  
- 按顺序计算每个表达式。  
- 最终结果为最后一个表达式 `表达式N` 的值。  

**示例**：
```javascript
let x = (1, 2, 3); // 先计算1，再计算2，最后计算3，x 被赋值为 3
console.log(x); // 3
```

### 常见用途
- **在 `for` 循环中同时更新多个变量**：
  ```javascript
  for (let i = 0, j = 10; i < j; i++, j--) { ... }
  ```
- **在需要表达式的上下文中执行多个操作**（如箭头函数体简写）：
  ```javascript
  const foo = () => (console.log('hi'), 42); // 打印并返回 42
  ```

### 优先级
逗号运算符的优先级**最低**，甚至低于赋值运算符（`=`）。因此，在没有括号的情况下，它的行为可能出乎意料。

**示例陷阱**：
```javascript
let a = 1, 2, 3;    // 语法错误，因为逗号在变量声明中是分隔符
let b = (1, 2, 3);  // 正确，b = 3

let c = 5, d = 6;   // 这是变量声明，不是逗号运算符
let e = (5, 6);     // e = 6

// 赋值优先级高于逗号
let x = 1, 2;       // 语法错误：因为解析为 let x = 1; 然后单独的 2 非法
let y = (1, 2);     // y = 2
```

### 与分隔符的区别
- **逗号运算符**：出现在表达式中，例如 `(a, b)`。
- **逗号分隔符**：用于分隔变量声明、函数参数、数组/对象字面量等，例如 `let a = 1, b = 2;` 或 `fn(a, b)`。此时逗号不是运算符，而是语法符号。

**总结**：逗号运算符是“多表达式合一”的工具，但因其优先级低，使用时务必添加括号明确意图。

## React (7题)

8. React中的legacy模式、blocking模式、concurrent模式有什么区别？
React 的三种模式（legacy、blocking、concurrent）是 React 18 引入的渲染分层概念，用于逐步迁移到并发渲染。

### 1. Legacy 模式（传统模式）
- **渲染方式**：同步、不可中断的渲染。React 17 及之前默认使用 `ReactDOM.render`。
- **特点**：渲染过程一旦开始就无法暂停，可能导致主线程长时间阻塞，用户交互响应变慢。
- **支持特性**：不支持并发特性（如 `useTransition`、`Suspense` 数据获取等）。

### 2. Concurrent 模式（并发模式）
- **渲染方式**：可中断、优先级可调的异步渲染。通过 `ReactDOM.createRoot` 启用（React 18 默认）。
- **特点**：渲染过程中可被更高优先级的任务（如用户输入）打断，完成后恢复，提升应用响应性。
- **支持特性**：完整支持并发特性，包括 `startTransition`、`useDeferredValue`、Suspense 数据获取、选择性水合等。

### 3. Blocking 模式（过渡模式）
- **渲染方式**：介于 legacy 和 concurrent 之间，通过 `ReactDOM.createBlockingRoot` 启用（仅用于逐步迁移）。
- **特点**：启用了部分并发特性（如 `Suspense`、自动批处理），但渲染仍是不可中断的（与 legacy 类似），作为从 legacy 到 concurrent 的桥梁，便于代码兼容。
- **适用场景**：需要逐步采用并发特性但又不想立即完全迁移的应用。

**总结**：legacy 是旧版同步渲染；concurrent 是新一代可中断并发渲染；blocking 是过渡版本，启用了部分新特性但渲染仍不可中断。新应用推荐直接使用 concurrent 模式。

9. 什么是React的lanes模型？它如何管理更新优先级？
**Lanes（车道）模型** 是 React 内部用于管理更新优先级的机制，它在 React 18 的并发渲染中取代了之前的 `expirationTime` 模型。Lanes 使用**位掩码（bitmask）** 来表示不同的优先级通道，每个 lane 对应一个比特位，数值越小通常优先级越高（但具体由 React 内部定义）。

### 如何管理更新优先级？
1. **分配优先级**：每次更新（如 `setState`、事件处理）都会被分配到一个或多个 lane 上，例如：
   - `SyncLane`：最高优先级，用于同步更新。
   - `InputContinuousLane`：用户输入等连续事件。
   - `DefaultLane`：默认异步更新。
   - `IdleLane`：空闲时执行的更新。
2. **位运算操作**：React 通过位运算（如 `&`、`|`）快速比较和合并不同优先级的更新，决定当前要处理哪些 lane。
3. **调度渲染**：在并发渲染中，React 会从当前所有待处理的更新中选出**优先级最高**的 lane 进行工作，并且可中断当前任务去处理更高优先级的更新（如用户点击）。
4. **批处理**：多个相同 lane 的更新可以合并成一次渲染，减少不必要的重复工作。

Lanes 模型使 React 能更精细地控制并发任务，支持时间切片、选择性水合等特性，同时保证高优先级交互的及时响应。开发者通常无需直接操作 lanes，但理解它能帮助掌握 React 的并发行为。

10. React中的useEvent（实验性API）是什么？它解决了什么问题？
**useEvent**（曾用名 `useEffectEvent`）是一个实验性 React Hook，用于定义一个函数，该函数在多次渲染中保持**稳定的引用**，同时又能**访问最新的 props 和 state**。

### 它解决了什么问题？
- **稳定函数引用**：与 `useCallback` 不同，`useEvent` 返回的函数**永远不会改变**（即使依赖变化），因此可以安全地传递给子组件或用于 `useEffect` 的依赖数组，而不会引起不必要的重渲染或重复执行。
- **始终访问最新值**：尽管函数引用稳定，但它内部仍然可以读取到最新的 props 和 state（类似于普通函数），无需在依赖数组中声明它们。
- **解决 `useCallback` 的痛点**：使用 `useCallback` 时，如果依赖频繁变化，函数引用也随之变化，可能导致子组件重渲染或 `useEffect` 无限循环。`useEvent` 将“事件处理”逻辑与渲染隔离，让这类函数既稳定又保持最新。

### 示例
```jsx
const onConnect = useEvent(() => {
  console.log('当前用户：', userId); // userId 始终是最新的
});
useEffect(() => {
  // 无论 userId 如何变化，onConnect 引用不变，effect 不会重复运行
  someApi.on('connected', onConnect);
  return () => someApi.off('connected', onConnect);
}, []); // 依赖为空，但 onConnect 仍能访问最新 userId
```

### 注意事项
- 不能在组件的渲染阶段调用 `useEvent` 返回的函数（只能用于副作用或事件回调）。
- 该 Hook 目前仍处于 **实验阶段**（React 18.2 RFC），需使用实验性版本或在未来稳定版中才可用。

简单来说，`useEvent` 填补了稳定函数与最新数据访问之间的空白，让开发者可以更自然地编写事件处理逻辑，同时避免性能陷阱。

13. 什么是React的双缓冲技术？current树和workInProgress树的关系是什么？
React 的**双缓冲技术**是指在内存中同时维护两棵 Fiber 树：**current 树** 和 **workInProgress 树**，以实现高效、可中断的渲染更新。

### 两棵树的关系
- **current 树**：对应当前屏幕上显示的内容。当应用首次渲染完成后，Fiber 树就称为 current 树。
- **workInProgress 树**：在更新过程中，React 基于 current 树克隆出一棵新的 Fiber 树，所有更新工作（如调用 render 函数、协调子节点）都在这个 workInProgress 树上进行。它完全在内存中构建，与用户可见的 current 树隔离。

两棵树的节点通过 `alternate` 属性相互关联：
- `current.alternate` 指向 workInProgress 中对应的节点。
- `workInProgress.alternate` 指向 current 中对应的节点。

### 工作流程
1. **更新触发**：当状态变化时，React 开始在 workInProgress 树上执行渲染工作。
2. **构建新树**：React 遍历 workInProgress 树，计算变化，并可能中断（在并发模式下）或继续。
3. **提交阶段**：当 workInProgress 树完全构建完成，React 会将 current 指针指向 workInProgress 树，使其变为新的 current 树（即“双缓冲交换”）。此时新屏幕显示内容。
4. **下次更新**：旧的 current 树被保留用于后续复用（作为新的 workInProgress 树的基础），从而避免重复创建 Fiber 节点，提升性能。

### 优势
- **可中断渲染**：更新在 workInProgress 树上进行，即使中途被中断（如用户输入），current 树依然完整，屏幕上不会出现不一致的 UI。
- **高效复用**：通过 alternate 链接，React 可以复用节点，减少创建和垃圾回收开销。
- **并发特性基础**：这种设计支持时间切片、任务优先级等并发渲染机制。

简单来说，current 树是“当前版本”，workInProgress 树是“下一个版本”，两者通过 alternate 双向关联，通过指针切换实现平滑更新。

```jsx
// 渲染 <img src={imageSrc} ref={imgRef} onLoad={handleImageLoad} />
```

### 3.2 裁剪框交互
- 使用绝对定位的 `<div>` 作为裁剪框，通过 `useRef` 获取其 DOM 节点。
- 监听鼠标事件：`onMouseDown` 开始拖动（或调整大小），`onMouseMove` 更新坐标/尺寸，`onMouseUp` 结束。

### 3.3 计算裁剪区域（图片原始像素坐标）
- 获取图片原始宽高：`imgRef.current.naturalWidth/Height`
- 获取图片显示宽高：`imgRef.current.clientWidth/Height`

```jsx
const ctx = canvas.getContext('2d');

ctx.drawImage(
```

- **跨域**：如果图片来自外部 CDN，需设置 `crossOrigin="anonymous"` 且服务端允许跨域，否则 canvas 会被污染（无法导出）。

- **裁剪框约束**：禁止拖出图片可视区域，缩放时保持最小尺寸。
- **性能**：`mousemove` 事件中避免频繁重绘，可使用 `requestAnimationFrame` 节流。
- **移动端支持**：需适配触摸事件（`touchstart`/`touchmove`/`touchend`）。

15. Next.js中的unstable_cache和React的cache有什么区别？
`unstable_cache`（Next.js）和 `cache`（React）都是用于缓存数据或函数结果的机制，但它们在**作用域、生命周期和使用场景**上有本质区别。

| 特性 | React `cache` | Next.js `unstable_cache` |
|------|---------------|--------------------------|
| **所属框架** | React 内置（自 18 起实验性，19 稳定） | Next.js 专用（`next/cache` 或 `next` 导出） |
| **缓存范围** | **请求级内存缓存**：在同一个请求（服务端）或会话（客户端）内，对相同的参数只执行一次函数。 | **持久化缓存**：可跨请求缓存数据，例如写入文件系统或 Redis，支持基于标签的重新验证。 |
| **生命周期** | 与请求/组件生命周期绑定：服务器端请求结束时缓存清除，客户端页面刷新后丢失。 | 可配置 `revalidate` 时间或通过 `revalidateTag` 手动失效，缓存持久存储。 |
| **典型用途** | 在 React 服务端组件中避免重复的数据库查询或 API 请求（如两个组件依赖同一数据）。 | 缓存昂贵的计算、数据库查询结果，实现增量静态生成（ISR）或数据层的持久缓存。 |
| **API 签名** | `const cachedFn = cache(fn)`，返回的函数可根据参数缓存结果。 | `const getCachedData = unstable_cache(fn, keyParts?, options?)`，返回一个函数，执行后会持久缓存结果。 |
| **依赖跟踪** | 依赖参数自动进行浅比较。 | 需要显式提供 `keyParts` 来构建缓存键，并可指定 `tags` 用于重新验证。 |
| **稳定性** | React 19 中稳定（`cache` 已从 `experimental` 移入 `react`）。 | 名称含 `unstable`，API 未来可能调整，但已在生产广泛使用。 |

### 它们如何一起工作？
- React `cache` 通常用于**同一请求内**避免重复调用，例如在一个服务端组件树中多个地方请求同一用户数据，它会在内存中复用。
- Next.js `unstable_cache` 则用于**跨请求**缓存，例如将用户数据持久化，并设置 `revalidate` 或配合 `revalidateTag` 实现按需更新。

**示例**：  
```jsx
import { cache } from 'react';
import { unstable_cache } from 'next/cache';

// React cache：防止同一请求内重复请求
const getUser = cache(async (id) => {
  return db.user.findUnique({ where: { id } });
});

// Next.js unstable_cache：持久化缓存，并设置标签
const getCachedUser = unstable_cache(
  async (id) => getUser(id),   // 调用已缓存的 React 函数
  ['user', id],                // 缓存键
  { tags: [`user-${id}`], revalidate: 60 }
);
```

### 总结
- 使用 React `cache` 优化渲染期间的数据获取（请求级复用）。
- 使用 Next.js `unstable_cache` 实现持久化数据缓存和跨请求复用（如 ISR）。
- 两者可以嵌套结合，既获得请求内复用，又获得持久化能力。

16. 如何在Next.js中实现多主题切换？CSS变量和Tailwind如何配合使用？

## 1. 原理
- **CSS 变量**：在根元素（`:root`）定义一组主题颜色变量，在不同主题类（如 `.dark`）下覆盖这些变量。

- **主题切换**：通过 JavaScript 修改 `html` 或 `body` 的 `class`（或 `data-theme` 属性），触发 CSS 变量更新，界面颜色自动改变。

## 2. 实现步骤

### 2.1 定义主题 CSS 变量

```css
:root {

}

.dark {
```

```js
/** @type {import('tailwindcss').Config} */
module.exports = {

    extend: {
      colors: {
        background: 'var(--background)',
        foreground: 'var(--foreground)',
        primary: 'var(--primary)',
      },
    },
  },

}
```

现在可以在任何地方使用 Tailwind 类，如 `bg-background text-foreground`，它们会自动响应 CSS 变量变化。

### 2.3 创建主题切换组件

#### 使用 `next-themes` 库（推荐）

```jsx
import { useTheme } from 'next-themes'

export function ThemeToggle() {
  const { theme, setTheme } = useTheme()

      切换主题
    </button>

```

#### 手动实现（不使用库）
如果想自己控制，可以写一个客户端组件：

```jsx
'use client'
import { useEffect, useState } from 'react'

export function ThemeToggle() {
  const [theme, setTheme] = useState('light')

  useEffect(() => {
    const saved = localStorage.getItem('theme') || 'light'
    setTheme(saved)
    document.documentElement.classList.toggle('dark', saved === 'dark')
  }, [])

  const toggle = () => {
    const newTheme = theme === 'light' ? 'dark' : 'light'
    setTheme(newTheme)
    localStorage.setItem('theme', newTheme)
    document.documentElement.classList.toggle('dark', newTheme === 'dark')
  }

  return <button onClick={toggle}>切换主题</button>
}
```

注意手动实现需要处理 SSR 水合警告，可使用 `useEffect` 确保只在客户端运行。

17. Next.js的Turbopack是什么？它和Webpack有什么本质区别？
**Turbopack** 是 Next.js 推出的新一代打包工具，由 Webpack 的作者 Tobias Koppers 领导开发，使用 **Rust** 编写，旨在替代 Webpack 提供更快的开发体验，尤其在本地启动和热更新方面有数量级提升。

### 与 Webpack 的本质区别

| 维度 | Turbopack | Webpack |
|------|-----------|---------|
| **实现语言** | Rust（编译型，高性能） | JavaScript（解释型，受 Node.js 性能限制） |
| **架构设计** | 基于 **增量计算** 和 **函数式组合**，只重新计算变更部分 | 每次构建都遍历整个依赖图，即使小改动也要重新处理 |
| **缓存粒度** | 极细粒度的函数级别缓存，几乎无重复计算 | 粗粒度的模块级别缓存，仍需大量解析和转换 |
| **并发能力** | 原生利用多核 CPU，并行处理任务 | 通过 worker 池实现部分并行，受 JS 单线程限制 |
| **启动速度** | 毫秒级冷启动，得益于 Rust 编译和增量架构 | 秒级甚至十秒级启动，需要解析大量模块 |
| **热更新** | 基于函数的细粒度更新，极速响应 | 模块级热更新，复杂项目可能变慢 |
| **生态兼容** | 尚在发展中，支持大部分 Webpack loader/plugin 有过渡方案 | 成熟的生态系统，丰富的 loader 和 plugin |
| **目标场景** | 优先优化开发体验，为 Next.js 量身打造 | 通用打包工具，适用各种项目，但性能瓶颈明显 |

**核心区别**：Turbopack 通过 Rust 和增量计算从根本上改变了打包的底层模型，将性能放在首位，而 Webpack 因其 JavaScript 实现和历史设计，在大型项目中已出现性能瓶颈。

18. 如何在Next.js中实现内容安全策略（CSP）？nonce如何生成和使用？
在 Next.js 中实现内容安全策略（CSP）并使用 **nonce** 是一种常见的安全实践，它可以有效防止 XSS 攻击，同时允许必要的内联脚本执行。以下是具体实现方案。

---

## 1. CSP 与 nonce 简介
- **CSP** 通过 HTTP 头（`Content-Security-Policy`）限制页面可以加载的资源来源，例如 `script-src` 指定允许执行脚本的源。
- **nonce**（number used once）是一个**每个请求唯一**的随机字符串，用于在内联脚本或样式中标记为可信。在 CSP 头中通过 `'nonce-<base64>'` 指定，并在实际的 `<script nonce="...">` 中使用相同值，从而允许该内联脚本执行。

---

## 2. 在 Next.js 中设置 CSP 头

### 方式一：`next.config.js` 中添加静态头
适用于 CSP 规则固定，无需动态 nonce 的场景：
```js
// next.config.js
module.exports = {
  async headers() {
    return [
      {
        source: '/(.*)',
        headers: [
          {
            key: 'Content-Security-Policy',
            value: "default-src 'self'; script-src 'self' 'unsafe-inline'; ..."
          }
        ]
      }
    ]
  }
}
```
但这种方式**无法使用 nonce**，因为 nonce 需要每个请求动态生成。

### 方式二：使用中间件（Middleware）动态生成 nonce
中间件在每个请求前运行，可以生成 nonce 并设置 CSP 头，同时将 nonce 传递给页面组件。

**步骤：**
1. 在项目根目录创建 `middleware.ts`（或 `.js`）。
2. 生成安全的随机 nonce（如使用 `crypto.randomBytes` 或 Web Crypto API）。
3. 将 nonce 注入到响应头中（如 `x-nonce`），并在 CSP 头中使用它。
4. 在页面组件中读取该 nonce 并应用到内联脚本。

---

## 3. 在页面中使用 nonce

### 方案 A：Pages Router（使用 `_document.js`）
在 `pages/_document.js` 中生成 nonce 并传递给 `NextScript` 和 `Head`。

```jsx
// pages/_document.js
import Document, { Html, Head, Main, NextScript } from 'next/document'
import crypto from 'crypto'

class MyDocument extends Document {
  static async getInitialProps(ctx) {
    const initialProps = await Document.getInitialProps(ctx)
    return { ...initialProps }
  }

  render() {
    // 生成随机 nonce
    const nonce = crypto.randomBytes(16).toString('base64')
    // 将 nonce 添加到 CSP 头（需在服务器响应中设置，这里仅演示生成）
    // 实际设置 CSP 头应在中间件或自定义服务器中完成
    return (
      <Html>
        <Head nonce={nonce} />
        <body>
          <Main />
          <NextScript nonce={nonce} />
        </body>
      </Html>
    )
  }
}

export default MyDocument
```
然后在中间件中设置 CSP 头时，使用相同的 nonce 生成逻辑，并确保与 `_document` 中使用的 nonce 一致。但这种方式需要中间件和 `_document` 共享 nonce，通常通过响应头传递。

### 方案 B：App Router（使用中间件 + 布局组件）
App Router 中没有 `_document`，需通过中间件生成 nonce，并通过 `headers()` 在布局中获取。

**中间件 (`middleware.ts`)**：
```ts
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'
import crypto from 'crypto'

export function middleware(request: NextRequest) {
  const nonce = crypto.randomBytes(16).toString('base64')
  const cspHeader = `
    default-src 'self';
    script-src 'self' 'nonce-${nonce}' 'strict-dynamic' https: http:;
    style-src 'self' 'nonce-${nonce}';
    ...
  `.replace(/\s+/g, ' ').trim()

  const requestHeaders = new Headers(request.headers)
  requestHeaders.set('x-nonce', nonce)
  requestHeaders.set('Content-Security-Policy', cspHeader)

  const response = NextResponse.next({
    request: { headers: requestHeaders },
  })
  response.headers.set('x-nonce', nonce)
  response.headers.set('Content-Security-Policy', cspHeader)
  return response
}

export const config = {
  matcher: '/:path*',
}
```

**根布局 (`app/layout.tsx`)**：
```tsx
import { headers } from 'next/headers'
import Script from 'next/script'

export default function RootLayout({
  children,
}: {
  children: React.ReactNode
}) {
  const nonce = headers().get('x-nonce') || ''
  return (
    <html lang="en">
      <head>
        {/* 如果需要内联样式，添加 nonce */}
      </head>
      <body>
        {children}
        {/* Next.js 的脚本会自动使用 nonce 吗？需要手动处理 */}
        {/* 对于内联脚本，可以使用 next/script 并传递 nonce */}
        <Script
          src="https://example.com/script.js"
          strategy="afterInteractive"
          nonce={nonce}
        />
        {/* 如果有自定义内联脚本 */}
        <script
          dangerouslySetInnerHTML={{ __html: `console.log('hello')` }}
          nonce={nonce}
        />
      </body>
    </html>
  )
}
```

**注意**：Next.js 自身生成的脚本（如 `next.js`、`webpack.js`）默认不会自动带上 nonce。在 App Router 中，这些脚本通过 `next/script` 的 `afterInteractive` 策略加载，可以通过在 `RootLayout` 中添加一个全局的 `Script` 组件并传递 `nonce` 来覆盖所有脚本？实际上 Next.js 的内部脚本不通过 `next/script` 直接输出，而是由框架自动注入。为了给它们加上 nonce，需要利用 Next.js 的 `nonce` 配置项，目前官方推荐在 `_document` 中设置（Pages Router），App Router 暂时需要一些 hack，比如在中间件中修改 HTML 响应（不推荐）或等待 Next.js 官方支持。

一个折中方案：使用 Pages Router 或接受在 App Router 中暂时无法为所有内部脚本添加 nonce，但可以通过 `strict-dynamic` 放宽限制，允许信任由受信脚本加载的脚本。

---

## 4. 注意事项
- **nonce 必须足够随机**：使用 `crypto.randomBytes()` 生成，避免可预测。
- **每个请求唯一**：确保每次刷新页面都生成新 nonce，CSP 头也随之变化。
- **避免使用 `unsafe-inline`**：启用 nonce 后应移除 `'unsafe-inline'`，否则 nonce 失效。
- **测试**：使用浏览器开发者工具检查 CSP 头是否正确，以及是否有违规报告。
- **部署环境**：确保中间件在 Vercel 等平台正常工作，且 `crypto` 模块可用（Node.js 环境）。

---

## 5. 总结
- 推荐使用 **中间件** 生成 nonce 并设置 CSP 头。
- 在 **Pages Router** 中，通过 `_document` 将 nonce 传递给 `NextScript` 和 `Head`。
- 在 **App Router** 中，目前需手动为 `next/script` 和内联脚本添加 nonce，内部框架脚本暂时无法自动添加，但可结合 `strict-dynamic` 缓解风险。
- 始终确保 CSP 策略严格且经过充分测试，以平衡安全性与功能。

19. CSS的@layer规则是什么？它如何解决样式优先级问题？
`@layer` 是 CSS 级联层（Cascade Layers）规则，允许开发者将样式声明划分到不同的层中，并显式控制层的优先级顺序，从而解决样式冲突和覆盖问题。

### 工作原理
- 通过 `@layer` 可以定义命名层，例如 `@layer base, theme, components;`，这声明了三个层的顺序。
- 后续的样式可以用 `@layer base { ... }` 包裹，或通过 `@import` 带层名导入，将规则分配到指定层。
- 层的优先级由声明的顺序决定：**后声明的层优先级更高**，会覆盖前面层中的同名规则。未分层的样式被视为处于一个隐式层中，且其优先级**高于所有显式层**。

### 如何解决样式优先级问题
传统 CSS 中，优先级由选择器特异性、源码顺序等因素决定，难以在大型项目中预期和控制。级联层让开发者可以主动划分层级，例如：
- **基础层**：重置样式、全局变量。
- **主题层**：颜色、字体等主题变量。
- **组件层**：具体组件样式。
- **覆盖层**：特定页面的定制样式。

通过 `@layer` 声明顺序（如 `@layer base, theme, components, overrides;`），可以确保 `overrides` 层总是覆盖前面层，无论内部选择器的特异性如何，避免了因特异性竞争导致的意外覆盖。

### 示例
```css
@layer base, theme, components;

@layer base {
  button { padding: 8px; }   /* 基础样式 */
}

@layer theme {
  button { background: blue; } /* 主题层覆盖 base */
}

@layer components {
  .special-btn { background: red; } /* 组件层样式，不受层顺序影响特异性 */
}
```
在这个例子中，`theme` 层的 `button` 背景会覆盖 `base` 层的背景，因为 `theme` 层声明在后。即使 `.special-btn` 选择器特异性更高，它依然属于 `components` 层，其优先级仍然遵循层顺序。

### 优势
- **可预测的覆盖**：不再依赖源码顺序或特异性魔改。
- **模块化**：不同模块的样式可以安全地分层，避免相互干扰。
- **团队协作**：明确约定层的用途和顺序，降低维护成本。

`@layer` 是现代 CSS 管理大型代码库样式冲突的重要工具，已得到所有主流浏览器支持。

20. 什么是CSS的逻辑属性（Logical Properties）？margin-inline和margin-left有什么区别？
**CSS 逻辑属性** 是一组相对于文档流方向（即书写模式 `writing-mode`、文本方向 `direction` 和块级流向）定义的属性，而非传统的物理方向（上、下、左、右）。它们使布局能够自动适应不同的语言和排版模式（如从左到右、从右到左、竖排等），提升国际化能力。

### 逻辑属性与物理属性的对应
| 物理属性 | 逻辑属性 | 说明 |
|----------|----------|------|
| `margin-left` | `margin-inline-start` | 内联方向起始侧的外边距 |
| `margin-right` | `margin-inline-end` | 内联方向结束侧的外边距 |
| `margin-top` | `margin-block-start` | 块方向起始侧的外边距 |
| `margin-bottom` | `margin-block-end` | 块方向结束侧的外边距 |
| `margin-left` 和 `margin-right` 的简写 | `margin-inline` | 同时设置内联方向两侧的外边距 |
| `margin-top` 和 `margin-bottom` 的简写 | `margin-block` | 同时设置块方向两侧的外边距 |

### `margin-inline` 与 `margin-left` 的区别
- **`margin-left`**：始终作用于元素的**物理左边**，无论文档流方向是 LTR（从左到右）还是 RTL（从右到左）。
- **`margin-inline`**：是一个简写属性，同时设置内联方向两个侧的外边距，即相当于 `margin-inline-start` 和 `margin-inline-end`。它的作用侧会根据当前书写模式自动变化：
  - 在 LTR 水平书写模式下，`margin-inline` 控制的是**左和右**。
  - 在 RTL 水平书写模式下，`margin-inline` 控制的是**右和左**（即 start 对应右，end 对应左）。
  - 在竖排书写模式下（如 `writing-mode: vertical-rl`），`margin-inline` 控制的则是**上和下**（因为内联轴变成了垂直方向）。

#### 示例对比
```css
/* 物理属性：无论什么方向，左边距固定 */
.box {
  margin-left: 10px;
}

/* 逻辑属性：内联方向两侧边距，方向自适应 */
.box {
  margin-inline: 10px 20px; /* 相当于 start 10px, end 20px */
}
```
当页面从 LTR 切换到 RTL 时：
- 使用 `margin-left` 的元素仍然在左侧留下空白，可能导致布局错乱。
- 使用 `margin-inline` 的元素会自动将 10px 应用到右侧（即内联起始侧），20px 应用到左侧（内联结束侧），从而保持语义上的正确性（例如文本与容器边缘的间距）。

### 总结
逻辑属性让布局与文档流方向解耦，更适合多语言网站和复杂排版。`margin-inline` 是适应内联轴的双侧外边距，而 `margin-left` 是固定的物理左边距。现代开发中推荐优先使用逻辑属性，以提升布局的灵活性和国际兼容性。

21. CSS的aspect-ratio属性如何使用？它解决了什么问题？
`aspect-ratio` 是 CSS 属性，用于为元素指定一个**首选宽高比**，浏览器会根据该比例自动计算元素的尺寸，避免传统上使用 `padding-top` hack 或 JavaScript 来维持固定比例。

### 如何使用
语法：`aspect-ratio: <ratio>;`，其中 `<ratio>` 可以是分数形式如 `16/9`、`1/1`，或单一数字（如 `1` 表示 1:1）。

```css
.container {
  width: 100%;        /* 宽度由父容器决定 */
  aspect-ratio: 16/9; /* 高度自动按比例计算为 width * 9/16 */
}

.image {
  aspect-ratio: 1;    /* 正方形 */
}
```

### 解决了什么问题？
- **简化响应式布局**：以往要维持固定宽高比（如视频容器、卡片），必须用 `padding-top: 56.25%`（16:9）等 hack，不仅难记，而且对绝对定位元素或直接替换元素（如 `<img>`）支持不佳。现在只需一行 `aspect-ratio`。
- **增强可维护性**：代码更直观，无需额外包裹元素或计算百分比。
- **与原生元素兼容**：直接应用于 `<img>`、`<video>` 等元素，结合 `width` 或 `height` 的设定，能智能控制尺寸，避免变形。

### 注意事项
- 如果同时设置了 `width` 和 `height`，`aspect-ratio` 会被忽略（因为宽高已明确）。
- 浏览器会基于盒模型的内容区域计算比例，但受 `box-sizing` 影响。
- 支持所有现代浏览器（包括移动端）。

23. 前端如何实现构建产物的hash指纹？contenthash、chunkhash、hash有什么区别？
在前端构建工具（如 Webpack）中，给产物文件名添加哈希指纹是为了解决浏览器缓存问题——当文件内容变化时，文件名也变化，强制客户端加载最新资源。

### 如何实现
在 Webpack 的 `output.filename` 中配置占位符：
```js
output: {
  filename: '[name].[contenthash].js',
  chunkFilename: '[name].[contenthash].chunk.js',
}
```
配合 `MiniCssExtractPlugin` 对 CSS 也使用 `[contenthash]`。

---

### `hash`、`chunkhash`、`contenthash` 的区别

| 类型 | 计算范围 | 特点 | 适用场景 |
|------|----------|------|----------|
| **`hash`** | 一次构建整体生成一个 hash | 所有文件共享同一个 hash，任何一个文件变化都会导致所有文件名变化，缓存失效范围大。 | 极少使用，仅用于简单项目或特定需求。 |
| **`chunkhash`** | 基于同一个 chunk（入口及其依赖）生成 | 同一 chunk 输出的文件（如入口 JS 及其异步加载的模块）共享该 chunk 的 hash。如果 chunk 内任一模块变化，该 chunk 所有文件的 hash 都会变。 | 适用于按入口分离代码，但可能因异步加载或 CSS 提取导致不必要的缓存失效。 |
| **`contenthash`** | 基于文件内容生成（通常使用 MD4 等） | 每个文件独立计算 hash，只有文件自身内容变化才改变 hash，精确控制缓存。 | **最推荐**，尤其适合长期缓存策略，让未改动的文件继续使用缓存。 |

### 示例说明
假设项目有两个入口 `main.js` 和 `admin.js`，并提取了公共 CSS。

- **使用 `hash`**：一次构建产生一个 `7a2f3...`，所有文件都叫 `main.7a2f3.js`、`admin.7a2f3.js`、`styles.7a2f3.css`。修改 `main.js` 后所有文件名全变，用户需重新下载所有文件。
- **使用 `chunkhash`**：`main.js` 和其异步加载的模块属于 `main` chunk，输出 `main.abc123.js`；`admin.js` 输出 `admin.def456.js`；CSS 若被提取，可能仍属于对应 chunk，导致 CSS 和 JS 共享 hash。修改 `main.js` 中一行代码，`main.abc123.js` 的 hash 变为新值，同时如果 CSS 是从该 chunk 提取的，`main.css` 的 hash 也会变，即使 CSS 内容没变（因为 chunkhash 基于 chunk 整体内容）。
- **使用 `contenthash`**：`main.js` 生成 `main.abc123.js`，`styles.css` 生成 `styles.def456.css`。只修改 `main.js`，只有 `main.js` 的 hash 变化，`styles.css` 的 hash 保持不变，客户端可继续缓存 CSS。

### 总结
- 为了实现最优缓存，推荐 **`[contenthash]`** 用于所有静态资源（JS、CSS、图片等）。
- 配合 `optimization.moduleIds: 'deterministic'` 和 `runtimeChunk: 'single'` 可以进一步减少不必要的 hash 变化。
- 在 Webpack5 中，`[contenthash]` 已成为事实标准。

24. 什么是依赖提升（Hoisting）？它会导致什么问题？pnpm如何解决这个问题？
**依赖提升（Hoisting）** 是 npm（v3+）和 Yarn 等包管理器采用的一种优化策略。在早期 npm（v2）中，依赖是嵌套安装的，每个包都有自己的 `node_modules`，导致目录层级过深、路径太长，且同一个包可能被多次重复安装。为了解决这些问题，npm v3 引入了扁平化结构：将所有依赖（包括间接依赖）尽可能提升到项目根目录的 `node_modules` 顶层，形成一个尽量扁平的树。

### 依赖提升带来的问题
1. **幽灵依赖（Phantom Dependencies）**  
   项目代码可以直接引用未在 `package.json` 中声明的依赖，因为它们被提升到了顶层。这可能导致项目隐式依赖某个包，当该包不再被提升或版本变化时，项目就会无法运行。

2. **依赖版本冲突**  
   不同的依赖可能需要同一个包的不同版本。扁平化只能保留一个版本，包管理器需要自行决定保留哪个版本，可能导致某些依赖使用不兼容的版本，引发运行时错误。

3. **不确定性**  
   依赖提升的算法复杂，不同环境（如不同操作系统、安装顺序）可能产生不同的 `node_modules` 结构，导致“works on my machine”问题。

### pnpm 如何解决这些问题
pnpm 采用 **内容寻址存储** + **严格的依赖树结构** 来彻底避免依赖提升：

- **非扁平化的 `node_modules`**  
  pnpm 在项目根目录的 `node_modules` 下只放置项目的**直接依赖**，这些依赖是通过**符号链接**指向全局存储（`~/.pnpm-store`）中的实际文件。每个直接依赖自己的 `node_modules` 中又通过符号链接指向其所需的其他依赖，从而完整保留了依赖树原本的嵌套关系，没有任何提升。

- **避免幽灵依赖**  
  由于项目只能访问到 `package.json` 中声明的直接依赖（以及它们显式声明的依赖，但无法跨层级直接引用），未声明的包无法被导入，彻底杜绝了幽灵依赖。

- **严格的版本隔离**  
  每个包都可以使用其自身指定的版本，互不干扰，因为依赖树的结构确保了每个包的依赖都存在于自己的 `node_modules` 下，不会有版本冲突。

- **节省磁盘空间**  
  通过硬链接和符号链接，同一版本的包只在全局存储中保存一份，既保证了结构的正确性，又避免了重复下载和磁盘浪费。

**总结**：pnpm 通过摒弃依赖提升，以符号链接和内容寻址的方式构建了严格、可预测的 `node_modules` 结构，解决了幽灵依赖、版本冲突和不确定性等问题。

25. 如何实现前端的性能预算（Performance Budget）？webpack-bundle-analyzer如何使用？
**前端性能预算**是一组预先设定的性能指标阈值（如首次内容绘制 < 1s、总包体积 < 200KB），在开发过程中持续检查，防止性能退化。

### 如何实现性能预算
1. **定义预算指标**：常见的有：
   - 体积预算：JavaScript/CSS/图片等资源总大小、单个文件大小。
   - 时间预算：FCP、LCP、TTI 等。
   - 请求预算：页面总请求数。

2. **自动化检查工具**：
   - **Webpack 内置**：在 `webpack.config.js` 中配置 `performance` 选项，设置 `maxEntrypointSize` 和 `maxAssetSize`，超出会输出警告或报错。
     ```js
     module.exports = {
       performance: {
         maxEntrypointSize: 250000, // 入口文件最大 250KB
         hints: 'warning' // 或 'error'
       }
     };
     ```
   - **bundlesize**：轻量级工具，在 CI 中运行，根据配置文件检查文件大小。
   - **Lighthouse CI**：集成 Lighthouse 跑分，设定性能分数阈值。
   - **Lighthouse Bot** 或 **WebPageTest API**：在 CI 中运行性能测试并断言。

3. **集成 CI/CD**：将预算检查加入 CI 流程（如 GitHub Actions），当超出预算时阻止合并。

---

### webpack-bundle-analyzer 如何使用
**作用**：以可视化树状图展示打包产物的构成，帮助分析哪些模块体积过大。

1. **安装**：
   ```bash
   npm install --save-dev webpack-bundle-analyzer
   ```

2. **配置**：在 `webpack.config.js` 中添加插件（仅在分析时启用，可放在 `analyze` 模式下）。
   ```js
   const BundleAnalyzerPlugin = require('webpack-bundle-analyzer').BundleAnalyzerPlugin;

   module.exports = {
     plugins: [
       new BundleAnalyzerPlugin({
         analyzerMode: 'static', // 生成 HTML 报告文件
         reportFilename: 'report.html',
         openAnalyzer: false, // 是否自动打开浏览器
       })
     ]
   };
   ```

3. **运行**：执行构建命令（如 `npm run build`），会在指定目录生成 `report.html`，打开后以交互式树图显示各模块大小。

4. **命令行快捷方式**：也可以直接通过 `webpack --profile --json > stats.json` 生成统计文件，然后用 `npx webpack-bundle-analyzer stats.json` 分析。

通过分析报告，可以定位体积过大的依赖，进而进行优化（如按需加载、替换库等），并将优化结果与性能预算结合，确保预算达标。

26. 什么是Changesets？它如何管理Monorepo的版本发布？
**Changesets** 是一个用于管理版本变更和发布流程的工具，尤其适合 Monorepo（如使用 pnpm、yarn 或 npm 的 workspaces）场景。它通过约定式的变更文件来追踪哪些包需要更新，并自动生成变更日志、升级版本和发布。

### 核心概念
- **变更集文件**：开发者每次修改后创建一个 `.changeset/*.md` 文件，内部使用 Markdown 描述变更内容，并标记受影响的包及版本更新类型（patch、minor、major）。
- **版本管理**：运行 `changeset version` 命令时，工具会读取所有变更集，更新对应包的 `package.json` 版本号，并生成/更新 `CHANGELOG.md` 文件。
- **发布**：`changeset publish` 会将所有需要发布的包发布到 npm，并删除已使用的变更集文件。

### 在 Monorepo 中管理版本发布的流程
1. **开发阶段**：开发者完成功能或修复后，运行 `changeset` 命令，交互式选择受影响的包和更新类型，并填写变更描述。这会在 `.changeset` 目录下生成一个临时 Markdown 文件。
2. **代码审查与合并**：变更集文件随代码一起提交到版本库。PR 合并后，CI 可以自动触发版本管理步骤。
3. **版本更新**（通常由 CI 执行）：运行 `changeset version`，该命令：
   - 根据所有未使用的变更集计算每个包的新版本号。
   - 更新 `package.json` 中的版本字段。
   - 为每个有变更的包生成或追加 `CHANGELOG.md` 条目。
   - 删除已使用的变更集文件。
4. **提交版本变更**：CI 自动提交版本更新和变更日志的改动（或创建一个新 PR）。
5. **发布**：运行 `changeset publish`，将包发布到 npm，并可选择生成 Git tag 和 GitHub release。

### 优点
- **自动化**：避免手动修改版本号和变更日志，减少人为错误。
- **依赖感知**：能正确处理 Monorepo 中包之间的依赖关系，确保依赖包的版本更新正确。
- **协作友好**：变更集与 PR 绑定，便于审查和追溯。
- **灵活**：支持自定义发布脚本、发布渠道（如 next、latest）等。

通过 Changesets，Monorepo 项目的版本发布变得规范、可预测且高效。

## TypeScript (2题)

27. TypeScript中的infer关键字是什么？如何使用它提取类型？
在 TypeScript 中，`infer` 是一个**用于在条件类型中声明待推断类型变量**的关键字。它允许我们在类型系统中“捕获”某个位置的具体类型，然后将其作为变量使用，从而实现强大的类型提取和模式匹配。

---

## 基本语法

`infer` 只能出现在条件类型的 `extends` 子句中，语法如下：

```typescript
type SomeType<T> = T extends SomePattern<infer U> ? U : never;
```

当 `T` 匹配 `SomePattern` 时，`infer U` 会捕获对应位置的类型，并在 `true` 分支中作为类型变量 `U` 使用。

---

## 常见使用场景及示例

### 1. 提取函数返回值类型（类似内置 `ReturnType`）

```typescript
type MyReturnType<T> = T extends (...args: any[]) => infer R ? R : never;

function foo() { return 42; }
type FooReturn = MyReturnType<typeof foo>; // number
```

### 2. 提取数组元素类型

```typescript
type ElementType<T> = T extends (infer U)[] ? U : never;

type StrArr = string[];
type Elem = ElementType<StrArr>; // string
```

### 3. 提取 Promise 的 resolve 类型

```typescript
type UnwrapPromise<T> = T extends Promise<infer U> ? U : T;

type P = Promise<number>;
type Resolved = UnwrapPromise<P>; // number
```

### 4. 提取函数第一个参数的类型

```typescript
type FirstArg<T> = T extends (arg: infer A, ...args: any[]) => any ? A : never;

function greet(name: string, age: number) {}
type Arg = FirstArg<typeof greet>; // string
```

### 5. 提取元组类型中的元素（组合使用多个 infer）

```typescript
type FirstAndRest<T> = T extends [infer First, ...infer Rest] 
  ? { first: First; rest: Rest } 
  : never;

type Tuple = [string, number, boolean];
type Result = FirstAndRest<Tuple>; 
// { first: string; rest: [number, boolean] }
```

---

## 工作原理

`infer` 就像类型层面的“模式匹配”：  
- 我们定义了一个条件类型，左侧是一个包含 `infer` 占位符的模式。  
- TypeScript 会检查传入的类型是否匹配该模式，如果匹配，就将 `infer` 位置的实际类型赋值给对应的类型变量。  
- 然后在 `true` 分支中可以使用这些变量构建新的类型。

---

## 注意事项

- `infer` 只能在条件类型的 `extends` 子句中使用，不能出现在其他地方。
- 可以同时使用多个 `infer`，只要它们位于模式中不同的位置。
- 如果模式匹配失败，整个条件类型走 `false` 分支（通常是 `never`）。
- `infer` 捕获的是类型，不是值，因此只能在类型层面使用。

---

## 实际应用

TypeScript 内置了许多基于 `infer` 的工具类型，例如：
- `ReturnType<Type>`
- `Parameters<Type>`
- `ConstructorParameters<Type>`
- `InstanceType<Type>`
- `Awaited<Type>`（递归提取 Promise）

你也可以用 `infer` 实现自定义的高级类型，如提取 React 组件 props 类型、从联合类型中提取特定成员等。

---

`infer` 是 TypeScript 类型系统强大表达能力的核心，熟练掌握它可以让我们编写出更灵活、更精确的类型工具。

28. TypeScript的条件类型（Conditional Types）如何工作？extends关键字在类型中的含义是什么？
在 TypeScript 中，**条件类型（Conditional Types）** 是一种根据类型关系动态选择类型的工具，其语法类似于 JavaScript 的三元表达式：

```typescript
T extends U ? X : Y
```

它的含义是：**如果类型 `T` 可以赋值给类型 `U`（即 `T` 是 `U` 的子类型），则结果类型为 `X`，否则为 `Y`。**

---

### `extends` 关键字在类型中的含义
在条件类型中，`extends` 不是指类的继承，而是用于检查**类型兼容性**，即判断左侧类型是否**可以赋值给**右侧类型。它遵循 TypeScript 的结构化子类型规则：
- 若 `T` 是 `U` 的子类型（或与 `U` 相同），则条件成立。
- 例如：`'a' extends string` 成立，`string extends 'a'` 不成立。

---

### 基本示例
```typescript
type IsString<T> = T extends string ? true : false;

type A = IsString<'hello'>; // true
type B = IsString<123>;      // false
```

---

### 条件类型的分配律（Distributive Conditional Types）
当 `T` 是一个**联合类型**时，条件类型会分发到联合的每个成员上：

```typescript
type ToArray<T> = T extends any ? T[] : never;

type Result = ToArray<string | number>; // string[] | number[]
```
相当于先对 `string` 得 `string[]`，对 `number` 得 `number[]`，再联合起来。

如果想避免分发，可以用方括号将 `T` 和 `U` 括起来：

```typescript
type ToArrayNonDist<T> = [T] extends [any] ? T[] : never;
type Result2 = ToArrayNonDist<string | number>; // (string | number)[]
```

---

### 结合 `infer` 进行类型提取
条件类型经常与 `infer` 关键字配合，在模式匹配中提取子类型：

```typescript
type ReturnType<T> = T extends (...args: any[]) => infer R ? R : never;

function foo() { return 42; }
type FooReturn = ReturnType<typeof foo>; // number
```

---

### 实际应用场景
- 过滤联合类型（如 `Exclude<T, U>` 内置工具类型）。
- 提取函数参数类型（`Parameters<T>`）。
- 根据属性值类型决定其他类型（如动态生成类型映射）。

条件类型是 TypeScript 类型系统强大表现力的核心，允许在类型层面进行逻辑判断和模式匹配，从而实现复杂的类型操作。

## 2. 组件数据结构设计

使用 **树形JSON Schema** 描述整个页面，每个节点代表一个组件。

### 基础字段
```typescript
interface ComponentNode {
  id: string;               // 全局唯一ID（UUID）
  type: string;             // 组件类型，如 'Button', 'Container'
  props: Record<string, any>; // 属性对象，包括样式、事件、插槽等
  children?: ComponentNode[]; // 子组件（仅容器组件有效）
  scope?: Record<string, any>; // 局部变量/数据源（可选）
}
```

### 扩展设计
- **样式描述**：将样式拆分为 `styles` 属性，支持类似 Tailwind CSS 类名或内联样式对象。
- **事件绑定**：用 `events` 字段描述，如 `{ onClick: { type: 'navigate', url: '/home' } }`，生成代码时转为函数。
- **响应式/条件渲染**：增加 `condition` 字段，支持表达式。
- **动态数据**：通过 `dataSource` 字段关联全局数据源或API。

这种结构易于序列化、存储和传输，也能直接驱动渲染。

## 3. 拖拽交互实现

### 3.1 拖拽流程
- **拖源**（组件库条目、画布内组件）：监听 `mousedown`，记录拖拽开始信息（组件类型、初始位置、源节点）。
- **拖过程**：`mousemove` 时计算光标位置，实时显示占位线/占位块，并高亮可放置区域。
- **放目标**：`mouseup` 时根据放置位置更新Schema（插入/移动/替换）。

### 3.2 技术选型
- **原生HTML5 Drag & Drop**：简单，但定制化困难，且无法在画布内自由拖拽（如调整嵌套层级）。
- **基于鼠标事件模拟**：更灵活，能精确控制拖拽反馈。实现方式：
  1. 在画布根容器监听 `mousedown`，通过事件委托识别拖拽句柄。
  2. 动态创建全屏遮罩层，防止文本选中，并在其上监听 `mousemove` / `mouseup`。
  3. 使用 `requestAnimationFrame` 优化拖拽性能。

### 3.3 位置判定算法
- **碰撞检测**：根据鼠标位置与画布内各容器的边界矩形，判断进入哪个容器以及插入位置（前后、内部）。
- **利用画布的 `getBoundingClientRect`** 结合虚拟坐标计算。
- 插入位置确定后，通过修改状态管理中的Schema数组顺序或嵌套关系完成更新。

---

## 4. 组件间通信

低代码平台的组件通信场景分为**编辑时**和**运行时**。

### 4.1 编辑时通信
- **父子组件**：通过渲染引擎在解析Schema时，将父组件的属性自动传递给子组件（如 `props.children`）。
- **跨层级/非父子组件**：采用**全局事件总线（Event Bus）**。例如，当在属性面板修改某个组件的属性时，派发 `component:update` 事件，渲染引擎监听后局部更新。
- **状态管理**：直接通过全局Store（Redux/Zustand）修改Schema，触发渲染引擎重新渲染。

### 4.2 运行时通信（生成的代码）
- 输出为常规 React/Vue 组件，遵循框架标准通信方式：
  - 父→子：`props`
  - 子→父：回调函数（如 `onClick` 触发父级事件）
  - 跨组件：Context/Provide-inject / 全局状态（如 Pinia/Vuex）
- 平台在生成代码时，根据用户在属性面板中设置的“事件动作”自动生成对应的通信代码。

## 5. 生成可执行代码

提供两种输出模式：

### 5.1 源码生成模式
将Schema递归转换为**目标框架的代码字符串**（如 React JSX、Vue SFC）。
- **实现方式**：使用 **AST 操作库**（如 `babel`、`recast`）或模板引擎（`Handlebars`）生成。
- 示例：根据 `type` 映射到导入语句，将 `props` 转换为属性表达式，`children` 递归生成。
- 优势：完全脱离平台，可独立部署、二次开发。

### 5.2 运行时解释模式
平台提供一个**渲染器组件**，接收Schema对象，动态加载对应组件并渲染。
- 组件库预先注册到全局组件映射表（`Map<type, Component>`）。
- 渲染器递归遍历Schema，为每个节点创建对应组件，并传入 `props` 和 `children`。
- 优势：无需编译，实时生效，适合内部预览和低代码运营系统。

## 6. Schema驱动渲染的实现

### 6.1 核心渲染器（React 示例）
```jsx
function Renderer({ schema, componentMap }) {
  const { id, type, props, children } = schema;
  const Component = componentMap[type];
  if (!Component) return null;

  // 递归渲染子节点
  const renderedChildren = children?.map(child => (
    <Renderer key={child.id} schema={child} componentMap={componentMap} />
  ));

  return (
    <Component {...props} key={id}>
      {renderedChildren}
    </Component>
  );
}
```

### 6.2 性能优化
- 为每个组件节点添加 `shouldComponentUpdate` 或使用 `React.memo` 结合 `props` 浅比较。
- 对于列表渲染，使用稳定且唯一的 `key`（Schema中的 `id`）。
- 拖拽高频更新时，采用**微任务批量更新**（如 `React unstable_batchedUpdates`）。

### 6.3 动态加载组件
组件库可拆分为异步Chunk，渲染器通过 `React.lazy + Suspense` 按需加载，减少首屏体积。

## 7. 撤销/重做（历史管理）

采用**命令模式 + 历史栈**。

### 7.1 数据结构
- `undoStack`：存储过去的状态快照（或操作逆动作）。
- `redoStack`：存储已撤销的状态快照。

### 7.2 实现策略
- **快照方案**：每次修改前，将当前完整Schema深拷贝一份推入 `undoStack`，`redoStack` 清空。用户点击撤销时，用栈顶快照替换当前状态，同时将该快照移入 `redoStack`。
- **命令方案**：定义 `AddCommand`、`MoveCommand`、`UpdatePropsCommand` 等，每个命令包含 `do()` 和 `undo()` 方法。此方案更精细，内存占用小。

### 7.3 集成状态管理
在Store中增加 `history` 模块：
```js
const historySlice = {
  past: [],
  future: [],
  add: (state) => { ... },
  undo: (state) => { ... },
  redo: (state) => { ... }
}
```
使用中间件自动捕获Schema变更并推入历史（如 Redux 的 `redux-undo` 库）。

### 8.1 预览
- 独立路由页面：使用相同渲染器，加载当前Schema，无需任何编辑UI。
- 可选模拟不同设备尺寸（内嵌 iframe 或 CSS 媒体查询）。

### 8.2 发布
- **编译打包**：调用后端API，将源码生成模式输出的代码与框架模板结合，进行生产环境构建（Webpack/Vite）。
- **导出静态文件**：生成HTML+JS+CSS，上传至CDN。
- **元数据存储**：将Schema存储至数据库，运行时模式只需保存JSON，预览时实时获取。


### 三、时间轴数据结构设计

采用**多轨道、离散片段**模型，每个轨道独立维护片段列表，片段按时间顺序排序。

#### 3.1 核心数据结构定义（TypeScript）

```typescript
// 视频片段
interface Clip {
  id: string;               // 唯一ID
  type: 'video' | 'audio' | 'image' | 'text';
  fileId: string;           // 关联的原始媒体文件ID（存储在IndexedDB中）
  startTime: number;        // 片段在时间轴上的起始时间（秒）
  endTime: number;          // 片段在时间轴上的结束时间（秒）
  sourceStart: number;      // 从原始媒体的哪一秒开始
  sourceEnd: number;        // 到原始媒体的哪一秒结束
  speed: number;            // 播放速率（0.5~4）
  volume: number;           // 音量（音频/视频轨）
  transform?: Transform;    // 位置、缩放、旋转（用于画中画、字幕）
  filters?: Filter[];      // 应用的滤镜/特效
}

// 轨道
interface Track {
  id: string;
  index: number;           // 轨道序号，决定叠加层级
  type: 'video' | 'audio' | 'subtitle' | 'effect';
  clips: Clip[];           // 按 startTime 升序存储
  muted?: boolean;
  locked?: boolean;
}

// 时间线项目
interface Timeline {
  duration: number;        // 总时长
  width: number;           // 输出分辨率宽
  height: number;          // 输出分辨率高
  fps: number;             // 帧率
  tracks: Track[];
  transitions?: Transition[]; // 转场：关联两个相邻片段
}
```

#### 3.2 操作算法
- **插入片段**：二分查找目标轨道中的插入位置，维护数组有序性。
- **移动/裁剪**：更新 `startTime`/`endTime` 或 `sourceStart`/`sourceEnd`，并检查与相邻片段的重叠约束。
- **转场**：在两个片段重叠区域生成一个 `Transition` 对象，包含类型、时长、参数，合成时对该区域应用特殊效果。
- **渲染调度**：根据当前播放时间，快速定位所有轨道中正在激活的片段，使用 **区间树** 或 **分段索引** 优化检索（`O(log n)`）。

### 四、大视频文件性能优化策略

#### 4.1 代理编辑（Proxy Workflow）
- 用户导入原始高码率视频时，**立即在后台生成低分辨率代理视频**（如 720p，H.264 baseline）。
- 预览、剪辑操作均基于代理文件，导出时再映射回原始文件进行高质量渲染。
- 使用 **WebCodecs** + **OffscreenCanvas** + **Worker** 实现纯前端转码。

#### 4.2 分块加载与流式解码
- 不将整个视频文件加载进内存，而是通过 **File API 的 `slice` 方法** 读取字节范围。
- 使用 **WebCodecs VideoDecoder** 逐帧解码，并缓存最近 N 帧（LRU）在内存中作为 **帧缓存池**。
- 当用户拖动时间轴时，预解码前后若干帧，提升跳转响应速度。

#### 4.3 多线程并行
- **解码线程**：每个视频片段分配一个 Worker，独立解码帧数据，通过 `SharedArrayBuffer` 将 YUV/ImageBitmap 传输给主线程。
- **渲染线程**：主线程仅负责合成绘制，通过 `requestAnimationFrame` 驱动。
- **特效计算**：使用 WebGL 着色器，将像素级运算卸载到 GPU。

#### 4.4 内存管理
- 限制同时解码的片段数量，超出则释放最久未使用的帧数据。
- 对于大型项目，采用 **虚拟滚动** 渲染时间轴缩略图，只加载当前视口范围内的片段封面。

### 五、帧精确预览与编辑的实现

#### 5.1 播放器内核
摒弃传统 `<video>` 元素（无法多轨同步、无法插入滤镜），改为**完全基于 WebCodecs + WebGL 的自定义渲染管线**。

- **视频解码**：使用 `VideoDecoder` 配置输出 `VideoFrame`，提取 `timestamp` 与期望帧对齐。
- **帧精确控制**：维护内部时钟 `currentTime`，根据帧率计算下一帧应显示的时间，解码器寻找对应关键帧后顺序解码到目标帧（seek 时使用 `VideoDecoder.reset()` + `decodeQueue`）。
- **多轨同步**：所有轨道以主视频轨的时钟为基准，解码器输出带时间戳的帧，合成器按时间戳统一渲染。

#### 5.2 音频处理
- 使用 **AudioContext** + **AudioWorklet**。
- 每个音频片段独立解码为 `AudioBuffer`，在 Worklet 中根据播放位置实时读取采样并混合。
- 支持音调变化、变速不变调（通过 `MediaStreamAudioDestinationNode` 或 ScriptProcessorNode 降级）。

#### 5.3 实时合成
1. 主循环 `requestAnimationFrame` 检查当前时间，若达到下一帧显示时间，则触发合成。
2. 收集所有视频轨道在当前时刻需要绘制的帧（`VideoFrame` 或 `ImageBitmap`）。
3. 按轨道层级顺序绘制到 WebGL 画布，同时应用转场、滤镜（着色器）。
4. 字幕轨通过 Canvas2D 或 WebGL 纹理绘制文本。
5. 音频 Worklet 持续输出混合 PCM 数据，通过 `AudioContext` 播放。

#### 5.4 帧精度保证
- 所有时间单位使用 **微秒（µs）** 存储，避免浮点误差。
- 解码器输出帧的 `timestamp` 与播放时间严格比较，允许 1ms 误差容限。
- 支持单帧步进：用户每按一次方向键，将当前时间移动到最近的帧边界，并强制解码该帧。

### 六、WebAssembly 的应用场景

WebAssembly 在此类重度计算场景中是性能加速的关键技术。

#### 6.1 媒体处理
- **FFmpeg.wasm**：封装 FFmpeg 核心能力，用于解析非常规封装格式（如 MOV、AVI）、转换编码格式（H.265→H.264）、提取音频流等。虽然性能不及原生，但可作为兜底方案。
- **自定义编解码器**：若浏览器未实现某编码（如 AV1 硬件解码支持有限），可集成开源解码器（如 dav1d）WASM 版本。
- **封装/解封装**：MP4 或 WebM 的 mux/demux 逻辑可用 WASM 加速。

#### 6.2 图像/视频特效
- **滤镜与转场**：基于像素的复杂算法（如高斯模糊、边缘检测、光流插帧）用 WASM 实现，比纯 JS 快 3~5 倍，同时避免 WebGL 着色器在某些场景的精度限制。
- **AI 抠图/美颜**：使用 TensorFlow.js 的 WASM 后端，或直接集成 ONNX Runtime Web 运行分割模型。

#### 6.3 音频处理
- **音频分析**：波形图绘制、响度标准化、人声分离等任务，计算量大，适合 WASM。
- **音频特效**：均衡器、混响、变声等 DSP 算法，使用 SIMD 指令优化。

#### 6.4 时间轴运算与资源调度
- 复杂转场过渡曲线的插值计算。
- 多轨道重叠区域的像素级混合算法。
- 资源依赖关系拓扑排序（导出任务调度）。

#### 6.5 性能对比策略
- **优先 WebCodecs + WebGL**：充分发挥浏览器原生能力。
- **WASM 作为补充**：处理浏览器未覆盖或性能不足的场景，并通过 `Worker` 线程调用避免阻塞 UI。

### 七、总结

本设计方案围绕 **纯前端、高性能、可扩展** 的原则，通过分层架构实现关注点分离：

- **视图层** 使用 React 提供流畅交互；
- **状态层** 采用可预测的数据结构，支持复杂时间线操作；
- **核心层** 深度整合 WebCodecs、WebGL、Web Audio 和 WebAssembly，构建了自定义渲染管线，实现帧精确编辑与实时预览；
- **性能层** 通过代理编辑、分块解码、多线程、GPU 加速等手段，有效支撑大型视频项目。

该方案已在部分开源项目（如“腾讯云创·视频剪辑”、“稿定设计视频编辑器”）中有类似实践，证明其在 Web 环境中实现专业级视频剪辑的可行性。
