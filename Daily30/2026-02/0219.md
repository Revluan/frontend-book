## 性能优化 (28题)

1. 什么是关键请求链（Critical Request Chain）？如何识别和优化关键请求链？
**关键请求链** 是指页面渲染或交互所必需的、且相互依赖的一系列资源请求。这些资源通常是阻塞渲染的 CSS、JavaScript 或字体等，它们的加载顺序和完成时间直接影响首次内容绘制（FCP）和可交互时间（TTI）。识别和优化关键请求链是提升网页加载性能的核心任务。

## 如何识别关键请求链

主要借助浏览器开发者工具：

1. **Network 面板**  
   - 查看瀑布图（Waterfall）：请求的发起时间、持续时间以及依赖关系。关键请求通常位于瀑布图的最左侧，且后面跟着其他请求。
   - 筛选资源类型：重点关注 CSS、JS、字体等可能阻塞渲染的资源。
   - 查看 Initiator（发起者）：确定请求是由哪个 HTML 标签或脚本发起的，从而理清依赖链条。

2. **Performance 面板**  
   - 录制页面加载过程，分析主线程任务和网络请求的时间线。
   - 在“Main”部分查看解析 HTML、执行 JS、应用样式等任务的时间，结合网络请求确定哪些资源阻塞了渲染。
   - 使用“Experience”或“Lighthouse”标签页，识别关键的请求链建议。

3. **Lighthouse 报告**  
   - 运行 Lighthouse 审计，它会指出“消除渲染阻塞资源”并提供具体的关键请求链列表。

**关键请求链示例**：
- HTML 请求 → 发现 CSS 和 JS 链接 → 并行下载 CSS 和 JS → CSS 完成前 JS 可能被推迟 → CSS 完成后渲染首次内容。那么 CSS 就是关键请求链的一部分。

---

## 如何优化关键请求链

1. **减少关键请求数量**  
   - 内联关键 CSS：将首屏所需的最小 CSS 直接嵌入 HTML，避免额外请求。
   - 内联关键 JS：将关键的 JavaScript 逻辑（如首屏渲染、功能启动）内联，非关键部分异步加载。
   - 合并文件：合并多个 CSS/JS 文件减少请求数（需权衡缓存粒度）。

2. **优化资源加载顺序**  
   - 预加载关键资源：使用 `<link rel="preload">` 提前加载 CSS、字体或重要 JS。
   - 预连接：`<link rel="preconnect">` 或 `<link rel="dns-prefetch">` 加速跨域连接。
   - 推迟非关键资源：使用 `async` / `defer` 加载 JS，`media` 属性加载非首屏 CSS。

3. **利用 HTTP/2 多路复用**  
   - 开启 HTTP/2 可并行传输多个小文件，减少连接开销。

4. **压缩与缓存**  
   - 压缩 CSS、JS 和 HTML（如 Gzip、Brotli），使用高效图片格式。
   - 设置强缓存策略，避免重复加载关键资源。

5. **服务端优化**  
   - 服务器端渲染（SSR）生成包含首屏内容的 HTML，减少客户端请求依赖。
   - 使用 CDN 加速资源分发。

通过持续监测关键请求链并应用上述优化，可以显著缩短首屏加载时间，提升用户体验。

2. 前端如何实现资源的优先级控制？fetchpriority属性如何使用？
### 前端如何实现资源的优先级控制？

资源优先级控制是指通过技术手段影响浏览器加载关键资源的顺序和带宽分配，从而优化页面性能，尤其是首屏渲染和用户交互。常见的控制方式包括：

- **隐式控制**：利用浏览器默认行为，如将关键 CSS 放在 `<head>`、JS 脚本使用 `async`/`defer`、提前加载资源（`<link rel="preload">`）等。
- **显式控制**：通过 `fetchpriority` 属性直接向浏览器提示资源的相对优先级。

---

### `fetchpriority` 属性如何使用？

`fetchpriority` 是浏览器提供的一个**提示性属性**，允许开发者指定资源的加载优先级（高、低、自动），可应用于 `<img>`、`<link>`、`<script>`、`<iframe>` 等元素以及 `fetch()` API 中。

#### 1. 在 HTML 元素上使用
```html
<!-- 高优先级：关键图片（如 LCP 元素） -->
<img src="hero.jpg" fetchpriority="high" alt="关键图片">

<!-- 低优先级：非首屏图片 -->
<img src="footer.jpg" fetchpriority="low" alt="底部图片">

<!-- 预加载样式，但优先级设为低（例如非关键样式） -->
<link rel="preload" href="non-critical.css" as="style" fetchpriority="low">

<!-- 脚本，默认优先级可能是高，但可以手动调低 -->
<script src="analytics.js" fetchpriority="low"></script>
```

#### 2. 在 `fetch()` API 中使用
```javascript
// 高优先级的数据请求
fetch('/api/important-data', { priority: 'high' });

// 低优先级的日志上报
fetch('/api/log', { priority: 'low', keepalive: true });
```

#### 3. 属性取值
- `high`：高优先级，适用于影响核心体验的资源（如 LCP 图片、关键 CSS）。
- `low`：低优先级，适用于可延迟加载的资源（如分析脚本、非首屏图片）。
- `auto`：默认值，由浏览器自行决定优先级（通常基于资源类型和上下文）。

---

### 注意事项
- **仅为提示**：浏览器会根据自身调度算法尽量尊重提示，但不保证完全遵循。
- **不要滥用**：过度使用 `high` 可能导致其他资源被饿死，反而降低性能。
- **结合其他优化**：与 `preload`、`preconnect` 等配合使用效果更佳。
- **浏览器支持**：主流现代浏览器（Chrome/Edge 101+、Safari 16.4+、Firefox 121+）已支持。

通过合理设置 `fetchpriority`，可以让关键资源更快加载，从而提升 LCP 等核心性能指标。

3. 什么是RAIL性能模型？Response、Animation、Idle、Load分别代表什么指标？
**RAIL 性能模型** 是 Google 提出的以用户为中心的性能评估模型，它将用户体验分解为四个关键阶段，并为每个阶段设定了明确的性能目标。

### RAIL 四个阶段及其指标

| 字母 | 阶段 | 指标 | 性能目标 |
|------|------|------|----------|
| **R** | **Response**（响应） | 用户操作（点击、触摸、按键）到页面反馈的时间。 | **100ms 以内**，让用户感觉操作是即时响应的。 |
| **A** | **Animation**（动画） | 每一帧的渲染时间，包括滚动、交互动画等。 | **每帧 16ms 以内**（对应 60fps），保证动画流畅无卡顿。 |
| **I** | **Idle**（空闲） | 主线程空闲时间，用于执行延迟任务（如数据预加载、分析上报）。 | **将大任务拆分为 ≤50ms 的块**，避免阻塞用户交互。 |
| **L** | **Load**（加载） | 页面内容加载完成的时间，尤其是首屏展现。 | **首屏加载在 1s 内完成**，或尽快让用户看到有用内容（结合网络条件）。 |

RAIL 模型强调以用户为中心，帮助开发者针对不同交互场景设置合理的性能预算，从而优化用户体验。

4. 如何优化JavaScript的执行性能？代码拆分的最佳实践是什么？
### 优化 JavaScript 执行性能
1. **减少重排与重绘**  
   - 批量修改 DOM（使用 `DocumentFragment` 或离线 DOM）。  
   - 避免频繁读取布局属性（如 `offsetTop`），可将读取缓存。  
2. **使用防抖与节流**  
   - 对滚动、输入等高频率事件进行防抖（debounce）或节流（throttle）。  
3. **合理使用定时器与帧动画**  
   - 视觉变化使用 `requestAnimationFrame`，确保与屏幕刷新同步。  
   - 非视觉任务（如数据上报）可用 `setTimeout`/`setInterval` 且注意清理。  
4. **将耗时任务拆解或移出主线程**  
   - 使用 `Web Worker` 处理复杂计算，避免阻塞 UI。  
   - 长任务拆分为多个微任务（如 `setTimeout` 分割）。  
5. **优化循环与数据操作**  
   - 优先使用普通 `for` 循环（比 `forEach` 快），避免在循环中访问全局变量。  
   - 使用合适的数据结构（如 `Map`/`Set` 替代对象进行频繁查找）。  
6. **缓存重复结果**  
   - 缓存 DOM 查询结果、计算结果（如 `memoization`）。  
7. **避免内存泄漏**  
   - 及时移除事件监听、定时器，注意闭包引用。  
8. **使用性能工具定位瓶颈**  
   - Chrome DevTools 的 Performance 面板分析主线程任务。  
9. **按需加载和代码拆分**（见下文）也间接提升初始执行性能。

### 代码拆分的最佳实践
1. **按路由拆分**  
   - 每个页面独立打包，访问时才加载对应代码（React 配合 `React.lazy` + `Suspense`）。  
2. **按组件拆分**  
   - 对非首屏组件（如弹窗、复杂图表）使用动态 `import()`，减少初始包体积。  
3. **提取第三方库**  
   - 将稳定的库（如 React、Lodash）单独打包（webpack 的 `splitChunks`），利用浏览器缓存。  
4. **合理设置分包策略**  
   - 避免分包过多导致请求数暴增；可使用 `splitChunks` 的 `cacheGroups` 将公共模块合并。  
5. **预加载关键资源**  
   - 使用 webpack 魔法注释：`import(/* webpackPrefetch: true */ './module')` 在空闲时预取。  
   - 对首屏必要但非初始的资源使用 `<link rel="preload">`。  
6. **模块联邦（微前端）**  
   - 在大型应用中，通过 Module Federation 共享公共模块，避免重复下载。  
7. **CSS 拆分**  
   - 同样可按路由拆分 CSS（如 `MiniCssExtractPlugin` 配合动态导入）。  
8. **监测与分析**  
   - 使用 `webpack-bundle-analyzer` 定期检查包体积，持续优化。

5. 什么是Paint Holding？浏览器如何避免白屏闪烁？
**Paint Holding** 是浏览器（特别是 Chrome）采用的一种渲染优化技术，旨在**消除页面导航或跨文档切换时的白屏闪烁**。当用户从当前页面跳转到新页面时，传统渲染流程会立即清除屏幕内容，然后等待新页面绘制，这可能导致短暂的白屏。Paint Holding 通过**延迟清屏并复用上一帧的像素**，直到新页面内容完全就绪，然后平滑地切换显示，从而避免视觉空白。

### 工作原理
- 当导航开始时，浏览器不会立即丢弃当前页面的渲染输出，而是“持有”其最后的可视内容。
- 同时，新页面在后台进行渲染、合成和栅格化，整个过程不更新屏幕。
- 一旦新页面所有图层准备就绪，浏览器在下一帧直接替换为新的像素，实现无缝过渡。

该技术依赖于浏览器的合成器线程和主线程的紧密协作，确保在导航期间屏幕持续显示旧内容，消除了因清屏和渲染延迟造成的闪烁。Paint Holding 对于提升用户体验，尤其是网络较慢或页面复杂时，效果显著。

6. 前端如何实现增量渲染？时间分片和优先级调度如何结合？
**增量渲染**是指将渲染工作拆分成多个小任务，分散在多个帧中完成，以避免长时间阻塞主线程导致界面卡顿。它通常与**时间分片**和**优先级调度**结合，确保高优先级任务（如用户交互）能及时响应。

### 时间分片
将一个大任务（如组件树渲染）分割成多个小单元，在每一帧的空闲时间执行一部分。浏览器提供了 `requestIdleCallback` 来在空闲时段执行低优先级任务，但更常用的是 React 的调度器（Scheduler），它利用 `MessageChannel` 或 `setTimeout` 模拟时间分片，主动让出主线程。

### 优先级调度
为不同类型的任务分配不同优先级，高优先级任务（如点击事件）可以**中断**正在进行的低优先级任务（如数据预加载），确保交互反馈迅速。React 18 的并发渲染通过优先级调度实现了可中断的渲染。

### 结合方式
- **任务拆分**：将渲染工作拆分为 fiber 节点，每个节点是工作单元。
- **时间分片**：在每帧开始前，计算剩余时间，依次处理工作单元，若时间用完则挂起，等待下一帧继续。
- **优先级中断**：当高优先级任务到来（如用户输入），调度器立即暂停当前低优先级工作，优先执行高优先级任务，完成后恢复剩余低优先级工作。

**示例**（React 并发特性）：
- `useTransition` 将状态更新标记为低优先级，允许被高优先级更新打断，避免界面卡顿。
- `useDeferredValue` 延迟非紧急部分的值，确保用户输入等紧急更新优先。

通过结合时间分片和优先级调度，前端可以实现流畅的交互体验，同时完成复杂的渲染任务。

7. 什么是INP（Interaction to Next Paint）？它和FID有什么区别？如何优化INP？
**INP（Interaction to Next Paint）** 是 Google Core Web Vitals 中即将取代 FID 的新指标，用于全面衡量页面对用户交互的响应速度。它记录从用户发起交互（如点击、按键）到浏览器完成下一次视觉更新（显示交互结果）所经过的时间。

### INP 与 FID 的核心区别

| 维度 | FID（First Input Delay） | INP（Interaction to Next Paint） |
|------|--------------------------|----------------------------------|
| **测量范围** | 仅测量页面的**首次输入延迟**，即从用户首次交互到主线程开始处理该事件的时间。 | 测量**所有交互**（点击、触摸、键盘等）的响应延迟，并取整个会话中表现最差的交互（第98百分位）作为最终值。 |
| **时间范围** | 只包含输入延迟（事件排队等待时间），不包含事件处理、渲染时间。 | 包含完整延迟：输入延迟 + 事件处理时间 + 浏览器渲染时间（直到下一帧绘制）。 |
| **目标** | 评估首次交互的感知延迟。 | 评估页面在整个生命周期中所有交互的响应性，更全面反映用户体验。 |

### 如何优化 INP

1. **减少输入延迟**  
   - 避免长任务阻塞主线程，拆分长任务（使用 `setTimeout` 或 `scheduler.postTask`）。  
   - 使用 Web Worker 处理计算密集型任务，释放主线程。  
   - 减少第三方脚本的影响，延迟加载或异步执行非关键脚本。

2. **优化事件处理程序**  
   - 精简事件回调，避免复杂计算和频繁 DOM 操作。  
   - 对高频事件（如滚动、输入）使用防抖（debounce）或节流（throttle）。  
   - 优先使用 `passive` 事件监听器（如 `{ passive: true }`）避免阻止滚动。

3. **缩短渲染时间**  
   - 避免在事件处理中触发强制重排（如反复读取并修改布局属性）。  
   - 使用 `requestAnimationFrame` 批量更新视觉变化。  
   - 减少 DOM 节点数量和样式复杂度，降低渲染成本。

4. **优化 JavaScript 执行**  
   - 减少主线程上的总任务量，按需加载代码（代码拆分）。  
   - 避免在事件回调中进行大量循环或递归，可使用 Web Worker 替代。  
   - 利用浏览器的调度器（如 `scheduler.yield()`）主动让出主线程。

5. **监控与分析**  
   - 使用 Performance API 或 Lighthouse 识别导致 INP 较差的交互。  
   - 结合 RUM（真实用户监控）收集 INP 数据，持续优化。

通过综合优化输入响应、事件处理和渲染流水线，可显著改善 INP，提供更流畅的交互体验。

8. 如何优化CSS选择器的性能？哪些选择器性能较差？
CSS 选择器的性能主要取决于浏览器的匹配机制（**从右向左匹配**），即先找到页面中所有符合最右侧选择器的元素，再逐级向上检查父元素。因此，**最右侧的选择器（关键选择器）对性能影响最大**。以下是性能较差的选择器类型及优化建议：

---

## 性能较差的选择器

1. **通用选择器 `*`**  
   - 作为关键选择器时，会匹配页面所有元素，然后逐级向上过滤，代价极高。
   - 示例：`#content *` 会先匹配所有元素，再筛选父元素为 `#content` 的。

2. **后代选择器（特别是深层嵌套）**  
   - 如 `div ul li a`，最右侧 `a` 会匹配所有链接，然后逐层检查祖先，深度越深，遍历开销越大。

3. **标签选择器单独作为关键选择器**  
   - 如 `div`、`span`，如果页面标签数量多，匹配范围就大，性能比类选择器差。

4. **属性选择器**  
   - 如 `[type="text"]`、`[class^="icon-"]`，需要遍历属性值，相对较慢。

5. **复杂伪类选择器**  
   - 如 `:nth-child`、`:nth-of-type`、`:not` 等，需要计算元素在兄弟中的位置或取反，开销较大。

6. **未限定的类/ID选择器与标签组合**  
   - 如 `div.class` 比单独 `.class` 多了一次标签检查，属于过度限定，但现代浏览器差异不大。

---

## 优化建议

1. **使用类选择器替代标签选择器**  
   - `.menu-item` 优于 `li`，减少匹配范围。

2. **避免使用通用选择器作为关键选择器**  
   - 若必须用 `*`，确保其左侧有高效限定，如 `#content *` 仍会匹配大量元素，尽量改为 `.content *` 或直接用类。

3. **减少选择器深度**  
   - 尽量不超过 3 层，可用子选择器 `>` 替代后代选择器，明确层级关系，但子选择器同样从右向左匹配，只是限制直接父级。

4. **避免过度限定**  
   - `#id` 已经是唯一，无需再加标签或类，如 `div#nav` 可简化为 `#nav`。

5. **谨慎使用属性选择器和复杂伪类**  
   - 如果必须使用，尽量让关键选择器尽量高效，如 `input[type="text"]` 可改用类 `.text-input`。

6. **利用继承减少选择器**  
   - 公共样式可设置在父元素上，子元素继承，避免为每个元素写重复选择器。

7. **采用 BEM 等命名规范**  
   - 如 `.block__element--modifier`，使选择器扁平、低特异性，减少嵌套。

8. **避免使用通配符 `*` 重置样式**  
   - 可使用 `margin:0; padding:0;` 单独指定常用元素，或使用现代重置库（如 normalize.css）有选择地重置。

9. **将复杂选择器移到外部**  
   - 例如用 JavaScript 添加类来控制样式，减少 CSS 选择器的复杂度。

10. **在开发工具中检查选择器性能**  
    - Chrome DevTools 的 Performance 面板可以记录样式重算时间，帮助定位慢选择器。

---

## 现代浏览器的影响

现代浏览器对 CSS 选择器已做了大量优化（如哈希索引、缓存等），通常几百个选择器对性能影响微乎其微。但**在移动端、低性能设备或复杂单页应用中，仍需关注**，尤其是在高频触发动效（如滚动、动画）时，避免使用昂贵的选择器。

**总结**：优先使用类选择器，保持选择器简短，避免深层嵌套和昂贵伪类，可以确保 CSS 选择器性能无忧。

9. 什么是资源hint？dns-prefetch、preconnect、prefetch、preload、modulepreload的使用场景分别是什么？
**资源提示（Resource Hints）** 是通过 `<link>` 标签或 HTTP 头部向浏览器提供的优化指令，告知未来可能需要的资源，以便浏览器提前执行部分操作（如 DNS 解析、连接建立、下载资源），从而提升页面加载性能。

### 常见资源提示的使用场景

| 资源提示 | 作用 | 使用场景 |
|----------|------|----------|
| **`dns-prefetch`** | 提前解析指定域名的 DNS，不建立连接。 | 当页面需要请求第三方域名（如 CDN、字体、API）但尚未明确具体资源时，提前解析 DNS 减少域名解析延迟。 |
| **`preconnect`** | 提前完成 DNS 解析、TCP 握手和 TLS 协商，建立完整的连接。 | 明确知道即将与某个域名建立连接（如加载字体、请求接口），节省连接建立时间，尤其适合对延迟敏感的跨域请求。 |
| **`prefetch`** | 在空闲时下载未来可能需要的资源（如下一页面），优先级较低。 | 用于预加载用户下一步可能访问的页面资源（如翻页、选项卡内容），加速后续导航，但不应占用当前页面关键资源带宽。 |
| **`preload`** | 强制浏览器立即加载当前页面必需的关键资源（如字体、首屏图片、核心 CSS/JS），具有高优先级。 | 适用于确保某些资源不会因解析顺序而延迟渲染，例如声明式提前加载字体避免 FOIT，或加载异步模块。需指定 `as` 属性。 |
| **`modulepreload`** | 专门用于 ES 模块，不仅预加载模块，还会解析编译模块（类似 `preload` 但针对模块）。 | 在基于模块的现代前端应用（如使用 import maps）中，预加载关键模块及其依赖，减少模块加载和解析时间。 |

**注意**：合理使用这些提示能优化性能，但过度或错误使用可能浪费带宽，需根据实际场景谨慎选择。

10. 前端如何实现渐进式图片加载？LQIP、SQIP、BlurHash分别是什么？
**渐进式图片加载**是一种优化用户体验的策略，先快速展示低质量或模糊的占位图，然后逐步替换为高质量原图，避免页面因等待图片而显得空白，同时减少感知加载时间。

常见的实现方案包括 **LQIP、SQIP 和 BlurHash**，它们各有特点：

---

### 1. LQIP（Low Quality Image Placeholders，低质量图片占位符）
- **原理**：生成原图的低分辨率版本（如 20x20 像素），压缩为很小的图片（通常几 KB）。页面加载时先显示这张模糊的缩略图，然后异步加载原图，加载完成后替换。
- **实现方式**：
  - 在服务端生成缩略图（如用 Sharp、ImageMagick），以 Base64 或独立图片文件嵌入 HTML/CSS。
  - 前端使用 `<img>` 或 CSS `background-image` 加载缩略图，然后用 JavaScript 加载原图并渐显。
- **优点**：简单、兼容性好，所有浏览器都支持。
- **缺点**：缩略图仍然需要下载，可能增加请求数；模糊效果较生硬。

---

### 2. SQIP（SVG-based Image Placeholders，基于 SVG 的占位符）
- **原理**：使用算法将原图简化为**由简单形状组成的 SVG**（如三角形、渐变），生成非常小的 SVG 文件（通常 500 字节到 1KB）。SVG 可以矢量化缩放，显示为艺术化的模糊轮廓，然后原图加载后覆盖。
- **实现方式**：
  - 用工具（如 [sqip](https://github.com/axe312ger/sqip)）将图片转换为 SVG 占位符。
  - 将 SVG 内联到 HTML，原图异步加载。
- **优点**：占位符体积极小，且矢量化后任何尺寸都清晰；视觉风格独特，可作为一种设计元素。
- **缺点**：生成过程较复杂，需特定工具；效果取决于图片内容，对于复杂图片可能失真。

---

### 3. BlurHash
- **原理**：将图片计算为一个**极短的 Base64 编码字符串**（通常 20-30 个字符），解码后可生成模糊的缩略图。该算法由 Wolt 开发，专门用于快速生成占位符。
- **实现方式**：
  - 服务端使用 BlurHash 库对图片编码，得到字符串。
  - 前端将字符串解码为画布图像（通过 JavaScript 库），显示为模糊占位图，然后加载原图覆盖。
- **优点**：字符串极短，可内联到 HTML 或 API 响应中，不增加额外网络请求；解码速度快，模糊效果平滑。
- **缺点**：需要前端解码库（约 3KB gzip）；无法预览颜色复杂的细节，但作为占位足够。

---

### 对比总结

| 技术 | 占位符形式 | 体积 | 实现复杂度 | 视觉质量 |
|------|------------|------|------------|----------|
| LQIP | 低分辨率图片 | 几 KB | 简单 | 模糊，可能像素化 |
| SQIP | 矢量 SVG | <1KB | 中等 | 艺术化模糊，无像素感 |
| BlurHash | 编码字符串 | <100 字节 | 中等 | 均匀模糊，无形状细节 |

**选择建议**：
- 追求简单通用：**LQIP**。
- 希望极致体积且接受艺术化风格：**SQIP**。
- 需要体积小且效果平滑，尤其适合后端 API 返回：**BlurHash**。

无论哪种方案，通常配合 **懒加载（Lazy Loading）** 使用，图片进入视口时才加载原图，进一步提升性能。

11. 什么是Passive Event Listeners？它如何提升滚动性能？
**Passive Event Listeners（被动事件监听器）** 是 DOM 规范中引入的一种事件监听选项，旨在提升页面滚动性能，特别是在触摸屏上。它通过在 `addEventListener` 中传递 `{ passive: true }` 选项来实现。

### 如何提升滚动性能？
传统的事件监听器中，即使开发者没有调用 `preventDefault()`，浏览器也必须**等待**事件处理函数执行完毕，才能确定是否阻止默认行为（如滚动）。这种等待会导致滚动产生延迟（卡顿），因为浏览器需要先执行 JavaScript 再决定是否滚动。

当设置 `{ passive: true }` 时，开发者明确告诉浏览器：**“我不会在这个事件处理函数中调用 `preventDefault()`，请放心地立即执行默认行为（如滚动）。”** 于是浏览器可以在不等待 JavaScript 的情况下，同步处理滚动，从而大幅提升滚动的流畅度。

### 使用场景与示例
- **典型应用**：`touchstart`、`touchmove`、`wheel` 等可能触发滚动的移动端事件。
  ```javascript
  // 优化滚动性能
  document.addEventListener('touchmove', handler, { passive: true });
  ```
- **注意**：如果在被动监听器中调用 `preventDefault()`，浏览器会忽略它（并可能在控制台警告），因为已经承诺不会阻止默认行为。

### 浏览器默认行为
现代浏览器已将某些事件（如 `touchstart`、`touchmove`、`wheel`）在 `window`、`document` 和 `body` 上的监听器默认设为 `{ passive: true }`，以自动优化滚动。但手动添加监听器时，建议显式指定以覆盖默认或确保性能。

通过使用被动事件监听器，可以消除滚动延迟，让页面滑动像原生应用一样顺滑。

12. 如何优化字体加载性能？font-display的各个值（auto、block、swap、fallback、optional）有什么区别？
优化字体加载性能的核心是控制字体下载和渲染的行为，以减少不可见文本（FOIT）和布局偏移。主要策略包括：

### 1. 使用 `font-display` 属性
`font-display` 是 CSS 中用于控制自定义字体加载过程的属性，它定义了字体在加载不同阶段（阻塞期、交换期、失败期）的行为。五个值的区别如下：

| 值 | 阻塞期（Block Period） | 交换期（Swap Period） | 行为描述 | 适用场景 |
|-----|------------------------|------------------------|----------|----------|
| **`auto`** | 由浏览器决定（通常同 `block`） | 浏览器决定 | 浏览器默认策略，通常类似于 `block`，但具体行为可能不同。 | 不确定用户偏好的默认值。 |
| **`block`** | 约 3 秒 | 无限期 | 在阻塞期内，文本使用不可见的回退字体（FOIT），若 3 秒内字体加载成功，则立即显示自定义字体；若超过 3 秒，则切换到回退字体，但一旦字体加载完成，仍会交换为自定义字体。 | 需要优先保证自定义字体显示，能接受短暂不可见文本的场景（如 Logo、标题）。 |
| **`swap`** | 极短（通常 ≤100ms） | 无限期 | 阻塞期极短，立即使用回退字体显示文本（FOUT），当自定义字体加载成功后立即交换。 | 希望文本尽快可见，允许字体切换导致样式变化（如正文内容）。 |
| **`fallback`** | 极短（约 100ms） | 约 3 秒 | 阻塞期短，立即显示回退字体，但在约 3 秒内若自定义字体加载成功，则交换；超过 3 秒后即使字体加载完成也不再交换，保持回退字体。 | 平衡性能和显示，适用于对字体要求中等，且希望避免后期突然切换的场景。 |
| **`optional`** | 极短（≤100ms） | 无 | 浏览器判断字体是否可能快速加载（如缓存中），若是则使用自定义字体；否则直接使用回退字体，且永不交换。 | 对性能敏感，字体非必要（如系统字体即可），避免因字体下载拖慢渲染。 |

**注意**：不同浏览器对时间阈值的实现可能略有差异，但基本符合上述描述。

### 2. 其他优化技巧
- **预加载关键字体**：使用 `<link rel="preload" as="font">` 提前下载字体，避免解析到 CSS 时才发起请求。
- **子集化字体**：通过 `unicode-range` 只加载页面用到的字符，大幅减少字体文件体积。
- **使用现代字体格式**：优先使用 WOFF2，它压缩率更高。
- **利用可变字体**：单个文件包含多种字重和样式，减少请求数。
- **合理设置缓存**：通过强缓存或协商缓存，避免重复下载。
- **考虑系统字体作为回退**：指定合适的回退字体族（如 `sans-serif`），确保降级时风格接近。

结合 `font-display` 和上述优化，可以有效提升字体加载性能，在确保文本可见的同时，尽可能使用设计所需的自定义字体。

13. 什么是Navigation Timing API和Resource Timing API？如何使用它们监控性能？
**Navigation Timing API** 和 **Resource Timing API** 是浏览器提供的性能监控接口，允许开发者以编程方式获取页面导航和资源加载的详细时间数据，从而分析性能瓶颈。

---

## Navigation Timing API
用于测量**页面导航和加载**各个阶段的时间，包括重定向、DNS 查询、TCP 连接、请求响应、DOM 解析等。

### 如何使用
```javascript
const perfData = performance.getEntriesByType('navigation')[0];
console.log(perfData);
```
返回的 `PerformanceNavigationTiming` 对象包含以下关键时间戳（以毫秒为单位）：
- `startTime`：开始导航的时间（通常为 0）
- `redirectStart` / `redirectEnd`：重定向开始/结束时间
- `domainLookupStart` / `domainLookupEnd`：DNS 查询开始/结束时间
- `connectStart` / `connectEnd`：TCP 连接建立时间（含 TLS 握手）
- `requestStart` / `responseStart`：请求开始/收到首个字节时间（TTFB）
- `responseEnd`：响应接收完成时间
- `domInteractive`：DOM 解析完成，DOMContentLoaded 事件即将触发
- `domContentLoadedEventStart` / `domContentLoadedEventEnd`：DOMContentLoaded 事件开始/结束
- `loadEventStart` / `loadEventEnd`：load 事件开始/结束
- `duration`：整个导航耗时（通常到 loadEventEnd）

通过计算差值可得到各阶段耗时：
```javascript
const ttfb = perfData.responseStart - perfData.requestStart;
const domLoad = perfData.domContentLoadedEventEnd - perfData.domContentLoadedEventStart;
```

---

## Resource Timing API
用于监控**单个资源**（图片、样式、脚本、XHR 等）的加载性能。

### 如何使用
```javascript
const resources = performance.getEntriesByType('resource');
resources.forEach(resource => {
  console.log(resource.name, resource.duration, resource.transferSize);
});
```
每个 `PerformanceResourceTiming` 对象包含类似 Navigation Timing 的时间属性，但针对该资源：
- `initiatorType`：发起资源的类型（如 `img`、`script`、`fetch`）
- `name`：资源的 URL
- `transferSize`：传输大小（字节）
- `decodedBodySize`：解码后大小
- 其他时间属性与 Navigation Timing 类似（如 `responseStart`、`responseEnd`）

可用来统计：
```javascript
const slowResources = resources.filter(r => r.duration > 1000); // 找出加载超 1s 的资源
const totalSize = resources.reduce((sum, r) => sum + (r.transferSize || 0), 0);
```

---

## 监控性能的常见做法
1. **收集数据**：在页面适当阶段（如 `load` 事件后）通过 `performance.getEntriesByType()` 获取性能条目。
2. **计算关键指标**：
   - **TTFB**（首字节时间）：`responseStart - requestStart`
   - **FCP**（首次内容绘制）：需结合 Paint Timing API（`performance.getEntriesByType('paint')`）
   - **DOM 解析耗时**：`domInteractive - responseEnd`
   - **资源加载总耗时**：最大资源的 `duration` 或总和
3. **上报分析**：将数据发送到后端监控系统（如 Google Analytics、自建 RUM 平台），用于长期监测真实用户体验。

**注意**：这些 API 在页面关闭后数据依然可用，但上报应在用户离开前完成（可使用 `sendBeacon` 或监听 `visibilitychange`）。所有现代浏览器均支持。

14. 前端如何实现组件的按需加载？动态导入的最佳实践是什么？
**按需加载（懒加载）** 是一种优化策略，仅在需要时才加载组件或资源，减少首屏资源体积，提升页面加载速度。其核心机制是**动态导入（`import()`）**，它返回一个 Promise，允许在运行时异步加载模块。

---

## 实现组件的按需加载

### 1. 动态导入语法
```javascript
import(/* webpackChunkName: "my-chunk" */ './MyComponent')
  .then(module => {
    // 使用模块
    const MyComponent = module.default;
  })
  .catch(err => console.error('加载失败', err));
```

### 2. 在框架中应用

#### React
- 使用 `React.lazy` 包裹动态导入，返回一个可渲染的组件。
- 配合 `<Suspense>` 显示加载占位。
```jsx
const MyComponent = React.lazy(() => import('./MyComponent'));

function App() {
  return (
    <Suspense fallback={<div>Loading...</div>}>
      <MyComponent />
    </Suspense>
  );
}
```
- **路由懒加载**：在 React Router 中同样使用 `React.lazy` 加载路由组件。

#### Vue
- 使用 `defineAsyncComponent` 定义异步组件。
```javascript
const MyComponent = defineAsyncComponent(() => import('./MyComponent.vue'));
```
- 或在路由配置中直接返回 `import()`。
```javascript
const routes = [
  { path: '/foo', component: () => import('./Foo.vue') }
];
```

#### 原生或其它框架
- 直接调用 `import()` 并在回调中动态插入组件/脚本。

---

## 动态导入的最佳实践

1. **合理划分代码块**  
   - **路由级别**：每个路由对应一个 chunk，访问时加载。  
   - **组件级别**：对非首屏的大组件（如弹窗、复杂图表）进行拆分。  
   - **库级别**：将第三方库单独拆包（如 `vendor`），利用缓存。

2. **命名 chunk**（Webpack 魔法注释）  
   使用 `/* webpackChunkName: "name" */` 为 chunk 指定名称，便于识别和管理。
   ```javascript
   import(/* webpackChunkName: "modal" */ './Modal');
   ```

3. **预加载/预获取关键资源**  
   - `webpackPrefetch`：在空闲时加载将来可能需要的资源。
   - `webpackPreload`：立即加载当前导航需要的资源（高优先级）。
   ```javascript
   import(/* webpackPrefetch: true */ './NextPage');
   ```

4. **错误处理与降级**  
   添加 `.catch()`，在加载失败时显示重试按钮或错误提示，避免应用崩溃。

5. **避免过度拆分**  
   碎片化过多的文件会增加 HTTP 请求数（但 HTTP/2 多路复用可缓解）。需权衡 chunk 数量与体积，通常单个 chunk 小于 30KB 时收益递减。

6. **与服务端渲染（SSR）兼容**  
   在 SSR 中，动态导入需特殊处理，例如使用 `@loadable/component` 或 Next.js 的 `dynamic` 函数，它们能确保服务端正确加载模块并避免水合错误。

7. **使用缓存策略**  
   确保动态 chunk 的 URL 带有哈希，实现长期缓存。

8. **模块格式一致性**  
   确保动态导入的模块使用默认导出或具名导出，并在使用时正确引用（如 `module.default`）。

通过以上实践，可以在保证性能的同时，提供流畅的用户体验。

15. 什么是Layout Shift？如何避免CLS（Cumulative Layout Shift）问题？
**Layout Shift（布局偏移）** 是指页面在加载过程中，可见元素的位置突然发生变化（例如图片加载后撑开空间、广告插入导致内容下移）。这种偏移会干扰用户操作，造成不良体验。

**Cumulative Layout Shift（累积布局偏移，CLS）** 是 Core Web Vitals 之一，用于量化页面整个生命周期中所有意外布局偏移的总和。CLS 分数越低越好（建议 < 0.1）。

### 常见导致 CLS 的原因
- 图片、视频、iframe 等资源未指定尺寸，加载后改变周围布局。
- 动态插入的内容（如广告、横幅）未预留空间。
- 使用 Web 字体导致文本重新渲染（FOIT/FOUT）。
- 等待网络响应后更新 DOM 元素。
- CSS 动画或过渡影响元素位置。

### 如何避免 CLS
1. **为媒体元素设置明确尺寸**  
   为 `<img>`、`<video>`、`<iframe>` 添加 `width` 和 `height` 属性，或使用 CSS `aspect-ratio` 固定宽高比，浏览器可在加载前预留空间。
   ```css
   img { aspect-ratio: 16 / 9; width: 100%; height: auto; }
   ```

2. **预留动态内容的位置**  
   对于广告、弹窗等，预先分配相同尺寸的占位容器，或使用骨架屏保持空间。

3. **避免在现有内容上方插入内容**  
   除非是用户交互触发的（如点击展开），否则不要在视觉上推走已有内容。若必须插入，确保下方有足够空间或使用绝对定位。

4. **优化字体加载**  
   使用 `font-display: optional` 或 `swap` 并配合 `size-adjust` 等属性，减少字体切换导致的布局偏移。

5. **对动画使用 transform**  
   避免使用会改变布局的属性（如 `top`、`left`、`width`），优先使用 `transform: translate()` 或 `scale()`，它们不会触发布局偏移。

6. **懒加载占位**  
   对于懒加载的图片或组件，预先使用相同尺寸的占位元素。

7. **监控与测试**  
   使用 Lighthouse、Chrome DevTools 的 Performance 面板或 Web Vitals 扩展识别导致 CLS 的元素，并进行修复。

通过以上措施，可以显著降低 CLS 分数，提升页面视觉稳定性。

16. 如何优化第三方脚本的加载？async和defer属性有什么区别？
第三方脚本（如广告、分析工具、社交插件）往往会拖慢页面加载速度，影响用户体验和核心性能指标。优化第三方脚本的核心原则是：**尽可能推迟其加载和执行，减少对主线程的阻塞**。

---

## 一、优化第三方脚本的常见策略

1. **使用 `async` 或 `defer` 属性**  
   让脚本在不阻塞 HTML 解析的同时加载，具体区别见下文。

2. **预连接和预解析**  
   - `<link rel="preconnect" href="https://third-party.com">`：提前建立连接，减少 DNS+TCP+TLS 开销。  
   - `<link rel="dns-prefetch" href="https://third-party.com">`：仅 DNS 解析，更轻量但效果弱于 preconnect。

3. **延迟加载脚本**  
   - 将脚本动态插入到页面（例如在 `load` 事件后加载）。  
   - 使用 Intersection Observer 实现“滚动到可视区域才加载”。

4. **使用服务端代理**  
   将第三方脚本放到自己的服务器上，并合并请求、开启强缓存，减少跨域开销。

5. **优先使用轻量替代方案**  
   例如使用精简版的 Google Analytics（`gtag.js` 替代 `analytics.js`），或选择性能更好的第三方服务。

6. **合理设置资源提示**  
   对首屏必要的第三方脚本，可使用 `preload` 提前下载（需指定 `as` 类型），但需谨慎，可能抢占关键资源带宽。

---

## 二、`async` 和 `defer` 的区别

两者都是用于控制脚本加载和执行时机的 `<script>` 属性，主要区别如下：

| 特性 | `async` | `defer` |
|------|---------|---------|
| **加载时机** | 下载过程不阻塞 HTML 解析，下载完成后立即停止解析并执行脚本。 | 下载过程不阻塞 HTML 解析，等待 HTML 解析完成后（DOMContentLoaded 前）按顺序执行。 |
| **执行时机** | 脚本下载完成后立即执行，可能在 HTML 解析中途执行。 | 在 HTML 解析完成后，`DOMContentLoaded` 事件之前执行。 |
| **执行顺序** | **不保证顺序**：多个 `async` 脚本谁先下载完谁先执行。 | **保证顺序**：按照在页面中出现的先后顺序依次执行。 |
| **适用场景** | 独立、互不依赖的第三方脚本（如广告、分析），且不依赖于 DOM 完全解析。 | 需要操作 DOM 或依赖其他脚本的模块，例如 `jQuery`、业务逻辑库。 |
| **对 DOMContentLoaded 的影响** | 可能在 DOMContentLoaded 之前或之后执行，取决于下载速度。 | 总是在 DOMContentLoaded 之前执行。 |

### 图示对比
```html
<!-- 默认（同步） -->
<script src="a.js"></script>           <!-- 阻塞解析，直到下载并执行 -->

<!-- async -->
<script async src="b.js"></script>      <!-- 下载不阻塞，执行可能阻塞 -->

<!-- defer -->
<script defer src="c.js"></script>      <!-- 下载不阻塞，解析完按顺序执行 -->
```

**最佳实践**：
- 对于不依赖页面 DOM 且不需要保证顺序的第三方脚本，使用 `async`。
- 对于需要操作 DOM 或依赖其他脚本的第三方库，使用 `defer`。
- 若脚本与首屏无关，可考虑动态插入（`document.createElement('script')`）并延迟加载。

通过合理组合上述优化，可以最大程度减少第三方脚本对页面核心体验的负面影响。

17. 什么是Content Visibility？它如何优化渲染性能？contain-intrinsic-size的作用是什么？
**Content Visibility** 是 CSS 中用于控制元素渲染的优化属性，通过 `content-visibility` 实现。它可以跳过屏幕外元素的渲染（包括布局和绘制），从而显著提升页面的初始加载和滚动性能。

### `content-visibility` 的工作原理
- 当设置 `content-visibility: auto` 时，浏览器会智能判断元素是否在视口内：
  - **屏幕外元素**：跳过其渲染（包括子树的样式计算、布局和绘制），仅保留占位空间。
  - **进入视口时**：自动恢复渲染，元素无缝显示。
- 这类似于懒渲染，但由浏览器原生实现，比手动懒加载更高效。

**示例**：
```css
.card {
  content-visibility: auto;
}
```

**优化性能**：
- 减少初始渲染时间，尤其适用于长列表、无限滚动或复杂组件。
- 滚动时，浏览器只渲染即将进入视口的元素，保持流畅。

---

### `contain-intrinsic-size` 的作用
当使用 `content-visibility: auto` 时，浏览器需要知道元素在未渲染时的尺寸，以正确计算布局和占位空间。`contain-intrinsic-size` 就用来为元素**提供一个默认的尺寸**，防止因元素内容未渲染而导致布局偏移（CLS）。

**语法**：
```css
.element {
  content-visibility: auto;
  contain-intrinsic-size: 100px 200px; /* 宽度 100px，高度 200px */
}
```
- 可以只指定一个值（同时用于宽高）或两个值（宽度和高度）。
- 也可以使用 `contain-intrinsic-width` 和 `contain-intrinsic-height` 单独设置。

**作用**：
- 告诉浏览器该元素在未渲染时的预估大小，确保页面在元素渲染前后布局稳定，避免跳跃。
- 如果不设置，浏览器可能默认使用最小尺寸（如 0），导致元素进入视口时突然撑开，引发 CLS。

---

**总结**：`content-visibility` 与 `contain-intrinsic-size` 结合使用，既能跳过屏幕外渲染提升性能，又能通过预设尺寸保证布局稳定性，是优化长列表和复杂页面的利器。

18. 前端如何实现预渲染（Prerendering）？和SSR、SSG有什么区别？
**预渲染（Prerendering）** 是指在**构建阶段**为单页应用（SPA）的每个路由生成对应的静态 HTML 文件。用户访问时直接返回这些预先生成的 HTML，然后在客户端进行 hydration，使其成为可交互的 SPA。其目的是改善首屏加载速度和 SEO（因为搜索引擎可以直接抓取完整内容）。

### 如何实现预渲染？
- **使用插件**：例如在 Webpack 构建流程中加入 `prerender-spa-plugin`，它会模拟浏览器访问路由并抓取渲染后的 HTML。
- **框架方案**：例如 React 的 `react-snap`，或 Vue 的 `prerender-spa-plugin`。
- **手动爬取**：使用 Puppeteer 在构建后自动访问页面并保存 HTML。

---

### 与 SSR、SSG 的区别

| 特性 | 预渲染 (Prerendering) | 静态站点生成 (SSG) | 服务端渲染 (SSR) |
|------|------------------------|---------------------|------------------|
| **渲染时机** | 构建时 | 构建时 | 每次请求时 |
| **内容类型** | 适用于内容变化不频繁的页面 | 适用于内容相对静态的页面 | 适用于动态、个性化内容 |
| **实现方式** | 构建时抓取 SPA 路由生成 HTML | 框架（如 Next.js）在构建时执行数据获取并生成 HTML | 服务器在请求时执行数据获取并渲染 HTML |
| **优点** | 改善 SPA 的 SEO 和首屏，无需服务器 | 极快的首屏响应，可托管于 CDN | 实时数据，适合高动态内容 |
| **缺点** | 内容更新需要重新构建 | 内容更新需重新构建 | 服务器负载较高，响应略慢 |

**总结**：
- **预渲染** 是针对 SPA 的优化手段，本质是构建时静态生成。
- **SSG** 是框架级的静态生成，与预渲染目标一致，但通常集成在开发流程中。
- **SSR** 是实时渲染，适合动态内容。

19. 什么是Performance Observer API？如何使用它监控PerformanceEntry？
**PerformanceObserver API** 是一种用于监控性能条目（PerformanceEntry）的接口，它允许开发者订阅特定类型的性能事件（如资源加载、绘制时间、长任务等），并在这些事件发生时异步接收通知。这比手动轮询 `performance.getEntries()` 更高效、更及时，且能避免遗漏那些可能在轮询间隙发生并很快被丢弃的条目（如 `mark` 和 `measure`）。

---

### 如何使用 PerformanceObserver

#### 1. 创建观察者实例
```javascript
const observer = new PerformanceObserver((list, observer) => {
  // 获取当前批次的所有性能条目
  const entries = list.getEntries();
  entries.forEach(entry => {
    console.log(entry.entryType, entry.name, entry.startTime, entry.duration);
  });
});
```

#### 2. 配置要观察的条目类型
调用 `observer.observe()` 并传入一个对象，指定 `entryTypes` 数组（要监听的类型）或 `type` 单个类型。
```javascript
// 同时观察多种类型
observer.observe({ entryTypes: ['resource', 'paint', 'layout-shift'] });

// 观察单一类型（推荐，更清晰）
observer.observe({ type: 'largest-contentful-paint' });
```

#### 3. 可选：获取缓冲区的历史条目
如果希望在观察开始时立即获取已经产生的条目（例如页面加载初期的事件），可以添加 `buffered: true` 选项：
```javascript
observer.observe({ type: 'paint', buffered: true });
```
此时回调会立即收到之前已经记录但尚未被处理的 paint 条目。

#### 4. 断开观察
不再需要时，可以断开观察者以释放资源：
```javascript
observer.disconnect();
```

---

### 常见的 PerformanceEntry 类型

| entryType | 描述 |
|-----------|------|
| `'navigation'` | 页面导航相关的计时（页面加载各阶段），即 `PerformanceNavigationTiming` |
| `'resource'` | 资源加载（图片、脚本、样式等）的计时，即 `PerformanceResourceTiming` |
| `'paint'` | 首次绘制（FP）和首次内容绘制（FCP） |
| `'largest-contentful-paint'` | 最大内容绘制（LCP） |
| `'first-input'` | 首次输入延迟（FID）的相关数据 |
| `'layout-shift'` | 布局偏移（CLS）的单个偏移事件 |
| `'longtask'` | 长任务（超过 50ms 的任务） |
| `'mark'` / `'measure'` | 自定义性能标记和测量（通过 `performance.mark()` 创建） |
| `'element'` | 元素渲染计时（如 Largest Contentful Paint 对应的元素） |

---

### 示例：实时监控资源加载
```javascript
const observer = new PerformanceObserver((list) => {
  list.getEntries().forEach(entry => {
    if (entry.entryType === 'resource') {
      console.log(`资源加载：${entry.name}，耗时：${entry.duration}ms`);
    }
  });
});
observer.observe({ entryTypes: ['resource'] });
```

---

### 优点与注意事项
- **优点**：
  - 异步处理，不阻塞主线程。
  - 可以捕获那些仅在特定时刻存在的条目（如 `'mark'`）。
  - 支持 `buffered` 选项，避免丢失早期数据。
- **注意事项**：
  - 浏览器兼容性：现代浏览器基本都支持，但某些类型（如 `'layout-shift'`、`'largest-contentful-paint'`）需要较新版本。
  - 在回调中应避免执行耗时操作，以免影响性能条目本身的准确性。

PerformanceObserver 是构建性能监控工具、上报真实用户性能数据（RUM）的基础，也是开发者理解和优化页面性能的重要接口。

20. 如何优化动画性能？will-change属性的正确使用方式是什么？
## 优化动画性能的关键方法

动画性能优化的核心目标是**保持 60fps 的流畅度**，避免主线程阻塞和布局抖动。以下是一些有效手段：

### 1. 使用合适的 CSS 属性
- **优先使用 `transform` 和 `opacity`**：这两个属性由合成器（compositor）单独处理，不会触发布局（Layout）和绘制（Paint），性能最佳。
- **避免动画触发 Layout 的属性**：例如 `width`、`height`、`top`、`left`、`margin` 等，它们会导致重排（reflow）和重绘，消耗较大。

### 2. 利用硬件加速
- 通过设置 `will-change` 或使用 3D 变换（如 `translateZ(0)`）将元素提升为独立合成层（Compositing Layer），由 GPU 处理动画，避免影响主线程。
- 但不要滥用，否则会占用过多内存。

### 3. 减少主线程负担
- 使用 `requestAnimationFrame` 同步动画循环，避免掉帧。
- 将耗时计算移至 Web Worker，避免阻塞主线程。
- 避免在动画过程中执行高开销的 JavaScript 操作。

### 4. 简化渲染复杂度
- 降低动画元素的层级深度，减少层叠上下文数量。
- 对复杂动画，考虑使用 Canvas 或 WebGL 替代 CSS 动画。

### 5. 合理使用 `will-change`

---

## `will-change` 属性的正确使用方式

`will-change` 是一个 CSS 属性，用于**提前告知浏览器**某个元素即将发生的变化，以便浏览器提前进行优化（如创建合成层），从而提升动画流畅度。

### 基本语法
```css
.element {
  will-change: transform, opacity;  /* 告知即将变化的属性 */
}
```

### 正确使用方式
1. **只在即将变化时应用**  
   - 在动画开始前通过 JavaScript 添加 `will-change`，动画结束后移除。
   - 避免在默认样式表中滥用（长期设置会导致内存占用）。
   ```javascript
   element.addEventListener('mouseenter', () => {
     element.style.willChange = 'transform';
   });
   element.addEventListener('animationend', () => {
     element.style.willChange = 'auto';
   });
   ```

2. **针对将要变化的属性**  
   - 只指定确实会变化的属性（如 `transform`、`opacity`、`top`、`left`），不要列出无关属性。
   - 如果同时变化多个属性，可以逗号分隔。

3. **适度使用**  
   - 只对需要动画的关键元素使用，避免为大量元素设置 `will-change`，否则会占用 GPU 内存，反而降低性能。

4. **作为最后的手段**  
   - 先尝试优化动画本身，如果遇到卡顿且无法通过其他方式优化，再使用 `will-change`。

### 错误用法
```css
/* 不要对所有元素滥用 */
* {
  will-change: transform;
}
```
这会导致每个元素都创建合成层，内存爆炸，性能急剧下降。

### 浏览器如何响应 `will-change`
- 浏览器会将该元素提升到合成层，使其动画由 GPU 加速。
- 对于某些属性（如 `transform`），会提前准备该层，避免动画启动时的创建开销。
- 注意：`will-change` 是提示而非命令，浏览器可能忽略。

通过结合上述优化方法和正确使用 `will-change`，可以显著提升动画的流畅度，实现丝滑的用户体验。

21. 什么是HTTP/3和QUIC协议？它们对前端性能有什么影响？
HTTP/3 是基于 **QUIC 协议** 的下一代 HTTP 协议。QUIC（Quick UDP Internet Connections）最初由 Google 开发，后成为 IETF 标准。它将传输层从 TCP 改为 UDP，并集成了 TLS 加密，旨在解决 TCP 的固有局限性，从而显著提升网络性能，尤其对前端用户体验有积极影响。

---

## 1. QUIC 协议的核心特性
- **基于 UDP 的多路复用**：QUIC 在单个连接上支持多个独立的流，流之间相互隔离，避免了 TCP 的队头阻塞（HOL）——即使一个流丢包，其他流不受影响。
- **更快的连接建立**：QUIC 结合了传输和加密握手，通常只需 1-RTT（往返时间）甚至 0-RTT 即可建立连接并发送数据，相比 TCP+TLS 的 2~3 RTT 大幅缩短延迟。
- **连接迁移**：QUIC 使用连接 ID 而非 IP+端口标识连接，当网络切换（如 Wi-Fi 切换到 4G）时连接保持不变，无需重连。
- **内置加密**：所有 QUIC 流量默认加密，TLS 集成在协议内部，减少了协商开销并增强安全性。
- **改进的拥塞控制和丢包恢复**：每个流独立控制，可更精细地调整。

## 2. HTTP/3 如何利用 QUIC
HTTP/3 将 HTTP/2 的帧和流映射到 QUIC 的流上，继承了 QUIC 的所有优势，同时使用新的 QPACK 头部压缩算法（替代 HPACK），解决流间头部阻塞问题。

---

## 3. 对前端性能的影响

### 3.1 减少页面加载延迟
- **0-RTT 连接**：对于重复访问的用户，可以直接发送请求，无需等待握手，显著缩短首字节时间（TTFB）。
- **更快的 TLS 握手**：QUIC 将传输与加密握手合并，比传统 TCP+TLS 更高效。

### 3.2 消除队头阻塞
- HTTP/2 虽然多路复用，但底层 TCP 的队头阻塞依然存在——如果一个 TCP 包丢失，后续所有流都必须等待重传。QUIC 的流独立隔离，丢包只影响对应的流，其他资源可继续加载，尤其适合包含大量小资源的现代网页。

### 3.3 更好的弱网和移动网络表现
- **连接迁移**：用户在移动网络环境下切换 Wi-Fi 或蜂窝网络时，连接不中断，视频、文件上传等长连接任务不会重新开始。
- **更好的拥塞控制**：QUIC 可在用户空间实现更灵活的算法，适应动态网络，减少重传延迟。

### 3.4 提升多路复用的效率
- 单个 QUIC 连接可以并行传输多个 HTTP 请求/响应，无需像 HTTP/1.1 那样建立多个连接，也无需担心 TCP 连接数限制。这降低了服务器资源消耗，同时避免了连接竞争。

### 3.5 头部压缩优化
- QPACK 专门针对 QUIC 的流特性设计，解决了 HPACK 在流间可能产生的队头阻塞，使头部传输更高效。

---

## 4. 实际收益场景
- **首屏加载**：0-RTT 和快速握手让首屏内容更快到达。
- **图片/脚本并发加载**：多个资源并行传输不受单个丢包影响。
- **实时通信**：如 WebSocket 替代方案，QUIC 的低延迟和连接迁移优势明显。
- **移动端体验**：用户在网络切换时页面不会卡顿或重连。

---

## 5. 采用现状
- 主流浏览器（Chrome、Firefox、Safari、Edge）均已支持 HTTP/3。
- 大型 CDN 和网站（如 Google、Facebook、Cloudflare）已部署 HTTP/3。

尽管 HTTP/3 在初期可能因 UDP 在某些网络中受限而回退到 HTTP/2，但随着基础设施升级，其性能优势将愈发明显。前端开发者无需修改代码即可受益，因为协议协商由浏览器和服务器自动完成。

22. 前端如何实现离线优先（Offline First）策略？Service Worker的缓存策略有哪些？
**离线优先（Offline First）** 是一种应用设计理念，确保应用在无网络连接时仍能提供核心功能，并在网络恢复后自动同步数据。实现这一策略通常依赖 **Service Worker** 和客户端存储（如 Cache API、IndexedDB），通过智能缓存和后台同步来提升用户体验。

---

## 一、实现离线优先的关键技术

1. **Service Worker**  
   作为浏览器与网络之间的代理脚本，可拦截网络请求，决定从缓存返回还是从网络获取，并管理缓存内容。

2. **Cache API**  
   用于存储静态资源（HTML、CSS、JS、图片）的键值对缓存，配合 Service Worker 实现资源离线访问。

3. **IndexedDB**  
   存储结构化数据（如用户生成的内容、API 响应），支持复杂查询和离线数据操作，网络恢复后与服务器同步。

4. **Background Sync**  
   允许 Service Worker 在网络恢复时自动重试失败请求，确保数据最终一致。

---

## 二、Service Worker 的缓存策略

以下是五种核心缓存策略，可根据资源类型和业务需求组合使用。

### 1. Cache Only（仅缓存）
- **流程**：只从缓存中读取，不发送网络请求。若缓存未命中则失败。
- **适用场景**：永远不会变化的静态资源（如版本固定的库、Logo）。
- **优点**：最快，无网络依赖。
- **缺点**：更新需更新 Service Worker 并清理旧缓存。

### 2. Network Only（仅网络）
- **流程**：始终从网络获取，不使用缓存。
- **适用场景**：实时性要求高的数据（如股票价格、用户状态）。
- **优点**：数据最新。
- **缺点**：离线时完全不可用。

### 3. Cache First， falling back to Network（缓存优先，网络后备）
- **流程**：先查缓存，命中则返回；否则请求网络，并将响应存入缓存后返回。
- **适用场景**：不常变化的资源（如 CSS、JS、字体、头像），适合提升重复访问速度。
- **优点**：快速，减少网络流量。
- **缺点**：缓存过期后需要更新机制（如版本管理）。

### 4. Network First， falling back to Cache（网络优先，缓存后备）
- **流程**：先尝试网络请求，成功则返回并更新缓存；若网络失败（超时或离线），则返回缓存。
- **适用场景**：数据更新频繁但仍需离线访问的页面（如新闻列表、博客文章）。
- **优点**：尽可能保证内容新鲜，同时提供离线回退。
- **缺点**：网络慢时可能延迟。

### 5. Stale-While-Revalidate（更新后重新验证）
- **流程**：同时从缓存和网络获取。先返回缓存（如有），同时发起网络请求，获取后更新缓存，下次访问使用新内容。
- **适用场景**：资源可容忍短暂过时，但又希望后台更新的场景（如头像、分析脚本）。
- **优点**：极快响应，且后台保持更新。
- **缺点**：首次访问可能使用旧内容，但通常可接受。

---

## 三、离线优先策略的完整实现步骤

1. **注册 Service Worker**，并在 `install` 事件中预缓存关键资源（HTML 骨架、CSS、基础 JS）。
2. **在 `fetch` 事件中**，根据请求类型选择合适的缓存策略（例如对 HTML 用 Network First，对静态资源用 Cache First）。
3. **使用 IndexedDB 存储动态数据**，并实现后台同步：当网络离线时，将用户操作暂存，网络恢复后通过 `sync` 事件发送到服务器。
4. **提供友好的离线界面**：检测网络状态，告知用户当前处于离线模式，并展示可用的缓存内容。
5. **定期清理旧缓存**，避免磁盘空间溢出。

---

## 四、示例代码（简化版）

```javascript
// Service Worker 部分
self.addEventListener('install', event => {
  event.waitUntil(
    caches.open('static-v1').then(cache => cache.addAll([
      '/',
      '/styles/main.css',
      '/scripts/app.js'
    ]))
  );
});

self.addEventListener('fetch', event => {
  const request = event.request;
  // 对 HTML 请求使用 Network First
  if (request.mode === 'navigate') {
    event.respondWith(
      fetch(request).catch(() => caches.match('/offline.html'))
    );
  } else {
    // 对静态资源使用 Cache First
    event.respondWith(
      caches.match(request).then(response => response || fetch(request))
    );
  }
});
```

通过上述策略和工具，前端可以实现强大的离线优先体验，让应用在弱网或无网环境下依然可用，显著提升用户满意度。

25. 什么是关键CSS（Critical CSS）？如何提取和内联关键CSS？
**关键 CSS（Critical CSS）** 是指页面首屏（或初始视口）渲染所必需的 CSS 规则。提取并内联关键 CSS 可以消除渲染阻塞，使浏览器尽早绘制内容，显著提升首次内容绘制（FCP）和最大内容绘制（LCP）的性能。

---

## 为什么要提取和内联关键 CSS？
- **默认情况**：浏览器需要下载并解析完所有 CSS 文件后才开始渲染页面，导致白屏时间过长。
- **优化后**：将首屏必需的 CSS 内联在 `<head>` 中，浏览器无需等待外部 CSS 即可立即渲染，同时剩余的非关键 CSS 可异步加载，不影响首屏。

---

## 如何提取关键 CSS？

### 1. 手动分析（不推荐）
通过浏览器开发者工具识别首屏元素对应的样式，但效率低、难以维护。

### 2. 自动化工具
常用工具会根据指定的视口尺寸（如 1300x900）遍历页面，收集渲染时实际应用的 CSS 规则。

#### 常用工具
- **Critical**：Node.js 库，可生成关键 CSS 并自动内联。
- **Penthouse**：Critical 的核心依赖，也可单独使用。
- **criticalCSS**：另一个流行的提取工具。
- **构建插件**：
  - Webpack：`critters-webpack-plugin`、`html-critical-webpack-plugin`。
  - Next.js：内置优化，通过 `next.config.js` 的 `experimental.criticalCSS` 或自动提取。

### 3. 使用 Critical 库（示例）
```bash
npm install -g critical
```

```bash
critical https://example.com --base . --width 1300 --height 900 --inline > index-critical.html
```
该命令会生成一个内联了关键 CSS 的新 HTML 文件。

### 4. 集成到构建流程（Webpack 示例）
```js
const Critters = require('critters-webpack-plugin');

module.exports = {
  plugins: [
    new Critters({
      preload: 'media', // 预加载非关键 CSS
      preloadFonts: true, // 预加载字体
    }),
  ],
};
```
该插件在构建时自动提取关键 CSS 并内联，同时将剩余 CSS 异步加载。

---

## 如何内联关键 CSS？
1. **直接嵌入**：将提取的 CSS 代码放入 HTML 的 `<style>` 标签中，通常放在 `<head>` 底部。
2. **异步加载剩余 CSS**：
   - 使用 `<link rel="preload" as="style" href="non-critical.css" onload="this.onload=null;this.rel='stylesheet'">` 实现预加载并异步应用。
   - 或使用 `loadCSS` 等 polyfill 兼容旧浏览器。

---

## 注意事项
- **视口尺寸**：提取时需指定典型视口，否则可能遗漏首屏样式。
- **动态内容**：若页面内容异步加载，需确保关键 CSS 包含初始状态样式。
- **伪类/动画**：`:hover`、`@keyframes` 等可能被误判为非关键，需手动保留。
- **字体**：内联关键字体（如 Base64 编码）可消除 FOIT，但需权衡体积。
- **重复加载**：内联的样式不应再被外部 CSS 重复加载，否则会覆盖且浪费带宽。

通过提取和内联关键 CSS，页面可实现更快的首屏渲染，是优化 Core Web Vitals 的重要实践。

28. 如何优化React应用的Bundle大小？代码分割、Tree Shaking、动态导入的综合应用策略是什么？
优化 React 应用的 Bundle 大小是提升首屏加载速度和用户体验的关键。综合运用 **代码分割（Code Splitting）**、**Tree Shaking** 和 **动态导入（Dynamic Imports）** 可以有效减少初始包体积，并按需加载资源。

---

## 1. 核心概念回顾

- **代码分割**：将应用拆分成多个小块（chunks），按需加载，避免一次性加载整个应用。
- **Tree Shaking**：消除 JavaScript 上下文中未引用的代码（dead code），依赖 ES6 模块的静态结构。
- **动态导入**：使用 `import()` 语法在运行时异步加载模块，是代码分割的具体实现手段。

---

## 2. 综合应用策略

### 2.1 按路由拆分（最常用）
利用框架的路由懒加载功能，将每个路由对应的页面组件拆分为独立 chunk。访问对应路由时再加载该 chunk。

**React 实现**（结合 React Router）：
```jsx
import { lazy, Suspense } from 'react';

const Home = lazy(() => import('./routes/Home'));
const About = lazy(() => import('./routes/About'));

function App() {
  return (
    <Routes>
      <Route path="/" element={
        <Suspense fallback={<div>Loading...</div>}>
          <Home />
        </Suspense>
      } />
      <Route path="/about" element={
        <Suspense fallback={<div>Loading...</div>}>
          <About />
        </Suspense>
      } />
    </Routes>
  );
}
```

### 2.2 按组件拆分
对非首屏的复杂组件（如弹窗、折叠内容、图表）进行动态导入，仅在需要时才加载。

```jsx
const HeavyChart = lazy(() => import('./HeavyChart'));

function Dashboard() {
  const [showChart, setShowChart] = useState(false);
  return (
    <div>
      <button onClick={() => setShowChart(true)}>显示图表</button>
      {showChart && (
        <Suspense fallback={<div>Chart loading...</div>}>
          <HeavyChart />
        </Suspense>
      )}
    </div>
  );
}
```

### 2.3 库拆分与 Vendor 分离
- 将第三方依赖（如 React、lodash）单独打包，利用浏览器缓存。
- 在 Webpack 中通过 `splitChunks` 配置提取公共模块：
  ```js
  optimization: {
    splitChunks: {
      chunks: 'all',
      cacheGroups: {
        vendor: {
          test: /[\\/]node_modules[\\/]/,
          name: 'vendors',
          chunks: 'all',
        },
      },
    },
  }
  ```

### 2.4 动态导入与魔法注释
使用 Webpack 魔法注释为 chunk 命名，便于调试和缓存策略：
```js
const Modal = lazy(() => import(/* webpackChunkName: "modal" */ './Modal'));
```
还可配合 `webpackPrefetch` / `webpackPreload` 优化加载时机。

### 2.5 Tree Shaking 配置
- 确保使用 ES6 模块（`import` / `export`），避免 CommonJS（如 `require`）。
- 在 `package.json` 中设置 `"sideEffects": false`，告知 Webpack 哪些文件有副作用（如 CSS、polyfill），以便安全删除未引用代码。
- 对于无法 tree-shaking 的库（如 lodash），使用子路径导入（`import debounce from 'lodash/debounce'`）替代全库导入。

### 2.6 使用生产构建
- 设置 `mode: 'production'`（Webpack）或 `npm run build`（Create React App）启用压缩、优化。
- 确保环境变量 `NODE_ENV=production` 以移除开发警告。

### 2.7 分析 Bundle
定期使用工具分析包体积，找出优化点：
- `webpack-bundle-analyzer`
- `source-map-explorer`
- `@next/bundle-analyzer`（Next.js）

### 2.8 其他优化技巧
- 使用动态 `import()` 加载国际化语言包。
- 对图片等静态资源使用 CDN 并压缩。
- 避免内联大文件，转为异步加载。
- 移除未使用的依赖，升级库到最新版（可能包含体积优化）。

```typescript
let initialized = false

async function ensureInit() {
  if (initialized) return
  await esbuild.initialize({ wasmURL: '/esbuild.wasm', worker: false })
  initialized = true

// 自定义插件：拦截 node_modules 请求，走 esm.sh
const esmPlugin: esbuild.Plugin = {
  name: 'esm-resolver',
  setup(build) {
    // 裸模块 → esm.sh CDN
    build.onResolve({ filter: /^[^./]/ }, args => ({
      path: `https://esm.sh/${args.path}`,
      external: true,       // 生成 importmap，运行时加载
      namespace: 'esm-cdn'
    }))

    // 虚拟文件系统读取
    build.onLoad({ filter: /.*/, namespace: 'file' }, async args => {
      const content = await readFromOPFS(args.path)
      return { contents: content, loader: inferLoader(args.path) }
    })
  }
}

self.onmessage = async ({ data: { files, entryPoint } }) => {
  await ensureInit()
  
  const result = await esbuild.build({
    entryPoints: [entryPoint],
    bundle: true,
    write: false,
    format: 'esm',
    plugins: [esmPlugin],
    sourcemap: 'inline',       // 调试用
    splitting: true,           // 代码分割
    outdir: '/',
  })

  self.postMessage({ type: 'built', outputs: result.outputFiles })
}
```

## 文件系统模拟

### OPFS（Origin Private File System）

```typescript
// fs-worker.ts — OPFS 同步 API 只能在 Worker 内使用
class VirtualFS {
  private root!: FileSystemDirectoryHandle

  async init() {
    this.root = await navigator.storage.getDirectory()
  }

  // 同步读（Worker 内）
  readFileSync(path: string): string {
    const handle = this.resolveSync(path)
    const file = handle.createSyncAccessHandle()
    const buf = new DataView(new ArrayBuffer(file.getSize()))
    file.read(buf, { at: 0 })
    file.close()
    return new TextDecoder().decode(buf.buffer)
  }

  writeFileSync(path: string, content: string) {
    const handle = this.resolveSync(path)
    const file = handle.createSyncAccessHandle()
    const encoded = new TextEncoder().encode(content)
    file.write(encoded, { at: 0 })
    file.truncate(encoded.byteLength)
    file.flush()
    file.close()
  }

  // 文件变更通知主线程（watch）
  private watchers = new Map<string, Set<() => void>>()
  
  watch(path: string, cb: () => void) {
    if (!this.watchers.has(path)) this.watchers.set(path, new Set())
    this.watchers.get(path)!.add(cb)
  }
}
```

## 关键设计决策总结

选择 esbuild-wasm 而非 Babel 是因为速度差距显著，TypeScript 项目冷启动可以从 10s+ 降到 1s 以内。选择 OPFS 而非纯 IndexedDB 是因为 OPFS 的 `createSyncAccessHandle` 可以在 Worker 内同步读写，避免大量 await 串行，同时性能接近原生文件系统。Service Worker 作为"本地 CDN"是整个架构的关键，它让 iframe 的模块请求可以被拦截并返回编译结果，是实现浏览器内运行时的核心机制。

```typescript
// 材质变体预定义（运营配置）
interface MaterialVariant {
  id: string
  name: string          // "哑光黑" / "金属银"
  textures: {
    diffuse: string     // KTX2 路径
    normal: string
    roughnessMetalness: string
    emissive?: string
  }
  params: {
    baseColor: string
    roughness: number
    metalness: number
    clearcoat?: number  // 上光效果
  }
}

class MaterialSystem {
  private cache = new Map<string, THREE.MeshStandardMaterial>()
  
  async applyVariant(
    model: THREE.Group,
    variant: MaterialVariant,
    renderer: THREE.WebGLRenderer
  ) {
    const cacheKey = variant.id
    
    if (!this.cache.has(cacheKey)) {
      const mat = await this.buildMaterial(variant, renderer)
      this.cache.set(cacheKey, mat)
    }
    
    const material = this.cache.get(cacheKey)!
    
    // 遍历模型所有 Mesh，替换材质
    model.traverse(node => {
      if (node instanceof THREE.Mesh) {
        // 平滑过渡：通过 opacity 渐变
        this.transitionMaterial(node, material)
      }
    })
  }

  private transitionMaterial(mesh: THREE.Mesh, target: THREE.MeshStandardMaterial) {
    const current = mesh.material as THREE.MeshStandardMaterial
    let progress = 0
    
    const animate = () => {
      progress += 0.05
      // 线性插值颜色
      current.color.lerp(target.color, progress)
      current.roughness += (target.roughness - current.roughness) * progress
      current.metalness += (target.metalness - current.metalness) * progress
      
      if (progress < 1) requestAnimationFrame(animate)
      else mesh.material = target  // 切换完毕
    }
    animate()
  }
}
```

```typescript
// 动态 LOD：根据相机距离实时切换
function useDynamicLOD(
  lodMeshes: { mesh: THREE.Mesh; maxDistance: number }[]
) {
  useFrame(({ camera }) => {
    lodMeshes.forEach(({ mesh, maxDistance }) => {
      const distance = camera.position.distanceTo(mesh.position)
      mesh.visible = distance <= maxDistance
    })
  })
}

// Three.js 内置 LOD 对象
function ProductModelLOD() {
  const lod = useMemo(() => {
    const lodObj = new THREE.LOD()
    
    // 距离 0-3m：高精度
    lodObj.addLevel(highDetailMesh, 0)
    // 距离 3-8m：中精度
    lodObj.addLevel(midDetailMesh, 3)
    // 距离 8m+：低精度
    lodObj.addLevel(lowDetailMesh, 8)
    // 距离 20m+：不渲染
    lodObj.addLevel(new THREE.Object3D(), 20)
    
    return lodObj
  }, [])
  
  useFrame(({ camera }) => lod.update(camera))
  
  return <primitive object={lod} />
}

// 屏幕空间 LOD（更精确）：根据模型占屏幕面积决定精度
function screenSpaceLOD(
  mesh: THREE.Mesh,
  camera: THREE.Camera,
  screenHeight: number
): 'high' | 'mid' | 'low' {
  const box = new THREE.Box3().setFromObject(mesh)
  const size = box.getSize(new THREE.Vector3())
  
  // 计算模型在屏幕上的像素高度
  const distance = camera.position.distanceTo(mesh.position)
  const fov = (camera as THREE.PerspectiveCamera).fov * Math.PI / 180
  const pixelHeight = (size.y / distance) * (screenHeight / (2 * Math.tan(fov / 2)))
  
  if (pixelHeight > 400) return 'high'
  if (pixelHeight > 150) return 'mid'
  return 'low'
}
```

```typescript
async function launchWebXR(modelUrl: string) {
  const session = await navigator.xr!.requestSession('immersive-ar', {
    requiredFeatures: ['hit-test', 'dom-overlay'],
    domOverlay: { root: document.getElementById('ar-overlay')! }
  })
  
  renderer.xr.enabled = true
  renderer.xr.setSession(session)
  
  // 创建 Hit Test Source（检测现实平面）
  const refSpace = await session.requestReferenceSpace('viewer')
  const hitTestSource = await session.requestHitTestSource!({ space: refSpace })
  
  let placed = false
  const reticle = createReticle()   // 放置指示圆环
  scene.add(reticle)
  
  session.addEventListener('select', () => {
    if (reticle.visible && !placed) {
      // 用户点击 → 在检测到的平面上放置模型
      const model = gltf.scene.clone()
      model.position.setFromMatrixPosition(reticle.matrix)
      model.scale.setScalar(0.3)  // 根据产品实际尺寸调整
      scene.add(model)
      placed = true
    }
  })
  
  // XR 渲染循环
  renderer.setAnimationLoop((_, frame) => {
    if (!frame) return
    
    const hitTestResults = frame.getHitTestResults(hitTestSource!)
    
    if (hitTestResults.length > 0) {
      const hit = hitTestResults[0]
      const pose = hit.getPose(xrRefSpace)!
      reticle.visible = true
      reticle.matrix.fromArray(pose.transform.matrix)
    } else {
      reticle.visible = false
    }
    
    renderer.render(scene, camera)
  })
}
```

## 性能监控

```typescript
// 运行时 FPS / 内存监控，自动降级
class PerformanceMonitor {
  private frameCount = 0
  private lastTime = performance.now()
  private fps = 60
  
  update() {
    this.frameCount++
    const now = performance.now()
    const elapsed = now - this.lastTime
    
    if (elapsed >= 1000) {
      this.fps = (this.frameCount / elapsed) * 1000
      this.frameCount = 0
      this.lastTime = now
      
      // FPS 低于 30 → 自动降低渲染质量
      if (this.fps < 30) this.downgrade()
    }
  }
  
  private downgrade() {
    const renderer = useThree.getState().gl
    const current = renderer.getPixelRatio()
    if (current > 1) {
      renderer.setPixelRatio(current - 0.5)  // 降低分辨率倍率
    }
  }
}
```

## 关键设计决策总结

**为什么不用 `<model-viewer>`**：Google 的 Web Component 封装过死，无法实现材质切换动画、自定义后处理、热点标注等需求，适合 90% 需求的简单场景，但无法支撑完整产品展示平台。

**按需渲染是最重要的移动端优化**：`frameloop="demand"` 配合 `invalidate()`，用户不操作时 GPU 完全空闲，发热和耗电问题立竿见影。

**KTX2 是贴图策略的核心**：相比传统 PNG/JPG，GPU 原生解压意味着贴图常驻压缩态在显存里，一张 2048 的 PBR 贴图从 16MB 显存降到 2-4MB，移动端显存瓶颈直接被解除。

**AR Quick Look 是 iOS 的正确答案**：WebXR 在 iOS Safari 上支持有限，而 Quick Look 是系统级能力，体验远好于任何 Web 实现，服务端提前转 USDZ 是必要的基础设施投入。
