## 前端安全 (28题)

1. 什么是反射型XSS、存储型XSS、DOM型XSS？它们的攻击原理和防御方法分别是什么？
### 反射型 XSS
- **攻击原理**：攻击者构造包含恶意脚本的 URL，诱使用户点击。服务器接收到请求后，将脚本作为响应的一部分反射回页面（例如在错误信息或搜索结果中），浏览器解析并执行该脚本。
- **防御方法**：
  - 对用户输入进行严格的**输入验证**（如仅允许合法字符）。
  - 对输出到 HTML 的内容进行**上下文感知的编码**（如 HTML 实体编码）。
  - 使用 **CSP（内容安全策略）** 限制脚本来源。

### 存储型 XSS
- **攻击原理**：攻击者将恶意脚本提交到目标服务器（如评论、留言板），服务器存储该内容。其他用户访问相关页面时，服务器从数据库取出并返回，浏览器执行脚本。
- **防御方法**：
  - **输入过滤**：在存储前对用户输入进行严格过滤或净化。
  - **输出编码**：在展示用户生成内容时进行 HTML 编码。
  - 使用安全的富文本编辑器并配置合适的过滤规则。

### DOM 型 XSS
- **攻击原理**：完全发生在客户端，不涉及服务器。恶意数据通过 URL 片段（#...）、document.referrer 或 window.name 等 DOM 属性传入，客户端 JavaScript 不安全地处理这些数据（如使用 innerHTML、eval 等），导致脚本执行。
- **防御方法**：
  - 避免使用 `innerHTML`、`document.write`、`eval` 等危险 API，改用 `textContent`、`setAttribute` 等安全方法。
  - 对动态插入的内容进行**转义**或使用 DOM 解析器。
  - 验证和清理所有不可信来源的数据（如 URL 参数）。
  - 使用 **CSP** 限制脚本执行，防止内联脚本。

**通用防御**：
- 实施 **CSP** 策略，禁止内联脚本和限制脚本来源。
- 使用现代框架（如 React、Vue），它们默认对绑定内容进行转义。
- 设置 HTTP 响应头 `X-XSS-Protection: 1; mode=block`。

2. 什么是CSRF攻击？SameSite Cookie的Strict、Lax、None模式有什么区别？
**CSRF（跨站请求伪造）** 攻击是指攻击者诱导用户在已登录的网站下执行非本意的操作。当用户访问恶意网站时，该网站自动向目标网站发起请求（如图片、表单），浏览器会自动携带用户的 cookie，导致目标网站误以为是用户本人操作。

### SameSite Cookie 的三种模式

| 模式 | 行为 | 适用场景 |
|------|------|----------|
| **Strict** | 仅在同站请求（顶级域名+协议相同）中发送 cookie，任何跨站请求均不携带。 | 安全性最高，适合银行等敏感操作，但外部链接进入时需重新登录。 |
| **Lax** | 在跨站链接、GET 表单、预加载请求中发送 cookie，但 POST、AJAX、图片等跨站请求不发送。 | 默认行为（现代浏览器未设置时），平衡安全与体验，适合大多数网站。 |
| **None** | 所有跨站请求都发送 cookie，但必须同时设置 `Secure` 属性（仅 HTTPS）。 | 适用于需要跨站共享 cookie 的场景（如 SSO、嵌入服务），但需注意 CSRF 风险。 |

**注意**：浏览器默认将未设置 SameSite 的 cookie 视为 Lax；设置 None 时必须同时使用 Secure，否则会被拒绝。

3. 前端如何防止点击劫持（Clickjacking）？X-Frame-Options和CSP的frame-ancestors有什么区别？
点击劫持（Clickjacking）通过将目标网站嵌入透明 iframe 诱骗用户点击，防御的核心是**禁止页面被非法嵌入**。

### 主要防御方式
- **`X-Frame-Options` 响应头**：  
  - `DENY`：禁止任何页面嵌入。  
  - `SAMEORIGIN`：仅允许同源页面嵌入。  
  - `ALLOW-FROM uri`（已废弃）允许指定 URI，但支持度差。
- **CSP 的 `frame-ancestors` 指令**：  
  - 语法：`frame-ancestors 'self' https://example.com *.example.org`，可指定多个源。  
  - 支持通配符，更灵活强大，是 CSP2 推荐的现代方案。

### 两者区别
| 维度 | `X-Frame-Options` | `frame-ancestors` |
|------|--------------------|-------------------|
| **灵活性** | 仅支持单个固定值（DENY/SAMEORIGIN），不支持多源 | 支持多个源、通配符，粒度更细 |
| **兼容性** | 支持老旧浏览器（IE8+） | 需要浏览器支持 CSP（现代浏览器均支持） |
| **优先级** | 若两者同时存在，浏览器通常以 `frame-ancestors` 为准（规范建议） | 推荐仅使用 CSP 指令 |
| **使用建议** | 可作为向后兼容的补充 | 作为主要防御手段 |

**最佳实践**：优先使用 `frame-ancestors`，并为老旧浏览器降级到 `X-Frame-Options`（例如同时设置两个头，但需注意行为可能不一致）。

4. 什么是CSP（内容安全策略）？如何配置CSP头？nonce和hash的使用场景是什么？
**内容安全策略（CSP）** 是一种额外的安全层，用于检测和缓解特定类型的攻击，包括跨站脚本（XSS）和数据注入攻击。它通过允许服务器指定浏览器只能加载和执行来自可信源的资源（如脚本、样式、图片等），从而限制攻击者注入恶意代码的能力。

### 如何配置 CSP 头
CSP 通过 HTTP 响应头 `Content-Security-Policy` 实现，策略由一系列指令组成，每个指令控制一个资源类型。常见指令示例：

```http
Content-Security-Policy: default-src 'self'; 
                        script-src 'self' https://apis.example.com; 
                        style-src 'self' 'unsafe-inline'; 
                        img-src * data:;
```

- **default-src 'self'**：所有未明确指定指令的资源默认只允许同源加载。
- **script-src 'self' https://apis.example.com**：脚本只允许来自同源和指定域名。
- **style-src 'self' 'unsafe-inline'**：样式允许同源和内联（注意 `unsafe-inline` 会削弱安全性，尽量避免）。
- **img-src * data:**：图片允许任何来源及 data URI。

也可以在 HTML 中通过 `<meta>` 标签配置，但某些指令（如报告）可能不支持。

### nonce 和 hash 的使用场景
当需要执行内联脚本或样式时，为了避免使用 `unsafe-inline`，可以使用 **nonce** 或 **hash** 机制来精确允许特定的内联代码块。

#### 1. Nonce（一次性随机数）
- **原理**：服务器在生成页面时为每个请求生成一个唯一的随机数（nonce），同时将该 nonce 添加到 CSP 头中，并设置到内联 `<script>` 或 `<style>` 标签的 `nonce` 属性上。浏览器会检查两者是否一致，只有匹配的内联代码才被执行。
- **使用场景**：适用于动态生成的内联内容，例如服务端模板中嵌入的初始化数据、动态脚本等。每次请求的 nonce 不同，可防止攻击者预测并注入。
- **示例**：
  ```http
  Content-Security-Policy: script-src 'nonce-EDNnf03nceIOfn39fn3e9h3sdfa'
  ```
  ```html
  <script nonce="EDNnf03nceIOfn39fn3e9h3sdfa">
    // 可信的内联脚本
  </script>
  ```

#### 2. Hash（哈希值）
- **原理**：计算内联脚本或样式内容的哈希值（如 sha256），并将该哈希值添加到 CSP 头的相应指令中。当浏览器执行内联代码时，会计算其哈希值并与策略中的哈希比对，匹配则允许执行。
- **使用场景**：适用于静态、不经常变动的内联代码，例如固定的初始化脚本、第三方嵌入代码。如果内联内容变化，哈希值也必须更新。
- **示例**：
  ```http
  Content-Security-Policy: script-src 'sha256-+6WnX...4mZo='
  ```
  对应的内联脚本内容必须与生成该哈希的原始内容完全一致。

### 总结
CSP 是防范 XSS 的强大工具，通过精细控制资源加载和代码执行，大大增加攻击难度。nonce 和 hash 机制允许在避免 `unsafe-inline` 的同时，安全地使用必要的内联代码，是现代化 CSP 配置的核心部分。

5. 前端如何安全地存储敏感信息？localStorage、sessionStorage、Cookie、IndexedDB的安全性对比是什么？
在前端存储敏感信息（如认证令牌、个人隐私数据）时，安全性是首要考量。不同的存储机制各有其安全特性和风险，以下从多个维度对比 **localStorage**、**sessionStorage**、**Cookie** 和 **IndexedDB** 的安全性，并给出安全存储的最佳实践。

---

## 一、四种存储机制的安全性对比

| 维度 | localStorage | sessionStorage | Cookie | IndexedDB |
|------|--------------|----------------|--------|-----------|
| **存储持久性** | 永久，除非手动清除 | 标签页关闭即清除 | 可设置过期时间（Expires/Max-Age） | 永久，除非手动清除 |
| **同源策略** | 严格同源 | 严格同源 | 可设置 Domain，但一般同源 | 严格同源 |
| **自动携带（网络）** | 否 | 否 | 是（每个同源请求自动附加） | 否 |
| **XSS 攻击风险** | 高（任何页面内脚本可直接读取） | 高（同 XSS） | 可通过 HttpOnly 防止脚本读取，降低 XSS 风险 | 高（脚本可读取 IndexedDB 数据） |
| **CSRF 攻击风险** | 无（不会自动发送） | 无 | 高（自动发送，需用 SameSite、CSRF Token 防护） | 无 |
| **数据容量** | 约 5-10MB | 约 5-10MB | 约 4KB | 几百 MB 以上，适合大量结构化数据 |
| **访问方式** | 同步 JavaScript | 同步 JavaScript | 同步 JavaScript（除非 HttpOnly） | 异步 JavaScript |
| **加密存储** | 明文存储（可前端加密） | 明文存储（可前端加密） | 明文存储（可设置 Secure 仅 HTTPS 传输） | 明文存储（可前端加密） |

---

## 二、各存储机制的详细风险分析

### 1. localStorage
- **主要风险**：任何页面中的 XSS 漏洞都能直接通过 `localStorage.getItem()` 窃取所有数据。
- **适用场景**：仅存储非敏感、公开的数据（如用户偏好、主题设置）。**绝对不要存储认证令牌或个人身份信息**。

### 2. sessionStorage
- **风险**：与 localStorage 类似，XSS 同样可读取。但会话关闭后自动清除，暴露窗口缩小。
- **适用场景**：存储临时数据，如表单中间状态，但仍需避免敏感信息。

### 3. Cookie
- **风险**：
  - **XSS 风险**：若未设置 `HttpOnly`，脚本可读取 Cookie 内容。
  - **CSRF 风险**：Cookie 自动发送，攻击者可利用用户已登录状态发起跨站请求。
  - **网络嗅探**：若未设置 `Secure`，明文传输可能被截获。
- **优势**：通过 `HttpOnly` 和 `Secure` 标志可大幅提升安全性，成为存储认证令牌（如 Session ID、JWT）的较安全选择，但需配合 CSRF Token 或 `SameSite` 策略防御 CSRF。

### 4. IndexedDB
- **风险**：XSS 同样能通过脚本访问数据库内容。虽为异步，但攻击者仍可调用 API 窃取。
- **特点**：适合存储大量数据（如离线缓存、用户生成内容），但敏感数据必须加密后再存储。
- **注意**：IndexedDB 本身不提供加密，数据以明文形式存储在用户磁盘。

---

## 三、前端安全存储敏感信息的最佳实践

1. **尽量不存储敏感信息在前端**  
   敏感数据（如密码、信用卡号）应尽量减少在前端出现，仅在使用时通过内存临时持有，用完即置空。

2. **认证令牌存储推荐方案**  
   - **首选：HttpOnly + Secure + SameSite 的 Cookie**  
     将认证令牌放在 Cookie 中，并设置 `HttpOnly` 禁止脚本访问，`Secure` 确保仅 HTTPS 传输，`SameSite=Lax` 或 `Strict` 防御 CSRF。这是目前最安全的前端存储方式。
   - **备选：内存存储**  
     对于单页应用，令牌可存储在内存变量中（如 React 的 state），页面刷新即丢失，需配合刷新令牌机制。但此方案在刷新后需重新登录，体验不佳。

3. **非认证敏感数据的加密存储**  
   若必须存储用户隐私数据（如个人信息、离线数据），应使用 **Web Crypto API** 加密后再存入 IndexedDB 或 localStorage。密钥可派生自用户密码（如 PBKDF2），但需谨慎管理密钥。

4. **严格限制 XSS 漏洞**  
   - 输入过滤、输出编码。
   - 使用 CSP 禁止内联脚本和不安全来源。
   - 避免使用 `eval`、`innerHTML` 等危险 API。

5. **定期轮换令牌与数据清理**  
   - 令牌应有短期有效期，并实现刷新机制。
   - 敏感数据在不再需要时应主动从存储中移除。

6. **利用 Subresource Integrity (SRI) 和 HTTPS**  
   确保引用的第三方资源未被篡改，所有传输加密。

---

## 四、总结

| 存储方式 | 安全性评级（对敏感数据） | 推荐用途 |
|----------|-------------------------|----------|
| Cookie（HttpOnly+Secure+SameSite） | ★★★★☆ | 认证令牌、会话标识 |
| 内存（变量） | ★★★☆☆ | 临时敏感数据，刷新需重新获取 |
| IndexedDB（加密后） | ★★★☆☆ | 大量离线数据，加密存储 |
| sessionStorage | ★★☆☆☆ | 非敏感临时数据 |
| localStorage | ★☆☆☆☆ | 公开偏好设置 |

**核心原则**：防御 XSS 是前端安全的核心，所有能被脚本访问的存储都可能被窃取。因此，敏感信息的存储应优先选择 **HttpOnly Cookie**，并通过加密和严格的访问控制来降低风险。

6. 什么是HTTPS中间人攻击？前端如何检测和防御中间人攻击？
**HTTPS 中间人攻击**是指攻击者在客户端与服务器之间的通信链路上拦截并篡改数据，同时伪造服务器的证书，使客户端误以为正在与合法服务器建立安全连接，从而窃取或篡改传输的敏感信息。

---

## 前端如何检测和防御中间人攻击？

尽管前端无法完全杜绝中间人攻击（因为攻击发生在传输层），但可以借助以下策略提高检测能力和降低风险：

### 1. **强制使用 HTTPS 与 HSTS**
- **HSTS（HTTP Strict Transport Security）**：服务器通过响应头 `Strict-Transport-Security` 告知浏览器，在指定时间内只能通过 HTTPS 访问该域名，杜绝因用户手动输入 HTTP 或遭遇 SSL 剥离攻击而导致的降级。
- 前端可通过检查 `window.isSecureContext` 或 `location.protocol` 判断当前是否为 HTTPS，若非 HTTPS 则立即终止操作或提示用户。

### 2. **证书公钥固定（HPKP）与替代方案**
- 传统 HPKP 因风险较高已被废弃，但可结合 **证书透明度（Certificate Transparency, CT）** 和 **Expect-CT 响应头** 要求浏览器验证证书是否已公开记录。若证书未出现在 CT 日志中，浏览器可拒绝连接。
- 浏览器扩展或企业级应用可内置已知合法的公钥哈希，并在建立连接后比对，但需谨慎维护。

### 3. **使用 CSP 报告机制**
- 配置 `Content-Security-Policy-Report-Only` 头，并设置 `report-uri` 或 `report-to` 指令，将违规行为（如尝试加载不安全资源）上报到指定服务器，有助于发现潜在的中间人攻击迹象。

### 4. **子资源完整性（SRI）**
- 对于从 CDN 加载的脚本或样式，使用 `integrity` 属性提供期望的哈希值，浏览器会校验实际加载资源的哈希，若被篡改则拒绝执行。这能防范攻击者篡改第三方资源。

### 5. **前端主动检测异常**
- **检查协议**：在关键操作前验证当前页面是否为 HTTPS。
- **检查证书信息**：通过 `window.crypto` 或 `performance.getEntries()` 无法直接获取证书详情，但可使用 `RTCPeerConnection` 的某些 API 或利用服务端接口获取证书指纹并比对（需服务端配合）。
- **监听安全警告**：通过 `securitypolicyviolation` 事件捕捉 CSP 违规，或监听 `onload` 错误判断资源是否被篡改。

### 6. **用户教育与浏览器安全提示**
- 提醒用户不要忽略浏览器显示的“证书无效”或“连接不安全”警告，这些往往是中间人攻击的前兆。
- 使用现代浏览器，它们内置了证书吊销检查和 CT 策略。

### 7. **服务端强化**
- 配置严格的 TLS 协议（禁用过时协议）、使用强加密套件、启用 OCSP 装订等，使攻击者难以伪造有效证书。

---

**总结**：前端无法彻底防御中间人攻击，但通过 HSTS、SRI、CSP 和用户教育等手段，可以显著增加攻击成本并及早发现异常。最根本的防线仍在服务端正确配置 TLS 和使用安全的证书管理机制。

7. 什么是子资源完整性（SRI）？integrity属性如何工作？它解决了什么安全问题？
**子资源完整性（SRI）** 是一种安全机制，允许浏览器验证所获取的资源（如 JavaScript、CSS 文件）是否被意外篡改。它通过为资源提供一个加密哈希值，让浏览器下载后计算实际哈希并与之比对，确保资源完整且未被修改。

### `integrity` 属性如何工作？
- 在 `<script>` 或 `<link>` 标签中使用 `integrity` 属性，格式为 `哈希算法-哈希值`，例如：
  ```html
  <script src="https://example.com/app.js" 
          integrity="sha384-+B3k8C2k6lGq6t5+3p1I8N8l+8dFfB5jF5f5d5f5" 
          crossorigin="anonymous"></script>
  ```
- 浏览器下载资源后，使用指定的哈希算法（如 `sha384`）计算内容的哈希值，并与 `integrity` 值比对。
- 若一致，则正常执行/应用资源；若不一致，浏览器拒绝执行，并在控制台报错。

### 解决了什么安全问题？
- **防止供应链攻击**：当资源托管在第三方 CDN 时，SRI 可确保即便 CDN 被攻破或文件被篡改，恶意代码也不会在页面上执行。
- **防范中间人篡改**：即使 HTTPS 连接被意外中断或存在伪造证书，SRI 也能检测到资源内容的变更，增加一层安全保障。
- **确保缓存一致性**：对于可能被篡改的本地缓存，SRI 同样能验证其完整性。

**注意**：SRI 要求资源支持跨域（通常需配合 `crossorigin="anonymous"` 属性），且哈希值必须与资源内容严格对应。
