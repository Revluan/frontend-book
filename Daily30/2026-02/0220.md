## 前端架构 (28题)

1. 什么是BFF（Backend For Frontend）架构？它解决了什么问题？如何设计BFF层？
**BFF（Backend For Frontend）** 是一种为特定前端（如移动 App、桌面 Web、小程序）定制后端服务的架构模式。每个前端对应一个专属的 BFF 层，负责聚合底层服务的数据、转换格式、处理认证等，使前端无需关心后端服务细节。

---

## BFF 解决了什么问题？

1. **前后端需求不匹配**  
   后端通用 API 往往无法满足不同前端的差异化需求（例如移动端需要更少字段、PC 端需要更多关联数据）。BFF 可以按需聚合、裁剪数据，避免前端多次调用或过度获取。

2. **减少客户端复杂性与网络开销**  
   前端无需直接调用多个微服务，由 BFF 统一聚合数据，减少往返请求（RTT），提升性能。

3. **解耦前后端演进**  
   后端服务可以独立发展，不影响前端；前端也能灵活调整数据需求，无需强制后端修改。

4. **提升安全性**  
   BFF 可集中处理认证、授权、限流等安全策略，隐藏后端内部结构，降低攻击面。

5. **适配多端差异**  
   同一业务可针对不同终端（iOS/Android/Web）提供不同的 BFF，实现精细化优化。

---

## 如何设计 BFF 层？

### 1. 边界划分
- **按前端类型**：每个前端拥有独立的 BFF（如 `web-bff`、`mobile-bff`）。
- **按业务域**：复杂应用可再拆分（如订单BFF、用户BFF），但需避免过于碎片化。

### 2. 职责范围
- **数据聚合**：调用多个下游服务（微服务、数据库）并组合结果。
- **格式转换**：将后端数据转换为前端所需的 JSON 结构（字段重命名、类型转换）。
- **认证与会话**：处理用户登录状态、Token 校验，传递上下文。
- **轻量逻辑**：只包含前端特有的逻辑（如默认值、简单计算），不承载核心业务规则（应下沉到后端服务）。
- **缓存**：对非实时数据做适当缓存，减少下游压力。

### 3. 技术选型
- **语言/框架**：通常选择 Node.js（Express、Koa、NestJS）以利用 JavaScript 同构优势，也可用 Java、Go 等。
- **通信协议**：与下游服务采用 gRPC、REST 或消息队列，与前端通过 HTTP/JSON 或 GraphQL 交互。
- **GraphQL 作为 BFF**：GraphQL 天然适合 BFF 场景，可让前端声明式获取数据，但需注意复杂查询的性能。

### 4. 关键设计要点
- **服务发现与容错**：通过注册中心或配置中心动态发现后端服务，实现熔断、重试、超时控制（如 Hystrix、Resilience4j）。
- **数据聚合策略**：串行或并行调用（`Promise.all`），避免串行等待。
- **错误处理**：向后端传递标准错误码，同时向前端返回友好错误信息，避免暴露内部细节。
- **安全**：在 BFF 层实施身份验证、CSRF 防护、请求限流、输入校验。
- **版本管理**：BFF 可独立版本化，与前端同步发布，或通过 API 版本路径兼容旧端。
- **监控与日志**：记录请求链路、耗时、错误，便于排查问题。

### 5. 部署与运维
- 独立部署，与前端应用同生命周期，可按前端需求扩缩容。
- 使用容器化（Docker）和编排工具（Kubernetes）便于管理。

---

## 示例场景
某电商平台有 PC 端和移动端：
- **移动端 BFF**：聚合商品详情、评价、库存，返回轻量 JSON，并压缩图片 URL。
- **PC 端 BFF**：在移动端基础上增加推荐商品、相关文章等字段，满足大屏展示需求。

BFF 层将这些差异收敛在后端，前端只需调用各自的 BFF 即可。

---

## 总结
BFF 是多前端时代的重要架构模式，通过为每个前端定制后端边界，实现了关注点分离、性能优化和快速迭代。设计时应保持 BFF 轻量、无状态，专注于前端适配，核心业务逻辑仍由后端服务承载。

2. 前端如何实现插件化架构？插件的注册、卸载、通信机制如何设计？
插件化架构允许前端应用动态加载和运行第三方扩展，实现功能的灵活组合与独立迭代。设计一个好的插件系统需考虑**插件的定义、注册、生命周期管理、通信机制、安全隔离**等。以下是通用的设计方案：

---

## 一、插件化架构的核心要素

1. **插件定义**：约定插件的格式（如 JS 对象、类、模块），包含元数据（名称、版本、依赖）和生命周期方法。
2. **插件注册**：发现并加载插件，可以是静态配置或动态扫描。
3. **生命周期管理**：初始化、启动、停用、卸载等钩子，保证插件可安装和移除。
4. **通信机制**：插件与宿主、插件与插件之间的消息传递。
5. **隔离与安全**：限制插件对宿主环境的访问，避免冲突或破坏。
6. **依赖管理**：处理插件间的依赖关系。

---

## 二、插件注册机制

### 1. 插件定义格式
通常使用一个类或对象，暴露标准接口：
```typescript
interface Plugin {
  name: string;          // 唯一标识
  version?: string;
  dependencies?: string[];
  onActivate?: (context: PluginContext) => void | Promise<void>;  // 激活时调用
  onDeactivate?: () => void | Promise<void>;                      // 停用时调用
  // 可选的其他钩子（如配置变更、UI 渲染等）
}
```

### 2. 注册方式
- **静态配置**：在应用启动时通过配置文件或 `package.json` 声明插件列表。
- **动态扫描**：运行时扫描指定目录（如 `plugins/`）下的模块，动态加载。
- **按需加载**：使用 `import()` 动态加载插件代码，结合代码拆分减小首屏体积。

#### 示例：动态注册
```javascript
class PluginManager {
  constructor() {
    this.plugins = new Map();
    this.context = this._createContext();
  }

  // 注册单个插件
  async register(pluginModule) {
    const plugin = pluginModule.default || pluginModule;
    if (!plugin.name) throw new Error('Plugin must have a name');
    if (this.plugins.has(plugin.name)) return; // 避免重复注册

    // 初始化插件上下文（可注入 API、事件总线等）
    this.plugins.set(plugin.name, plugin);
    // 可在此处调用插件的初始化方法
    if (plugin.onActivate) {
      await plugin.onActivate(this.context);
    }
  }

  // 批量注册
  async registerAll(plugins) {
    await Promise.all(plugins.map(p => this.register(p)));
  }

  // 卸载插件
  async unregister(pluginName) {
    const plugin = this.plugins.get(pluginName);
    if (plugin?.onDeactivate) {
      await plugin.onDeactivate();
    }
    this.plugins.delete(pluginName);
  }

  _createContext() {
    return {
      // 暴露宿主 API，如事件总线、数据存储、UI 插槽等
      eventBus: new EventBus(),
      utils: { ... },
      // 限制敏感操作，可通过 Proxy 实现安全隔离
    };
  }
}
```

### 3. 加载插件代码
若插件是独立打包的，可通过 `<script>` 标签加载或使用动态 `import()`：
```javascript
// 动态加载远程插件
async function loadRemotePlugin(url) {
  const module = await import(url);
  pluginManager.register(module);
}
```

---

## 三、插件卸载机制

卸载时需要清理插件占用的资源，防止内存泄漏。设计如下：
- **调用 `onDeactivate`**：插件在此释放事件监听、定时器、DOM 节点等。
- **移除事件监听**：事件总线应自动清理插件注册的回调（可通过弱引用或插件 ID 标记）。
- **销毁 UI 组件**：如果插件渲染了界面，应提供移除方法。

示例：
```javascript
class PluginManager {
  async unregister(pluginName) {
    const plugin = this.plugins.get(pluginName);
    if (!plugin) return;
    if (plugin.onDeactivate) {
      await plugin.onDeactivate();
    }
    // 移除事件总线中该插件的所有监听（假设事件总线支持按插件过滤）
    this.context.eventBus.removeByPlugin(pluginName);
    // 清理其他资源...
    this.plugins.delete(pluginName);
  }
}
```

## 四、通信机制设计

### 1. 事件总线（全局/局部）
提供一个集中式的事件总线，插件可订阅和发布事件。
```javascript
class EventBus {
  constructor() {
    this.listeners = new Map();
  }

  on(event, callback, pluginName) {
    if (!this.listeners.has(event)) this.listeners.set(event, []);
    this.listeners.get(event).push({ callback, pluginName });
  }

  emit(event, data) {
    const list = this.listeners.get(event);
    if (list) {
      list.forEach(item => item.callback(data));
    }
  }

  // 按插件移除监听（卸载时调用）
  removeByPlugin(pluginName) {
    for (let [event, list] of this.listeners) {
      const filtered = list.filter(item => item.pluginName !== pluginName);
      if (filtered.length === 0) this.listeners.delete(event);
      else this.listeners.set(event, filtered);
    }
  }
}
```

### 2. 插件间直接通信
通过上下文暴露其他插件的 API（需权限控制），或通过中介者模式。

### 3. 共享状态管理
可使用 Redux、MobX 等状态库，插件通过 dispatch action 修改状态，但需确保 action 命名不冲突。

### 4. 插槽（Slot）模式
为 UI 插件提供固定插槽（如工具栏、侧边栏），插件可注册组件渲染到指定位置。宿主负责渲染这些插槽。

---

## 五、安全与隔离

- **沙箱执行**：使用 `iframe`、`Web Worker` 或 `Shadow DOM` 隔离插件的 JavaScript 和样式。
- **API 代理**：通过 `Proxy` 限制插件对宿主对象的访问，只暴露安全的 API。
- **权限声明**：插件在注册时声明所需权限（如网络请求、文件读写），宿主根据配置授予或拒绝。

---

## 六、完整示例（简化）

```javascript
// 宿主应用
const eventBus = new EventBus();
const pluginManager = new PluginManager(eventBus);

// 插件定义（my-plugin.js）
export default {
  name: 'my-plugin',
  onActivate(ctx) {
    console.log('Plugin activated');
    ctx.eventBus.on('user:click', this.handleClick, this.name);
  },
  onDeactivate() {
    console.log('Plugin deactivated');
    // 清理工作
  },
  handleClick(data) {
    console.log('User clicked', data);
  }
};

// 宿主加载插件
import MyPlugin from './plugins/my-plugin.js';
pluginManager.register(MyPlugin);

// 触发事件
eventBus.emit('user:click', { id: 42 });

// 卸载插件
await pluginManager.unregister('my-plugin');
```

设计一个支持数百页面、几十子系统、多团队协作的大型企业级中后台前端架构，需要综合考虑**微前端集成、技术栈统一、模块化、工程化、权限安全、性能和可维护性**。以下是我的设计方案：

## 一、整体架构：微前端 + Monorepo

采用 **微前端** 架构将系统拆分为多个独立开发、独立部署的子应用（子系统），每个子应用可由不同团队维护。同时使用 **Monorepo** 管理所有子应用和共享库，便于统一版本和依赖。

### 1.1 微前端集成方案
- **基座（主应用）**：负责登录认证、布局框架（顶部导航、侧边栏）、注册子应用、全局权限控制、公共状态管理。
- **子应用**：每个子系统作为一个独立项目，可以自主选择技术栈（但建议统一为 React 或 Vue 以减少维护成本），通过微前端协议暴露生命周期。
- **集成方式**：采用 **qiankun**（基于 single-spa）或 **micro-app**（基于 Web Components）。两者都成熟，qiankun 社区更广，micro-app 更轻量。也可考虑 Webpack 5 **Module Federation** 实现运行时共享，但需要更精细的配置。
- **路由整合**：主应用配置子应用的路由前缀，将对应路径的请求代理到子应用。子应用内部路由独立管理。

### 1.2 共享库
- **基础组件库**：统一 UI 组件库（如 Ant Design 或 Element Plus），封装业务组件，发布为 npm 包。
- **工具库**：公共函数（如日期格式化、请求封装）、权限校验、埋点 SDK 等。
- **API 客户端**：统一封装 axios，配置拦截器、token 注入、错误处理。
- **主题定制**：使用 CSS 变量或主题配置（如 Ant Design 的 `ConfigProvider`），主应用统一提供主题切换能力。

## 三、代码组织结构（Monorepo）

使用 `pnpm` 和 `workspace` 组织如下：

```
packages/
├── apps/
│   ├── main-app/            # 主应用
│   ├── sub-app-a/            # 子系统A
│   ├── sub-app-b/            # 子系统B

├── libs/
```

## 四、代码质量和一致性

- **代码规范**：统一 ESLint（Airbnb 风格 + 项目定制）、Prettier，提交时自动格式化。
- **类型安全**：TypeScript 严格模式，共享类型在 `shared-types` 包中定义。
- **提交规范**：使用 Commitizen 规范提交信息，自动生成 changelog。
- **代码审查**：PR 必须通过 CI 检查和至少一名 reviewer 批准。
- **单元测试**：核心模块（utils、api-client）需 80% 覆盖率；UI 组件使用 Storybook 开发和测试。
- **分支策略**：Git Flow 或 GitHub Flow，主分支保护。

## 五、子系统间通信

- **主应用提供事件总线**：基于 `mitt` 或 `tiny-emitter`，子应用可订阅和触发全局事件（如切换菜单、刷新数据）。
- **共享状态**：通过主应用的全局状态（Redux store）向下传递，子应用通过 props 或 context 获取。子应用也可通过主应用提供的 API 修改全局状态。
- **路由跳转**：使用主应用的路由实例或 `history` 对象进行跨子应用跳转。
- **若需要深度通信**，可考虑使用 `window.postMessage` 或自定义事件，但应尽量收敛到主应用协调。

## 六、统一登录和权限控制

### 6.1 认证（SSO）
- 接入公司的统一身份认证系统（OAuth2 / CAS），主应用负责登录流程。
- 登录后获取 token（JWT），存储在内存或 httpOnly cookie（更安全）。
- 子应用不直接处理登录，所有 API 请求自动携带 token（通过主应用或共享 api-client 统一注入）。

### 6.2 权限模型
采用 **RBAC**（基于角色的访问控制）或 **ABAC**（基于属性的访问控制），权限数据由后端返回。

- **静态权限**：菜单、按钮可见性，前端根据后端返回的权限点动态生成路由和按钮。
- **动态权限**：数据级权限由后端接口控制。
- 主应用在登录后获取用户角色和权限列表，存入全局状态。
- 子应用通过主应用提供的权限 hook（如 `useAuth`）判断是否渲染某按钮。

### 6.3 路由权限控制
- 主应用动态注册子应用路由，并根据权限过滤可访问的子应用。
- 子应用内部路由也需根据权限动态生成（可通过高阶组件封装 `Route` 组件）。

## 七、性能优化和监控

### 7.1 性能优化
- **代码分割**：子应用按需加载，内部路由也懒加载。
- **依赖共享**：使用 Module Federation 共享公共依赖（React、AntD），避免重复加载。
- **资源优化**：图片压缩、使用 WebP，开启 Gzip / Brotli，CDN 加速。
- **缓存策略**：静态资源添加 hash，强缓存；HTML 文件协商缓存。
- **虚拟列表**：针对长列表优化。
- **预加载**：空闲时预加载可能访问的子应用。

### 7.2 监控
- **性能监控**：使用 Web Vitals 收集 FCP、LCP、CLS 等指标，上报到监控系统。
- **错误监控**：接入 Sentry，捕获 JavaScript 错误、资源加载失败、API 异常，并记录用户行为。
- **埋点**：自定义事件上报（如页面访问、按钮点击），用于分析用户行为。
- **日志**：子应用统一使用主应用提供的 logger 工具，便于聚合分析。

## 八、快速迭代和灰度发布

### 8.1 CI/CD 流程
- **持续集成**：PR 触发 lint、test、build；主分支合并后自动构建并发布到预发环境。
- **持续部署**：手动触发生产发布，支持一键回滚。

### 8.2 灰度发布策略
- **基于用户**：根据用户 ID 哈希或 Cookie 分流，将部分用户流量导向新版本子应用。
- **基于子应用**：子应用独立部署，通过网关或主应用配置控制灰度比例（例如 10% 用户访问新版 A 应用）。
- **蓝绿部署**：保留旧版本，随时切换。

### 8.3 版本管理
- 子应用版本与主应用版本解耦，独立迭代。
- 使用 `changesets` 管理公共库版本，遵循 SemVer。

## 一、整体架构：微前端 + 边缘计算 + 分地区部署

### 1.1 多租户隔离与定制
- **租户标识**：通过域名（如 `tenant1.example.com`）或 URL 路径（如 `example.com/tenant1`）区分租户。前端在启动时获取租户 ID，用于后续 API 请求和配置加载。
- **租户专属配置**：使用**配置中心**（如 Apollo、Nacos）存储每个租户的主题、功能开关、权限、品牌信息等。前端在应用初始化时根据租户 ID 获取配置，动态渲染界面。
- **租户数据隔离**：前端只负责展示，数据隔离由后端通过租户 ID 在数据库层面实现。前端 API 请求需携带租户 ID（如放在请求头 `X-Tenant-ID`）。
- **代码隔离**：若租户定制差异较大（如独立业务流程），可采用**微前端**架构，为每个租户加载不同的子应用或组件模块，通过动态加载实现。
- **构建隔离**：通用代码打包为共享库，租户特定代码可单独构建，通过 CDN 按需分发。

### 1.2 多地区部署与数据同步
- **静态资源分发**：使用全球 CDN（如 Cloudflare、Akamai）部署前端静态资源（HTML、JS、CSS、图片），确保用户就近访问。
- **计算边缘化**：利用边缘计算平台（如 Cloudflare Workers、Vercel Edge Functions、AWS Lambda@Edge）执行轻量级前端逻辑（如动态生成 HTML、租户识别、A/B 测试、重定向），减少到源站的往返。
- **API 网关**：在每个地区部署 API 网关，将请求路由到最近的后端服务集群。后端服务可多活部署，通过全球负载均衡（如 AWS Route 53）实现就近接入。
- **数据同步**：对于必须全局一致的数据（如用户配置），采用分布式数据库（如 CockroachDB、Google Spanner）或数据复制（如跨区域主从同步）。前端应尽量缓存数据，减少跨区域查询。

### 1.3 高并发与高可用
- **静态资源 CDN**：CDN 天然支持高并发，通过边缘节点缓存，降低源站压力。
- **动态内容缓存**：对非个性化数据（如公共页面）可启用浏览器缓存或 CDN 缓存（如 Cache-Control: s-maxage）。个性化内容通过边缘计算生成，避免多次回源。
- **负载均衡**：使用全局负载均衡器分发流量到不同地区的源站集群，每个集群内水平扩展。
- **容灾**：多地区多活部署，当某地区故障时，DNS 或边缘网关自动将流量切到健康地区。
- **降级方案**：
  - **静态降级**：若 API 不可用，返回本地缓存数据或默认界面（如“服务繁忙”页）。
  - **功能降级**：通过配置中心动态关闭非核心功能（如评论、推荐），确保核心流程可用。
  - **CDN 降级**：若源站完全不可用，CDN 可返回已缓存的最新静态页面（需预先配置）。

### 1.4 动态配置与热更新
- **配置中心**：使用 Apollo 或自研配置服务，前端在启动时通过租户 ID 拉取配置，并监听配置变更（WebSocket 或轮询）。
- **热更新机制**：
  - **静态资源**：通过版本号（如 `app.[contenthash].js`）实现无感更新，用户下次访问自动加载新版本。
  - **动态模块**：若采用微前端，可通过动态加载新版本子应用，无需刷新页面（需模块联邦或加载器支持）。
  - **特性开关**：配置中心实时推送开关，前端应用内定时检查或通过 WebSocket 接收变更，动态启用/关闭功能。

### 1.5 可扩展性
- **微前端架构**：按业务域拆分子应用，各团队独立开发、独立部署，降低耦合，便于扩展新功能。
- **插件化**：核心功能通过插件机制扩展，新业务以插件形式接入主应用。
- **组件库**：统一的基础组件库，支持主题定制，新页面可直接复用。
- **API 设计**：前端与后端通过 GraphQL 或 BFF 层交互，减少多次请求，后端可灵活扩展字段。

### 1.6 CDN 与边缘计算应用
- **边缘渲染（ESR）**：在 CDN 边缘节点使用 Workers 或 Lambda@Edge 动态生成 HTML，结合租户配置和个性化数据，实现首屏极速渲染。
- **智能路由**：根据用户地理位置将请求导向最近的 API 网关。
- **A/B 测试**：在边缘根据 Cookie 或随机数分配不同版本的静态资源，无需回源。
- **安全防护**：CDN 提供 DDoS 防护、WAF 等。

### 1.7 全球用户性能监控（RUM）
- **真实用户监控**：接入 RUM 工具（如 Datadog、New Relic、自研 SDK），收集各地区的页面加载时间（FCP、LCP）、API 延迟、错误率。
- **性能分析**：按国家/地区、运营商、浏览器等维度聚合数据，识别性能瓶颈（如某地区 CDN 节点慢、API 响应慢）。
- **告警**：设置性能阈值，当某地区指标下降时自动告警，触发降级或运维响应。
- **日志采样**：对错误和慢请求进行全量采集，其他数据采样上报以节省流量。
