## JavaScript (10题)

1. JavaScript中的try-catch能捕获哪些类型的错误？Promise的错误如何捕获？async函数中的错误处理最佳实践是什么？
### JavaScript 中的错误捕获

#### 1. `try-catch` 能捕获哪些类型的错误？
`try-catch` 只能捕获**同步代码**中抛出的错误，包括：
- 显式抛出的错误（`throw new Error(...)`）。
- 运行时错误（如引用未定义变量、类型错误、范围错误等）。
- 任何同步函数调用内部抛出的错误。

**无法捕获**的错误：
- 异步代码中的错误（如 `setTimeout`、`setInterval`、事件监听器内的错误）。
- Promise 中未被 `.catch()` 或 `try-catch`（配合 `await`）捕获的错误（会触发 `unhandledrejection` 事件）。
- 语法错误（`SyntaxError`），它们在代码解析阶段抛出，不在运行时。

#### 2. Promise 的错误如何捕获？
Promise 的错误捕获主要有两种方式：
- **使用 `.catch()` 方法**：在 Promise 链末尾添加 `.catch()` 处理任何前面抛出的错误。
  ```javascript
  fetch(url)
    .then(response => response.json())
    .catch(error => console.error('捕获错误：', error));
  ```
- **使用 `try-catch` + `async/await`**（见下文）。
- **全局捕获未处理的 Promise 错误**：监听 `unhandledrejection` 事件。
  ```javascript
  window.addEventListener('unhandledrejection', event => {
    console.error('未处理的 Promise 错误：', event.reason);
  });
  ```

#### 3. async 函数中的错误处理最佳实践
`async` 函数返回一个 Promise，内部错误会导致返回的 Promise 被拒绝。推荐做法：
- **使用 `try-catch` 包裹 `await` 表达式**，可以像同步代码一样处理错误。
  ```javascript
  async function fetchData() {
    try {
      const response = await fetch(url);
      const data = await response.json();
      return data;
    } catch (error) {
      console.error('请求失败：', error);
      // 可以重新抛出、返回默认值或进行降级处理
      return null;
    }
  }
  ```
- **如果不需要在函数内处理错误，可以让错误自然传播**，由调用方通过 `.catch()` 或外层 `try-catch` 捕获。
  ```javascript
  async function fetchData() {
    const response = await fetch(url);
    return response.json(); // 错误将传递给调用方
  }
  // 调用方
  fetchData().catch(error => console.error(error));
  ```
- **避免在 `async` 函数中忘记 `await` 或 `.catch()`**，否则错误会被吞没（除非有全局监听）。
- **对于多个并发 Promise**，可使用 `Promise.all` 或 `Promise.allSettled` 结合 `try-catch` 统一处理。
  ```javascript
  try {
    const results = await Promise.all([promise1, promise2]);
  } catch (error) {
    // 任一 promise 失败即进入此处
  }
  ```

**总结**：优先使用 `try-catch` 处理 `async` 函数内的错误，保持代码清晰；对于无法在本地处理的错误，向上传递并由调用方统一处理；始终为顶层 Promise 添加 `.catch()` 或全局 rejection 监听。

2. 什么是JavaScript的AOP（面向切面编程）？如何实现方法拦截和增强？
**AOP（面向切面编程）** 是一种编程范式，允许将横切关注点（如日志、权限、性能监控）与核心业务逻辑分离，通过预编译或运行时动态代理，在不修改源代码的情况下对方法进行拦截和增强。

### 在 JavaScript 中实现 AOP 的常见方式

#### 1. 高阶函数（函数装饰器）
通过包装原函数，在调用前后插入逻辑。

```javascript
function log(targetFn) {
  return function(...args) {
    console.log('调用前', args);
    const result = targetFn.apply(this, args);
    console.log('调用后', result);
    return result;
  };
}

function add(a, b) {
  return a + b;
}

const enhancedAdd = log(add);
enhancedAdd(2, 3); // 输出日志
```

#### 2. Proxy 对象
拦截对象属性的读取、赋值及方法调用。

```javascript
const obj = {
  greet(name) {
    return `Hello, ${name}`;
  }
};

const proxy = new Proxy(obj, {
  get(target, prop, receiver) {
    const original = target[prop];
    if (typeof original === 'function') {
      return function(...args) {
        console.log(`方法 ${prop} 被调用，参数:`, args);
        const result = original.apply(this, args);
        console.log(`方法返回:`, result);
        return result;
      };
    }
    return Reflect.get(target, prop, receiver);
  }
});

proxy.greet('World');
```

#### 3. 装饰器（需 Babel/TypeScript）
ES Next 装饰器提案可简洁地增强类方法。

```javascript
// 启用装饰器支持
function log(target, name, descriptor) {
  const original = descriptor.value;
  descriptor.value = function(...args) {
    console.log(`调用 ${name}，参数:`, args);
    const result = original.apply(this, args);
    console.log(`返回:`, result);
    return result;
  };
  return descriptor;
}

class Calculator {
  @log
  add(a, b) {
    return a + b;
  }
}
```

### 核心要点
- **Join Point（连接点）**：被拦截的方法。
- **Advice（增强逻辑）**：执行的前置/后置/环绕处理。
- **织入**：将增强逻辑应用到目标对象（通过高阶函数、Proxy 等）。

AOP 让代码更模块化，避免横切逻辑污染业务方法，提高可维护性和复用性。

3. 手写实现一个throttle函数，要求支持leading和trailing两种模式。
以下是一个支持 `leading` 和 `trailing` 模式的 `throttle` 函数实现，并附带取消方法。

```javascript
/**
 * 节流函数
 * @param {Function} func - 要执行的函数
 * @param {number} wait - 等待时间（毫秒）
 * @param {Object} options - 配置项
 * @param {boolean} options.leading - 是否在开始时执行（默认 true）
 * @param {boolean} options.trailing - 是否在结束后执行（默认 true）
 * @returns {Function} 节流后的函数
 */
function throttle(func, wait, options = {}) {
  let timeout = null;
  let previous = 0; // 上次执行时间戳
  const { leading = true, trailing = true } = options;

  const throttled = function (...args) {
    const now = Date.now();

    // 如果上次执行时间为 0 且 leading 为 false，则将上次执行时间设为当前
    // 这样第一次触发时不会立即执行，而是进入计时等待
    if (!previous && leading === false) {
      previous = now;
    }

    const remaining = wait - (now - previous);

    // 如果剩余时间 ≤ 0 或剩余时间 > wait（可能由于系统时间调整），则可以执行
    if (remaining <= 0 || remaining > wait) {
      if (timeout) {
        clearTimeout(timeout);
        timeout = null;
      }
      previous = now;
      func.apply(this, args);
    } else if (!timeout && trailing !== false) {
      // 如果 trailing 模式开启且没有定时器，则设置定时器在剩余时间后执行
      timeout = setTimeout(() => {
        // 如果 leading 为 false，则重置上次执行时间为 0，以确保下一次触发时不会立即执行
        previous = leading === false ? 0 : Date.now();
        timeout = null;
        func.apply(this, args);
      }, remaining);
    }
  };

  // 提供取消方法，用于清除定时器并重置状态
  throttled.cancel = function () {
    if (timeout) {
      clearTimeout(timeout);
      timeout = null;
    }
    previous = 0;
  };

  return throttled;
}
```

### 使用示例
```javascript
const log = () => console.log('执行', Date.now());
const throttledLog = throttle(log, 1000, { leading: true, trailing: true });

// 快速连续调用
throttledLog(); // 立即执行
throttledLog(); // 被忽略
throttledLog(); // 被忽略
// 1秒后，最后一次调用会触发 trailing 执行
```

### 关键说明
- **leading**: `true` 时，第一次调用会立即执行；`false` 时，第一次调用不会执行，而是等待 `wait` 时间后执行（如果 `trailing` 为 `true`）。
- **trailing**: `true` 时，在停止触发后 `wait` 毫秒会执行最后一次调用；`false` 时，不会执行最后一次调用。
- 如果同时设置 `leading: false, trailing: false`，函数将永远不会执行（通常不推荐）。
- 该实现正确处理了 `this` 和参数，并提供了 `cancel` 方法以手动取消延迟执行。

4. JavaScript中的Date对象有哪些坑？如何处理时区问题？dayjs和moment.js有什么区别？
### JavaScript 中 `Date` 对象的常见坑

1. **月份从 0 开始**：`new Date(2023, 0, 1)` 表示 2023 年 1 月 1 日，很容易写错为 12 月。
2. **日期解析不一致**：不同浏览器对 `new Date('2023-01-01')` 的解析可能不同（视为 UTC 还是本地时间），标准格式应为 `YYYY-MM-DDTHH:mm:ss.sssZ`。
3. **时间戳单位**：`Date.now()` 返回毫秒级时间戳，而很多后端接口使用秒级，需手动转换。
4. **时区混乱**：`getHours()` 返回本地时区的小时，而 `getUTCHours()` 返回 UTC 小时，容易混用。
5. **日期运算麻烦**：直接加减天数可能跨月，需用 `setDate` 或 `setMonth` 处理边界。
6. **构造函数重载**：不同参数个数（字符串、多个数值）行为差异大，易出错。
7. **没有内置时区支持**：无法直接处理非本地时区（如 Asia/Shanghai）。

### 如何处理时区问题？

- **存储与传输**：统一使用 UTC 时间戳或 ISO 8601 字符串（带 `Z` 后缀），避免歧义。
- **显示时转换**：使用 `toLocaleString` 或 `Intl.DateTimeFormat` 并指定 `timeZone` 选项。
  ```javascript
  new Intl.DateTimeFormat('zh-CN', { timeZone: 'Asia/Shanghai' }).format(date);
  ```
- **避免本地时区干扰**：若只需操作日期（年月日），使用 UTC 方法（如 `getUTCFullYear`）或先转换为 UTC 字符串。
- **复杂时区需求**：使用第三方库（如 `date-fns-tz`、`Luxon`、`moment-timezone`）。

### day.js 与 moment.js 的区别

| 特性 | day.js | moment.js |
|------|--------|-----------|
| **体积** | ~2KB（核心），轻量 | ~70KB，较大 |
| **不可变性** | 不可变（每次操作返回新对象） | 可变（默认会修改原对象） |
| **API 设计** | 与 moment.js 高度兼容，迁移成本低 | 成熟但庞大 |
| **插件化** | 按需加载插件（如时区、高级格式化） | 功能内置，无法按需减重 |
| **状态** | 积极维护，社区活跃 | 已进入维护模式，不再新增功能（建议新项目改用其他库） |
| **时区支持** | 需引入 `dayjs/plugin/timezone` 和 `dayjs/plugin/utc` | 需单独引入 `moment-timezone` |
| **性能** | 通常更快 | 相对较慢 |

**总结**：新项目推荐使用 **day.js**（轻量、现代）或 **date-fns**（函数式），moment.js 适用于维护旧项目。

5. 什么是JavaScript的尾调用优化（TCO）？哪些场景下浏览器不会进行TCO？
**尾调用优化（TCO）** 是一种编译器优化技术，指在函数的最后一步（尾位置）调用另一个函数时，当前函数的栈帧可以被复用，而无需创建新的栈帧。这能有效减少递归调用的内存消耗，避免栈溢出。

### 尾调用优化的条件（ES6 规范要求）
要使尾调用被优化，必须同时满足以下条件（在**严格模式**下）：
1. **尾调用必须是函数的最后一步操作**，即 return 语句中直接返回另一个函数的调用结果，且该调用之后没有其他操作（如赋值、运算等）。
2. **尾调用函数不能是闭包**，即不能引用当前函数中的变量（自由变量），否则需要保留当前环境。
3. **尾调用函数调用时，当前函数的栈帧不再需要**，即没有 `this` 绑定或 `arguments` 需要保留（严格模式下 `arguments` 不会被优化）。
4. 代码必须处于**严格模式**（非严格模式下 TCO 不被保证）。

### 哪些场景下浏览器不会进行 TCO？
#### 1. 不满足规范条件
- **非严格模式**：大多数引擎仅在严格模式下尝试优化。
- **调用后还有操作**：例如 `return g() + 1;` 或 `const x = g(); return x;` 不是尾调用。
- **闭包引用**：尾调用函数内部使用了外层函数的变量（如 `function f() { let a = 1; return function() { return a; } }` 的返回不是尾调用优化）。
- **尾调用不是函数调用**：如 `return;` 或 `return 1;` 不是尾调用。

#### 2. 浏览器引擎未实现或默认关闭
- **主流浏览器支持情况**：
  - **Safari**（JavaScriptCore）是唯一实现 TCO 的浏览器，但需满足严格条件。
  - **Chrome/Edge**（V8）和 **Firefox**（SpiderMonkey）出于调试友好、性能权衡等原因，**未实现 TCO**，任何尾调用都不会被优化。
  - Node.js 基于 V8，同样不支持 TCO。

#### 3. 调试或 eval 环境
- 当使用 `eval()` 或在开发者工具的控制台中执行代码时，引擎可能禁用优化以保证调试信息的准确性。

### 替代方案
由于 TCO 在生产环境不可靠，推荐使用以下方式避免递归栈溢出：
- **改用循环**（如 for、while）。
- **使用 trampoline 函数**：将递归转为循环调用。
- **使用 `setTimeout` 或 `Promise` 拆分栈**（不推荐，影响性能）。

总结：尾调用优化虽好，但实际浏览器支持有限，编码时应避免依赖 TCO 处理深度递归。

6. 解释JavaScript的相等性比较：==、===、Object.is()的区别，NaN和NaN比较的特殊情况。
### 三种相等性比较的区别

| 比较方式 | 行为描述 | 特殊处理 |
|----------|----------|----------|
| **`==` （抽象相等）** | 比较前进行**类型转换**，将两边转为相同类型再比较。 | 规则复杂，如 `null == undefined` 为 `true`，`'' == 0` 为 `true`。 |
| **`===` （严格相等）** | 不进行类型转换，类型不同直接返回 `false`。 | 推荐默认使用。 |
| **`Object.is()`** | 基本同 `===`，但修复了两个特殊处理：**`NaN` 等于自身**，**`+0` 不等于 `-0`**。 | 用于需要明确区分这些边界值的场景。 |

---

### `NaN` 比较的特殊情况
- **`NaN === NaN` → `false`** （严格相等也返回 `false`）
- **`NaN == NaN` → `false`** （抽象相等也返回 `false`）
- **`Object.is(NaN, NaN)` → `true`** （唯一认为 `NaN` 与自身相等的方式）
- 检测 `NaN` 的正确方式：`Number.isNaN()` 或 `isNaN()`（注意后者有隐式转换）。

**补充**：`+0 === -0` → `true`，但 `Object.is(+0, -0)` → `false`。

**总结**：日常开发推荐使用 `===`；仅在需要精确处理 `NaN` 或 `±0` 时使用 `Object.is()`。

7. 什么是可选链运算符的短路特性？它和&&运算符有什么区别？
### 可选链运算符（`?.`）的短路特性
当可选链运算符左侧的值为 `null` 或 `undefined` 时，整个表达式会**立即返回 `undefined`**，并且**不会继续评估**右侧的属性访问、方法调用或表达式。这可以避免因访问不存在属性而引发的 `TypeError`。

**示例**：
```javascript
const obj = null;
console.log(obj?.name); // 输出 undefined，不会报错
console.log(obj?.name.toUpperCase()); // 输出 undefined，不会尝试调用 toUpperCase
```

### 可选链（`?.`）与逻辑与（`&&`）的区别

| 区别点 | 可选链 `?.` | 逻辑与 `&&` |
|--------|-------------|-------------|
| **短路条件** | 仅当左侧为 `null` 或 `undefined` 时短路。 | 左侧值为**假值**（`false`、`0`、`''`、`null`、`undefined`、`NaN`）时短路。 |
| **适用场景** | 专用于**属性访问**或**方法调用**。 | 通用逻辑运算，可连接任何表达式。 |
| **短路返回值** | 返回 `undefined`。 | 返回左侧的**假值**（若左侧为假）或右侧的值（若左侧为真）。 |
| **对其它假值的处理** | 如果左侧为 `0`、`''`、`false` 等，不会短路，继续访问属性（可能导致错误）。 | 遇到任何假值都会短路。 |

**示例对比**：
```javascript
const obj = { count: 0 };

// 可选链：0 不是 null/undefined，所以继续访问 .toString
console.log(obj.count?.toString()); // "0"

// &&：0 是假值，所以直接返回 0，不会调用 .toString
console.log(obj.count && obj.count.toString()); // 0

// 可选链：访问不存在属性返回 undefined，不会报错
console.log(obj.none?.value); // undefined

// &&：访问不存在属性返回 undefined（假值），所以短路返回 undefined
console.log(obj.none && obj.none.value); // undefined
```

**总结**：可选链是更安全的属性访问方式，仅关注 `null/undefined`；而 `&&` 是通用逻辑运算符，适用于条件判断和避免访问假值属性（但可能错误地屏蔽有效假值）。

8. JavaScript中如何实现私有属性？#私有字段和闭包实现私有属性有什么区别？
在 JavaScript 中实现私有属性主要有两种方式：**闭包**和**私有字段（`#`）**。它们各有特点，适用于不同场景。

---

## 1. 如何实现私有属性？

### 方式一：闭包（Closure）
利用函数作用域和变量引用，将变量隐藏在构造函数或模块内部，通过特权方法暴露。

```javascript
// 构造函数 + 闭包
function Person(name) {
  let _name = name; // 私有变量
  this.getName = function() {
    return _name;
  };
  this.setName = function(newName) {
    _name = newName;
  };
}
const p = new Person('Alice');
console.log(p.getName()); // 'Alice'
console.log(p._name); // undefined
```

**模块模式**（IIFE）也可以创建私有变量：
```javascript
const myModule = (function() {
  let privateVar = 0;
  return {
    increment() { privateVar++; },
    get value() { return privateVar; }
  };
})();
```

### 方式二：私有字段（Private Fields）
ES2022 引入的类私有字段，使用 `#` 前缀，在类内部可直接访问，外部无法访问。

```javascript
class Person {
  #name; // 私有字段声明
  constructor(name) {
    this.#name = name;
  }
  getName() {
    return this.#name;
  }
}
const p = new Person('Bob');
console.log(p.getName()); // 'Bob'
console.log(p.#name); // SyntaxError: Private field '#name' must be declared in an enclosing class
```

私有字段也支持私有方法：
```javascript
class Example {
  #privateMethod() {
    return 'secret';
  }
  publicMethod() {
    return this.#privateMethod();
  }
}
```

---

## 2. 私有字段与闭包实现私有属性的区别

| 维度 | 闭包实现 | 私有字段 |
|------|----------|----------|
| **语言级别** | 利用函数作用域模拟，非原生私有。 | 语言内置的真正的私有性（ES2022+）。 |
| **访问方式** | 只能通过闭包内的特权方法访问。 | 只能在类内部直接通过 `this.#field` 访问，外部任何方式都无法访问（包括 `Object.getOwnPropertySymbols` 等反射手段）。 |
| **语法清晰度** | 代码较冗长，需要手动编写 getter/setter。 | 语法简洁直观，`#` 明确表示私有。 |
| **继承** | 闭包变量存在于实例上，不会被子类继承；特权方法若定义在原型上则无法访问私有变量（通常定义在实例上）。 | 私有字段**不会被继承**，子类无法访问父类的私有字段。若需要访问，父类可提供受保护的方法。 |
| **内存占用** | 每个实例都创建独立的闭包函数（如 getter/setter），可能增加内存开销。 | 私有字段存储在实例内部，方法在原型上，内存效率更高。 |
| **性能** | 访问私有变量需要经过闭包查找，略慢。 | 私有字段是引擎直接支持，访问速度更快。 |
| **调试与工具支持** | 在控制台中难以直接查看私有变量，但可通过闭包内方法间接查看。 | 现代开发者工具（如 Chrome）支持在控制台显示私有字段（但无法从外部代码访问），更易调试。 |
| **强制私有性** | 闭包变量并非绝对安全，某些场景（如 `eval`、`with`）可能被绕过，但现代代码中基本安全。 | 私有字段是语法强制，任何试图在外部访问都会触发语法错误，彻底杜绝意外访问。 |
| **适用环境** | 适用于所有 JavaScript 环境（包括旧浏览器），无需编译。 | 需要 ES2022 环境或通过 Babel 编译（但编译后本质是用 WeakMap 模拟）。 |
| **TypeScript 的 private** | TypeScript 的 `private` 修饰符是编译时检查，运行时仍然是公开属性。 | TypeScript 3.8+ 支持 `#` 私有字段，编译后可能转换为 WeakMap 等实现。 |

---

## 总结

- **闭包**：适合需要兼容旧环境、或希望创建真正的“不可访问”变量（如模块内部状态）的场景。但写法稍显笨重，且每个实例都会创建新的方法。
- **私有字段**：现代 JavaScript 推荐的私有属性实现方式，语法简洁、性能好、强制私有，特别适合类定义。推荐新项目使用。

两者可以结合使用：例如在类内部，私有字段存放数据，特权方法提供操作；在模块中，用闭包隐藏模块内部状态。

9. 手写实现一个发布订阅模式，要求支持优先级队列和命名空间。
```javascript
/**
 * 支持优先级和命名空间的发布订阅模式实现
 * - 命名空间为点分隔的字符串，触发时会匹配所有以该前缀开头的命名空间
 * - 优先级数字越小，执行优先级越高（默认 0）
 */
class EventEmitter {
  constructor() {
    // 使用 Map 存储订阅，键为完整的命名空间字符串，值为 { callback, priority } 的数组
    this.subscriptions = new Map();
  }

  /**
   * 订阅事件
   * @param {string} namespace 命名空间，如 'user.login'
   * @param {Function} callback 回调函数
   * @param {number} priority 优先级，默认 0（数字越小优先级越高）
   */
  on(namespace, callback, priority = 0) {
    if (typeof callback !== 'function') {
      throw new TypeError('callback must be a function');
    }
    if (!this.subscriptions.has(namespace)) {
      this.subscriptions.set(namespace, []);
    }
    this.subscriptions.get(namespace).push({ callback, priority });
  }

  /**
   * 一次性订阅，触发后自动移除
   * @param {string} namespace
   * @param {Function} callback
   * @param {number} priority
   */
  once(namespace, callback, priority = 0) {
    const wrapper = (...args) => {
      callback(...args);
      this.off(namespace, wrapper);
    };
    // 保留原回调以便外部可以通过原回调移除（但 wrapper 与原 callback 不同，需要注意）
    // 为了能通过原 callback 移除，我们需要存储关系。简化起见，我们要求用户使用 once 时不要依赖 off 移除
    this.on(namespace, wrapper, priority);
  }

  /**
   * 移除订阅
   * @param {string} namespace 命名空间
   * @param {Function} [callback] 要移除的特定回调，不传则移除该命名空间下的所有订阅
   */
  off(namespace, callback) {
    if (!this.subscriptions.has(namespace)) return;

    if (callback === undefined) {
      // 移除整个命名空间的订阅
      this.subscriptions.delete(namespace);
    } else {
      // 移除特定回调
      const listeners = this.subscriptions.get(namespace);
      const filtered = listeners.filter(item => item.callback !== callback);
      if (filtered.length === 0) {
        this.subscriptions.delete(namespace);
      } else {
        this.subscriptions.set(namespace, filtered);
      }
    }
  }

  /**
   * 触发事件
   * @param {string} namespace 触发命名空间（可以是前缀）
   * @param {...any} args 传递给回调的参数
   */
  emit(namespace, ...args) {
    // 收集所有匹配的订阅（命名空间以 namespace 开头）
    const matchedListeners = [];
    for (const [key, listeners] of this.subscriptions.entries()) {
      // 判断是否以前缀开头，可以是完全相等或子命名空间
      if (key === namespace || key.startsWith(namespace + '.')) {
        matchedListeners.push(...listeners);
      }
    }

    // 按优先级升序排序（数字小优先），相同优先级保持原顺序（稳定排序）
    matchedListeners.sort((a, b) => {
      if (a.priority !== b.priority) {
        return a.priority - b.priority;
      }
      // 保持原顺序（但由于是合并多个数组，原顺序不一定能保证稳定，但数组本身按插入顺序）
      // 这里通过索引保证稳定较复杂，简化处理：不额外处理
      return 0;
    });

    // 执行所有回调
    for (const { callback } of matchedListeners) {
      callback(...args);
    }
  }

  /**
   * 清空所有订阅
   */
  clear() {
    this.subscriptions.clear();
  }

  /**
   * 获取指定命名空间下的订阅数量（精确匹配）
   */
  listenerCount(namespace) {
    return this.subscriptions.has(namespace) ? this.subscriptions.get(namespace).length : 0;
  }
}

// 使用示例
const bus = new EventEmitter();

// 订阅
bus.on('user', (name) => console.log('user:', name), 1);
bus.on('user.login', (name) => console.log('login:', name), 0); // 优先级更高
bus.on('user.logout', (name) => console.log('logout:', name), 2);

// 触发前缀 'user' 会同时触发 'user', 'user.login', 'user.logout'
bus.emit('user', 'Alice');
// 输出顺序（按优先级）：
// login: Alice   (优先级0)
// user: Alice    (优先级1)
// logout: Alice  (优先级2)

// 只触发精确命名空间
bus.emit('user.login', 'Bob');
// 输出：login: Bob

// 移除订阅
bus.off('user.login');
bus.emit('user', 'Charlie'); // login 不会被触发
```

### 关键设计说明
- **命名空间前缀匹配**：触发 `'a'` 会同时触发所有以 `'a'` 或 `'a.'` 开头的命名空间，实现层次传播。
- **优先级排序**：采用数字越小优先级越高的约定，排序时使用 `sort`，默认稳定排序（ES2019 后保证稳定），但合并多个数组时的原始顺序可能不完全保持，如有需要可额外记录添加顺序。
- **内存管理**：移除订阅后若列表为空则删除 Map 键，避免内存泄漏。
- **简单性**：`once` 实现利用了包装函数，但会导致 `off` 无法直接移除原回调（需用包装函数引用），但常见场景下够用。

10. JavaScript的Map和Object作为哈希表有什么区别？什么场景下应该使用Map？
JavaScript 的 `Map` 和普通对象 `Object` 都可以作为键值对集合使用，但在设计和使用上有显著区别。以下是主要对比以及使用 `Map` 的推荐场景。

---

### `Map` 与 `Object` 的主要区别

| 特性 | `Map` | `Object` |
|------|-------|----------|
| **键的类型** | 任意类型（包括对象、函数、NaN、Symbol 等）。 | 只能是字符串或 Symbol（其他类型会隐式转为字符串）。 |
| **键值对的顺序** | 严格保持插入顺序，迭代时按插入顺序返回。 | 自有属性有一定顺序：整数键按升序，字符串按插入顺序，Symbol 在最后，但规则复杂，通常认为顺序不可靠。 |
| **大小获取** | 内置 `size` 属性，直接获取条目数。 | 需通过 `Object.keys(obj).length` 计算。 |
| **迭代器** | 默认可迭代，可直接使用 `for...of` 遍历 `keys()`、`values()`、`entries()`。 | 需先转换为数组（如 `Object.entries()`）才能迭代。 |
| **性能** | 针对频繁增删键值对优化，通常比对象更高效。 | 适合静态或较少的属性操作，大量增删可能稍慢。 |
| **原型链** | 没有原型链，不会意外继承属性。 | 有原型链，可能包含继承的属性和方法（如 `toString`），需用 `hasOwnProperty` 判断。 |
| **内存占用** | 略高于对象，但差异很小。 | 相对紧凑，适合简单结构。 |
| **序列化** | 无法直接通过 `JSON.stringify` 序列化（会变成空对象）。需手动转换。 | 原生支持 JSON 序列化。 |
| **类型安全性** | 键不受隐式转换影响，例如 `NaN` 可作为键且与自身相等。 | 数字键会被转为字符串，`obj[1]` 和 `obj['1']` 等价。 |

---

### 什么场景下应该使用 `Map`？

1. **键不是字符串或 Symbol**  
   例如需要使用对象、DOM 节点、函数等作为键时，`Map` 是唯一选择。

2. **需要频繁增删键值对**  
   `Map` 在大量插入和删除操作中性能更好，且 `size` 属性方便动态监控集合大小。

3. **需要保证键值对的插入顺序**  
   若依赖遍历顺序（如实现 LRU 缓存、有序列表），`Map` 提供了可靠的顺序保证。

4. **需要与外部数据（如数组）频繁转换**  
   `Map` 直接支持 `forEach`、`for...of` 等迭代方法，配合扩展运算符可轻松转为数组。

5. **需要避免原型链干扰**  
   若希望集合纯净，不受 `hasOwnProperty` 或 `toString` 等原型属性影响，`Map` 更安全。

6. **需要键的严格相等语义**  
   例如 `NaN` 作为键时，`Map` 认为 `NaN === NaN`，而对象会将 `NaN` 转为字符串 `"NaN"`。

---

### 何时仍然使用 `Object`？

- 作为简单的记录（Record），键为字符串且结构固定（如配置对象、DTO）。
- 需要与 JSON 互操作（例如从 API 接收数据）。
- 需要利用原型链继承方法（但通常不推荐）。
- 代码量小且无需复杂操作时，对象语法更简洁（如 `obj.key` vs `map.get('key')`）。

**总结**：现代 JavaScript 开发中，`Map` 适用于动态、频繁操作的键值集合，而 `Object` 更适合静态结构或需要与 JSON 交互的场景。

## React (10题)

11. React中的useInsertionEffect是什么？它和useLayoutEffect的执行时机有什么不同？
`useInsertionEffect` 是 React 18 新增的 Hook，专为 CSS-in-JS 库设计，用于在 DOM 更新后、布局计算前同步插入样式节点。它与 `useLayoutEffect` 的核心区别在于**执行时机**：

- **`useInsertionEffect`**：在 React 完成 DOM 突变（更新）之后、浏览器进行布局计算之前同步执行。此时可安全插入 `<style>` 标签或修改全局样式，但**不能读取布局信息**（如元素尺寸），因为布局尚未发生。
- **`useLayoutEffect`**：在布局计算之后、浏览器绘制之前同步执行。此时可以读取 DOM 布局（如 `getBoundingClientRect`），但会阻塞绘制。

### 为什么需要 `useInsertionEffect`？
在 CSS-in-JS 库（如 styled-components、Emotion）中，需要在元素渲染前将样式插入到文档中，避免因样式动态注入导致额外布局抖动。若使用 `useLayoutEffect` 插入样式，可能会在布局计算后再次触发样式变更，造成不必要的重绘。`useInsertionEffect` 的时机确保样式在布局前生效，且不会干扰布局读取。

### 注意事项
- 该 Hook 无法访问 DOM 引用（ref），因为此时 ref 可能尚未附加。
- 仅在客户端渲染时执行，服务端渲染（SSR）不会触发。

12. 什么是React的选择性Hydration？它如何提升SSR的性能？
**选择性 Hydration** 是 React 18 中基于 `Suspense` 的一项优化技术，它允许 React **按需、按优先级** 对服务端渲染（SSR）生成的 HTML 进行水合（即激活事件监听和状态），而不是一次性水合整个页面。

### 如何提升 SSR 性能？
1. **优先水合可交互区域**  
   页面中用户可能最先操作的部分（如导航栏、按钮）可以优先水合，使其更早变得可响应（提升 TTI，即可交互时间）。

2. **可中断的水合过程**  
   水合过程是可中断的，React 会根据用户交互动态调整优先级。例如，用户点击一个未水合的组件时，React 会中断低优先级的水合，立即水合该组件，实现“交互优先”。

3. **延迟水合次要内容**  
   处于屏幕外或低优先级的区域（如下方内容、弹窗）可以延迟水合，减少初始 CPU 负载，使主线程更流畅。

4. **避免全量水合阻塞**  
   传统 SSR 需要整个页面 JS 加载并水合后才能交互，而选择性 Hydration 允许页面逐步解锁交互能力，显著改善首屏加载体验。

**总结**：选择性 Hydration 通过细粒度、按需的水合策略，让页面“边加载边交互”，极大提升了大型 SSR 应用的感知性能和用户体验。

13. React中如何实现组件的预渲染？React.memo的第二个参数如何使用？
### React 中如何实现组件的预渲染？
预渲染（Prerendering）是指在构建时生成静态 HTML 文件，以便用户首次访问时直接展示内容，提升加载速度和 SEO。常见实现方式：

- **使用框架**：Next.js 的静态生成（`getStaticProps`）或 Gatsby 等框架内置预渲染。
- **手动预渲染**：在构建脚本中调用 `ReactDOMServer.renderToString` 或 `renderToStaticMarkup` 生成 HTML，并写入文件。可配合 `prerender-spa-plugin` 自动抓取路由生成静态页面。
- **服务端渲染（SSR）**：每次请求动态生成 HTML，虽不是预渲染但也能改善首屏。

### React.memo 的第二个参数如何使用？
`React.memo` 的第二个参数是一个自定义比较函数，用于控制组件是否重新渲染。它接收 `prevProps` 和 `nextProps`，返回 `true` 表示 props 相等（不重新渲染），返回 `false` 表示需要重新渲染。

```javascript
const MyComponent = React.memo(
  (props) => <div>{props.name}</div>,
  (prevProps, nextProps) => {
    // 仅当 name 相同时跳过渲染
    return prevProps.name === nextProps.name;
  }
);
```

**注意**：函数内需自行比较所有相关 props；若返回 `true` 但实际依赖的 props 变化，可能导致 UI 不更新。通常默认浅比较已足够，仅在需要精细控制时使用自定义比较。

14. 什么是React的Automatic Batching？它在React 18中有什么改进？
**Automatic Batching** 是 React 的一种优化机制，它会将多个状态更新（如 `setState`）合并为一次重新渲染，避免不必要的重复渲染，提升性能。

### React 18 之前的批处理
- 仅在 **React 事件处理函数** 中自动批处理。
- 在 **异步回调**（如 `setTimeout`、`Promise`、原生事件监听）中，更新不会批处理，每次 `setState` 都会触发独立渲染。

### React 18 的改进
React 18 通过引入 `createRoot` 扩展了自动批处理的适用范围：
- **所有场景下都自动批处理**：包括 `setTimeout`、`Promise`、原生事件、甚至 `useEffect` 内部的更新。
- 任何发生在同一同步任务中的多个状态更新都会被合并为一次渲染。

**退出机制**：若需要强制同步更新，可使用 `flushSync` 包裹更新，使其立即执行并刷新 DOM。

**示例**：
```javascript
// React 18 中，以下更新会被批处理
setTimeout(() => {
  setCount(c => c + 1);
  setFlag(f => !f);
}, 1000);
```

这一改进减少了渲染次数，提升了应用性能，尤其是复杂异步场景下的表现。

15. 如何在React中实现全局状态管理？不使用Redux的情况下有哪些替代方案？
在 React 中实现全局状态管理，可以使用多种方案，其中 Redux 是最经典的，但并非唯一选择。以下是不使用 Redux 的常见替代方案及其特点：

---

### 1. **React Context API + useReducer**
- **简介**：React 内置的 Context 用于跨组件传递数据，结合 `useReducer` 管理复杂状态逻辑。
- **适用场景**：中小型应用，状态结构简单或中等复杂度，无需额外依赖。
- **优点**：无需安装外部库，与 React 深度集成。
- **缺点**：Context 的值变化会导致所有消费组件重渲染（除非配合 `memo`），且不适合高频更新。

### 2. **Zustand**
- **简介**：极简的轻量级状态管理库，基于不可变状态和 hooks，API 类似 Redux 但更简洁。
- **适用场景**：中小型项目，追求简单性和性能。
- **优点**：体积小（~1KB），无需 Provider，直接通过 hook 访问状态，支持中间件。
- **代码示例**：
  ```jsx
  import create from 'zustand';
  const useStore = create(set => ({ count: 0, inc: () => set(state => ({ count: state.count + 1 })) }));
  ```

### 3. **Jotai**
- **简介**：原子状态管理库，灵感来自 Recoil，但更轻量。状态由原子（atom）组成，可组合。
- **适用场景**：需要细粒度状态拆分和依赖追踪的复杂应用。
- **优点**：原子化设计避免多余渲染，支持异步和派生状态，TypeScript 友好。

### 4. **Recoil**
- **简介**：Facebook 官方推出的原子状态管理库，与 React 并发模式兼容。
- **适用场景**：大型应用，状态依赖复杂，需要精细控制渲染。
- **优点**：原子 + 选择器（selector）模型，支持异步查询，可观察状态图。

### 5. **MobX**
- **简介**：响应式状态管理库，通过可观察对象自动追踪状态变化并更新视图。
- **适用场景**：适合面向对象风格，需要自动依赖追踪的复杂应用。
- **优点**：代码简洁，无需手动优化渲染，支持计算属性和反应。
- **示例**：
  ```jsx
  import { observable, action } from 'mobx';
  import { observer } from 'mobx-react';
  class Store { @observable count = 0; @action inc = () => this.count++; }
  ```

### 6. **XState**
- **简介**：基于有限状态机的状态管理库，适合处理复杂流程和状态机场景。
- **适用场景**：需要明确状态转换（如表单步骤、加载流程）的应用。
- **优点**：状态可视化，逻辑严谨，避免无效状态。

---

### 如何选择？
- **简单项目**：Context + useReducer 足够。
- **追求轻量和性能**：Zustand 或 Jotai。
- **复杂依赖和原子化需求**：Recoil 或 Jotai。
- **响应式编程偏好**：MobX。
- **状态机场景**：XState。

每种方案都有其设计哲学，根据团队熟悉度和项目需求权衡即可。

16. React中的useReducer和Redux的reducer有什么区别？什么时候使用useReducer？
### `useReducer` 与 Redux 的 Reducer 区别

| 维度 | `useReducer` (React Hook) | Redux Reducer |
|------|----------------------------|---------------|
| **作用范围** | 仅在**单个组件内部**管理状态，通常配合 `useContext` 可跨组件，但无全局单一 store。 | 应用级全局状态管理，所有 reducer 组合成单一 store，整个应用共享。 |
| **状态存储** | 状态存储在组件内部，组件销毁则状态消失。 | 状态存储在 Redux store 中，独立于组件树，持久存在。 |
| **配套工具** | 无内置中间件、DevTools 等，但可手动组合 `useContext` 传递 dispatch。 | 提供强大的中间件（如 thunk、saga）、DevTools 时间旅行、状态持久化等生态。 |
| **异步处理** | 需要手动在 `useEffect` 或事件中处理异步，再调用 dispatch。 | 通过中间件（如 redux-thunk）支持异步 action。 |
| **性能优化** | 默认可能引起子组件重渲染，需配合 `useMemo`、`memo` 优化。 | 通过 `connect` 或 `useSelector` 的浅比较，可精确控制组件更新。 |
| **使用复杂度** | 轻量，适合局部复杂状态。 | 较重，适合大型应用，需要配置 store、中间件等。 |

---

### 什么时候使用 `useReducer`？

- **组件内部状态逻辑较复杂**：例如有多个子值、或下一个状态依赖于之前的状态（如购物车、表单）。
- **状态更新需要可预测性**：通过 action 显式描述更新意图，使代码更易理解和测试。
- **状态逻辑可复用**：可以将 reducer 函数提取到组件外部，供多个组件共享（但状态仍独立）。
- **与 `useContext` 结合**：可在中等规模应用中实现简易的“局部全局状态”，避免层层传递 props。

**典型场景**：复杂表单、计数器进阶、撤销/重做功能、状态机等。当多个 `useState` 变得臃肿且相互依赖时，`useReducer` 是更好的选择。

17. 如何在React中实现路由权限控制？动态路由如何配置？
在 React 中实现路由权限控制，通常结合 React Router 和全局状态管理（如 Redux、Context）。核心思路是根据用户权限动态过滤可访问的路由，并在渲染时进行校验。以下是具体实现方式和动态路由配置的示例（基于 React Router v6）。

---

### 1. 定义路由配置数组
每个路由可以附加权限元信息（如 `requiresAuth`、`roles`、`permission`）。

```jsx
// routes.js
const routes = [
  {
    path: '/',
    element: <HomePage />,
  },
  {
    path: '/dashboard',
    element: <Dashboard />,
    meta: { requiresAuth: true, roles: ['admin', 'editor'] }
  },
  {
    path: '/admin',
    element: <AdminPanel />,
    meta: { requiresAuth: true, roles: ['admin'] }
  },
  {
    path: '/login',
    element: <Login />,
    meta: { requiresAuth: false }
  },
  {
    path: '/403',
    element: <Forbidden />,
  },
  {
    path: '*',
    element: <NotFound />,
  }
];
```

### 2. 封装权限校验逻辑
创建一个函数，根据当前用户权限（从全局状态获取）判断是否允许访问某个路由。

```jsx
// utils/auth.js
export const hasPermission = (user, route) => {
  const { meta = {} } = route;
  if (!meta.requiresAuth) return true; // 公开路由
  if (!user) return false; // 未登录
  if (meta.roles && !meta.roles.some(role => user.roles.includes(role))) {
    return false; // 角色不匹配
  }
  // 可继续检查更细粒度的权限点
  return true;
};
```

### 3. 生成可访问的路由并渲染
使用 `useRoutes` 钩子动态生成路由表。将用户信息和路由配置传入，过滤出符合权限的路由。

```jsx
// App.js
import { useRoutes } from 'react-router-dom';
import { useSelector } from 'react-redux'; // 假设使用 Redux 管理用户状态
import { routes } from './routes';
import { hasPermission } from './utils/auth';

function App() {
  const user = useSelector(state => state.user.currentUser); // 获取用户信息

  // 过滤路由
  const filteredRoutes = routes.filter(route => hasPermission(user, route));

  // 生成路由元素
  const routing = useRoutes(filteredRoutes);
  return routing;
}
```

### 4. 处理重定向（如未登录跳转登录页）
可以在过滤时自动将未授权的路由替换为 `/403` 或 `/login`，更推荐在渲染时通过 `Navigate` 组件处理。或者使用路由守卫的方式：

在封装权限校验后，为需要权限的路由元素包裹一层守卫组件：

```jsx
const ProtectedRoute = ({ children, meta }) => {
  const user = useSelector(state => state.user.currentUser);
  const navigate = useNavigate();

  useEffect(() => {
    if (!user) {
      navigate('/login', { replace: true });
    } else if (meta?.roles && !meta.roles.some(role => user.roles.includes(role))) {
      navigate('/403', { replace: true });
    }
  }, [user, meta, navigate]);

  return user ? children : null; // 未登录时返回 null（因为会跳转）
};

// 然后在 routes 中动态包裹 element
const routes = [
  // ...
  {
    path: '/dashboard',
    element: <ProtectedRoute meta={{ requiresAuth: true, roles: ['admin'] }}>
              <Dashboard />
            </ProtectedRoute>
  }
];
```

### 5. 动态路由配置（从后端获取）
如果路由完全由后端动态返回，可以在登录后请求后端接口获取路由配置，然后动态添加到路由系统中。

```jsx
// 登录成功后
fetch('/api/user/routes')
  .then(res => res.json())
  .then(remoteRoutes => {
    // 将后端返回的 JSON 转换成 React Router 的配置格式
    const dynamicRoutes = remoteRoutes.map(r => ({
      path: r.path,
      element: lazyLoad(r.component), // 动态加载组件
      meta: r.meta,
    }));
    // 合并静态路由（如登录页、404）并设置到路由状态中
    setRoutes([...staticRoutes, ...dynamicRoutes]);
  });
```

然后使用 `useRoutes` 渲染动态路由表。注意组件需要动态导入（React.lazy），并配合 Suspense。

### 6. 注意事项
- 前端权限控制只能增强用户体验，真正的权限校验必须在后端执行。
- 路由配置中的组件可能较多，可以使用 `React.lazy` 进行代码分割。
- 如果使用 `useRoutes`，每次用户权限变化（如登出）都需要重新生成路由表，确保路由及时更新。

以上方案覆盖了常见的路由权限控制需求，并支持静态或动态路由配置。

18. React中的getDerivedStateFromProps为什么是静态方法？它有什么限制？
`getDerivedStateFromProps` 被设计为静态方法，主要有以下原因和限制：

### 为什么是静态方法？
- **强制纯函数**：静态方法无法访问 `this`，避免在方法内调用实例方法、访问 `refs` 或执行副作用，确保该方法仅根据传入的 `props` 和 `state` 计算新状态，符合纯函数原则。
- **安全性**：防止开发者误用（如发起网络请求、订阅事件），减少因错误使用生命周期引发的 bug。
- **未来兼容**：为 React 的并发渲染（如时间切片）提供保障，静态方法不会依赖实例，可安全地在多次渲染中重复调用。

### 主要限制
1. **无法访问实例**：不能使用 `this.props`、`this.setState` 或任何实例方法，只能通过参数获取 `props` 和 `state`。
2. **返回值严格**：必须返回一个对象用于更新 `state`，或返回 `null` 表示无更新；返回值会浅合并到 `state`。
3. **每次渲染都会触发**：包括初始化和后续更新，因此不适合执行副作用（副作用应放在 `componentDidUpdate` 中）。
4. **易滥用导致复杂**：大多数场景下，可以用完全受控组件、`key` 或 `memoization` 替代派生状态，避免不必要的复杂性。
5. **与旧生命周期差异**：它替代了 `componentWillReceiveProps`，但无法像后者那样获取旧 `props`（可通过比较参数中的 `prevState` 与当前 state 间接实现）。

19. 什么是React的Offscreen组件？它的使用场景有哪些？
**React 的 Offscreen 组件**是一个实验性组件（通常通过 `unstable_Offscreen` 引用），用于标记部分 UI 为“离屏”状态。当 Offscreen 包裹的组件被隐藏时，React **不会卸载它们**，而是将其保留在虚拟 DOM 中并**冻结渲染**，同时保持内部 state、context 等状态不变。再次显示时，组件可以快速恢复渲染而无需重新初始化。

### 工作原理
- 通过 `mode` 属性控制显示/隐藏：`mode="visible"` 正常渲染，`mode="hidden"` 将子树标记为离屏。
- 离屏子树仍然存在于 fiber 树中，但跳过实际渲染（不提交到 DOM），且保留所有 hooks 状态。
- 再次切换为 `visible` 时，React 直接复用现有 fiber 节点并重新提交渲染，非常高效。

### 使用场景
1. **标签页/卡片切换**  
   切换不同标签页时，保留隐藏标签页的输入状态、滚动位置等，避免重复获取数据或重置表单。
   ```jsx
   <Offscreen mode={activeTab === 'tab1' ? 'visible' : 'hidden'}>
     <Tab1 />
   </Offscreen>
   ```

2. **路由缓存（类似 KeepAlive）**  
   离开页面时隐藏但保留状态，返回时立即呈现，提升多页签或历史导航的体验。

3. **虚拟化列表的预渲染**  
   提前渲染视口外的列表项并标记为 hidden，当用户滚动进入时快速变为 visible，消除白屏。

4. **模态框/抽屉**  
   关闭弹窗时保持内部表单数据，再次打开无需重新填写。

5. **动画过渡**  
   在元素退出动画期间将其保持为 hidden，动画结束后再真正移除，实现流畅的消失效果。

### 与常规隐藏方式的区别
- **`display: none`**：仅 CSS 隐藏，组件仍在 DOM 中且可能触发浏览器重绘，但 React 仍会进行完整的渲染工作。
- **条件渲染（`&&` 或三元）**：组件完全卸载，状态丢失，重新显示时需从头初始化。
- **Offscreen**：React 层面跳过渲染，保留状态，性能最优，适合需要“记忆”的隐藏场景。

### 注意
- 目前是**实验性 API**，仅在 React 的 experimental 版本中可用，未来可能变动。
- 使用前需评估稳定性，生产环境谨慎采用。

20. 如何在React中实现骨架屏？Suspense和loading状态如何结合使用？
骨架屏（Skeleton Screen）是在页面数据加载完成前，通过显示页面的大致轮廓（如占位色块）来提升用户感知体验的一种技术。在 React 中，实现骨架屏可以手动编写，也可以结合 `Suspense` 和加载状态优雅地展示。

---

### 1. 实现骨架屏的常见方式

#### 手动编写骨架屏组件
创建一个独立的组件，用 CSS 模拟内容布局（如矩形、圆角、闪烁动画）。

```jsx
const Skeleton = () => (
  <div className="skeleton">
    <div className="skeleton-avatar" />
    <div className="skeleton-line" />
    <div className="skeleton-line" />
  </div>
);
// 配合 CSS 动画（如 @keyframes shimmer）
```

#### 使用第三方库
如 `react-loading-skeleton`，可快速生成占位元素。

```jsx
import Skeleton from 'react-loading-skeleton';
const MyComponent = () => <Skeleton count={5} />;
```

---

### 2. 结合 Suspense 与骨架屏

`Suspense` 是 React 内置组件，允许在子组件准备好之前显示 fallback 内容。它适用于代码分割（`React.lazy`）以及支持 Suspense 的数据获取场景。

#### 场景一：代码分割
```jsx
import { lazy, Suspense } from 'react';
const LazyComponent = lazy(() => import('./LazyComponent'));

function App() {
  return (
    <Suspense fallback={<Skeleton />}>
      <LazyComponent />
    </Suspense>
  );
}
```
当模块加载时，`<Skeleton />` 会作为占位符显示。

#### 场景二：数据获取（需配合支持 Suspense 的库）
例如使用 React Query 的 suspense 模式：

```jsx
import { Suspense } from 'react';
import { useSuspenseQuery } from '@tanstack/react-query';

function UserProfile() {
  const { data } = useSuspenseQuery({ queryKey: ['user'], queryFn: fetchUser });
  return <div>{data.name}</div>;
}

function App() {
  return (
    <Suspense fallback={<Skeleton />}>
      <UserProfile />
    </Suspense>
  );
}
```
数据加载期间，`<Skeleton />` 自动展示，加载完成后替换为真实内容。

---

### 3. 传统 loading 状态与骨架屏结合

若不使用 Suspense，可手动管理 loading 状态：

```jsx
function Profile() {
  const [loading, setLoading] = useState(true);
  const [data, setData] = useState(null);

  useEffect(() => {
    fetchData().then(res => {
      setData(res);
      setLoading(false);
    });
  }, []);

  if (loading) return <Skeleton />;
  return <div>{data.name}</div>;
}
```

---

### 总结
- **骨架屏**提升加载感知，可以手动实现或借助库。
- **Suspense** 提供声明式 fallback，简化 loading 状态管理，尤其适合与 React.lazy 及支持 Suspense 的数据获取库结合。
- 两者结合能写出更简洁、用户友好的加载体验。

21. Next.js 14的Partial Prerendering是什么？它如何结合静态和动态内容？
**Partial Prerendering（PPR）** 是 Next.js 14 引入的一项实验性特性，允许在同一个路由中**同时使用静态和动态渲染**，结合了静态站点生成（SSG）的速度与服务器端动态内容的实时性。

### 工作原理
- 利用 React 的 **Suspense** 将页面划分为静态外壳和动态部分。
- **静态外壳**（如布局、导航、骨架屏）在构建时预渲染为静态 HTML，可被 CDN 缓存，实现极快加载。
- **动态部分**（如个性化数据、实时内容）在请求时由服务器流式渲染，通过 Suspense 的 fallback 先展示占位内容，数据就绪后替换。

### 如何结合静态和动态内容？
```jsx
export default function Page() {
  return (
    <div>
      <Header /> {/* 静态部分 */}
      <Suspense fallback={<ProfileSkeleton />}>
        <Profile /> {/* 动态部分，在请求时渲染 */}
      </Suspense>
    </div>
  );
}
```
在构建时，`<Header />` 会被预渲染为静态 HTML，而 `<Profile />` 区域保留为动态占位符。当用户访问页面时，静态 HTML 立即展示，同时服务器开始渲染 `<Profile />` 并通过流式响应发送到客户端，实现无缝更新。

### 优势
- **性能提升**：静态内容快速响应，动态内容按需加载，减少首屏时间。
- **简化开发**：无需为整个页面选择静态或动态，可以混合使用，代码更直观。
- **缓存友好**：静态外壳可长期缓存，动态部分仍保持实时性。

PPR 目前处于实验阶段，但为未来 Next.js 应用的性能优化提供了新方向。

22. Next.js中的Draft Mode是什么？它如何帮助预览未发布的内容？
**Draft Mode** 是 Next.js 的一项功能，允许在静态生成（SSG）或增量静态再生（ISR）的页面中**动态渲染未发布的内容**，用于预览草稿。

### 如何工作？
1. **启用草稿模式**：通过调用 `res.setDraftMode({ enable: true })`（或 `draftMode.enable()`）设置一个安全的 HTTP-only cookie（`__prerender_bypass`）。
2. **绕过静态缓存**：当用户带有此 cookie 访问页面时，Next.js 会绕过静态缓存，动态执行 `getStaticProps`（或 App Router 中的页面）以获取最新数据（如从 CMS 获取草稿内容）。
3. **预览内容**：页面会展示草稿而非已发布的内容，同时保留正常站点的其他功能。

### 如何帮助预览？
- 内容编辑在 CMS 中点击“预览”时，触发一个 API 路由（如 `/api/draft`），验证秘密令牌后启用草稿模式，并重定向到目标页面。
- 此后，编辑即可看到实时草稿内容，而普通用户仍看到已发布的静态版本。

### 关键点
- **安全**：需通过秘密令牌或类似机制防止未授权访问。
- **灵活性**：适用于 Headless CMS、博客、电商等需要内容审核的场景。
- **在 App Router 中**：使用 `draftMode()` 方法。

23. 如何在Next.js中实现增量静态生成（ISR）？fallback: 'blocking'和fallback: true有什么区别？
在 Next.js 中，**增量静态生成（ISR）** 允许在构建后按需更新静态页面，无需重新构建整个应用。实现方式如下：

### 实现 ISR 的基本步骤
1. **在 `getStaticProps` 中设置 `revalidate` 属性**  
   ```jsx
   export async function getStaticProps() {
     const data = await fetchData();
     return {
       props: { data },
       revalidate: 60, // 每60秒重新验证一次
     };
   }
   ```
   当访问页面时，Next.js 会先返回缓存的静态页面，同时若超过 `revalidate` 时间，会在后台触发页面重新生成。

2. **对于动态路由（如 `pages/posts/[id].js`）**，还需在 `getStaticPaths` 中配合 `fallback` 选项控制未预先生成页面的行为。

---

### `fallback: true` 与 `fallback: 'blocking'` 的区别
当用户请求一个未在 `getStaticPaths` 中预先生成的路径时，`fallback` 决定如何处理：

| 选项 | 行为 | 用户体验 | 适用场景 |
|------|------|----------|----------|
| **`fallback: true`** | 立即返回一个“降级”页面（通常显示加载中），同时在服务器端生成该页面。生成完成后，后续请求直接返回生成的静态页面。 | 用户会先看到 fallback 内容（如骨架屏），然后页面自动更新为真实内容。 | 需要快速响应，且愿意处理前端加载状态；适合内容较多的站点，避免长时间等待。 |
| **`fallback: 'blocking''`** | 服务器同步生成页面，生成期间请求被阻塞（等待）。完成后返回最终 HTML，之后该页面被缓存。 | 用户会等待直到页面完全生成（类似 SSR），无中间状态。 | 希望保持简单的前端逻辑，且页面生成时间可接受；适合少量未预生成的页面。 |

#### 代码示例
```jsx
// pages/posts/[id].js
export async function getStaticPaths() {
  const posts = await fetchPostIds();
  const paths = posts.map(post => ({ params: { id: post.id } }));
  return {
    paths,
    fallback: true, // 或 'blocking'
  };
}

export async function getStaticProps({ params }) {
  const post = await fetchPost(params.id);
  return {
    props: { post },
    revalidate: 60,
  };
}
```

### 注意
- `fallback: true` 需要在组件内判断 `router.isFallback` 来展示加载状态。
- `fallback: 'blocking'` 无需特殊判断，但首次访问会稍慢（生成时间）。

24. Next.js的Route Handlers和API Routes有什么区别？什么时候使用Route Handlers？
Next.js 的 **Route Handlers** 和 **API Routes** 都用于创建 API 端点，但属于不同的路由系统：

| 特性 | API Routes (Pages Router) | Route Handlers (App Router) |
|------|---------------------------|-----------------------------|
| **位置** | `pages/api` 目录下 | `app` 目录下，通过 `route.js`/`route.ts` 文件定义 |
| **路由定义** | 文件路径对应 API 路径（如 `pages/api/user.js` → `/api/user`） | 文件路径即路由，支持更灵活的命名（如 `app/user/route.js`） |
| **HTTP 方法** | 导出函数命名如 `handler(req, res)`，通过 `req.method` 判断 | 直接导出名称为 HTTP 方法（如 `GET`、`POST`）的函数，代码更清晰 |
| **请求/响应** | 使用 Node.js 的 `req`/`res` 对象 | 使用 Web 标准的 `Request` 和 `Response` 对象 |
| **静态生成** | 不支持静态生成 | 支持静态生成（通过 `export const dynamic = 'force-static'`） |
| **中间件集成** | 需通过自定义中间件或 `next-connect` | 与 Next.js 中间件无缝集成，且支持在 Route Handler 中直接使用 `cookies()`、`headers()` 等辅助函数 |
| **与页面共存** | 独立于页面路由 | 可与相同路径的页面共存（如 `app/user/page.js` 和 `app/user/route.js` 分别处理页面和 API） |

### 什么时候使用 Route Handlers？
- **使用 App Router 的新项目**：自然选择 Route Handlers 以保持一致性。
- **需要 Web 标准 API**：如希望在边缘环境运行，或复用 `fetch`、`Request`/`Response`。
- **需要静态生成 API 响应**：可将动态数据提前静态化，提升性能。
- **与页面共享同一路由结构**：例如 `/dashboard` 既要有页面又要有 API 端点，使用 Route Handlers 更简洁。
- **利用内置辅助函数**：如 `cookies()`、`redirect()` 等，简化开发。

如果仍在使用 Pages Router，则应继续使用 API Routes；否则新项目推荐 Route Handlers。

25. 如何在Next.js中优化字体加载？next/font的工作原理是什么？
在 Next.js 中，`next/font` 是一个内置模块，用于自动优化字体加载，提升页面性能与用户体验。它通过构建时处理字体文件、生成优化的 CSS 规则并自动应用，解决了传统字体加载常见的问题（如布局偏移、网络延迟、渲染阻塞）。

---

### 如何在 Next.js 中优化字体加载？

#### 1. 使用 `next/font` 引入字体
- **本地字体**：将字体文件放在 `public/fonts/` 或项目内，通过 `next/font/local` 引入。
  ```jsx
  import localFont from 'next/font/local';
  const myFont = localFont({ src: './my-font.woff2' });
  ```
- **远程字体**（如 Google Fonts）：通过 `next/font/google` 引入。
  ```jsx
  import { Inter } from 'next/font/google';
  const inter = Inter({ subsets: ['latin'] });
  ```

#### 2. 将字体应用到页面或组件
- 在组件中通过 `className` 使用生成的 CSS 类名。
  ```jsx
  <div className={inter.className}>文本内容</div>
  ```
- 或在全局样式文件中注入字体变量。
  ```jsx
  import { inter } from './fonts';
  <html className={inter.className}>...
  ```

#### 3. 配置优化选项
- `subsets`：加载指定字符子集（如拉丁、中文），减少体积。
- `display`：控制字体加载时的回退策略，默认 `'optional'`（极短阻塞后使用系统字体）。
- `weight`、`style`：指定字体粗细和样式，支持可变字体。
- `preload`：自动预加载字体文件（默认开启）。
- `fallback`：自定义回退字体。

---

### `next/font` 的工作原理

#### 1. **构建时处理**
- 在 `next build` 阶段，`next/font` 会下载远程字体（如 Google Fonts）或读取本地字体文件，根据配置生成优化的字体文件（如子集化、格式转换）。
- 这些文件会被放置在 `.next/static/media` 目录，并自动添加内容哈希以实现长期缓存。

#### 2. **生成 CSS `@font-face` 规则**
- 为每个字体生成一个包含 `@font-face` 规则的 CSS 类，其中包含：
  - 字体文件的 URL（指向构建后哈希化的文件）。
  - `font-display` 策略（默认为 `optional`，避免阻塞渲染）。
  - `size-adjust`、`ascent-override` 等属性，用于调整字体度量，消除布局偏移（CLS）。
- 这些 CSS 规则会被内联到页面 `<head>` 中，避免额外请求。

#### 3. **自动预加载**
- 自动在页面头部添加 `<link rel="preload" as="font">`，提前加载关键字体文件，减少首次渲染延迟。
- 预加载仅针对实际使用的字符子集，避免加载无用字形。

#### 4. **集成 CSS-in-JS 与样式系统**
- 生成的字体 CSS 类可直接应用于元素，或通过 `style` 对象的 `fontFamily` 属性注入（`inter.style.fontFamily`）。
- 支持 Tailwind CSS 等框架，可通过 CSS 变量共享字体。

#### 5. **消除布局偏移（CLS）**
- 通过内置的 `size-adjust` 和度量覆盖，让字体的占位空间与最终渲染空间一致，即使字体未加载完成，也不会导致页面跳动。
- 例如，`next/font` 会根据字体实际度量自动计算 `ascent-override` 等值，覆盖回退字体的默认度量。

#### 6. **智能回退**
- 允许通过 `fallback` 选项指定系统字体作为回退，当自定义字体未加载时立即显示，同时确保页面样式稳定。

#### 7. **可变字体支持**
- 如果字体支持可变轴（如 `Inter` 的可变版本），`next/font` 可生成单个文件包含所有粗细，进一步减少体积。

#### 8. **与服务端渲染（SSR）兼容**
- 在服务器端渲染时，`next/font` 会自动提取关键字体 CSS，并注入到初始 HTML 中，确保首屏字体样式正确，无 FOUT/FOIT。

---

### 总结
`next/font` 将字体优化从运行时转移到构建时，通过自动子集化、内联 CSS、预加载和度量调整，显著提升字体加载性能，同时简化开发流程。它是现代 Next.js 应用优化字体加载的推荐方案。

26. Next.js中如何处理环境变量？NEXT_PUBLIC_前缀的作用是什么？
在 Next.js 中，环境变量通过 **`.env` 文件** 或系统环境变量来管理，为不同环境（开发、生产）提供配置。

### 基本用法
- 在项目根目录创建 `.env.local` 文件，添加键值对：
  ```
  DB_HOST=localhost
  API_KEY=secret
  ```
- Next.js 启动时会自动加载这些变量，并在 `next.config.js` 或服务器端代码（如 `getServerSideProps`、`API Routes`）中可通过 `process.env.DB_HOST` 访问。

### `NEXT_PUBLIC_` 前缀的作用
- **默认**：环境变量仅在 **Node.js 环境**（服务端）可用，不会暴露给浏览器端。
- **使用 `NEXT_PUBLIC_` 前缀**的变量会同时被**内联到客户端 JavaScript 包**中，从而可以在浏览器端代码（如 React 组件、`useEffect`）中通过 `process.env.NEXT_PUBLIC_ANALYTICS_ID` 访问。
  ```env
  NEXT_PUBLIC_GA_ID=UA-12345678-1
  ```
  这样，前端代码就可以安全地使用该变量，但请注意**任何以 `NEXT_PUBLIC_` 开头的变量都会暴露给客户端，切勿存放敏感信息**（如密钥、密码）。

### 文件优先级
Next.js 支持多个环境文件，按以下顺序加载（后面的覆盖前面的）：
1. `.env.$(NODE_ENV).local`（如 `.env.development.local`）
2. `.env.local`（不被 git 追踪）
3. `.env.$(NODE_ENV)`（如 `.env.development`）
4. `.env`

### 注意事项
- **敏感信息**（数据库密码、API 密钥）绝不要加 `NEXT_PUBLIC_`，仅在服务端使用。
- 修改变量后需重启开发服务器才能生效。
- 在 `next build` 时，`NEXT_PUBLIC_` 变量会被静态嵌入，因此修改后需重新构建。

27. 什么是esbuild？它为什么比Webpack快？它的局限性有哪些？
**esbuild** 是一个用 Go 语言编写的极速 JavaScript 打包器与压缩工具，专注于高性能和低延迟。

### 为什么比 Webpack 快？
- **语言优势**：使用 Go 编译为本地代码，直接运行在机器层面，避免了 Node.js 的 JIT 开销和事件循环限制。
- **高度并行**：内置并行算法，充分利用多核 CPU 同时解析、转换和生成代码。
- **无中间抽象**：跳过 Webpack 中复杂的插件链和 AST 反复生成，直接产出最终结果。
- **内存效率**：精心设计的数据结构和内存池，减少垃圾回收压力。
- **增量缓存**：智能缓存中间产物，大幅提升二次构建速度。

### 局限性
- **生态较弱**：插件数量远少于 Webpack，对自定义 loader、复杂代码分割等支持不足。
- **功能裁剪**：缺少某些高级特性（如 Module Federation、精细 HMR 控制）。
- **类型安全**：TypeScript 编译仅去除类型，不进行类型检查（需配合 `tsc`）。
- **资源处理**：对 CSS、图片等静态资源的处理能力相对基础。
- **生产稳定性**：在大型复杂项目中的长期可靠性验证不如 Webpack 广泛。

因此，esbuild 常作为 Vite 等工具的底层依赖，用于快速预构建依赖，而 Webpack 仍是生态最完整的通用打包工具。

28. 前端如何实现代码覆盖率统计？Istanbul的工作原理是什么？
**前端代码覆盖率统计**用于衡量测试用例对代码的执行程度，帮助发现未测试的代码区域。实现方式通常依赖于专门的工具（如 Istanbul）在测试过程中对代码进行插桩、收集执行数据并生成报告。

---

## 前端实现代码覆盖率统计的常见方式

1. **测试框架内置**：Jest 自带覆盖率收集（基于 Istanbul），只需在配置中开启 `collectCoverage`。
2. **Karma + karma-coverage**：在浏览器中运行测试时，karma-coverage 使用 Istanbul 对源码插桩，收集并输出报告。
3. **Cypress/Playwright + 覆盖率插件**：通过 `@cypress/code-coverage` 等插件，将浏览器端覆盖率数据合并到 Istanbul 报告中。
4. **手动插桩**：使用 `nyc` 命令行工具对源码插桩后运行测试，或通过 `babel-plugin-istanbul` 在构建时插桩。

无论哪种方式，核心都是**代码插桩**和**覆盖率数据收集**，而 Istanbul 是实现这些功能的基础工具。

---

## Istanbul 的工作原理

Istanbul 是一个 JavaScript 代码覆盖率工具，其核心原理分为三步：**插桩（Instrumentation）**、**执行**、**报告生成**。

### 1. 插桩（Instrumentation）
Istanbul 通过解析 JavaScript 代码生成抽象语法树（AST），然后在关键位置插入**计数器变量**。这些位置包括：
- **语句（Statement）**：每条语句执行时，对应的计数器 +1。
- **分支（Branch）**：如 `if`、`switch` 的每个分支，进入时计数器 +1。
- **函数（Function）**：函数被调用时计数器 +1。
- **行（Line）**：通常通过语句覆盖间接统计。

插桩后的代码会在运行时更新这些计数器，同时 Istanbul 会将所有计数器挂载到一个全局变量（如 `__coverage__`）上，以便后续收集。

### 2. 执行
测试运行时，插桩后的代码正常执行，每个计数器记录相应代码片段是否被执行过。所有计数器信息最终被汇总到 `__coverage__` 对象中。

### 3. 收集与报告生成
测试结束后，工具（如 `nyc` 或 karma-coverage）从 `__coverage__` 中读取数据，结合原始代码和插桩映射，计算出覆盖率指标：
- **语句覆盖率**：执行的语句数 / 总语句数。
- **分支覆盖率**：执行的分支数 / 总分​​支数。
- **函数覆盖率**：调用的函数数 / 总函数数。
- **行覆盖率**：有执行语句的行数 / 总行数（通常基于语句覆盖率计算）。

最后，生成可视化的报告（HTML、lcov、文本等），标出已执行/未执行的代码区域。

---

## 现代演进

- **`nyc`**：Istanbul 的命令行界面，用于插桩和报告生成。
- **`babel-plugin-istanbul`**：结合 Babel 在编译时插桩，避免修改源码。
- **`c8`**：基于 V8 内置的覆盖率机制（无需插桩），直接收集 Node.js 运行时的覆盖率数据，速度更快。

尽管工具形式变化，Istanbul 的插桩原理仍是许多前端覆盖率方案的基础。

29. 什么是Nx？它和Lerna、pnpm workspace有什么区别？
**Nx** 是一个智能的、可扩展的构建系统，专为管理大型单体仓库（monorepo）设计。它提供高级的任务编排、计算缓存、依赖图分析和插件生态，帮助团队高效地管理和构建多个项目/库。

### Nx 与 Lerna、pnpm workspace 的区别

| 特性 | Nx | Lerna | pnpm workspace |
|------|----|-------|----------------|
| **核心定位** | 完整的构建系统 + monorepo 管理 | 专注于多包管理和发布 | pnpm 内置的 workspace 机制，用于本地包链接 |
| **任务编排** | 智能分析项目依赖图，自动并行/顺序执行任务（如测试、构建） | 可批量执行脚本，但无依赖图分析，需手动配置顺序 | 无内置任务编排，需借助外部工具（如 npm scripts + concurrently） |
| **缓存与增量构建** | 内置计算缓存，可缓存任务结果，避免重复工作（本地和远程缓存） | 无缓存机制，每次执行都重新运行 | 无缓存 |
| **影响分析** | 通过 `affected` 命令，只运行受代码变更影响的项目任务 | 无此功能 | 无此功能 |
| **依赖管理** | 可搭配 npm/yarn/pnpm 使用，本身不处理依赖安装 | 与 yarn/npm 配合，使用 `lerna bootstrap` 安装依赖 | pnpm 的硬链接机制，节省磁盘空间，速度快 |
| **插件与扩展** | 丰富的插件（React、Angular、Node、Next.js 等），提供生成器、迁移工具 | 插件较少，基本只处理版本和发布 | 无插件生态 |
| **发布管理** | 不内置发布功能，可配合 `lerna` 或 `changesets` | 内置版本管理和发布到 npm | 无内置发布，需配合 `changesets` 或手动处理 |
| **使用复杂度** | 功能强大，学习曲线稍陡 | 简单易用，适合轻量级 monorepo | 极简，仅处理本地包链接，适合小型项目 |

### 它们可以协同工作
- **pnpm + Nx**：用 pnpm 管理依赖，用 Nx 进行任务编排和缓存，这是目前很流行的组合。
- **Lerna + Nx**：Lerna 负责版本和发布，Nx 作为其任务运行器（通过 `lerna run --nx`），获得缓存和依赖图分析能力。

### 总结
- 如果只是简单的多包管理（如几个内部包互相依赖），pnpm workspace 足够。
- 如果需要在多个包之间协调任务执行、优化构建速度、处理复杂的依赖关系，Nx 是更强大的选择。
- Lerna 逐渐演进，现在可与 Nx 结合使用，专注于发布流程。

30. 如何实现前端的版本管理和发布流程？语义化版本（Semantic Versioning）如何使用？
在前端项目中，版本管理和发布流程主要涉及**代码版本号规范**和**自动化部署策略**。语义化版本（SemVer）是其中最核心的版本号约定。

---

## 1. 语义化版本（Semantic Versioning）

### 格式：`主版本号.次版本号.修订号`（如 `2.5.1`）
- **主版本号**：当做了**不兼容的 API 修改**时递增（例如重构组件库，破坏现有接口）。
- **次版本号**：当增加了**向后兼容的新功能**时递增。
- **修订号**：当进行了**向后兼容的问题修复**时递增。

**预发布版本**：可附加 `-alpha.1`、`-beta.0` 等后缀，表示不稳定版本。  
**构建元数据**：可附加 `+build.123`，仅用于标识，不影响优先级。

### 使用示例（npm 包）
- 修复 bug：`npm version patch` → `1.0.0` → `1.0.1`
- 添加新功能：`npm version minor` → `1.1.0`
- 破坏性变更：`npm version major` → `2.0.0`

对于前端应用（非库），版本号更多用于标识发布版本，便于回滚和追踪，也可遵循 SemVer。

---

## 2. 前端版本管理与发布流程

### 2.1 版本号管理
- **package.json** 中的 `version` 字段记录当前版本。
- 使用工具自动更新版本和生成 CHANGELOG：
  - `standard-version`：基于 commit message 自动升级版本、打 tag。
  - `changesets`：适用于多包仓库（monorepo）的版本管理。
- 每次发布前，将版本号提交并打上 Git tag（如 `v1.2.3`）。

### 2.2 构建与资源版本化
- **静态资源（JS/CSS/图片）** 打包时生成**哈希后缀**（如 `app.8f3d2c.js`），确保内容变化时 URL 改变，彻底解决缓存问题。
- **HTML 入口文件**（如 `index.html`）不缓存或设置极短缓存，引用带有哈希的资源。

### 2.3 发布部署流程
典型的 CI/CD 流程：
1. **代码合并到主分支**（如 `main` 或 `release` 分支）。
2. **CI 触发**（GitHub Actions / GitLab CI）：
   - 运行测试、lint、类型检查。
   - 根据 commit 或手动触发确定版本更新类型（patch/minor/major）。
   - 运行构建命令（如 `npm run build`），生成带哈希的静态文件。
   - 可选：将构建产物上传至 CDN 或对象存储（如 AWS S3、OSS）。
3. **部署服务器**：
   - 将新版本文件上传到服务器/CDN 的对应目录（可按版本号存放，如 `/releases/v1.2.3/`）。
   - 更新符号链接或反向代理配置指向新版本，实现**零停机发布**。
   - 或者直接覆盖静态文件（配合哈希，旧文件仍可被缓存访问）。
4. **版本记录与回滚**：
   - 保留历史版本的构建产物。
   - 如需回滚，只需将入口文件指向旧版本目录或重新部署旧版本代码。

### 2.4 多版本共存与灰度发布
- 通过 Nginx 或网关根据 Cookie/Header 分发不同版本的前端资源。
- 使用部署平台（如 Vercel、Netlify）自动生成预览 URL 进行测试。

---

## 3. 最佳实践总结
- **遵循 SemVer**：清晰传达版本变更影响。
- **自动化版本管理**：利用工具减少人为错误。
- **资源哈希**：确保客户端缓存正确更新。
- **CI/CD 集成**：一键发布，降低操作风险。
- **回滚策略**：保留历史版本，支持快速恢复。

通过以上流程，前端项目可以高效、安全地进行版本迭代和发布。

## 一、整体系统架构

采用 **前后端分离 + SSE 流式响应** 模式，前端负责 UI 渲染和用户交互，后端负责 LLM 推理与流式传输。

```
用户 → 前端（React/Vue）→ API Gateway → AI 服务（流式返回）
                ↑                            ↓
                └──────── SSE 推送 ──────────┘
```

- **通信协议**：SSE (Server-Sent Events) 比 WebSocket 更轻量，天然支持断线重连，且只需 HTTP 即可。
- **请求流程**：
  1. 用户发送消息，前端将当前对话历史（上下文）拼接到请求体中。
  2. 后端收到请求，调用 LLM 并逐步返回文本块。
  3. 前端通过 `EventSource` 或 Fetch API 的 `Response.body`（ReadableStream）接收增量数据。
  4. 每收到一个 chunk，立即追加到当前回答的缓冲区，并触发 UI 更新。

## 二、前端核心模块设计

### 1. 消息数据结构

```typescript
interface Message {
  id: string;              // 唯一 ID，用于列表 key 和更新
  role: 'user' | 'assistant' | 'system';
  content: string;         // 完整内容（流式更新时动态追加）
  timestamp: number;
  status: 'sending' | 'streaming' | 'completed' | 'error';
  tokenCount?: number;     // 该消息消耗的 token 数（可选）
}
```

### 2. 消息列表渲染

- 使用 **虚拟列表（Virtual List）** 渲染大量历史消息，仅渲染可视区域，保证长对话性能。
- 每条消息组件独立，支持**按需渲染**（仅当内容变化时更新）。
- **滚动行为**：新消息到来时自动滚动到底部；用户手动滚动后暂停自动滚动。

### 3. Markdown 与代码高亮

- **解析渲染**：使用 `marked` 或 `remark` 将 Markdown 转为 HTML。
- **代码高亮**：搭配 `highlight.js` 或 `prism.js`，在渲染完成后对 `pre code` 进行高亮处理。
- **性能优化**：
  - 使用 `useMemo` 缓存已编译的 HTML 字符串，避免重复解析。
  - 对于超长消息，考虑将 Markdown 编译移至 Web Worker，避免阻塞主线程。
- **复制代码**：
  - 在每个代码块右上角放置“复制”按钮。
  - 点击后调用 `navigator.clipboard.writeText()`，并提供视觉反馈（Toast）。

### 4. 停止生成

- 前端维护一个 **AbortController**，用户点击“停止”时调用 `abort()`，后端应监听连接关闭并中断 LLM 生成。
- 同时前端将消息状态置为 `completed`，不再接收后续数据。

## 三、流式数据处理与渲染性能

**核心挑战**：每秒可能收到多次 chunk，频繁更新 React/Vue 组件会导致卡顿。

### 1. 增量更新策略

- **使用不可变数据结构**：每次收到 chunk，创建新的 `Message` 对象（或使用 Immer 产生新 state），触发 React 的浅比较更新。
- **细粒度更新**：仅更新正在接收的这条消息的 `content`，其他消息不受影响。
- **批量更新**：使用 `requestAnimationFrame` 或 `debounce` 合并短时间内多次 content 更新，减少渲染频率。
  ```js
  // 伪代码：合并 16ms 内的多次 content 更新
  let pendingContent = '';
  function scheduleRender() {
    if (!rafId) {
      rafId = requestAnimationFrame(() => {
        updateMessageContent(pendingContent);
        pendingContent = '';
        rafId = null;
      });
    }
  }
  ```

### 2. 虚拟列表 + 高度自适应

- 由于消息内容不断变长，虚拟列表需支持**动态高度**。可在渲染前预估行数，或采用 `react-virtual` 的 `measure` 功能。
- 流式生成时，当前正在输出的消息高度会频繁变化。解决方案：
  - 临时**禁用该消息的虚拟化**（让其脱离虚拟滚动，绝对定位在底部），完成后再重新融入列表。这是 ChatGPT 官方使用的技巧。

### 3. 避免重绘整个列表

- 将消息列表组件拆分为 **固定头部 + 虚拟列表 + 底部固定区域**。底部区域专门渲染当前正在生成的助理消息，不参与虚拟滚动。
- 当消息完成时，将其从底部区域移入虚拟列表中。

## 四、打字机效果（Streaming Output）

### 1. 技术选型

- **逐字输出**：模拟人打字，提升等待体验。
- 实现方法：
  - 后端返回完整的 word 或句子块（避免逐字请求）。
  - 前端每收到一个 chunk，直接追加到内容末尾，而不是逐字显示（逐字会增加前端复杂度，且无必要）。
  - 若需要逐字动画，可以在追加 chunk 后，通过 CSS 动画控制透明度或光标闪烁，但多数产品（如 ChatGPT）直接显示完整块。

**推荐做法**：**块级渲染**，每收到一个完整 token 块（通常是一个单词或几个汉字）立即渲染，配合平滑的滚动。

### 2. 光标指示

- 在未完成的消息末尾添加一个闪烁的“▍”光标，使用 CSS 动画实现。
- 当消息状态变为 `completed` 时移除光标。

- 最准确的方式：**后端返回每次补全消耗的 token 数**（包括请求中的历史 token 和新生成 token）。

### 2. 实时估算

- 若后端不提供，前端可使用轻量库（如 `gpt-3-encoder`）估算用户输入和助手回复的 token 数，但仅作参考。

### 3. 展示位置

- **当前对话 token 使用量**：显示在侧边栏或顶部，帮助用户控制上下文长度。
- **每条消息 token 数**：可鼠标悬浮时显示，或仅在调试模式下显示。

## 二、异步任务状态管理 —— 基于状态机

每个图片生成请求都是一个**独立任务**，我们需要精确记录其生命周期。

### 1. 任务模型（Task）

```typescript
interface GenerationTask {
  id: string;               // 唯一 ID (uuid)
  prompt: string;           // 提示词
  params: GenerationParams; // 宽高、模型、负向提示词等
  status: 'pending' | 'queued' | 'generating' | 'completed' | 'failed' | 'canceled';
  progress: number;         // 0-100，可用于进度条
  result?: {
    imageUrl: string;       // 最终图片 URL（CDN）
    thumbnailUrl?: string;  // 缩略图 URL
    width: number;
    height: number;
    seed?: number;
  }[];
  createdAt: number;
  updatedAt: number;
  error?: string;
  abortController?: AbortController; // 用于取消
}
```

### 2. 状态流转

```
pending → queued → generating → completed
             ↓          ↓           ↑
           failed ← cancel ← ──────┘
```

- **pending**：用户点击生成，任务创建但未加入队列。
- **queued**：已加入前端队列，等待发送。
- **generating**：请求已发出，后端正在处理。
- **completed**：成功获得图片。
- **failed**：后端返回错误或网络异常。
- **canceled**：用户主动取消。

### 3. 全局状态设计（Zustand 示例）

```typescript
const useTaskStore = create((set) => ({
  tasks: Record<string, GenerationTask>,
  queue: [],                // 任务ID顺序队列
  activeTasks: Set<string>, // 正在执行的任务ID

  addTask: (task) => ...,
  updateTask: (id, partial) => ...,
  removeTask: (id) => ...,
  cancelTask: (id) => {
    const task = get().tasks[id];
    task.abortController?.abort();
    set(state => ({ tasks: { ...state.tasks, [id]: { ...task, status: 'canceled' } } }));
  },
}));
```

## 三、生成队列管理 —— 并发控制与优先级

### 1. 为什么需要队列？

- 避免瞬间发送上百个生成请求压垮浏览器连接池。
- 防止用户无限制并发消耗后端资源。
- 支持批量生成（一次性提交多个提示词）。

### 2. 队列实现

**核心类** `TaskQueue`：

```typescript
class TaskQueue {
  private concurrency = 3;        // 最大并发数
  private queue: string[] = [];   // 等待队列（任务ID）
  private running = new Set<string>();

  async add(taskId: string) {
    this.queue.push(taskId);
    this.process();
  }

  private async process() {
    if (this.running.size >= this.concurrency) return;
    if (this.queue.length === 0) return;

    const taskId = this.queue.shift()!;
    this.running.add(taskId);

    try {
      await this.executeTask(taskId);
    } finally {
      this.running.delete(taskId);
      this.process(); // 继续处理下一个
    }
  }

  private async executeTask(taskId: string) {
    const task = store.getTask(taskId);
    // 更新状态为 generating
    store.updateTask(taskId, { status: 'generating' });

    // 发送请求，并传入 AbortSignal
    const response = await api.generateImage(task.prompt, {
      signal: task.abortController?.signal,
      onProgress: (progress) => store.updateTask(taskId, { progress }),
    });

    // 处理结果
    store.updateTask(taskId, { status: 'completed', result: response.images });
  }
}
```

### 3. 批量生成处理

- 用户输入多个提示词 → 前端拆分为多个独立任务，依次加入队列。
- 提供“全部取消”按钮，遍历 `running` 和 `queue` 分别取消。

## 四、图片加载与展示优化

### 1. 缩略图先行

- 后端生成图片后返回**原图 URL** 和 **缩略图 URL**（例如宽度 200px 的 WebP）。
- 列表页、历史记录中优先加载缩略图，点击放大后加载原图。

### 2. 虚拟滚动（Virtual Scroll）

- 生成历史可能包含成百上千张图片，使用 `react-window` 或 `vue-virtual-scroller` 只渲染可视区域的卡片。
- 每张卡片高度固定（或动态计算），滚动时动态加载图片。

### 3. 图片懒加载

- 使用 `<img loading="lazy" />` 原生属性，或 Intersection Observer 实现。
- 图片占位：先显示模糊缩略图（或骨架屏），再替换为清晰图。

### 4. 现代图片格式 & CDN

- 上传图片至对象存储（S3/OSS），通过 CDN 分发。
- 支持根据 URL 参数动态格式转换：`?format=webp&width=800`，前端根据浏览器支持自动请求 WebP。

### 5. 内存缓存

- 已加载过的图片利用浏览器 HTTP 缓存，配合 `Cache-Control` 强缓存。
- 对于用户频繁查看的图片（如当前生成批次），可在内存中保留 Blob URL。

## 五、进度展示与取消功能

### 1. 实时进度推送

- **推荐方案**：SSE（Server-Sent Events）。创建生成任务时，后端返回一个任务 ID，前端通过 `EventSource` 监听 `/api/tasks/{id}/progress` 流。
- **备选方案**：WebSocket 广播进度（适合全双工）。
- 每收到进度事件，更新对应任务的 `progress` 字段，UI 展示进度条。

### 2. 取消功能实现

- 前端：每个任务关联一个 `AbortController`，在 `cancelTask` 时调用 `abort()`。
- 后端：需监听请求中断（`req.on('close')`），主动停止 AI 生成并释放资源。
- UI：任务卡片上的“取消”按钮仅在 `status === 'queued'` 或 `'generating'` 时显示。

## 七、生成历史管理 —— 本地优先，云端为辅

### 1. 存储选型

- **IndexedDB**：存储所有任务元数据及图片 Blob（或 URL），支持大量数据和高性能查询。
- 使用 `localForage` 或 `idb` 封装，提供类似 `getTasks(offset, limit)` 的分页接口。

### 2. 加载策略

- 应用启动时，从 IndexedDB 读取最近 20 条任务展示，后续滚动时懒加载更多。
- 云端同步：用户登录后，增量上传本地任务（带时间戳），并下载云端历史合并（解决多端冲突，简单 LWW 即可）。

### 3. 删除与清理

- 支持单条/批量删除任务，同步删除 IndexedDB 记录及对应缓存图片。
- 提供“释放空间”功能，删除超过 N 天的历史或低分图片。

| **批量生成**   | 任务队列 + 并发控制（默认 3 并发），避免浏览器/后端过载                                     |
| **进度展示**   | SSE 实时推送进度，前端逐任务更新进度条，支持取消（AbortController）                         |
| **图片渲染性能** | 缩略图优先 + 虚拟滚动 + 懒加载 + CDN WebP 转换，内存中缓存 Blob URL                         |
| **图片编辑**   | 本地 Canvas 基础编辑（裁剪、旋转）+ AI 编辑包装为子任务，关联父任务形成版本树               |
| **历史记录**   | IndexedDB 持久化 + 分页加载，云端同步增量数据，支持离线访问                                 |
| **用户体验**   | 取消按钮实时响应，任务失败重试，错误提示友好，键盘快捷键（如 Ctrl+Enter 提交）               |

这个架构已在多个 AI 绘画工具（如 Stable Diffusion WebUI 前端、Midjourney 第三方客户端）中得到验证，能够支撑高并发生成、流畅的图片浏览和编辑体验。在面试中，重点突出**任务队列的并发控制、图片性能优化策略以及离线优先的历史存储**，即可展现架构深度。
